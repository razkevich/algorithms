The Three Pillars -- When to Use Which

Every production system emits three fundamentally different signal types. Each has its own pipeline, cost shape, and question it answers. The senior move is picking the right pillar for the question, not dumping everything into one.

Decision Table

Dimension Logs Metrics Traces
Signal type Discrete events (text/JSON) Numeric time-series Causally linked spans
Cardinality concern Low -- text is just bytes Critical -- each unique label combo = new series Moderate -- span count grows with fan-out
Retention cost High (GB/day, must store raw) Low (compressed numeric, downsample older data) Medium (sampling controls volume)
Query pattern Grep/filter by fields PromQL / aggregate across dimensions Trace ID lookup, service graph
Latency of insight Seconds (ingest + index) Near real-time (scrape interval) Seconds (span forwarding)
Primary question "Why did X fail?" "Is Y healthy?" "How did request Z flow?"

Pick the pillar by the question you need answered. Investigation starts from metrics (detect), pivots to traces (locate), and lands on logs (diagnose). The cost shape differs fundamentally: logs charge per GB, metrics charge per series count, traces charge per span. Misusing one pillar for another's job (e.g., high-cardinality labels on metrics to get "log-like" context) is the single most expensive mistake in observability.
Takeaway
  • Pick the pillar by question type. "What happened in this request?" = trace. "Is the system healthy right now?" = metrics. "Why did request X fail?" = logs.
  • Logs: volume is the killer. Metrics: cardinality is the killer. Traces: fan-out width is the killer.
  • All three become useful only when correlated by trace_id -- otherwise they are three separate silos.

Logs Pipeline

Structured log events flow from application through agent, optional buffer, processor, into a store, and finally to a query UI. The architecture choice is where to index and what to index.

App writes structured JSON to stdout. A log agent (Fluent Bit, Vector, Filebeat) tails the output and forwards it downstream. Without a Kafka buffer, agent connects directly to the processor -- simpler, but backpressure from the store propagates all the way to the agent.

Elasticsearch vs Loki: Indexing Trade-off

Dimension Elasticsearch (ELK) Loki (Grafana)
What is indexed Full inverted index over all fields + content Labels only (key-value pairs like app=api)
Query power Full-text search, complex aggregations, KQL Label filter + brute-force grep on chunks
Cost at scale High -- indexing is CPU + storage intensive Low -- compressed chunks in object storage (S3)
Best fit Complex search patterns, analytics over logs Known-service queries, cost-sensitive environments

Common Pitfalls

Pitfall 1: High-cardinality labels on metrics pretending to be logs. If you add user_id as a metric label, you create millions of time series. Use logs for per-user context, not metrics.

Pitfall 2: Logs as source of truth for billing/audit. Logs can be dropped under backpressure, reordered, or duplicated. For billing and audit trails, use a durable write-ahead log (Kafka with replication) or a dedicated audit store.
Takeaway
  • Don't index everything. Loki indexes labels (cheap); ES indexes content (expensive); pick by query pattern.
  • Kafka between agent and processor decouples ingestion from processing -- absorbs spikes without backpressure to the app.
  • Structured logs (JSON) with a consistent schema are the prerequisite for everything downstream. If your logs are unstructured text, you pay at parse time forever.

Metrics Pipeline (Prometheus Pull Model)

Prometheus discovers targets via service discovery, scrapes /metrics endpoints on a fixed interval, stores time-series locally, evaluates alert rules, and sends alerts to Alertmanager. The pull model means Prometheus owns the schedule -- it knows when a target is down (failed scrape) vs. simply quiet.

Prometheus uses a pull model: it actively scrapes /metrics endpoints on a configured interval (default 15s). Service discovery (Kubernetes SD, Consul, file-based) tells Prometheus where to find targets. This is fundamentally different from push (StatsD/Graphite): Prometheus knows a target is down if the scrape fails, while push systems can't distinguish "no data" from "target crashed."

Cardinality Explosion

A counter http_requests_total with labels {method, status, user_id}. With 100K active users, each unique combination becomes a distinct time series.

With just {method, status}, you have roughly 5 methods x 4 statuses = 20 series. Manageable. Prometheus stores ~3 bytes/sample at one sample per 15s.

Pull vs Push Comparison

Dimension Pull (Prometheus) Push (StatsD / Graphite)
Schedule ownership Prometheus controls when to scrape App decides when to emit
Failure detection Failed scrape = target down (explicit signal) No data = ambiguous (down? or just quiet?)
Short-lived processes Problematic -- may exit between scrapes (use Pushgateway) Works well -- fire-and-forget UDP

Long-Term Storage: Thanos / Cortex / Mimir

Prometheus stores locally with limited retention (default 15 days). For long-term storage and global view across clusters: Thanos (sidecar uploads blocks to S3, Thanos Query federates), Cortex/Mimir (horizontally-scalable Prometheus-compatible store, write path shards by tenant). All three support PromQL, so dashboards and alerts don't change.
Takeaway
  • Prometheus pull = service discovery + reliability (Prometheus owns the schedule). Cardinality is the cost lever.
  • Histograms over summaries -- histograms are aggregatable across replicas, summaries are not. Use _bucket counters with le bounds for percentile estimation.
  • Cardinality rule of thumb: if a label can have more than ~100 unique values, it probably doesn't belong on a metric. Use logs or traces for high-cardinality context.

Traces Pipeline (OpenTelemetry)

A trace is a tree of spans that records a single request's path across services. Each span captures timing, metadata, and a parent-child relationship. OpenTelemetry (OTel) is the vendor-neutral standard for instrumentation, collection, and export.

Client sends a request to Service A. The OTel SDK creates a root span, injects traceparent header into outgoing calls. Each downstream service reads the header, creates a child span. All spans share the same trace_id. The OTel Collector receives spans and forwards to the backend (Jaeger, Tempo, Honeycomb).

Context Propagation

The traceparent HTTP header carries: version-traceId-parentSpanId-traceFlags. Example: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01. The receiving service reads this, creates a child span whose parent_span_id matches, and forwards the updated header to its own downstream calls. Without this propagation, spans are orphaned -- they exist but cannot be assembled into a trace tree.

Sampling Strategies

Sampling is the primary cost control for traces. Two approaches with fundamentally different trade-offs.

Head-Based Sampling

Decision at request entry: sample 1% of all requests uniformly.

Total: 0 | Kept: 0 | Slow/Error kept: 0

Tail-Based Sampling

Collect all spans; decide after seeing complete trace. Keep all errors + slow + 10% of normal.

Total: 0 | Kept: 0 | Slow/Error kept: 0
Head rate 1%
Slow/Error % 5%
Head-based: simple, low overhead, but uniformly drops -- including interesting (slow/error) requests. Tail-based: collects everything temporarily, then decides based on trace properties -- keeps all errors and slow traces, samples normal ones. Trade-off: tail-based requires a collection buffer (the OTel Collector must hold spans in memory until the trace completes), which adds cost and complexity.
Takeaway
  • OTel is the vendor-neutral standard. Use the Collector as the fan-out point to multiple backends -- avoids vendor lock-in.
  • Tail-based sampling is the senior choice if cost and infra complexity allow. It preserves 100% of errors and slow traces while sampling normal traffic.
  • Context propagation (traceparent header) is the mechanism that makes distributed tracing work. Without it, you have orphaned spans, not traces.

Correlation Across Pillars

The three pillars become powerful only when connected. The integration layer is a single field: trace_id. Embed it in every log line, attach it as a metric exemplar, and every span carries it by definition. This lets you jump between pillars during investigation.

An investigation typically starts from a metrics alert (e.g., error rate spike), pivots to traces filtered by time window and affected service, then drills into logs for the specific trace_id that shows the failure. The reverse path works too: logs show a pattern, you check if it correlates with a metric anomaly, then trace individual requests to find the root cause.

Integration Patterns

Pattern 1: trace_id in every log line. Add trace_id and span_id fields to your structured logs. In Grafana, clicking a log line opens the trace in Tempo. Cost: near-zero (one extra field per log line).

Pattern 2: exemplars on metrics. Prometheus 2.27+ supports exemplars -- a trace_id attached to a specific metric sample. When viewing a metric spike in Grafana, clicking the exemplar dot opens the corresponding trace. Cost: near-zero (exemplars are stored alongside samples).

Pattern 3: derived metrics from traces. OTel Collector can compute RED metrics (Rate, Error, Duration) from span data, emitting them as Prometheus metrics. This means you don't need separate instrumentation for basic service health -- traces generate the metrics.
Takeaway
  • Trace ID in every log line + every metric exemplar = the integration layer. Without it, the pillars are three separate silos that happen to coexist.
  • The investigation flow: metrics (detect the anomaly) -> traces (locate the slow/failing path) -> logs (diagnose the root cause). Name this flow in interviews.
  • LGTM stack (Loki + Grafana + Tempo + Mimir) is the open-source answer. Datadog / Honeycomb / New Relic are the SaaS answers. The architecture is the same -- the integration point is always trace_id.
