Quorum + Anti-Entropy

R+W>N math, read repair, hinted handoff, Merkle-tree reconciliation. The Dynamo-paper foundations underlying Cassandra, DynamoDB, Riak, and most distributed-store consistency.

1. R+W>N -- Quorum Consistency Math

Replication factor N copies each write to N replicas. A read contacts R replicas and picks the latest. A write waits for W replicas to acknowledge. The Dynamo paper's central theorem: if R + W > N, at least one replica in the read set must hold the latest write.

Latency Implications

W=QUORUM waits for ceil(N/2)+1 acks, tolerating floor(N/2) slow replicas. W=ALL waits for the slowest replica, causing high tail latency. The sweet spot is QUORUM on both sides: strong consistency without worst-case tail.

Takeaway: R+W>N is the Dynamo paper's central theorem. QUORUM+QUORUM is the production default -- balanced fast read + fast write + strong consistency.

2. Read Repair (Synchronous on Read)

Every read is an opportunity to detect and repair replica drift. When the coordinator reads from R replicas and detects a timestamp mismatch, it reconciles to the latest value and sends a background repair write to stale replicas.

Takeaway: Read repair fixes lag opportunistically -- every read is a chance to detect and repair drift. Cheap, but only repairs keys that are actually read. Unread keys stay stale until anti-entropy repair.

3. Hinted Handoff (Write-Side Healing)

When a write's target replica is unreachable, the coordinator stores a "hint" -- the failed write, tagged with the intended target. When the target recovers, hints are replayed. Best-effort durability for transient failures.

Click "Play Animation" to see a write during a replica outage: coordinator stores hints, drains them on recovery.

Caveats

LimitationImpact
Hints have TTL (default 3h in Cassandra)If the target stays down longer than TTL, hints are dropped. Data diverges.
Coordinator dies = hints lostHints are stored locally on the coordinator's disk. No replication of hints themselves.
Not a substitute for full repairCovers transient failures. Long outages or partition events require Merkle-tree anti-entropy.
Takeaway: Hinted handoff = best-effort durability for writes during transient failures. Time-bounded (TTL); not a substitute for full anti-entropy repair.

4. Anti-Entropy via Merkle Trees

When replicas have drifted apart (hint TTL expired, long outage, bit rot), comparing every row is O(N) and expensive. A Merkle tree -- a binary tree of hashes -- lets two replicas find their differences in O(log N) comparisons. Leaves hash row groups; internal nodes hash their children.

Click "Play Diff Protocol" to watch two replicas compare Merkle trees: root mismatch, descend into differing subtrees, find the divergent leaf, reconcile.

Why O(log N)

At each tree level, compare hashes. Equal hashes mean the entire subtree is identical -- skip it. Only descend into mismatching subtrees. With 1M rows and 1024 rows per leaf, the tree has ~10 levels. A single-leaf difference requires ~10 hash comparisons, not 1M row comparisons.

Used by: Cassandra (nodetool repair), DynamoDB, Riak. Same structure powers Bitcoin block verification and IPFS content-addressing.

Takeaway: Merkle trees = log-cost diff. The standard for replica reconciliation at scale. Same structure used in Bitcoin/IPFS for content-addressing.

5. Latency Math -- Quorum Reads at Scale

Counterintuitive result: quorum reads (wait for 2-of-3) have better tail latency than reading from a single specific replica. You're waiting for the 2nd order statistic of 3 samples -- tolerating the slowest one.

Single replica Quorum (2-of-3) ALL (3-of-3)
100

The Math

If each replica independently completes within time t with probability F(t):

  • Single replica: P(done by t) = F(t)
  • ALL (3-of-3): P(done by t) = F(t)3 -- wait for slowest, worse tail
  • Quorum (2-of-3): P(done by t) = 3F(t)2 - 2F(t)3 -- at least 2 of 3 finish

At p99: F(t)=0.99. Single: 0.99. Quorum 2-of-3: 3(0.99)2 - 2(0.99)3 = 0.999702. ALL: (0.99)3 = 0.9703. Quorum p99 is better than single replica.

Takeaway: Quorum reads = better tail latency than reading from a specific replica. Count it as a feature, not just a consistency story. ALL reads have the worst tail because you wait for the slowest.

6. Consistency Models Spectrum

R+W>N gives you strong eventual consistency -- specifically "read-your-writes" and "monotonic reads" within a session. But it does not give linearizability, which requires additional coordination (clocks, a single leader, or consensus).

ModelGuaranteeExample SystemsCost
Eventual Reads may return stale values; replicas converge eventually Cassandra (default CL=ONE), DynamoDB (eventually consistent reads) Lowest latency, highest availability
Read-your-writes Client always sees its own writes (others may lag) Cassandra with QUORUM R+W, sticky sessions Moderate -- quorum coordination
Sequential All clients see same order (may not match wall-clock time) ZooKeeper (within a session) Single-leader or total-order broadcast
Linearizable Sequential + respects real-time ordering (every op appears atomic at one instant) Spanner (TrueTime), etcd/Raft consensus High -- clock sync or consensus per op
Strict Serializable Linearizable + serializable transactions (strongest) Spanner, CockroachDB, FoundationDB Highest -- 2PC + synchronized clocks
Takeaway: Quorum gives strong eventual consistency, not linearizability. Linearizability needs additional ordering primitives (synchronized clocks, a coordinator, or consensus). Know where your system sits on this spectrum.
