1. How MVCC works (xmin / xmax)

Every Postgres row has hidden columns: xmin (transaction ID that created this row version) and xmax (transaction ID that deleted or superseded it -- 0 if the version is still alive). A transaction with snapshot S sees a row version when:

xmin < S  AND  xmin committed  AND  (xmax = 0  OR  xmax > S  OR  xmax aborted)

2. Isolation levels -- anomalies and prevention

2a. Read Committed (Postgres default)

Each statement gets a fresh snapshot -- not the transaction. This prevents dirty reads but allows non-repeatable reads: the same SELECT in the same transaction can return different values if another transaction commits in between.

2b. Repeatable Read (Postgres = snapshot isolation)

Snapshot taken at first statement, held for the entire transaction. This prevents non-repeatable reads but allows write skew -- the anomaly Postgres RR does not prevent.

Classic example: the doctor-on-call constraint. Two doctors both check "is there at least one other doctor on call?" -- both see "yes" -- both update themselves to off-duty -- constraint violated, zero doctors on call.

3. VACUUM and bloat

Every UPDATE creates a new row version and marks the old one dead (xmax set). DELETEs do the same -- no data is physically removed immediately. Without VACUUM, dead versions pile up: table size grows while live rows stay flat.

Autovacuum threshold

The autovacuum daemon wakes periodically and vacuums tables that exceed the threshold formula:

dead_tuples > autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor * n_live_tup

With defaults (threshold=50, scale_factor=0.2), a table with 10,000 live rows triggers autovacuum at 50 + 0.2 * 10,000 = 2,050 dead tuples. For high-write tables, lower autovacuum_vacuum_scale_factor from 0.2 to 0.01-0.05.

Transaction ID wraparound

Postgres uses 32-bit transaction IDs (~4.2 billion). The XID space is circular: IDs "in the past" (more than 2 billion behind the current XID) are considered old. If a table is not vacuumed and XIDs advance past the wraparound horizon, Postgres must shut down to prevent data corruption.

Click "Advance XID" to move the current transaction counter forward. Watch the wraparound horizon approach. Click "Freeze" to push the frozen horizon forward.
Takeaway: VACUUM isn't optional. Tune autovacuum_vacuum_scale_factor for high-write tables. Wraparound is an emergency event -- vacuum_freeze_min_age exists for this.

5. Interview quick reference

The 30-second MVCC answer

"Postgres implements MVCC by storing multiple physical versions of each row. Every row has xmin (creating transaction) and xmax (deleting/superseding transaction). Readers see a consistent snapshot without acquiring locks -- they simply ignore row versions that are invisible to their snapshot. Writers create new versions rather than overwriting in place. The cost is dead row versions that VACUUM must reclaim. This architecture means readers never block writers and writers never block readers -- the fundamental reason Postgres handles mixed read/write workloads well."

The "name the anomaly" probe

Interviewer asks...You say...
"What does Read Committed allow?" Non-repeatable reads: same SELECT returns different results within one transaction because each statement re-snapshots. Also phantom reads (new rows appear).
"What does Repeatable Read allow?" Write skew: two transactions read overlapping data, each writes to a different row, both commit, and a multi-row invariant is violated. Classic example: the doctor-on-call constraint.
"How does Serializable work in Postgres?" SSI (Serializable Snapshot Isolation). Same snapshot mechanism as RR, plus dependency tracking. Postgres detects rw-dependency cycles and aborts one transaction. The application must retry. Cost: ~10-30% throughput overhead at high contention.
"Why not just use Serializable everywhere?" Retry overhead and reduced throughput. Most OLTP workloads don't have cross-row invariants that need serializable protection. Read Committed is sufficient when writes are independent or protected by explicit locks (FOR UPDATE).
"What is VACUUM and why does it matter?" MVCC produces dead row versions on every UPDATE/DELETE. VACUUM marks that space reusable. Without it: table bloat (wasted disk and slower seq scans), index bloat, and ultimately transaction ID wraparound (Postgres shuts down). Autovacuum handles this automatically, but high-write tables may need tuned thresholds.
"How would you build a job queue in Postgres?" SELECT ... FOR UPDATE SKIP LOCKED LIMIT N. Workers skip already-locked rows instead of blocking. Combined with an index on status, this gives you a zero-contention queue without external infrastructure. At very high throughput (>10K jobs/sec), consider dedicated systems like SQS or Redis streams.

Common mistakes in interviews

Mistakes to avoid:
  • Confusing Postgres RR with true serializability. Postgres Repeatable Read is snapshot isolation. It prevents phantom reads (unlike the SQL standard minimum) but allows write skew. Many candidates say "RR prevents all anomalies except phantoms" -- wrong for Postgres.
  • Saying "MVCC uses locks." MVCC's entire point is avoiding read locks. Writers take row-level locks against other writers, but readers use snapshot visibility, not locks.
  • Ignoring the retry obligation. Serializable will abort transactions. If your application doesn't retry on serialization failure, you've just made it less reliable than Read Committed.
  • Treating VACUUM as optional. "We'll tune it later" is how you get a transaction ID wraparound emergency at 3 AM.
  • Using SELECT ... FOR UPDATE when you mean SKIP LOCKED. FOR UPDATE without SKIP LOCKED serializes all workers onto one row. For queue patterns, you almost always want SKIP LOCKED.
