Bounded queues. The math of fanout amplifying tails. Hedged + tied requests. Dean's "Tail at Scale." The math behind why your microservice p99 is terrible and what to do about it.

1. Backpressure -- Why Bounded Queues

Production is producer + consumer. If the producer emits faster than the consumer processes, a queue forms between them. An unbounded queue grows until the process runs out of memory and crashes. A bounded queue forces a decision when full: block the producer, drop new work, or evict the oldest entry. That decision is backpressure.

2. Backpressure Mechanisms in Practice

Every network and application layer has its own backpressure mechanism. The dangerous leaks happen at layer boundaries -- TCP gives backpressure, but an in-process unbounded queue between your gateway and worker thread pool does not.

TCP Backpressure

Receiver advertises rwnd (receive window). Sender cannot outpace. When receiver buffer fills, window shrinks to 0 -- sender blocks. Built-in flow control at L4.

HTTP/2 Flow Control

Per-stream window on top of connection window. Can backpressure one slow stream without blocking the entire connection. Each stream independently flow-controlled.

Reactive Streams

Subscriber calls request(N) to pull N items from publisher. Demand-driven: publisher never sends more than requested. Non-blocking, async backpressure.

Message Queue + Ack

Consumer acks after processing. Broker won't redeliver (or counts against in-flight limit) until ack or timeout. Kafka: consumer controls offset. SQS: visibility timeout.

Semaphore at Gateway

Limit concurrent in-flight requests (e.g., max 100 workers). Request 101 gets 503 Service Unavailable. Simple, effective, coarse-grained.

Token Bucket

Tokens refill at steady rate R. Each request costs 1 token. Burst up to bucket size B. When empty, requests are queued or rejected. Rate limiting with burst tolerance.

Takeaway: Every layer has its backpressure mechanism. The leaks are at layer boundaries -- TCP gives backpressure; an in-process unbounded queue between gateway and worker does not. Audit each boundary.

4. p99 / p999 Math at Scale

The fanout multiplier: if a single service has p99 = 100ms (1% of requests exceed 100ms), and a user request fans out to N sub-requests in parallel, the probability that all N finish within 100ms is 0.99^N. As N grows, the chance of hitting at least one slow sub-request approaches certainty.

Takeaway: Tail latency compounds with fanout. p99 of a 10-fanout is worse than p99 of any single backend. p99 of a 100-fanout is catastrophically worse. This is why large microservice architectures have terrible p99.

5. Dean's Tail-at-Scale Tactics

Reference: Jeff Dean and Luiz Barroso, "The Tail at Scale" (2013). Techniques to reduce user-visible tail latency without fixing every backend's tail.

Hedged Requests

Send request to server A. After a short delay (e.g., the 95th percentile of typical latency), send a backup to server B. Take whichever responds first; cancel the other. 2x cost for dramatic tail reduction.

Click "Run Hedged Request" to see the two-server race. The client sends to A first, then after a delay hedges to B. First response wins.

Tied Requests

Send the request to N servers simultaneously. The first server to start processing notifies the others to cancel. Better than hedged because no wasted work -- only one actually processes. Requires server-side cooperation.

Click "Run Tied Request" to see servers coordinate. Only the first to dequeue actually processes; others drop the request.

Other Tactics

Micro-partitioning

Split each shard into 10x smaller pieces. If a shard fails, its load distributes as ~10% increase across others (vs. 100% in coarse partitioning). Faster recovery, smaller blast radius.

Selective Replication

Replicate hot keys MORE than cold keys. RF=5 for the top 1% of keys, RF=3 for the rest. More replicas = more choices for hedged/tied requests on the hottest data.

Late Binding

Don't decide which replica to query until the last possible moment. At dispatch time, read responsiveness signals (queue depth, recent latency) and pick the healthiest server.

Good Enough Responses

Return partial results if some sub-requests time out. A search page with 9/10 results is better than a timeout error. Requires the client to tolerate incomplete data.

Takeaway: Hedged + tied requests = the user-facing answer to backend tails. ~2x cost for ~10x tail-latency reduction. The tradeoff is almost always worth it for user-facing fanout paths.

6. Latency Budgets + SLO Design

Set a per-service latency budget. If service A has a 200ms budget and calls B (50ms) + C (50ms), A's local processing budget is 100ms. Every external call needs a timeout shorter than your own budget. The common bug: httpClient.Get(url) with no timeout -- cascading hang when a dependency goes slow.

Deadline Propagation

Pass your remaining deadline downstream. gRPC has this built in: each service truncates further calls to whatever time remains. If you have 150ms left and call a dependency, it gets a 150ms deadline -- not its "default" 500ms. This prevents stale work on requests that the client has already abandoned.

Service A (200ms budget) calls B and C in parallel. Each gets a 50ms budget. Local processing gets the remaining 100ms. Click "Simulate Dependency Blowout" to see what happens when C exceeds its budget.
Takeaway: Budgets + propagated deadlines = how you keep tail latency from compounding catastrophically. Every external call must have a timeout. Every timeout must be < your own remaining budget.
