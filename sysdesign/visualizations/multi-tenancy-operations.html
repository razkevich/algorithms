Multi-tenancy operations

Noisy-neighbor controls, tenant-aware caching/sharding, zero-downtime tenant migration, per-tenant cost. The day-2 ops that turn a multi-tenant architecture into a sustainable B2B SaaS.

1. Noisy-neighbor controls

The pool problem: tenant X consumes all CPU / queue / connections, and tenant Y starves. Three control mechanisms prevent this.

Control mechanisms

  • Rate limit per tenant -- token bucket scoped per tenant_id. Tenant X can do 100 req/s; bursts allowed up to 200. Independent of other tenants.
  • Quota per tenant -- monthly cap. "Free tier: 10K events/month." Triggers degraded service or block when hit.
  • Fair queuing -- when serving a shared queue (DB pool, request queue, message queue), interleave per-tenant rather than FIFO. Prevents one tenant's burst from monopolizing.

Fair queuing algorithms

  • Round-robin by tenant: simple, all tenants equal weight.
  • Weighted Fair Queuing (WFQ): each tenant has a weight proportional to their tier. Premium tenants get 3x the throughput of free-tier tenants.
  • Deficit Round Robin (DRR): balance bytes/cycles served per tenant; favor under-served tenant on next round.
  • Stochastic Fair Queuing (SFQ): hash flow ID to bucket; inter-bucket fair scheduling, intra-bucket FIFO.

Takeaway: Pool only works with isolation mechanisms inside it. Rate limit + quota for ingress; fair queuing for shared workers. Without these, one heavy tenant degrades every other tenant.

2. Per-tenant connection pooling

Anti-pattern: shared connection pool where one tenant's slow queries hold connections and others get 503. Fix: per-tenant connection pool with caps + statement_timeout for slow-query containment.

3. Tenant migration without downtime

Scenario: a tenant has outgrown the pool DB and needs to move to a dedicated DB (silo). Naive approach = stop service, dump, restore, restart. Downtime = many minutes to hours. The online migration pattern gives zero downtime.

Edge cases

  • Schema drift -- new DB might have different schema. Dual-write needs to translate at the message level.
  • Transactions across DBs -- avoid. Design dual-write at message-level (event from outbox); each DB consumes independently.
  • Failure during cutover -- rollback-able because old DB still has data and dual-write keeps it current. Easy to revert.

Tools: Stripe's migration framework, Vitess online schema changes, pg_logical for Postgres.

Takeaway: Dual-write + backfill + verify + flip = the canonical zero-downtime migration. Works for tenant migrations, schema migrations, datacenter migrations. The key insight: keep old DB current so rollback is always safe.

4. Tenant-aware caching

Naive cache: cache.get('user:42:profile'). Bug: which tenant's user 42? Cross-tenant cache leak -- a security bug, not just performance. Fix: always include tenant_id in every cache key.

// WRONG -- cross-tenant leak
cache.get('user:42:profile')

// CORRECT -- tenant-scoped
cache.get('tenant:abc:user:42:profile')

// Pattern: cache wrapper auto-prefixes with tenant context
class TenantCache {
  get(key) { return cache.get(`tenant:${ctx.tenantId}:${key}`); }
  set(key, val, ttl) { cache.set(`tenant:${ctx.tenantId}:${key}`, val, ttl); }
}

Cache eviction -- shared vs per-tenant LRU

Without per-tenant limits, one tenant's hot data evicts other tenants from cache. Per-tenant LRU buckets keep fairness.

Eviction strategies

  • Per-tenant TTL -- large tenants get longer TTL (cache more aggressively); small tenants shorter.
  • Per-tenant size limits -- tenant X can use up to N MB of cache; LRU evicts within tenant's bucket.
  • Cache segmentation -- dedicated Redis cluster per tier; pool tenants share one cluster, premium tenants share another.
Takeaway: Cache key MUST include tenant_id. Per-tenant LRU buckets prevent one tenant from evicting others. Cache leakage between tenants is a security bug, not just performance.

5. Tenant-aware sharding

The sharding key choice determines whether queries are efficient (single-shard) or expensive (scatter-gather). For B2B SaaS, tenant_id as partition column is almost always right.

Sharding strategies

  • Hash by tenant_id -- even distribution, but tenant data spread across all shards. Every single-tenant query is scatter-gather.
  • Hash by (tenant_id, pk) -- composite hash. Same tradeoff: even distribution, but no locality.
  • Tenant_id as partition column (Citus, Vitess) -- all of one tenant's data on one shard. Single-tenant queries hit one shard. Multi-tenant queries scatter. The right default for B2B.

Interactive: sharding strategies compared

Showing "Tenant as partition" mode. Each tenant's data lives entirely on one shard. Single-tenant queries hit one shard only.

Hot-tenant mitigations

  • Sub-shard the hot tenant -- split its partition across multiple shards.
  • Isolate whale -- move hot tenant to dedicated shard (silo for whales). Click "Hot tenant!" then "Isolate whale" above to see this.
  • Read replicas of the hot shard -- offload reads to replicas while writes go to primary.
Takeaway: Tenant-as-partition column = the right default for B2B SaaS. Cross-shard joins are rare; intra-tenant locality is high. Hot tenants get isolated on demand.

6. Cost estimation per tenant

The unit economics question: how much does it cost to serve tenant X? If you cannot compute it, you are losing money on whales while overcharging long-tail tenants.

Direct costs (per tenant)

Compute (req/s x CPU cost) + DB (storage + IOPS) + Network (cross-AZ traffic) + S3 (storage + ops) + Logs/metrics (volume).

Shared costs (allocated)

Control plane, engineering/SRE, LB/NAT/shared infra. Allocated pro-rata by usage, revenue, or tier-based markup.

7. Operational checklist

Quick reference for multi-tenant production readiness.

  • OK tenant_id in every log line / metric label / trace span.
  • OK tenant_id in every cache key.
  • OK Tenant-aware rate limit at gateway.
  • OK RLS in DB (or equivalent) for cross-tenant leak defense.
  • OK Per-tenant cost dashboard.
  • OK Tenant migration runbook (rehearsed).
  • OK Whale tenant isolation path (silo DB on demand).
  • OK Compliance escalation path (regulated tenant gets dedicated tier).
The senior tell. "Pool with per-tenant rate limit + RLS for leak defense + tenant_id in every log/cache/metric/trace. Whale tenants get their own DB on demand. Cost dashboard shows direct + allocated per tenant -- that is where pricing tiers start."
