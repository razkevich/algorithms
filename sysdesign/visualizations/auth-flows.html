Authorization Code with PKCE

The modern universal default. Works for SPAs, mobile apps, and confidential server-side clients. PKCE (Proof Key for Code Exchange) replaces the client secret requirement with a dynamic verifier -- making the flow safe even when the client cannot keep secrets.

Click "Play Full Flow" to animate the Authorization Code + PKCE grant step by step, or use "Step" to advance one message at a time.
Takeaways
  • Auth Code + PKCE is the universal modern default -- works for SPA, mobile, and confidential clients. Even web apps with a backend should use PKCE.
  • PKCE protects against intercepted auth codes: attacker needs code_verifier which only the legitimate client has.
  • state parameter prevents CSRF -- attacker cannot predict the random state value bound to the user's session.
  • The implicit grant is dead. Auth Code + PKCE replaced it for all client types.

Client Credentials (Service-to-Service)

No user involved. The token represents the client identity, not a user. Used for M2M (machine-to-machine) communication: cron jobs calling internal APIs, microservice-to-microservice auth, batch processors.

Click "Play Flow" to animate the client credentials grant. No user interaction -- just service-to-service authentication.
Takeaways
  • Client credentials = M2M. No user context. No refresh token (just request a new one before expiry).
  • mTLS-bound tokens (RFC 8705): bind token to client cert so a stolen token cannot be used by another client.
  • Service mesh (Istio, Linkerd) can inject tokens transparently -- the application never manages credentials directly.

Device Authorization Grant

For input-constrained devices (Smart TVs, CLI tools, IoT) that cannot run a browser. Decouples the authentication device from the authorization device -- same pattern as gh auth login.

Click "Play Flow" to animate the device authorization grant. The TV polls while the user authenticates on their phone.
Takeaways
  • Device grant = decouple authentication device from authorization device. Same pattern as gh auth login (CLI tool gets you to authenticate in browser).
  • Polling interval is server-specified; the client must respect it (Auth Server returns slow_down if too frequent).
  • The user_code is short-lived (typically 15 min) and single-use.

Deprecated Grants

These exist for legacy migration only. If you see them in a 2024+ design, flag them.

Implicit Grant (deprecated)

DEPRECATED
The implicit flow returns the access token directly in the URL fragment. This exposes tokens to browser history, referrer headers, and logs. Replaced by Auth Code + PKCE.

Resource Owner Password Credentials (deprecated)

DEPRECATED
Why deprecated: The client collects the user's username and password directly, then sends them to the Auth Server. The client sees the user's credentials -- a trust violation. Only acceptable for first-party legacy migration where you own both the client and the auth server, and are transitioning to a proper flow.

Grant Selection Decision Matrix

Client Type Grant User? Secret Safe? Key Detail
SPA (browser) Auth Code + PKCE Yes No No client_secret; PKCE replaces it
Mobile app Auth Code + PKCE Yes No Custom URL scheme for redirect_uri
Web app (server) Auth Code + PKCE Yes Yes Can also use client_secret; PKCE still recommended
Service / daemon Client Credentials No Yes M2M; use mTLS for cert-bound tokens
Smart TV / CLI Device Authorization Yes No No browser; user authenticates on separate device
Legacy first-party ROPC (migrate away) Yes N/A Client sees password; temporary only
Takeaways
  • If you see implicit or password grant in 2024+, it is a legacy migration. Default to Auth Code + PKCE.
  • Implicit exposed tokens in URL fragments -- browser history, referrer headers, server logs all become attack vectors.
  • Implicit had no refresh tokens -- forced re-authentication or silent iframe hacks.
  • The interview tell: name the right grant for the client type. SPA/mobile/web = Auth Code + PKCE. Service = Client Credentials. TV/CLI = Device Grant.

OIDC + ID Token + JWT Structure

Token Validation Steps (Resource Server)

JWT = self-describing token, verifiable without server lookup (vs opaque tokens which require introspection). Click the JWT parts above to decode, or animate the validation pipeline.

HS256 vs RS256

HS256 (symmetric): Shared secret between auth server and resource server. Works for monoliths. Dangerous for cross-org -- everyone who validates can also forge tokens.

RS256 (asymmetric): Auth server signs with private key; resource servers verify with public key (fetched from /.well-known/jwks.json). Standard for cross-team API auth. Resource servers can verify but never forge.
Takeaways
  • JWT = self-describing token, verifiable without server lookup (vs opaque tokens which require introspection). RS256 + JWKS = the cross-service standard.
  • JWS (signed) vs JWE (encrypted): JWS is far more common -- the payload is readable but tamper-evident. JWE encrypts the payload itself.
  • Validation order: decode header, fetch public key by kid from JWKS, verify signature, check exp/nbf, check iss/aud, check scopes.

Token Lifecycle -- Access vs Refresh

Short access tokens (5-15 min) for every API call. Long refresh tokens (days-months) used only at /token to mint new access tokens. Rotation detects theft.

Choose a scenario to animate. Normal lifecycle shows access token expiry and refresh. Rotation shows how each refresh yields a new refresh token. Theft detection shows what happens when an attacker uses a stolen refresh token.
Takeaways
  • Short access + long refresh + rotation = the right shape. JWT cannot be revoked instantly without a blocklist; embrace short expiry instead.
  • Refresh token rotation: each use returns a new refresh token; the old one is invalidated. If attacker uses stolen refresh, victim's next refresh fails -- breach detected, all sessions invalidated.
  • Access tokens in memory (SPA) or httpOnly cookie (web app). Refresh tokens always in secure storage (httpOnly, Secure, SameSite=Strict).
