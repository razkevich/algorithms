LSM trees vs B+ trees

Write amplification, read amplification, space amplification. Compaction strategies. The storage engine choices underlying every distributed DB. Pick 2 of 3.

1. The Three Amplification Metrics

Any storage engine has three costs. You can optimize two of three. The fourth constraint (durability) is non-negotiable. Every design decision is a point on this triangle.

Write Amplification (WA)

Physical bytes written / logical bytes inserted. Higher = SSD wears out faster, throughput drops. B+ trees rewrite full pages; LSM compaction rewrites data multiple times across levels.

Read Amplification (RA)

Physical bytes read / bytes returned. Higher = slower reads, more I/O. B+ trees descend 3-5 levels. LSM must check memtable + multiple SSTables (Bloom filters help).

Space Amplification (SA)

Physical bytes on disk / logical data bytes. Higher = more disk needed. B+ trees: 50-70% fill factor. LSM STCS: 2x during compaction merges.

Takeaway: Pick 2 of 3. The interview tell is naming this trade-off explicitly. "We chose LSM with leveled compaction because our workload is read-heavy after ingest, so we accept higher write amplification for lower read and space amplification."

2. B+ Tree Mechanics

The workhorse of relational databases. Internal nodes hold keys + child pointers for navigation. Leaf nodes hold the actual key-value data (or key + row-pointer). All leaves sit at the same depth. Leaves link horizontally for efficient range scans.

Click an operation to see B+ tree mechanics in action. Insert triggers page splits when a leaf is full.

Key Properties

Fanout
Each internal node holds ~100-1000 keys (in practice). A tree with fanout 500 and 3 levels indexes 125 million keys. 4 levels: 62.5 billion.
Fill Factor
Leaves filled 50-70% (Postgres default ~90% for sequential inserts, but splits reduce it). Empty space absorbs future inserts before triggering splits.
Page Splits
When a leaf overflows: allocate a new sibling, split keys at the median, push the median up to the parent. If the parent overflows, cascade the split upward. This is the primary source of write amplification.
Range Scans
Descend to the start key, then follow the leaf chain horizontally. No further tree traversal needed. This is why B+ trees dominate OLTP: point reads AND range scans are efficient.

Amplification Profile

WA: Moderate

Random page rewrites. A single row insert may rewrite a full 8-16KB page. Full-page writes for crash safety (WAL + dirty page flush).

RA: Low

~3-5 page reads per point lookup (tree depth). Top levels are cached in buffer pool in practice, so often 1-2 disk reads.

SA: Moderate

50-70% average fill factor = up to 1.5-2x logical data size on disk. Dead tuples (MVCC) add more in Postgres.

Used by: Postgres, MySQL InnoDB, SQLite, MongoDB WiredTiger (page-based, B+-ish), most filesystems (ext4, NTFS, APFS).

Takeaway: B+ tree = balanced read/write/space. The default for OLTP relational. Random-write cost is mitigated by page caching (buffer pool keeps hot pages in memory, batches flushes). When the working set fits in memory, B+ tree write performance is excellent.

3. LSM Tree Mechanics

Log-Structured Merge tree. Every write is sequential: append to WAL, insert into in-memory sorted structure (memtable), periodically flush to immutable sorted files (SSTables) on disk. Reads must check multiple locations. Compaction merges SSTables in the background to bound read amplification.

Click an operation to see LSM tree mechanics. Writes are always sequential. Reads must check multiple SSTables.

Write Path

1. Append to WAL
Write-ahead log on disk. Sequential append. Ensures durability even if process crashes before memtable flushes.
2. Insert into Memtable
In-memory sorted structure (skip list or red-black tree). O(log N) insert. Fast because it is entirely in memory.
3. Flush to SSTable
When memtable reaches size threshold (typically 64-256MB), freeze it, write as a new immutable SSTable to L0. Sequential write to disk. Old WAL segment can be discarded.
4. Background Compaction
Merges multiple SSTables into fewer, removing duplicates and expired tombstones. This is the ongoing operational cost -- the constant background hum of LSM.

Read Path

1. Check Memtable
Most recent writes are here. O(log N) lookup.
2. Check L0 SSTables
L0 SSTables may have overlapping key ranges. Must check each one (newest first). Bloom filter per SSTable to skip those that definitely do not contain the key.
3. Check L1, L2, ...
Each level has non-overlapping SSTables (in leveled compaction). Binary search on SSTable boundaries, then binary search within SSTable. Bloom filter skips most disk reads.
4. Merge Results
First match wins (most recent write). Tombstone = key was deleted.

Used by: RocksDB (Cassandra, ScyllaDB, MyRocks, CockroachDB, TiDB, YugabyteDB), LevelDB, BadgerDB, ClickHouse MergeTree.

Takeaway: LSM = sequential writes everywhere. Reads pay the cost (multiple SSTables to check). Compaction is the operational cost -- the constant background hum. Every write-heavy system interview should mention LSM as the storage engine choice and name the compaction strategy.

4. Compaction Strategies

Three flavors with very different trade-off profiles. The compaction strategy is the single most important tuning knob in an LSM-based system. Picking the wrong one for your workload is a production incident waiting to happen.

Size-Tiered Compaction (STCS)

When N similar-sized SSTables accumulate, merge them into one larger SSTable. Historically the Cassandra default. Optimizes for write throughput at the cost of space and read performance.

4 small SSTables of similar size merge into 1 medium SSTable. Then 4 mediums merge into 1 large. Each row is rewritten O(log N) times total.

WA: Low

Each row written ~log N times across the lifetime of the data. Minimal rewrites compared to leveled.

RA: Medium-High

Multiple overlapping SSTables at each "tier." Must check all of them for a point read. Bloom filters help but cannot eliminate all reads.

SA: High

During merge, both old and new SSTables exist temporarily. Peak disk usage can reach 2x steady state. This is the operational killer.

Leveled Compaction (LCS)

SSTables organized into levels. L0 allows overlap. L1+ has non-overlapping key ranges. Each level is ~10x the size of the previous. When a level is full, one SSTable is pushed down and merge-sorted with overlapping SSTables in the next level. The RocksDB default.

L0 SSTables (may overlap) get pushed down to L1. Each L1 SSTable covers a disjoint key range. When L1 is full, one SSTable merges down into L2, and so on.

WA: Medium-High

Each row rewritten O(L) times where L is the number of levels. Typically 5-10x in practice. This is the cost you pay for read efficiency.

RA: Low-Medium

At most 1 SSTable per level (non-overlapping). L0 may have a few overlapping. With Bloom filters, usually 1-2 disk reads for a point lookup.

SA: Low

10-15% overhead typical. Non-overlapping keys at each level means minimal duplication. Predictable disk usage.

Time-Window Compaction (TWCS)

Each time window (e.g., 1 day, 1 hour) produces its own SSTable. SSTables within a window are compacted together (using STCS). SSTables are never merged across windows. When the retention period expires, the entire SSTable is dropped. The perfect strategy for time-series data with TTL.

7 SSTables, one per day. After the 90-day retention period, the oldest SSTable is simply deleted -- no merge, no rewrite, no compaction overhead.

WA: Low

Compaction only within a time window. Old data is never rewritten -- it is dropped wholesale when its TTL expires.

RA: Low

Queries are almost always scoped to a time window. Within a window, 1 compacted SSTable per window means 1 read.

SA: Low

No cross-window duplication. Each window is compacted independently. TTL drop = instant space reclaim with no temporary spike.

5. Bloom Filters in LSM

Each SSTable has a Bloom filter built over its keys during flush/compaction. On read, the filter answers: "Is this key possibly in this SSTable?" If no, skip the disk read entirely. If yes, read the SSTable (may be a false positive).

Without Bloom filters, looking up a key that does not exist requires reading every SSTable across every level -- the worst-case read path. With Bloom filters at 1% false-positive rate, ~99% of SSTables are skipped.

How It Helps

Negative Lookups
The worst case for LSM without Bloom filters. A key that does not exist must be checked against every SSTable. With Bloom filters, 99%+ of SSTables return "definitely not here" instantly.
Tunable False-Positive Rate
RocksDB default: ~1% per SSTable. 10 bits per key = ~1% FPR. You can trade memory for lower FPR. At 0.1% FPR, the read amplification of LSM approaches B+ tree levels.
No False Negatives
If the filter says "not here," it is guaranteed correct. If it says "maybe here," you read the SSTable and find out. This asymmetry is what makes Bloom filters useful.
Memory Cost
~10 bits per key. For 1 billion keys: ~1.2 GB of memory for all Bloom filters. Cheap relative to the I/O savings.
Takeaway: Bloom filter is the read-amp killer. LSM without Bloom is unusable for negative lookups. In interviews, always mention Bloom filters when discussing LSM read path -- it shows you understand the practical read optimization, not just the theoretical multi-SSTable cost.
