Java Concurrency Patterns

ExecutorService, CompletableFuture, BlockingQueues, pitfalls, and virtual threads — the concurrency toolkit every senior interview expects you to own cold.

ExecutorService & Thread Pools

A thread pool recycles threads rather than creating/destroying them per-task. Three components determine behavior: the core pool, the work queue, and the max pool.

Pool Anatomy

Pool Types Comparison

Factory method Core Max Queue When to use
newFixedThreadPool(n) n n Unbounded LinkedBlockingQueue Steady, predictable workload; limits resource consumption
newCachedThreadPool() 0 Integer.MAX SynchronousQueue (0 capacity) Burst short-lived tasks; threads die after 60 s idle. OOM risk under sustained load
newScheduledThreadPool(n) n Integer.MAX DelayQueue Delayed / recurring tasks; cron-style scheduling
newSingleThreadExecutor() 1 1 Unbounded LinkedBlockingQueue Ordered sequential execution; event loop pattern
newWorkStealingPool() ForkJoinPool, parallelism = CPU count Divide-and-conquer, recursive tasks, parallel streams
OOM trap: newFixedThreadPool uses an unbounded queue. Under overload, the queue grows without limit. Always construct ThreadPoolExecutor directly with a bounded queue in production.

Thread Pool Sizing Formula

CPU-bound
Nthreads = Ncpu + 1
The +1 covers the occasional page fault / GC pause without over-subscribing cores.
IO-bound
N * (1 + W/C)
W = avg wait time, C = avg compute time. If W/C = 9 → 10x threads per core.
Cores: 4 W/C ratio: 9
CPU-bound: 5 threads. IO-bound: 40 threads.

shutdown() vs shutdownNow()

shutdown() Allowed to finish Complete normally void; use awaitTermination()

Takeaway
  • Never use Executors.newFixedThreadPool in production without bounding the queue — OOM guaranteed under sustained overload.
  • CallerRunsPolicy is the idiomatic backpressure valve: it slows the producer proportionally.
  • Sizing: IO-bound services often run 50–200 threads per node; CPU-bound keeps it N+1.

CompletableFuture Pipelines

CompletableFuture chains asynchronous stages without blocking threads between steps. Each stage may run on a different thread from the common fork-join pool (or a custom executor).

Core Operators

OperatorInput → OutputBlocks?Use case
thenApply(fn) T → U (sync transform) No Map result; runs on completing thread
thenApplyAsync(fn) T → U No Same but scheduled on FJ pool (or custom executor)
thenCompose(fn) T → CompletableFuture<U> No Flat-map / async chain; avoids nested futures
thenCombine(other, fn) (T, U) → V No Zip two futures; both must complete first
allOf(futures...) → CF<Void> No Fan-out; completes when all complete
anyOf(futures...) → CF<Object> No First to complete wins; race pattern
exceptionally(fn) Throwable → T No Error recovery; skipped on success
handle(fn) (T, Throwable) → U No Always called; inspect both value and exception

allOf — Fan-out Pattern

var futures = ids.stream()
    .map(id -> CompletableFuture.supplyAsync(() -> fetchItem(id), ioExecutor))
    .toList();

CompletableFuture.allOf(futures.toArray(new CompletableFuture[0]))
    .thenApply(v -> futures.stream().map(CompletableFuture::join).toList())
    .thenAccept(results -> process(results));

Custom Executors for CPU vs IO Stages

// IO executor: large pool, park threads while waiting
ExecutorService ioExec = Executors.newFixedThreadPool(100);

// CPU executor: N+1 threads, no context-switch waste
ExecutorService cpuExec = Executors.newFixedThreadPool(
    Runtime.getRuntime().availableProcessors() + 1);

CompletableFuture
    .supplyAsync(() -> fetchFromDb(id), ioExec)       // IO stage
    .thenApplyAsync(data -> transform(data), cpuExec) // CPU stage
    .thenAcceptAsync(result -> writeToDb(result), ioExec); // IO stage
Deadlock trap — blocking get() inside a pipeline: 
// WRONG: FJ pool exhausted, inner get() waits for outer, deadlock
CompletableFuture.supplyAsync(() -> {
    return innerFuture.get(); // blocks FJ thread!
});
Always use thenCompose instead of nesting get() calls inside async stages. If you must block, use a separate IO thread pool.
Takeaway
  • thenApply = sync map; thenCompose = async flatMap (avoids CompletableFuture<CompletableFuture<T>>).
  • Use different executors for IO vs CPU stages — mixing them on the FJ pool causes interference.
  • Never call .get() inside a CF stage — it parks the worker and can deadlock the FJ pool.
  • handle() is preferred over exceptionally() when you need access to both the value and the error.

Producer-Consumer & Blocking Queues

The canonical concurrency pattern: producers enqueue work, consumers dequeue and process. BlockingQueue is the thread-safe handoff point with built-in backpressure.

BlockingQueue Implementations

ClassBounded?OrderKey trait
ArrayBlockingQueue yes FIFO Fixed array backing; single lock for put & take (simpler, slightly lower throughput)
LinkedBlockingQueue Optional (defaults unbounded) FIFO Two separate locks for head/tail → higher throughput; default in newFixedThreadPool
PriorityBlockingQueue no Priority heap Elements must implement Comparable; no peek ordering guarantee across threads
SynchronousQueue Capacity = 0 Direct hand-off Every put blocks until a take is waiting; used in newCachedThreadPool
DelayQueue no Delay expiry Elements only visible after their delay expires; used in ScheduledThreadPoolExecutor

put/take vs offer/poll

Disruptor Pattern — Why 100x Faster

The LMAX Disruptor replaces BlockingQueue with a pre-allocated ring buffer. Producers and consumers coordinate via sequence numbers with no locking.

Why Disruptor is faster: (1) Ring buffer is pre-allocated — zero GC pressure from object creation. (2) Coordination via CAS on sequence numbers — no lock contention. (3) Cache-friendly: slots are contiguous in memory; false sharing eliminated by padding. (4) No blocking park/unpark syscalls — producers/consumers busy-spin or yield.

Trade-off: Fixed size (must fit in memory), complexity, overkill for <1M events/sec. Use ArrayBlockingQueue until profiling shows you need it.
Takeaway
  • Use ArrayBlockingQueue(n) for bounded producer-consumer — backpressure is automatic via put().
  • Use offer(e, timeout, unit) when producers should time out rather than block indefinitely.
  • The work queue inside ThreadPoolExecutor is itself a BlockingQueue — same API.
  • Disruptor: reach for it when you're at 1M+ events/sec and profiling shows lock contention in the queue.

Common Pitfalls & Debugging

Deadlock — Lock Ordering Violation

Thread A holds L1 and waits for L2. Thread B holds L2 and waits for L1. Neither can proceed.

Press "Animate Deadlock" to watch lock acquisition and the circular wait form.

Livelock vs Starvation

Livelock
Both threads keep retrying and yielding in response to each other. CPU is busy, no progress is made. Common in polite retry loops: "after you" → "no, after you" → forever.
// Classic livelock
while (!lock1.tryLock()) {
    lock2.unlock(); // yield
    Thread.yield();
    lock2.lock();   // re-acquire, retry
}
Starvation
A thread is perpetually denied CPU time because higher-priority threads always preempt it. Common with unfair locks and PriorityBlockingQueue under sustained high-priority load.
// Fix: use fair lock
ReentrantLock lock =
  new ReentrantLock(true); // fair
// FIFO ordering prevents starvation

Thread-Safe Collection Gotchas

synchronizedList + iterator = NOT thread-safe 
List<String> list = Collections.synchronizedList(new ArrayList<>());

// WRONG: lock released between hasNext() and next()
for (String s : list) { ... }

// CORRECT: external sync on the list itself
synchronized(list) {
    for (String s : list) { ... }
}

// BETTER for read-heavy: snapshot-on-write
List<String> list = new CopyOnWriteArrayList<>();
ConcurrentHashMap check-then-act is NOT atomic 
// WRONG: two separate atomic ops, race window between them
if (!map.containsKey(key)) {
    map.put(key, new Value());
}

// CORRECT: single atomic operation
map.computeIfAbsent(key, k -> new Value());

// Also atomic: putIfAbsent, compute, merge, replace

CopyOnWriteArrayList — When to Use

synchronizedListCopyOnWriteArrayList
Read concurrencyBlocks all reads/writesLock-free reads (snapshot)
Write costO(1) amortizedO(n) — full array copy
Iteration safetyRequires external syncAlways safe (stale snapshot)
Best fitBalanced read/writeFew writes, many readers (listeners, handlers)

ThreadLocal Memory Leak

Thread pool threads are reused — ThreadLocal values persist across tasks 
// Pattern: RequestContext via ThreadLocal
static final ThreadLocal<RequestContext> ctx = new ThreadLocal<>();

// Task 1 sets it, forgets to remove
ctx.set(userContext);
doWork();
// ctx.remove(); ← forgot this!

// Task 2, on the SAME thread later, sees Task 1's context
ctx.get(); // returns old RequestContext — SECURITY BUG

Fix: Always ctx.remove() in a finally block. Or use a framework (Spring, Quarkus) that handles cleanup automatically. In virtual threads (Java 21+), prefer ScopedValue over ThreadLocal.

Quick Debugging Reference

SymptomLikely causeDiagnostic
App hangs, CPU at 0% Deadlock jstack <pid> → look for "deadlock" section
App spinning, CPU at 100%, no progress Livelock or busy-spin without progress jstack <pid> → threads in RUNNABLE, same frames in repeated samples
Thread stuck in WAITING/BLOCKED Lock contention, starved thread jstack → "waiting to lock <0x...>"
Memory leak in web app ThreadLocal not cleaned up Heap dump → look for large ThreadLocalMap.Entry[]
Stale data across requests ThreadLocal not removed between tasks Add logging in filter/interceptor to check ctx.get() before set
Takeaway
  • Deadlock: enforce consistent lock ordering across all code paths. Use tryLock(timeout) as a safety net.
  • Collections.synchronizedList: safe for individual calls; external synchronized(list) required for iteration.
  • ConcurrentHashMap: compound actions (if absent → put) require computeIfAbsent/compute, not separate calls.
  • ThreadLocal in thread pools: always remove() in finally. Forgetting causes data leaks and security bugs.

Virtual Threads & Structured Concurrency (Java 21)

Virtual threads decouple concurrency from OS threads. A JVM can run millions of virtual threads on a handful of carrier (OS) threads by unmounting blocked threads from the carrier.

Platform Thread vs Virtual Thread

Creating Virtual Threads

// Option 1: Thread.ofVirtual() builder
Thread vt = Thread.ofVirtual().name("vt-1").start(() -> {
    doBlockingIO(); // carrier unmounts here, no OS thread parked
});

// Option 2: VirtualThreadPerTaskExecutor — drop-in for thread pool
try (ExecutorService exec = Executors.newVirtualThreadPerTaskExecutor()) {
    for (Request req : requests) {
        exec.submit(() -> handle(req)); // each task gets its own VT
    }
} // try-with-resources calls shutdown() + awaitTermination()

// Option 3: Structured concurrency (Java 21+)
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    Subtask<User>  user  = scope.fork(() -> fetchUser(id));
    Subtask<Order> order = scope.fork(() -> fetchOrder(id));
    scope.join().throwIfFailed();
    return new Response(user.get(), order.get());
}

Structured Concurrency — StructuredTaskScope

When Virtual Threads Help vs Don't

ScenarioVirtual threadsWhy
High-concurrency IO (DB, HTTP, file) Excellent Each blocking call unmounts; millions of requests on few OS threads
Thread-per-request HTTP servers (Tomcat, Jetty) Drop-in win Replace thread pool with newVirtualThreadPerTaskExecutor()
CPU-bound computation No benefit VTs don't create extra CPU. Use ForkJoinPool / parallel streams
Pinned threads (synchronized block + IO) Carrier pinned synchronized + blocking IO pins the carrier OS thread — negates benefit. Use ReentrantLock instead.
ThreadLocal state propagation Caution VTs are cheap but still carry ThreadLocals. Prefer ScopedValue (JDK 21 preview) for propagation.

Migration Guidance

IO-bound services: drop thread pools
// Before
ExecutorService exec =
  Executors.newFixedThreadPool(200);

// After — simpler, scales better
ExecutorService exec =
  Executors.newVirtualThreadPerTaskExecutor();
CPU-bound: keep pools
// Keep ForkJoinPool / fixed pool
// for CPU-bound work
ExecutorService cpu =
  Executors.newFixedThreadPool(
    N_CPU + 1);

// Avoid: one VT per CPU task still
// competes for the same N cores
Pinning trap: A synchronized method that calls blocking IO pins the carrier OS thread, limiting you to ~200 carriers. Replace with ReentrantLock where IO is performed inside critical sections.
Takeaway
  • Virtual threads are cheap to create (heap, not OS). Use one per IO task freely.
  • Structured concurrency (StructuredTaskScope) ties subtask lifetimes to parent scope — automatic cancellation on failure, no leak.
  • Watch for pinning: synchronized + blocking IO parks the carrier. Migrate to ReentrantLock.
  • CPU-bound work: keep ForkJoinPool. VTs don't conjure extra CPU cores.
