Kubernetes topologies

Watch kubectl apply propagate through the apiserver, etcd, controllers, scheduler, kubelet. Click "kill apiserver," watch the reconciler keep going. Build the intuition for "explain how k8s actually works."

Control Plane + Data Plane

Every Kubernetes operation is a reconciliation loop: controllers watch desired state in etcd via the apiserver, compare to actual state, and converge. kubectl apply triggers a cascade: Deployment controller creates ReplicaSet, ReplicaSet controller creates Pods, Scheduler binds Pods to Nodes, Kubelet starts containers.

The control plane is the brain: apiserver (the front door), etcd (the source of truth), controller-manager (the reconcilers), scheduler (the matchmaker). Worker nodes run kubelet (the agent) and kube-proxy (the network plumber). Everything communicates through the apiserver -- no component talks to etcd directly except apiserver.
Takeaways
  • The reconciler pattern is the entire k8s philosophy. apiserver is the source of truth (via etcd). Everything else is a controller polling for changes.
  • No component except apiserver reads/writes etcd. This is a deliberate bottleneck -- it makes the system auditable and consistent.
  • Killing the scheduler leaves pods Pending. Killing an apiserver in HA mode is transparent -- other apiservers continue serving via etcd raft consensus.

Pod Scheduling: Filter, Score, Bind

The scheduler watches for Pending pods, then runs a two-phase algorithm: Filtering (which nodes can run this pod?) then Scoring (which of those is best?). The highest-scoring node gets the pod bound to it.

5 nodes with varying CPU and memory capacity. A new pod requests 500m CPU and 1Gi memory. The scheduler filters nodes that cannot satisfy the request, then scores the survivors to pick the best fit.
Takeaways
  • Filter then Score then Bind. PriorityClass + preemption is how production traffic kicks tier-2 workloads off when capacity is tight.
  • requests are guarantees (used for scheduling). limits are ceilings (used for enforcement). Schedule by requests, throttle/kill by limits.
  • topologySpreadConstraints is the modern replacement for pod anti-affinity -- it distributes replicas across zones/nodes evenly.

Networking: Services, Ingress, CNI

Every pod gets its own IP (from the CNI plugin). Services provide stable virtual IPs. kube-proxy writes iptables/IPVS rules to forward traffic from Service IP to pod IPs. Ingress adds L7 routing on top.

ClusterIP is the default Service type: a virtual IP reachable only inside the cluster. kube-proxy on every node programs iptables/IPVS rules that DNAT traffic destined for the ClusterIP to one of the backing pod IPs (round-robin or random).
Takeaways
  • Pod IPs are ephemeral; Service IPs are stable. kube-proxy is just iptables/IPVS rule-writing -- it does not proxy traffic itself (in iptables mode).
  • Ingress is L7 (Host/path routing) in front of Services. The Ingress controller is itself a Pod running nginx/Traefik/ALB, fronted by a LoadBalancer Service.
  • CNI plugins (Calico, Cilium, Flannel) implement the "every pod gets a routable IP" contract. NetworkPolicy is the firewall -- ingress/egress rules on pod label selectors.

Storage: PV / PVC / StorageClass

Kubernetes decouples storage requests (PVC) from actual storage (PV) with a matchmaker layer (StorageClass). The CSI driver handles the real provisioning -- creating EBS volumes, NFS mounts, or Ceph blocks.

A Pod declares a volumeMount. A PVC (PersistentVolumeClaim) requests storage by size and access mode. If no matching PV exists, the StorageClass triggers dynamic provisioning via the CSI driver, which creates the actual cloud volume.
Takeaways
  • PVCs are claims (demand); PVs are real volumes (supply). StorageClass is the matchmaker (dynamic provisioning). This decoupling lets developers request storage without knowing the infrastructure.
  • RWO (ReadWriteOnce) is the most common access mode -- a single node mounts the volume. EBS volumes are RWO and AZ-bound -- WaitForFirstConsumer binding mode prevents cross-AZ scheduling mistakes.
  • StatefulSet gives each replica its own PVC via volumeClaimTemplates. On delete + recreate, the same PVC reattaches -- data persists across pod identity.

HA Control Plane

Production Kubernetes runs 3+ control-plane nodes: etcd forms a raft quorum, multiple apiservers sit behind a load balancer, and scheduler/controller-manager use lease-based leader election. Lose one node, the cluster keeps working.

3 control-plane nodes, each running apiserver + etcd + scheduler + controller-manager. etcd uses Raft consensus: writes go to the leader, replicate to followers. apiserver instances are stateless -- any can serve reads/writes (they all talk to etcd). Scheduler and controller-manager use lease objects for leader election -- only one active instance at a time.
Takeaways
  • etcd quorum = majority (2 of 3, 3 of 5). Losing one node is safe; losing two means the cluster cannot write. This is why 3 is the minimum for HA.
  • apiserver is stateless -- scale it horizontally behind a load balancer. The bottleneck is etcd, not apiserver.
  • Scheduler and controller-manager run active/standby via lease objects. On leader death, a standby acquires the lease within seconds.
