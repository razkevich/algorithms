Distributed ID generation

Snowflake, UUID v7, ULID, KSUID, Hi-Lo. The canonical 64-bit packing. The clock-skew failure mode you have to mitigate. The first question of every URL Shortener / Twitter design round.

1. The 5 Properties

Every ID scheme trades off these axes. No scheme aces all five -- pick by what your system actually needs.

Snowflake -- Globally unique via machine ID partitioning. 64-bit compact. K-sortable by timestamp prefix. No coordination (local generation). Vulnerable to clock skew (not monotonic-safe without mitigations).
Key insight. The axes are:
  • Globally unique -- no duplicates across nodes
  • Compact -- small byte / character footprint
  • Sortable -- k-sortable, approximately ordered by creation time
  • No coordination -- generated locally without round-trip
  • Monotonic / clock-safe -- robust to clock skew, NTP corrections

2. DB Sequences (Centralized)

Postgres BIGSERIAL, MySQL AUTO_INCREMENT. One source of truth -- guaranteed unique + monotonic. But every insert needs a round-trip to the coordinator. At scale, the sequence becomes a bottleneck.

Direct Sequence vs Hi-Lo

Direct sequence. Every ID requires a round-trip to Postgres. 3 services, 3 round-trips per ID. The sequence is a single point of bottleneck at high throughput.
Takeaway. DB sequence for low-throughput apps. Hi-Lo for medium (reduces coordination 1000x). Snowflake-class for high throughput (zero coordination per ID).

3. UUID Variants

128-bit identifiers, 36-character hex string with dashes. The version determines how those bits are filled -- and whether the result is sortable.

4. ULID

26-character Crockford Base32 string. Same idea as UUID v7 -- timestamp prefix + randomness -- but with a more compact, URL-safe encoding.

Structure

unix_ts_ms48 bits (10 chars)
randomness80 bits (16 chars)

Total: 128 bits encoded as 26 chars of Crockford Base32. Alphabet: 0123456789ABCDEFGHJKMNPQRSTVWXYZ (excludes I, L, O, U for readability).

Example: 01H8XGJWZ3F8Q9NJ4MZRGW3KE2
First 10 chars = timestamp (ms since Unix epoch). Next 16 chars = cryptographic randomness.
Lexicographically sortable by generation time. Case-insensitive. No special characters -- URL-safe and copy-pasteable.

Crockford Base32 Encoding

Alphabet: 0123456789ABCDEFGHJKMNPQRSTVWXYZ
Excludes I (confused with 1), L (confused with 1), O (confused with 0), U (to avoid accidental obscenity).
Case-insensitive decoding: i/I/l/L all decode as 1; o/O decodes as 0.
This makes ULIDs robust to human transcription errors -- a practical advantage over hex encoding.

Collision Probability

With 80 random bits per millisecond, the probability of collision within the same millisecond is 1 / 2^80 = approximately 8.3 x 10^-25 per pair. Even at 1 million IDs per millisecond, the probability is negligible -- roughly 10^-13 per millisecond. The spec also defines monotonic ordering within the same millisecond: if two ULIDs share the same timestamp, the random component is incremented rather than regenerated, guaranteeing sort order.

Use when: you want a sortable, URL-friendly ID and don't want UUID dashes. Same underlying idea as UUID v7 -- timestamp + random -- just a different, more compact encoding. If your ecosystem already uses UUIDs everywhere, prefer v7 for consistency.

5. KSUID (K-Sortable Unique ID)

Segment's design. 27-character base62 string. 160 bits total -- more random bits than ULID for even lower collision probability.

Structure

timestamp32 bits (seconds since 2014-05-13)
payload (random)128 bits

Total: 160 bits. Encoded as 27 chars of base62 (0-9, A-Z, a-z). Custom epoch: 2014-05-13T16:53:20Z (Segment's founding moment).

Trade-off. KSUID has 128 random bits (vs 80 for ULID) -- vanishingly low collision probability. But only 1-second timestamp resolution: multiple IDs within the same second sort by random suffix, not by actual creation order. Used by Segment, Stripe.

Epoch Choice

KSUID uses a custom epoch of 2014-05-13T16:53:20Z (Unix timestamp 1400000000). With 32 bits of seconds, the maximum lifespan is 2^32 seconds = ~136 years from epoch, reaching until approximately 2150. Compare to Snowflake's 41-bit ms timestamp (69 years) -- KSUID's coarser resolution buys much longer lifespan.

Use when: you want maximum collision resistance and second-level sort order is sufficient. If you need millisecond ordering within the same second, prefer ULID or UUID v7.

6. Snowflake (Twitter)

Twitter's 2010 design. 64-bit integer -- fits in a BIGINT column, a JavaScript safe integer (with care), and a single register. The canonical interview answer for high-throughput distributed ID generation.

Bit Allocation

Custom epoch: 2010-11-04T01:42:54.657Z (Twitter's Snowflake launch). 41 bits of milliseconds = ~69.7 years from epoch.

Throughput math. 12-bit sequence = 4,096 IDs per millisecond per node. 10-bit machine ID = 1,024 unique nodes (32 datacenters x 32 workers). Total: 4,096 x 1,000 x 1,024 = ~4.2 billion IDs/second across the cluster.

Clock-Skew Failure Mode

If a node's clock goes backwards (NTP correction, leap second, VM migration), Snowflake IDs can collide with prior IDs. This is the failure mode interviewers probe for.

Click "Animate Clock Skew" to see the failure mode. Node generates IDs at timestamps 498-502. Then NTP corrects the clock backwards. The next ID reuses a timestamp from the past -- potential collision with an ID already issued.

Mitigations

StrategyHow it worksTrade-off
Block until catch-up If now < lastTimestamp, spin-wait until clock catches up. Refuse to generate IDs during the gap. Brief unavailability. Simple. Twitter's original approach.
Monotonic counter + offset Track lastTimestamp. If clock goes back, keep using lastTimestamp and increment sequence. Only advance when real clock exceeds stored timestamp. IDs during skew have slightly stale timestamps. Always available.
TrueTime bounds (Spanner) Google's GPS + atomic clock infrastructure gives a time interval [earliest, latest]. Wait out the uncertainty before committing. Requires specialized hardware. Gold standard for distributed timestamps.
Takeaway. Snowflake = high throughput, sortable, no coordination -- at the cost of clock-skew vulnerability. Worth it for ID-heavy workloads. The senior tell: name the 41/10/12 bit allocation and the clock-skew mitigation in the same breath.

7. Snowflake Variants

Different teams optimize the 64-bit budget for different shard counts, throughput, and longevity. The pattern is the same; the bit allocation differs.

Sonyflake (Sony)

0sign
39-bit time10ms units (~174 years)
8-bit seq256/10ms
16-bit machine65,536 nodes

Longer lifespan (174 years vs 69). More machines (65K vs 1K). Lower per-tick throughput (256 per 10ms = 25,600/s per node). Optimized for long-lived deployments with many small services.

Instagram

41-bit timestampms since 2011-01-01
13-bit shard8,192 logical shards
10-bit seq1,024/ms/shard

Generated inside Postgres via a PL/pgSQL function. Each shard is a logical Postgres schema. 13-bit shard ID supports 8,192 shards -- Instagram's sharding strategy baked into the ID.

Discord

0sign
41-bit timestampms since 2015-01-01
5-bit wkworker
5-bit procprocess
12-bit seq4,096/ms

Nearly identical to Twitter's layout. Custom epoch 2015-01-01. Worker + process instead of datacenter + worker -- same 10-bit machine space.

Why variants exist. The 64-bit budget is fixed. Each team slides the boundaries based on their constraints: more machines vs more throughput vs longer lifespan. The pattern -- timestamp | machine | sequence -- is universal. The bit allocation is the engineering decision.

Why the Bit Allocation Matters in Interviews

What interviewers actually want to hear. Not "I'd use Snowflake" but rather: "I'd allocate 41 bits to millisecond timestamp for ~69 years of headroom, 10 bits to machine ID giving us 1,024 nodes, and 12 bits to a per-millisecond sequence counter for 4,096 IDs per node per ms. The risk is clock skew -- I'd mitigate with a monotonic counter that refuses to go backwards." This level of specificity is the staff-level signal. Naming the scheme is table stakes; deriving the constraints from the bit budget is the tell.

B-Tree Index Implications

ID format directly impacts database write performance. Random IDs (UUID v4) cause random B-tree leaf page inserts -- every insert potentially touches a different page, fragmenting the buffer pool and causing write amplification. Sorted IDs (Snowflake, UUID v7, ULID) append to the rightmost leaf -- sequential I/O, minimal page splits, better cache utilization. This is why UUID v7 exists: it gives you UUID compatibility with B-tree-friendly write patterns.
