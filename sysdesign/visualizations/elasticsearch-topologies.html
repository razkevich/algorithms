Elasticsearch topologies

Master election (voting config), shard routing, query/fetch phases, cluster state recovery. The 7.x changes fixed split-brain. The shard count you set at index creation is the one you have to live with -- pick wisely.

Single Node -- Write Path and Refresh Cycle

A single ES node holds 5 primary shards (0 replicas). Writes go through the coordinating role, route to the correct shard via hash(_routing || _id) % num_primary_shards, append to the translog (durable), and sit in an in-memory buffer until the next refresh makes them searchable.

refresh_interval 1s
Writes are appended to the translog immediately (durable on disk). They sit in an in-memory buffer until the next refresh cycle creates a new Lucene segment, making them searchable. Refresh is expensive -- it creates a new segment.
Takeaways
  • ES is near-real-time, not real-time. The default 1s refresh_interval means a write is not searchable for up to 1 second.
  • Increase refresh_interval for high-throughput indexing (bulk loads). Refresh is expensive -- it creates a new in-memory segment and triggers segment merges.
  • Refresh is not flush. Refresh makes searchable (segment in memory); flush persists segments to disk and clears the translog.

Cluster + Master Election (Voting Config in 7.x+)

5 nodes: 3 master-eligible (M1, M2, M3) + 2 data-only (D1, D2). The voting configuration determines which nodes' votes count. Quorum = majority of voting config. Since 7.0, ES uses a Raft-like protocol and auto-manages the voting config -- no more minimum_master_nodes.

M1 is the elected master. Voting configuration: {M1, M2, M3}. Quorum requires 2 of 3 votes. The master maintains cluster state and broadcasts changes to all nodes via 2-phase commit (publish + commit).
Takeaways
  • Always odd number of master-eligible nodes. 3 is the production minimum.
  • Voting-only nodes are the cheap tiebreaker -- they vote but never become master. Useful for even-count clusters.
  • 7.x voting config auto-management solved the split-brain that plagued 6.x and earlier. Removed minimum_master_nodes (operator footgun -- misconfigure it and you get split-brain).

Indexing + Sharding

Index products: number_of_shards: 4, number_of_replicas: 2. Total physical shards = 4 x (1+2) = 12. ES distributes them across 5 data nodes, keeping primary + replicas of the same shard on different nodes.

Doc ID to Shard Assignment

Enter a doc ID and click Route to see hash(_id) % 4 shard routing.
4 primary shards (P0-P3) each with 2 replicas = 12 physical shards distributed across 5 data nodes. Shard routing: hash(_routing or _id) % number_of_shards. Primary shard count is fixed at index creation -- cannot change without reindex.
Takeaways
  • number_of_shards is fixed at index creation time. Cannot change without reindex. Pick based on target shard size (~10-50GB each), data volume, and node count.
  • Replicas serve reads in parallel -- replicas are the read scaling lever.
  • wait_for_active_shards: 1 (default) = primary only, all = all in-sync replicas. Trade-off durability vs availability.

Search Routing -- Query Phase + Fetch Phase

A search fans out to one copy of each shard (primary or replica). The two-phase protocol keeps network transfer minimal: query phase returns only doc IDs + scores; fetch phase retrieves full documents for the final top-K.

Search uses a scatter-gather pattern. Phase 1 (query): coordinating node fans out to one copy of each shard, each returns top-K doc IDs + scores (lightweight). Phase 2 (fetch): coordinating node requests full _source for only the final top-K docs. Adaptive Replica Selection (ARS) picks the fastest copy.
Takeaways
  • Search latency = max(per-shard query) + max(per-shard fetch) + merge overhead.
  • Deep pagination is anti-shard: from: 9990, size: 10 requires every shard to compute top-10000, sort and merge. Use search_after or scroll API instead.
  • ARS removes hot replicas from the rotation automatically -- it uses EWMA of past response times to pick the most responsive copy.

Cluster State + Recovery

The cluster state (index metadata, shard routing table, node list) is held by master and broadcast to all nodes. Shard states: INITIALIZING | STARTED | RELOCATING | UNASSIGNED. Cluster health = function of shard state.

Cluster health: GREEN
All primaries and replicas assigned. Cluster state is maintained by the master node and broadcast to all nodes via 2-phase commit. On node failure, master detects via heartbeat, promotes replicas, and schedules new replica creation to restore replication factor.
Takeaways
  • YELLOW = working but at-risk (some replicas unassigned). RED = data unavailable (some primaries unassigned). Yellow during rolling upgrade is expected and acceptable.
  • Disable shard allocation during rolling upgrades (cluster.routing.allocation.enable: none) to prevent unnecessary shard movement. Re-enable after.
  • Shard awareness (zone allocation) keeps primaries and replicas in different availability zones -- this is the multi-zone HA story.
