SQS / SNS Topologies

Watch visibility timeouts expire, DLQ routing trigger, SNS fanout fan out. Build the intuition that survives interview pressure.

SQS Standard Queue

Standard queues deliver messages at least once, with best-effort ordering. Consumers must be idempotent because the same message can be delivered more than once. Visibility timeout makes a message temporarily invisible while being processed — preventing double-processing under normal conditions.

Vis. timeout 6s
SQS Standard: producers send messages into the queue; consumers call ReceiveMessage (long poll). The message becomes invisible (visibility timeout) while one consumer processes it. If the consumer ACKs (DeleteMessage), the message is gone. If the consumer crashes before ACKing, the timeout expires and the message reappears — delivered again to another consumer. This is the source of at-least-once duplicates.

Long Polling vs Short Polling

Short Polling (default WaitTimeSeconds=0)

  • Returns immediately — even if queue is empty
  • Each empty response still costs money (per-request pricing)
  • Requires tight loop → wasted CPU + cost
  • Can miss messages across distributed servers (SQS is distributed; short poll hits a subset)

Long Polling (WaitTimeSeconds=1–20)

  • Request blocks server-side until a message arrives or timeout
  • Reduces empty responses → lower cost, lower CPU
  • Queries all distributed SQS servers — fewer missed messages
  • AWS recommendation: always use WaitTimeSeconds=20
Takeaways
  • Visibility timeout (default 30s, max 12h): must be longer than your processing time or you get duplicates. Set it 2x your P99 processing latency.
  • At-least-once + best-effort ordering: consumers MUST be idempotent. Use a DB upsert or a set-based dedup in Redis keyed on MessageId.
  • Long polling (WaitTimeSeconds=20) is almost always correct. Short polling wastes money and can miss messages.
  • Max 256KB per message. Larger payloads: store in S3, put the S3 key in the SQS message (Extended Client Library pattern).

SQS FIFO Queue

FIFO queues guarantee exactly-once processing and strict ordering per MessageGroupId. Groups are independent — messages in different groups can be processed in parallel while each group preserves its internal order.

FIFO queues maintain strict per-group order. Producers tag each message with a MessageGroupId (e.g. "order:user-123"). All messages in that group are processed in the exact order sent. Different groups are independent — Group A and Group B are processed concurrently by separate consumers.

Takeaways
  • MessageGroupId controls the unit of ordering — use it as the entity ID (user ID, order ID). One in-flight message per group at a time.
  • MessageDeduplicationId deduplicates within a 5-min sliding window. If you don't provide one, enable content-based deduplication (SHA-256 of body).
  • Throughput cap (300/s per action) is per-queue, not per-group. If you hit it, use multiple FIFO queues + routing by shard key at producer.
  • FIFO queues require queue name to end in .fifo. SNS FIFO → SQS FIFO = ordered fanout (covered in Tab 4).

Dead Letter Queue (DLQ)

When a message exceeds maxReceiveCount without being deleted, SQS routes it to the configured Dead Letter Queue. DLQs isolate poison pills and processing bugs, preventing queue stalls. Use CloudWatch alarms on DLQ depth as your primary alerting signal.

maxReceiveCount 3
Each time a consumer receives a message and doesn't delete it (either returns it via ChangeMessageVisibility or lets the visibility timeout expire), the ReceiveCount increments. When ReceiveCount exceeds maxReceiveCount, SQS moves the message to the DLQ automatically. DLQ Redrive lets you replay those messages back to the source queue after fixing the root cause.
Takeaways
  • Always configure a DLQ. Without it, poison pills loop forever, consuming capacity and delaying all other messages.
  • Set maxReceiveCount=3–5. Lower = faster DLQ routing (good for poison pills); higher = more retry attempts (good for transient errors).
  • DLQ alarm on depth > 0 is your canary. A clean queue should always have DLQ depth = 0. Any non-zero value means a consumer is broken or a payload is malformed.
  • DLQ Redrive (StartMessageMoveTask API) replays messages back to the source queue at a controlled rate after you fix the bug.
  • DLQ retention period must be ≥ source queue retention. If source keeps messages for 4 days and DLQ only 1 day, messages can expire in DLQ before you redrive.

SNS Fanout + Filter Policies

SNS pushes a message to all subscribed endpoints simultaneously. Combined with SQS subscriptions and filter policies, you get selective fanout: each downstream team gets only the events they care about — without producers knowing about consumers.

Publish "order.created" — billing gets it (no filter), inventory gets it (matches filter), analytics does NOT (filter wants shipped). Publish "order.shipped" — billing gets it, analytics gets it, inventory does NOT. Publish "order.cancelled" — only billing gets it. Filter policies decouple producers from consumers: the publisher never changes when a new subscriber is added.

SNS FIFO + SQS FIFO — Ordered Fanout

Standard SNS + Standard SQS

  • Best-effort ordering across subscribers
  • At-least-once delivery
  • Nearly unlimited throughput
  • Use for: notifications, logs, best-effort workflows

FIFO SNS + FIFO SQS

  • Strict ordering preserved end-to-end
  • Exactly-once within dedup window
  • Same 300/3000 msg/s throughput cap
  • Use for: financial events, audit trails that fan out to multiple services
Takeaways
  • SNS + SQS = push-to-pull buffering. SNS pushes to SQS; consumers pull from SQS at their own pace. This absorbs traffic bursts — the classic "fan out + buffer" pattern.
  • Filter policies are evaluated server-side at SNS before delivery. You're charged for the Publish API call, not for filtered-out deliveries to subscribers.
  • Raw message delivery: by default SNS wraps the payload in a JSON envelope. Enable raw delivery on the SQS subscription when the consumer doesn't know about SNS and just wants the original body.
  • SNS has no message retention (unlike Kafka). If SQS is unavailable when SNS pushes, the message is lost. SNS retries for HTTP endpoints but not SQS delivery failures (SQS is highly durable itself).

SQS / SNS vs Kafka — Decision Matrix

Both solve async messaging but with fundamentally different models. SQS/SNS is fully managed, serverless, and designed for task queues and event fanout. Kafka is a distributed log — replay, consumer groups, and stream processing are first-class. Pick by workload shape, not familiarity.

Interview Decision Tree

Hybrid Architectures

Kafka for streams, SQS for tasks

  • Kafka ingests high-volume events (clickstream, CDC)
  • Kafka consumer writes enriched events to SQS for downstream workers
  • SQS workers handle bursty, finite-lifetime tasks (send email, resize image)
  • Best of both: Kafka replay + SQS managed scaling

SNS + SQS + DLQ + Kafka

  • SNS → SQS for low-volume operational events
  • Kafka for high-volume data pipeline events
  • DLQ on every SQS queue — non-negotiable
  • Kafka Connect for CDC → Kafka → S3 for data lake
Key interview signals — say these unprompted
  • SQS = queue (delete on ACK), Kafka = log (immutable, offset-based). This is the fundamental model difference. Interviewers want to hear you articulate it.
  • If you need multiple independent services to consume the same event stream, use Kafka (consumer groups) or SNS+SQS (separate queues per subscriber). SQS alone only delivers each message to one consumer.
  • If cost is a constraint: SQS is nearly free at moderate volume. Kafka (MSK) has hourly broker cost regardless of traffic — don't choose it for a low-volume use case.
  • If replay is mentioned: Kafka. Period. SQS does not support replay; once deleted, gone.
  • SQS/SNS is serverless and scales to zero — correct choice when throughput is unpredictable or low-baseline (e.g. Lambda-based microservices).
