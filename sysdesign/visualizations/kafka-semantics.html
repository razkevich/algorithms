Kafka -- semantics + data modeling

Partition keys, compaction vs retention, exactly-once semantics, consumer offsets, the transactional API. The senior tell isn't using Kafka -- it's avoiding the seven ways your pipeline loses, duplicates, or reorders data.

1. Partition Key Design

The partition key is the ordering boundary. All messages with the same key land on the same partition via hash(key) % numPartitions. Within a partition, order is guaranteed. Across partitions, there is no ordering.

Partition count change breaks ordering

Increasing partition count changes hash(key) % N. The same key can map to a different partition after the change, breaking per-key ordering across the boundary.

Consumer group parallelism

Each partition is consumed by exactly one consumer in a group. Adding consumers beyond the partition count leaves them idle. This means partition count = max parallelism.

Takeaway: Partition key = ordering domain. Hot key = anti-pattern (one partition saturated, one consumer overloaded). Increasing partitions breaks key ordering across the change. Mitigation: pick partition count generously up front (10x current need), or use a fixed-modulus partitioner. Partition count = max consumer parallelism within a group.

2. Compaction vs Retention

Two retention modes per topic determine what Kafka keeps and what it discards.

Time/size retention (default)

Kafka deletes records older than retention.ms or beyond retention.bytes. The log is a sliding window of events.

Click "Animate" to see time-based deletion in action.

Log compaction

Kafka keeps only the latest record per key. Records with null value are tombstones -- the key is deleted on compaction. The result: a compacted topic is a table representation in log form.

Click "Animate" to see compaction collapse updates to latest-per-key.
Time/Size RetentionLog Compaction
KeepsAll records within windowLatest record per key only

AnalogyStream of eventsDB table as a log (key = primary key)

Compacted topic as materialized table

A compacted topic is semantically equivalent to a database table: each key is a row, each new record is an upsert, and a null value is a delete. Kafka Streams and ksqlDB build materialized views directly from compacted topics.

Takeaway: Retention = stream of events. Compaction = log of latest-state-per-key (table representation). Compacted topics are the foundation of Kafka Streams state stores and CDC pipelines. Stream-table duality: every stream can be compacted into a table, and every table change log is a stream.

3. Producer Semantics

Three delivery guarantees on the produce side. The choice is a trade-off between latency, durability, and deduplication.

Acks and replication

The acks setting determines when the broker acknowledges a write. Combined with min.insync.replicas, this controls the durability guarantee.

At-Most-Once

acks=0, no retry

At-Least-Once

acks=all, retry on timeout

Exactly-Once (Idempotent)

enable.idempotence=true

Click "Animate" to see how each semantic handles a broker crash during produce.
Takeaway: Idempotent producer = the modern default. It solves at-least-once becoming exactly-once for the producer side only via PID + sequence dedup on the broker. The consumer side is a separate problem.

StrategyCommit timingCrash effectGuarantee
Auto-commitEvery auto.commit.interval.msReprocess since last auto-commitAt-least-once (with surprise duplicates)
Manual commit afterAfter processingReprocess uncommitted batchAt-least-once (explicit)
Manual commit beforeBefore processingRecords lost (committed but unprocessed)At-most-once
Takeaway: At-least-once + idempotent processing in app code = practical exactly-once for most systems. Auto-commit is the source of mysterious duplicates. Manual commit-after-process is the safe default.

5. Transactional API -- True Exactly-Once

The producer-consumer transaction: read from topic A, process, write to topic B + commit offset on topic A -- atomically. This is Kafka's exactly-once semantics (EOS).

isolation.levelBehaviorUse case

Takeaway: True EOS in Kafka = idempotent producer + transactional API + read_committed consumer. Performance cost is ~1.5-3x vs at-least-once. Use for financial/correctness-critical pipelines. For everything else, at-least-once + idempotent consumers is cheaper and sufficient.

6. Common Pitfalls

PitfallCauseSymptomFix
max.poll.interval.ms exceeded Slow per-record processing Consumer kicked from group; rebalance storm Smaller batches, longer interval, or async processing
Rebalance storm GC pauses, slow heartbeat, network instability Consumers continuously joining/leaving Cooperative-sticky assignor; longer session.timeout.ms
Partition skew Hot key concentrates traffic One consumer overloaded, others idle Split key (e.g., user42-shard0), or go keyless
Consumer lag Consumer not keeping up with producer rate Growing per-partition lag in JMX metrics More consumers (up to partition count); larger fetch; faster processing
Out-of-order delivery Retry with max.in.flight.requests > 1 Messages arrive out of sequence Idempotent producer (fixes for up to 5 in-flight)
acks=1 data loss Leader crash before replication Acknowledged message lost acks=all + min.insync.replicas=2
Unclean leader election All ISR replicas down; out-of-sync replica elected Data loss from lagging replica becoming leader unclean.leader.election.enable=false (prefer unavailability over data loss)
Takeaway: Most Kafka production incidents trace to: hot keys (skew), slow consumers (rebalance storms), or wrong acks setting (data loss). The interview version: name the pitfall, state the config knob, explain the trade-off.

7. Schema Management

Schema Registry enforces the contract between producers and consumers. Each message carries a schema ID; the registry validates compatibility before allowing a new schema version.

Schema v1 (current)

  "type": "record",

  "fields": [

8. Configuration Quick Reference

The configs that appear in every Kafka interview, grouped by concern. Know the default, the production recommendation, and the trade-off.

Producer configs

ConfigDefaultProductionWhy
acks all (Kafka 3.0+) all Durability. Combined with min.insync.replicas for the full guarantee.
enable.idempotence true (3.0+) true Dedup retries via PID+sequence. No reason to disable.
max.in.flight.requests.per.connection 5 5 (with idempotence) Up to 5 is safe with idempotent producer. Without it, set to 1 or accept reordering risk.
retries 2147483647 Default (bounded by delivery.timeout.ms) Let delivery.timeout.ms control the overall retry window, not retry count.
linger.ms 0 5-100 Batch more records per request. Higher throughput, slight latency increase.
compression.type none lz4 or zstd Reduces network and disk I/O. lz4 for speed, zstd for ratio.

Consumer configs

ConfigDefaultProductionWhy
enable.auto.commit true false Manual commit gives explicit control over at-least-once vs at-most-once.
max.poll.interval.ms 300000 (5 min) Tune to processing time Exceeded = consumer kicked from group. Set to max expected batch processing time + margin.
max.poll.records 500 Tune to batch size Smaller = faster commits, less reprocessing on crash. Larger = higher throughput.
isolation.level read_uncommitted read_committed for EOS Required to skip aborted transactions. Only matters with transactional producers.
partition.assignment.strategy RangeAssignor CooperativeStickyAssignor Reduces rebalance pauses. Incremental rebalance instead of stop-the-world.

Broker / topic configs

ConfigDefaultProductionWhy
min.insync.replicas 1 2 (with RF=3) With acks=all: ensures at least 2 replicas have the record before ack. Tolerates 1 broker failure.
unclean.leader.election.enable false (2.8+) false Prefer unavailability over data loss. An out-of-sync replica as leader = data loss.
replication.factor 1 3 3 replicas = survive 1 broker loss with min.insync.replicas=2.
cleanup.policy delete compact for state topics delete = retention-based. compact = keep latest per key. compact,delete = both.
Takeaway: The interview-safe production defaults: acks=all + min.insync.replicas=2 + replication.factor=3 + enable.idempotence=true + manual offset commit + CooperativeStickyAssignor. Know why each one matters and what you trade.
