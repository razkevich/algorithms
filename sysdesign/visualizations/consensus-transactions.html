Distributed transactions + sagas

2PC, 3PC, saga (orchestration vs choreography), TCC, outbox. The patterns and the failure modes for multi-service consistency. The interview tell isn't picking one -- it's naming the failure mode you're choosing.

1. Two-Phase Commit (2PC)

A coordinator drives atomic commit across participants. Phase 1: every participant votes. Phase 2: coordinator broadcasts the decision. If all voted YES, commit; if any voted NO (or timed out), abort.

Two-Phase Commit (2PC): the coordinator sends PREPARE to all participants. Each votes YES or NO. If all YES, the coordinator sends COMMIT. If any NO (or timeout), it sends ABORT. Click a scenario above to animate.
Takeaway
  • 2PC provides strong atomicity: all-or-nothing across participants.
  • The coordinator is a single point of failure. If it crashes between Phase 1 and Phase 2, participants are blocked -- holding locks, unable to decide independently.
  • Used in distributed databases (XA protocol); microservices avoid it because the blocking failure mode is unacceptable at scale.

2. Three-Phase Commit (3PC)

3PC inserts a PRE-COMMIT phase between voting and committing. After all participants vote YES, the coordinator sends PRE-COMMIT (everyone now knows the decision is to commit) before the final COMMIT. This lets participants recover from coordinator failure without blocking -- if the network is synchronous.

3PC adds a PRE-COMMIT phase so participants know the decision before the final COMMIT. If the coordinator crashes after PRE-COMMIT, participants can independently proceed to COMMIT (they know everyone voted YES). Click to animate.
Takeaway
  • 3PC solves the blocking problem of 2PC -- but only under the assumption of a synchronous network (bounded message delays, no partitions).
  • In real distributed systems with network partitions, 3PC does not help: a partitioned participant in PRE-COMMIT state and a partitioned participant that never received PRE-COMMIT can reach contradictory decisions.
  • The extra round trip adds latency. Rarely used in practice.

3. Saga -- Orchestration

A central orchestrator (state machine) sequences local transactions across services. Each step either succeeds (advance) or fails (run compensating actions in reverse). No distributed locks -- each service commits locally.

The orchestrator drives a saga: Booking -> Payment -> Notification. If any step fails, it runs compensating actions in reverse order. Each compensation must be idempotent (it may be retried). Click a scenario to animate.
Takeaway
  • Orchestration = central state machine that owns the workflow. Easy to reason about, easy to observe (single source of saga state).
  • Compensating actions must be idempotent -- if the orchestrator retries a compensation (e.g., after its own crash), the service must handle duplicates.
  • State persistence: orchestrator writes its progress to a durable store. On crash, it recovers from the log and resumes from the last completed step.
  • Examples: AWS Step Functions, Temporal, Camunda, Netflix Conductor.

4. Saga -- Choreography

No central orchestrator. Each service publishes domain events; downstream services react. The saga emerges from the chain of events. Failure triggers compensating events in reverse.

Choreography: each service publishes events, others react. No central coordinator -- the saga is the emergent chain of events. Click a scenario to animate.

Orchestration vs Choreography

DimensionOrchestrationChoreography
ObservabilityHigh -- orchestrator owns all stateLow -- state scattered across service logs

Takeaway
  • Choreography = fully event-driven, no coordinator SPOF. Easier to scale, harder to reason about.
  • Risk of cyclic event chains and implicit coupling (service A reacts to B's event which reacts to A's event).
  • Orchestration is the senior default unless coupling is truly intolerable or the flow is very simple (2-3 services, linear chain).

5. TCC (Try-Confirm-Cancel)

Each business operation exposes three APIs: Try (reserve resources without finalizing), Confirm (finalize the reservation), Cancel (release it). The coordinator calls Try on all, then Confirm (or Cancel if any Try failed).

TCC: each service implements Try/Confirm/Cancel. The coordinator calls Try on all services; if all succeed, Confirm all. If any Try fails, Cancel those that succeeded. Click to animate.
Takeaway
  • TCC is application-level 2PC: services explicitly design reservation semantics (Try = hold seat, Confirm = issue ticket, Cancel = release seat).
  • More predictable than naked saga compensation because the reservation phase is explicit -- you know exactly what to undo.
  • Trade-off: every service must implement 3 APIs per operation. Higher development cost, but cleaner failure modes.
  • Compared to DB-level 2PC: TCC operates at the business logic layer; 2PC operates at the transaction manager layer.

6. Outbox Pattern (the dual-write fix)

The core problem: a service needs to write to its database AND publish an event to a message broker. Doing both individually risks inconsistency -- one can succeed while the other fails.

The dual-write failure modes

Two failure modes. DB-first: DB write succeeds, broker publish fails -- other services miss the event. Broker-first: event published, DB write fails -- other services see a ghost event for data that doesn't exist. Click to animate.

The Outbox solution

Outbox pattern: App writes the business row + an outbox row in the SAME database transaction (atomic). A relay process (polling or CDC/Debezium) reads the outbox table and publishes to the broker. Consumer deduplicates via inbox table. Click to animate.
Takeaway
  • The dual-write problem appears everywhere microservices touch databases AND brokers. It is a fundamental consistency challenge.
  • Outbox pattern: business data + outbox event in ONE transaction. Relay (poll or CDC) publishes from outbox to broker.
  • Inbox pattern (consumer side): consumer stores event ID in an inbox table. If the same event arrives twice, it's a no-op (idempotent consumer).
  • Both ends must be idempotent: producer retries publish, consumer deduplicates on receive.

7. Decision Matrix -- When to Use Which

ScenarioPatternWhy
2-service atomicity, both DBs, willing to block on failure 2PC Strongest guarantee, but coordinator SPOF and blocking. Rare in microservices; common in distributed DBs (XA).
Multi-service workflow, want central control and observability Saga (orchestration) Central state machine, clear failure handling, easy to monitor. Senior default for complex workflows.
Multi-service, fully decoupled, simple linear flow Saga (choreography) No coordinator SPOF, scales independently. Use for simple 2-3 service chains where coupling is intolerable.
Need explicit "reservation" semantics, predictable failure TCC Each service defines Try/Confirm/Cancel. More development cost, cleaner undo semantics than ad-hoc compensation.
DB write + event publish must be atomic Outbox + Inbox Solves the dual-write problem. Works with any saga variant. The foundational pattern for event-driven architectures.
The senior tell. When asked "how do you handle multi-service consistency?", the right opening is: "I'd avoid distributed transactions where possible -- saga with compensating actions OR outbox pattern. Distributed 2PC only when I control both sides and can tolerate the blocking failure mode." Then name the specific failure mode you're accepting. That's what separates senior from mid-level: not picking the "right" pattern, but articulating the trade-off you're choosing.
