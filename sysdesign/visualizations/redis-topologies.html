Single-Threaded Command Processing

Redis is single-threaded: all commands serialize through one queue, one at a time. A slow command (KEYS *) head-of-line-blocks every other client until it completes.

Speed 1.0x
Redis processes commands one at a time on a single thread. Fast ops (GET/SET/INCR/HGET) finish in microseconds. Slow ops (KEYS *, SUNIONSTORE on huge sets, large LRANGE) block the event loop and stall every other client until they complete.
Takeaways
  • Single-threaded does not mean slow. Operations are O(microseconds); the bottleneck is sustained throughput per instance (~100k ops/s).
  • Use UNLINK instead of DEL for big keys (async free in a background thread).
  • Use SCAN instead of KEYS for namespace iteration -- cursor-based, never blocks.

Sentinel Failover

Sentinel monitors a master and its replicas. On master failure: detect, reach quorum, elect a leader, promote a replica, reconfigure the topology. The entire sequence takes seconds -- watch it step by step.

Repl. lag 200ms
SDOWN timeout 3000ms
Sentinel watches a master and its replicas. Clients connect through Sentinel to discover the current master address. When the master fails, Sentinels detect it, reach quorum, elect a leader among themselves, and promote the best replica.
Takeaways
  • Why 3+ sentinels: quorum (majority) requires odd count; 1 sentinel cannot self-correct, 2 deadlock on disagreement.
  • Async replication = data loss possible on failover. min-replicas-to-write makes the master refuse writes when fewer than N replicas are connected -- sacrifices availability for durability.
  • Sentinel watches one master + its replicas. For multiple datasets, run multiple Sentinel constellations, or use Cluster.

Cluster: Sharding, Slots, and Gossip

Redis Cluster splits the keyspace into 16384 slots distributed across primaries. Each key maps deterministically to a slot via CRC16(key) % 16384. Gossip protocol handles failure detection and topology propagation.

Redis Cluster partitions 16384 slots across primaries. Each key is hashed with CRC16 to determine its slot and owning primary. Gossip protocol (PING/PONG between every pair of nodes) detects failures.
Takeaways
  • 16384 slots is fixed by design -- gives explicit control over which slots migrate to which node, unlike the implicit movement of consistent hashing.
  • Cluster has no cross-shard transactions. Multi-key ops require all keys in the same slot -- use hash tags {...} to colocate.
  • REPLICAOF is not symmetric: when you partition and heal, the minority side's writes are reconciled by accepting the majority's view (last-writer-wins per key).
