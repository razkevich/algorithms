Distributed locks -- how they actually fail

The naive Redis lock has two failure modes. Redlock has a third. etcd is safer but slower. None of them are safe without fencing tokens. Click through the failure animations.

Single-Instance Redis Lock (and why it fails)

Lock = SET lock:job clientId NX PX 10000. Looks simple. Two failure modes make it unsafe for anything that matters.

Speed 1.0x
Single-instance Redis lock: Client A calls SET lock:job A NX PX 10000. If OK, it holds the lock for up to 10 seconds. On release, DEL lock:job. Client B retries until the key is gone. Click "Happy Path" to see it work, then click the failure buttons.
Takeaways
  • Single-instance lock is unsafe under both process pause AND async replication failover.
  • Process pause (GC, swap, network) can outlast the TTL -- the lock expires while the holder still thinks it owns it.
  • Master failover with async replication can lose the lock key entirely -- replica promoted without the write.
  • The naive SET NX PX answer in interviews fails this scrutiny. Name both failure modes to stand out.

Redlock (Multi-Instance Redis)

Antirez's algorithm: N=5 independent Redis nodes (no replication). Client acquires on each within timeout T. If majority (3/5) within T minus clock drift, lock is held. Sounds safe -- Martin Kleppmann showed why it is not.

Speed 1.0x
Redlock: client sends SETNX to 5 independent Redis nodes in parallel. If it acquires on 3/5 (majority) within timeout T minus safety drift, the lock is considered held. Click "Acquire" to see the happy path.
Takeaways
  • Redlock is faster than consensus systems but does NOT provide a fencing token.
  • Kleppmann's critique: if any client experiences a process pause or clock jump after acquiring the majority, two clients can hold simultaneously.
  • Antirez's response: in practice the algorithm is fine for most use cases, but admits fencing tokens (which Redlock does not provide) are needed for shared-state writes.
  • Pair with token-checking on the resource side, OR use a real consensus system (etcd/ZK).

etcd / ZooKeeper -- Consensus-Backed Leases

3 etcd nodes running Raft. Client creates a lease (e.g., 10s TTL), then Put(key, value, leaseId) with Compare(version=0) (CAS). Only one client wins. Lease auto-renews via KeepAlive heartbeats. On crash -- no heartbeat, lease expires, key deleted, next client wins.

Speed 1.0x
etcd uses Raft consensus -- writes are committed when a majority of nodes agree. A lease is a TTL-bound session: the key exists as long as the lease is alive. KeepAlive heartbeats renew the lease. If heartbeats stop, the lease expires and the key is deleted.
Takeaways
  • etcd/ZK = strongly consistent leases. Safer than Redlock. Slower (consensus per op).
  • ZooKeeper analog: ephemeral sequential nodes + watches. When client session ends, ephemeral node deleted, next-in-line is unblocked.
  • etcd provides a monotonic revision with each write -- this is a fencing token out of the box.
  • Use when correctness matters more than speed: leader election, job scheduling, config coordination.

Database-Based Locks (Postgres)

Two flavors: advisory locks for application-level coordination, and row locks (FOR UPDATE SKIP LOCKED) for queue-style patterns. No extra infrastructure needed -- just your existing database.

Speed 1.0x
Postgres advisory locks: pg_advisory_lock(key) acquires an application-level lock. Per-session (released on disconnect) or per-transaction (released on commit). No data is locked -- it is purely a coordination primitive. Row locks with FOR UPDATE SKIP LOCKED let workers dequeue jobs without blocking each other.
Takeaways
  • DB lock = simplest, strongest consistency. Best when you already have the DB and don't want extra infrastructure.
  • SKIP LOCKED = the canonical Postgres-as-queue pattern. Workers grab the next unlocked row, skip locked ones, no contention.
  • Pros: strongly consistent (it is a real database), no extra infra, transactional semantics.
  • Cons: ties up DB connections; lock holder failure ties up rows until transaction timeout; doesn't scale to extreme throughput.

Fencing Tokens -- The Missing Piece

The Kleppmann diagram, made interactive. Without fencing tokens, no lock service is safe under process pauses. With fencing tokens, the resource server rejects stale writes -- the lock is just an optimization, not a safety mechanism.

Without fencing token -- corruption

With fencing token -- safe

Speed 1.0x
Fencing tokens: the lock service issues a monotonically increasing token with each acquisition. The resource server tracks the highest token it has seen and rejects any write with a lower token. This makes the resource self-protecting -- even if two clients think they hold the lock, only the one with the higher token can write.
Takeaways
  • Fencing tokens are the only way to be safe under process pauses. Any lock service without monotonic tokens is suspect for shared-state writes.
  • ZooKeeper provides zxid (transaction ID). etcd provides revision. Both are monotonic.
  • Redlock does NOT provide a fencing token -- you would have to layer one on top (e.g., from a separate counter), defeating the purpose.
  • The interview tell: naming fencing tokens unprompted signals deep understanding of distributed locking.

Comparison Matrix

Quick reference for interview answers. The key differentiator is safety -- which approaches actually prevent two clients from writing to the same resource simultaneously?

Approach Throughput Latency Safety Fencing Token Ops Complexity When to Pick
Single Redis Very high (~100k/s) Sub-ms Unsafe (2 failure modes) No Trivial Best-effort dedup, rate limiting, idempotency guards where occasional double-execution is tolerable
Redlock (5 nodes) High (~10k/s) ~5-15ms Contested (Kleppmann critique) No 5 independent Redis instances When you need better-than-single-Redis but cannot afford consensus latency; pair with fencing on the resource
etcd lease Moderate (~5-10k/s) ~5-20ms Strong (Raft consensus) Yes (revision) 3-5 node etcd cluster Leader election, job scheduling, config coordination -- correctness over speed
ZooKeeper lease Moderate (~5-10k/s) ~5-20ms Strong (ZAB consensus) Yes (zxid) Complex (JVM, quorum, sessions) Same as etcd; prefer etcd in new systems unless ecosystem demands ZK (Kafka pre-KRaft, Hadoop)
Postgres advisory Moderate (DB-bound) ~1-10ms Strong (ACID) Manual (use a sequence) No extra infra Already have Postgres; low lock volume; don't want to add Redis/etcd
Postgres FOR UPDATE SKIP LOCKED Moderate (DB-bound) ~1-10ms Strong (row-level ACID) Yes (row version / xmin) No extra infra Queue/worker pattern -- each worker grabs next unlocked job, no contention
DynamoDB conditional write High (partition-level) ~5-10ms Strong (per-item linearizable) Manual (use a counter attribute) Managed service AWS-native; per-item locking; condition expression on version attribute
Chubby (Google) Moderate ~5-20ms Strong (Paxos consensus) Yes (sequencer) Google-internal Concept only -- Chubby's sequencer IS the fencing token pattern; cite as the origin
The decision tree: (1) Is correctness critical? If no, single Redis is fine. If yes: (2) Do you already have Postgres? Use advisory locks or FOR UPDATE SKIP LOCKED. (3) Need distributed + correct? etcd lease with fencing token. (4) Redlock only if you accept the Kleppmann risk and layer your own fencing.
Takeaways
  • No lock is safe without resource-side enforcement. Fencing tokens make the resource self-protecting.
  • The decision is not "which lock is best" -- it is "how much correctness do I need, and what infrastructure do I already have?"
  • In interviews: name single-Redis as the baseline, acknowledge its failure modes, propose etcd/ZK for correctness, and mention fencing tokens unprompted. That is the signal.
