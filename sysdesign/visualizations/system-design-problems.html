URL Shortener

Core idea: A KV lookup with two paths -- shorten (write) and redirect (read). Write rate is low; the interesting engineering is in ID generation (collision-free, distributed) and caching the hot 20% of URLs that absorb 80% of reads. The CDN edge is your first line of defense.

Deep Dive: ID Generation

Three strategies, each with a different trade-off on collision risk, coordination cost, and sortability. Snowflake is the interview-safe default for any system that needs globally unique, time-ordered IDs without central coordination.

Deep Dive: Hot URL Caching & Thundering Herd

80/20 rule: cache the top 20% of URLs in Redis, serve redirects from CDN edge. The failure mode is thundering herd -- a popular cached URL expires, and hundreds of concurrent requests all miss cache simultaneously, hammering the DB.
Toggle between the problem (herd) and the fix (mutex lock on cache miss). Only one thread queries the DB; others wait for the cache to repopulate.
Pattern: Cache stampede prevention. Also applies to: Distributed Cache (dedicated tab), News Feed (feed cache expiry), any read-heavy system with TTL-based caching.

Deep Dive: Custom Alias Race Condition

User wants /my-brand as a custom alias. Two users submit the same alias simultaneously. Check-then-write is not atomic -- both pass the check, one overwrites the other. Fix: conditional write. In DynamoDB: PutItem with ConditionExpression: attribute_not_exists(pk). In SQL: INSERT ... ON CONFLICT DO NOTHING + check affected rows.
Two users try to claim the same custom alias simultaneously. Without conditional writes, one silently overwrites the other.
Pattern: Conditional write / compare-and-swap. Also applies to: idempotency keys (Payment), lease acquisition (Job Scheduler), any "claim" operation in distributed systems.
Transfer: URL Shortener is the simplest KV system. The patterns it introduces -- Snowflake IDs, cache stampede prevention, conditional writes -- recur in every other problem on this page.

News Feed / Timeline

Core idea: Read/write asymmetry forces a choice. Pre-compute feeds on write (fanout-on-write) makes reads O(1) but writes O(followers). Compute on read (fanout-on-read) makes writes O(1) but reads O(following). Celebrities with 50M followers break fanout-on-write. The real answer is hybrid: push to ordinary followers, pull celebrities into the feed on read.

Architecture: Fanout-on-Write vs. Fanout-on-Read

Toggle between fanout-on-write and fanout-on-read to see how the same "user posts" event takes completely different paths. Watch which boxes light up and the cost annotation.

Deep Dive: Celebrity (Hot-Key) Problem

A user with 50M followers posts. Fanout-on-write must push to 50M feed caches -- minutes of latency, massive write amplification. The fix: hybrid model. Maintain a is_celebrity flag (follower count > threshold). Push to ordinary followers; for celebrity posts, merge them into the reader's feed at read time.
Watch the difference: naive pushes to all followers (slow, expensive). Hybrid pushes only to ordinary followers; celebrity posts are pulled at read time.
Pattern: Hot-key mitigation via asymmetric processing. Also applies to: hot partition in Distributed Cache, surge pricing in Ride-Share, viral video in Video Streaming.

Deep Dive: Cursor-Based Pagination

Offset pagination breaks when new items are inserted: page 2 shifts, you see duplicates or miss items. Cursor pagination (pass last_seen_id) is stable under inserts -- the cursor points to a fixed position in the sorted set regardless of what was added above it.
Watch what happens to "Page 2" when a new post is inserted at the top. Offset pagination shifts; cursor pagination stays stable.
Pattern: Cursor-based pagination. Also applies to: Typeahead (suggestion lists), Messenger (message history), any paginated API with real-time inserts.

Deep Dive: Feed Ranking

Chronological feed is simple but low-engagement. Ranked feed: each candidate post gets a relevance score (recency, affinity, engagement rate, content type) and the feed is re-sorted by score. The ranking model runs offline; results are cached per user with a TTL. Stale-while-revalidate: serve the cached ranked feed while a background job recomputes.
Pattern: Offline scoring + cache + stale-while-revalidate. Also applies to: Typeahead (popularity ranking), Ride-Share (driver ranking by ETA), any system with expensive personalized computation.
Transfer: News Feed is the canonical read-heavy, write-amplification problem. The hybrid fanout pattern (push common, pull expensive) is the same shape as CDN caching (cache popular, origin-fetch rare) and notification delivery (batch low-priority, push high-priority).

Chat / Messenger

Core idea: HTTP is stateless; chat needs persistent connections (WebSocket). The hard part is not the protocol -- it is routing. When user A sends to user B, and B is connected to a different server among 10K servers, how does the message get there? Answer: pub-sub. Each server subscribes to channels for its connected users. The message bus does the routing.

Architecture: Message Delivery

Step 0/6
Step through the message delivery flow: User A sends a message that gets routed through the pub-sub layer to User B on a different chat server.

Deep Dive: Connection Routing via Pub-Sub

Each chat server subscribes to a Redis/Kafka channel for every connected user. When a message arrives for user B, it is published to B's channel. Whichever server has B's WebSocket connection receives it and pushes it down the socket. On server crash: client reconnects (new server), new server subscribes to B's channel. Messages published during reconnect are buffered in the channel (Kafka) or retrieved from the messages DB.
Watch a server crash: the client detects the broken connection, reconnects to a new server, which subscribes to the user's channel. Pending messages are delivered.
Pattern: Pub-sub for connection-agnostic routing. Also applies to: Webhook delivery (event fanout), News Feed (fanout-on-write via Kafka), any system where producer and consumer are decoupled.

Deep Dive: Message Ordering

Global ordering across all conversations is unnecessary and expensive. Per-conversation sequence numbers are sufficient: each conversation has a monotonically increasing counter. The sender's message gets the next sequence number; the receiver re-orders by it. If messages arrive out of order (network reordering), the client buffers and sorts before displaying.
Watch messages arrive out of order and the client re-sort them by sequence number before displaying.
Pattern: Per-partition sequence numbers. Also applies to: Kafka partition ordering, Event sourcing sequence, any system where total order is too expensive but partition order suffices.

Deep Dive: Presence (Online/Offline)

Heartbeat from client every N seconds. Server writes SET user:B:presence ONLINE EX 30 to Redis. If the client disconnects, the key expires after TTL -- user appears offline. Edge case: heartbeat arrives 1 second before TTL expiry, but network delay causes a 2-second gap. Solution: set TTL to 2-3x heartbeat interval for jitter tolerance.
Watch the heartbeat / TTL dance. Normal: heartbeat resets TTL before expiry. Disconnect: no heartbeat, TTL counts to zero, user appears offline.
Pattern: TTL-based liveness. Also applies to: Job Scheduler (worker heartbeat / lease), Rate Limiter (sliding window expiry), any distributed system that needs failure detection without coordination.
Transfer: Messenger is the canonical real-time, connection-oriented problem. The pub-sub routing pattern is the same shape used in webhook delivery, notification services, and multiplayer game servers. The presence heartbeat pattern is the same shape as leader lease in Job Scheduler.

Webhook Delivery System

Core idea: Reliable async delivery to external HTTP endpoints you don't control. The endpoint can be down for hours. You must retry without duplicating side effects. This is the canonical at-least-once delivery problem: guaranteed delivery + idempotent consumers. The engineering is in the retry state machine and fair queuing across tenants.

Architecture: Event to Delivery

Watch the delivery flow: event is enqueued, a worker picks it up, attempts HTTP POST to the customer endpoint. On failure, exponential backoff retries until success or DLQ.

Deep Dive: Retry State Machine

Every delivery attempt transitions through a state machine: PENDING (in queue) -> IN_FLIGHT (worker processing) -> SUCCESS or RETRY (back to queue with backoff) -> DLQ (after max retries). The backoff schedule is exponential: 1s, 2s, 4s, 8s, 16s... capped at a maximum interval.
Max retries 5
Adjust max retries and watch the delivery attempt cycle through states. Each retry doubles the wait time.
Pattern: Exponential backoff + DLQ. Also applies to: any external API call, payment retries, message delivery, distributed system communication where the other side may be temporarily unavailable.

Deep Dive: Idempotency

At-least-once delivery means duplicates are possible. The customer must handle them. Solution: include a X-Delivery-Id header (UUID) with every webhook. The customer stores seen delivery IDs and ignores duplicates. This is the same pattern as idempotency keys in payments -- the shape is identical, only the context differs.
The webhook includes X-Delivery-Id header. Customer stores seen IDs. First delivery: process normally. Duplicate: recognized and ignored.
Pattern: Idempotency via unique delivery/request ID. Also applies to: Payment (idempotency key), Job Scheduler (job dedup key), any at-least-once system.

Deep Dive: Per-Tenant Fair Queuing

One misbehaving tenant (slow/down endpoint) can consume all retry slots, starving healthy tenants. Fix: one logical sub-queue per tenant, workers round-robin across tenants. A slow tenant's queue grows, but it only blocks itself.
Toggle between single FIFO (one slow tenant blocks everyone) and fair per-tenant queuing (slow tenant only blocks itself).
Pattern: Per-tenant / per-key isolation. Also applies to: Rate Limiter (per-user buckets), Job Scheduler (per-tenant job queues), multi-tenant SaaS in general.
Transfer: Webhook delivery is the canonical reliable-async-delivery problem. The retry state machine + DLQ pattern appears in every message-driven system. The idempotency pattern appears everywhere money or state mutations are involved.

Distributed Cache

Core idea: A cache is a ring of KV servers with consistent hashing. The interesting engineering is not the happy path -- it is what breaks. Hot keys overwhelm one shard. Cache stampede hammers the DB on TTL expiry. Eviction policy determines what stays warm. Each failure mode has a specific, nameable fix.

Architecture: Consistent Hash Ring

A consistent hash ring with virtual nodes. Add/remove nodes to see which key ranges remap. Only 1/N keys move on topology change -- that is the whole point of consistent hashing.

Deep Dive: Hot Key Problem

One key (celebrity profile, viral post) gets 100x normal traffic, overwhelming the shard that owns it. Three solutions, each with a different trade-off:
L1: each app server keeps an in-process cache for hot keys (cheapest, but stale). Replicas: dedicated read replicas for hot keys (consistent, but more infra). Sharding: append random suffix to key, spread reads across N shards, merge on read (most complex, best distribution).
Pattern: Hot-key mitigation. Also applies to: News Feed (celebrity fanout), Ride-Share (surge zone), Rate Limiter (high-traffic user), any system with skewed access patterns.

Deep Dive: Cache Stampede

A cached item expires. N concurrent requests all miss simultaneously, all query the DB, all write the same value back. The DB gets N identical queries instead of 1. Three fixes:
No protection: all threads hit DB. Mutex: one thread acquires lock, others wait. Early refresh: background job refreshes before TTL expires, no miss ever happens.
Pattern: Stampede / thundering herd prevention. Also applies to: URL Shortener (hot URL cache), News Feed (feed cache), any read-through cache with TTL.

Deep Dive: Eviction Policies

When cache is full, something must go. LRU (Least Recently Used): evict the item not accessed for the longest time -- good default. LFU (Least Frequently Used): evict the item with fewest total accesses -- better for skewed workloads. FIFO: evict oldest inserted -- simplest, worst hit rate.
Cache (capacity 5): empty
Pattern: Eviction strategy selection. LRU is the default. LFU when you have clear hot/cold separation. FIFO only for append-only streams. The Redis maxmemory-policy config maps directly to this decision.
Transfer: Distributed Cache is the foundational caching problem. Every other system on this page has a caching layer, and the same failure modes (hot key, stampede, eviction) apply everywhere.

Ride-Sharing / Location Match

Core idea: Find nearby drivers in real-time. Geohash encodes latitude/longitude as a string where shared prefixes mean spatial proximity. "Nearby" becomes a prefix query on a sorted set. Matching is a greedy bipartite assignment approximated by ranking candidates by ETA.

Architecture: Ride Request Flow

Rider requests a ride. The location service queries the geohash grid for nearby drivers, ranks by ETA, and dispatches the best match.

Deep Dive: Geohash Precision

Geohash divides the world into a grid of cells. Higher precision = smaller cells. Precision 4 (~40km) is too coarse for ride matching. Precision 6 (~1.2km) is the sweet spot. Always query the target cell + 8 neighbors to avoid boundary misses.
Precision 5
Adjust precision to see cell size change. At precision 5, each cell is roughly 5km x 5km. Query the center cell + 8 neighbors for a 15km search radius.
Pattern: Geospatial indexing via geohash. Also applies to: food delivery, local search, any "find nearby X" problem. Redis GEOADD/GEORADIUS uses geohash internally.

Deep Dive: Driver Location Updates

1M active drivers, each reporting location every 4 seconds = 250K writes/sec. This is too much for any relational DB. Solution: Redis sorted set with GEOADD. Reads use GEORADIUS. The location data is ephemeral (a driver's position from 30 seconds ago is useless), so Redis's in-memory model is a perfect fit -- no durability needed.
Watch 250K writes/sec flow from drivers through the location service to Redis. A relational DB would collapse under this write rate; Redis handles it in-memory without breaking a sweat.

Transfer: Ride-sharing is the canonical real-time geospatial problem. Geohash indexing applies to any location-based service. The ephemeral-data-in-Redis pattern applies to presence, counters, and session state.

Payment / Digital Wallet

Core idea: The one problem where eventual consistency is the wrong default. Correctness beats availability. The three key primitives: idempotency keys (safe retries without double-charge), the saga pattern (distributed transactions without 2PC's blocking coordinator), and append-only ledgers (immutable audit trail, balance as derived state).

Architecture: Transfer (Saga Pattern)

Step 0/5
Step through a money transfer: debit A, credit B, handle failure with compensating transactions. Each step shows the saga state.

Deep Dive: Idempotency Key

Client generates a UUID before the request. Server stores (idempotency_key, response) before processing. On retry (same key), server returns the stored response without re-executing. This makes retries safe -- network timeouts, client crashes, load balancer retries all produce the same result exactly once.
Send the first request, then retry with the same idempotency key. The server returns the stored result without re-processing.
Pattern: Idempotency key. Also applies to: Webhook delivery (delivery ID), Job Scheduler (job dedup), any API that mutates state and may be retried.

Deep Dive: Saga vs. 2PC

2PC (two-phase commit) uses a coordinator that locks all participants, then commits or aborts. If the coordinator fails while holding locks, all participants are blocked. Saga: each step is a local transaction with a compensating action. No global locks. Trade-off: saga allows temporary inconsistency (A debited but B not yet credited), but recovers via compensation.

Pattern: Saga for distributed transactions. Also applies to: any multi-service workflow (order -> payment -> inventory -> shipping), Job Scheduler (multi-step jobs), any system where 2PC's blocking is unacceptable.

Deep Dive: Append-Only Ledger

Never store balance as a mutable column. Two concurrent transfers can read the same balance, both pass the check, both write -- resulting in a negative balance. Instead: append-only ledger entries (debit/credit records). Balance = SUM(credits) - SUM(debits). The ledger is immutable -- no UPDATE, no DELETE. Audit trail is built in.
Add credits and debits to the ledger. Balance is always derived from the sum of entries, never stored as a mutable value.
Pattern: Append-only / event-sourced state. Also applies to: any audit-sensitive system (banking, healthcare), event sourcing in general, Kafka's commit log is the same shape.
Transfer: Payment is the canonical correctness-over-availability problem. Idempotency keys, sagas, and append-only ledgers are the three primitives. Every financial or state-critical system uses some combination of these.

Distributed Rate Limiter

Core idea: Enforce "max N requests per window per user" without a central bottleneck. Token bucket is the most interview-friendly algorithm: intuitive (bucket fills at constant rate, each request consumes a token), handles bursts naturally (full bucket = burst capacity), and maps cleanly to two Redis keys.

Architecture: Token Bucket at API Gateway

Request rate 5/sec
Adjust the request arrival rate and watch tokens being consumed. When the bucket is empty, requests are rejected (429). The bucket refills at a constant rate.

Deep Dive: Algorithm Comparison

Three algorithms, each with a distinct failure mode. Fixed window: burst of 2N at boundary. Sliding window log: exact but memory-expensive (stores every timestamp). Token bucket: handles bursts gracefully, constant memory.
Fixed window: limit is 10/min. Attacker sends 10 requests at 0:59 and 10 at 1:00 -- 20 requests in 2 seconds, both windows pass. Sliding log catches it but stores every timestamp. Token bucket naturally rate-limits bursts.

Deep Dive: Redis Implementation

Fixed window: INCR user:123:window:17 + EXPIRE 60. Sliding log: ZADD user:123:requests timestamp + ZRANGEBYSCORE. The critical detail: read-then-write must be atomic. If you INCR and EXPIRE in two separate commands, a crash between them leaves a counter without TTL (memory leak). Solution: Lua script that executes atomically on the Redis server.
Non-atomic: INCR and EXPIRE as separate commands. A crash between them leaves a key without TTL, leaking memory forever. Lua script: both operations execute atomically inside Redis.
Pattern: Lua scripts for atomic multi-step Redis operations. Also applies to: Distributed Cache (atomic cache-aside), Messenger (atomic presence update), any system needing read-modify-write in Redis.

Deep Dive: Local vs. Central Coordination

Strict consistency: every request checks central Redis (+1 RTT latency, ~1-3ms). Approximate: each edge node keeps a local counter, syncs to Redis every 100ms. The race window is small (at most N_nodes * local_limit overshoot). For most API rate limiting, the approximate approach is fine -- you are protecting against abuse, not enforcing exact billing.
Central: every request checks Redis (+1 RTT). Local: each node counts locally, syncs every 100ms. Small overshoot window but much lower latency.
Pattern: Local-aggregate-sync for approximate distributed counters. Also applies to: analytics counters, view counts, any metric where exactness can be traded for latency.
Transfer: Rate limiter is the canonical "enforce a constraint across distributed nodes" problem. Token bucket appears in network QoS, API gateways, and anywhere burst control is needed. The local-vs-central trade-off is the same consistency-latency trade-off that appears everywhere.

Distributed Job Scheduler

Core idea: Run jobs reliably at scheduled times across a fleet of workers, with at-least-once semantics + idempotent jobs. Two hard parts: (1) who decides which worker runs which job -- a leader with a lease, and (2) what happens when a worker dies mid-job -- the lease expires, another worker reclaims it.

Architecture: Schedule to Execution

Watch a job flow from the schedule DB through the leader to a worker. On worker crash, the lease expires and another worker reclaims the job.

Deep Dive: Leader Election + Lease

One scheduler instance polls for due jobs and assigns them. Others are standby. The leader holds a lease (a key with TTL in Redis/etcd). It heartbeats the lease every T/3 seconds. If the leader dies, the lease expires after T seconds, and a standby wins the next CAS (compare-and-swap) to become the new leader.
Watch the leader heartbeat its lease. When it dies, the TTL counts down and a standby takes over.
Pattern: Lease-based leader election. Also applies to: any single-writer pattern, shard ownership, Kafka partition leader, distributed lock with automatic release.

Deep Dive: Missed Fire Recovery

The scheduler was down during a job's scheduled time. On restart, it checks: last_fired_at < scheduled_at AND scheduled_at < now(). Three policies: (1) Fire once (catch up the most recent missed run), (2) Fire all (catch up every missed run), (3) Skip (do nothing, wait for next schedule). The policy is configured per job.
Scheduler was down from 10:00 to 10:45. Job was scheduled at 10:00, 10:15, 10:30. Choose a missed-fire policy to see recovery behavior.
Pattern: Missed-fire policies. Also applies to: cron-like systems (Quartz, Airflow), any scheduled task that must handle downtime gracefully.

Deep Dive: Idempotent Jobs

At-least-once delivery means a job may execute twice (worker crashes after completing but before ACKing). Jobs must be idempotent: write to an append-only store with a dedup key, or use SELECT FOR UPDATE on the job row as a mutex. If the job has external side effects (send email), store a "sent" flag and check before sending.
Watch what happens when a job executes twice: the second run checks the dedup key and skips the side effect.
Pattern: Idempotent execution. Same shape as Payment idempotency keys and Webhook delivery IDs. The universal rule: any operation that may be retried must be safe to repeat.
Transfer: Job Scheduler is the canonical "reliable execution at a future time" problem. The lease pattern is the same as Kafka partition leadership. The missed-fire pattern is the same as event replay in event-sourced systems. Idempotent jobs are the same shape as idempotent API endpoints.

Video Streaming

Core idea: Three sub-problems with different architectures: (1) upload -- chunked ingest to object storage, (2) processing -- transcoding to multiple bitrates via job queue, (3) playback -- CDN-delivered adaptive bitrate streaming. The player dynamically switches quality based on measured bandwidth.

Architecture: Upload + Transcode + Playback

Toggle between upload (client -> S3 -> transcode workers -> multiple resolutions) and playback (player -> CDN edge -> adaptive bitrate). Watch the flow animate.

Deep Dive: Adaptive Bitrate (HLS/DASH)

The player requests a manifest file (.m3u8 for HLS) listing segment URLs at multiple quality levels. It measures download speed for each segment and switches quality accordingly. Bandwidth drops? Next segment is 480p instead of 1080p. The switch is per-segment, so it is seamless.
Bandwidth 8 Mbps
Adjust bandwidth mid-playback to see quality adaptation. The player selects the highest quality that fits within available bandwidth.
Pattern: Adaptive quality based on client-measured conditions. Also applies to: any progressive loading (image quality, map tile resolution), graceful degradation under load.

Deep Dive: Transcoding Pipeline

One upload generates N output profiles (240p, 480p, 720p, 1080p). A job queue fans out to N transcoding workers. Each profile completes independently -- the video becomes partially available (720p ready before 1080p). Progress tracking per profile, with webhook notification on each completion.
Watch parallel transcoding: each resolution completes at a different time. The video is playable as soon as the first profile finishes.
Pattern: Fan-out to parallel workers with partial availability. Also applies to: image processing (multiple sizes), document conversion, any batch job that produces multiple independent outputs.

Deep Dive: CDN Cache Hierarchy

Three-tier hierarchy: edge (closest to user) -> regional (shared across edges) -> origin (S3). Popular videos are cached at edge (lowest latency). Long-tail videos miss at edge, hit regional. Very rare videos go all the way to origin. Cache warming: for anticipated popular content (new show release), pre-push to edges before launch.
Popular: cached at edge, served in ~5ms. Long-tail: misses edge, misses regional, fetches from origin S3. First-request latency: ~200ms. Subsequent requests cached at regional level.
Pattern: Multi-tier caching with popularity-based warming. Also applies to: URL Shortener (CDN edge for popular URLs), any content delivery system with skewed access patterns.
Transfer: Video streaming combines three patterns: chunked upload (same as large file upload), fan-out processing (same as webhook delivery), and CDN-based delivery (same as any content-heavy system). Adaptive bitrate is unique to media but the principle of client-measured adaptation applies broadly.

Search Typeahead / Autocomplete

Core idea: Return the top K suggestions for a query prefix in under 100ms. The trie is the classic data structure -- prefix lookup is O(prefix length). At scale, you shard by prefix, cache aggressively in Redis, and debounce keystrokes on the client to avoid sending a request per character.

Architecture: Keystroke to Suggestions

Watch keystrokes trigger debounced API calls. The first request checks Redis cache; on miss, it queries the trie service and populates the cache for subsequent lookups.

Deep Dive: Trie Traversal

The trie stores prefixes as a tree. Each node represents a character. To find suggestions for "sys", traverse root -> s -> y -> s, then collect all leaf nodes below. Each leaf stores a suggestion with its frequency weight. The top K by weight are returned.
Click a prefix to see the trie traversal. The highlighted path shows which nodes are visited. Deeper prefix = fewer results but more specific.
Pattern: Trie (prefix tree). O(L) lookup where L = prefix length. Interview-friendly because it is visually intuitive and maps directly to the problem structure. At scale, each subtree becomes a shard.

Deep Dive: Trie Sharding

A single trie for all prefixes does not fit on one machine at scale. Shard by the first 2 characters: "sy*" goes to shard 3, "ca*" goes to shard 7. Hot prefixes (common starting letters like "th", "wh") get dedicated replicas. The routing layer hashes the first 2 chars to determine the shard.
Click a prefix to see which shard handles it. Hot prefixes have replicas for load distribution.
Pattern: Prefix-based sharding. Also applies to: any trie or prefix-indexed system, DNS resolution (zone delegation), geohash (prefix = region).

Deep Dive: Popularity Ranking Pipeline

Suggestions are sorted by search frequency. A log stream feeds into Kafka, an aggregation job computes counts, and updates trie node weights. The pipeline runs on a schedule (every 15 minutes). Cache TTL determines staleness: shorter TTL = fresher suggestions but more computation. A good default: 5-minute cache TTL with 15-minute aggregation.
Watch the ranking pipeline: search logs flow through Kafka to an aggregation job that updates trie weights, then flushes to cache.
Pattern: Stream processing for near-real-time aggregation. Also applies to: News Feed (engagement scoring), Ride-Share (demand aggregation), any system that needs near-real-time derived metrics.

Deep Dive: Freshness for Trending Terms

A new trending term needs to appear within minutes, not wait for the next batch aggregation. Solution: a real-time event stream bypass. High-velocity search terms (detected by a count-min sketch or simple threshold) are written directly to the Redis cache for their prefix, bypassing the batch pipeline. The batch pipeline eventually catches up and takes over.
A trending term spikes. The real-time path writes it directly to Redis cache, bypassing the batch pipeline. Users see it within seconds.
Pattern: Lambda architecture (batch + real-time bypass). Also applies to: any system where batch processing is too slow for trending/breaking content. The real-time path handles the hot head; the batch path handles the long tail.
Transfer: Typeahead is the canonical prefix-search problem. Trie sharding is the same shape as key-range partitioning. The ranking pipeline is the same shape as any stream-processing aggregation. The freshness bypass is a mini lambda architecture.
