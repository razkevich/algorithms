1. The Inverted Index

A traditional database stores doc -> fields. A search engine stores term -> list of docs. That's the inversion.

Notice: fox and foxes are different terms because the standard analyzer does not stem. dog and dogs likewise. This is why analyzer choice matters -- next section.

What's Actually Stored

The posting list stores more than just doc IDs and term frequencies. A full Lucene posting list entry contains:

"quick" -> [
  doc1: { tf: 1, positions: [1], offsets: [(4,9)] },
  doc2: { tf: 1, positions: [1], offsets: [(5,10)] },
  doc3: { tf: 1, positions: [2], offsets: [(10,15)] }
]

Positions enable phrase queries: "quick brown" matches only if "quick" is at position N and "brown" at position N+1. Without positions, you can find docs containing both terms but can't verify adjacency.

Offsets enable highlighting: ES can mark the exact character range in the original text that matched.

Doc values (column-oriented storage) are stored separately for sorting and aggregations -- the inverted index is for searching, doc values are for everything else.
Takeaway: Inverted index = mapping from term to (doc IDs + term frequencies + positions). The "index" your DBA thinks about is forward; this one is inverted. Every search query starts here.

3. BM25 -- the Modern Relevance Score

ES 5.0+ uses BM25 by default (replaced TF-IDF). The formula:

score(D, Q) = sum over query terms t of:
    IDF(t) * TF_part(t, D)

where:
    IDF(t) = log( (N - df(t) + 0.5) / (df(t) + 0.5) + 1 )
    TF_part = (tf * (k1 + 1)) / (tf + k1 * (1 - b + b * (|D| / avgdl)))

Defaults:  k1 = 1.2 (TF saturation)    b = 0.75 (length normalization)

The rarer the term, the more it discriminates. This is why stop-word removal matters less in BM25 than in boolean search -- common words naturally get low IDF.

Length Normalization (b)

b controls how much document length penalizes the score.
At b=1: a term in a 100-word doc scores much lower than in a 10-word doc (same TF).
At b=0: length is ignored entirely.
At b=0.75 (default): moderate normalization. Short docs get a mild boost.

4. Search Context vs Filter Context

Two query contexts in a bool query. The distinction is the single biggest performance lever in ES query design.

{
  "bool": {
    "must":   [{ "match": { "description": "phone" } }],   // scored (BM25)
    "filter": [{ "term":  { "category": "electronics" } }, // cached bitset, NOT scored
               { "range": { "price": { "lte": 1000 } } }]
  }
}

must / should = SCORED

Goes through analyzers, IDF lookups, BM25 computation. Expensive. Determines ranking.

Filter Caching

Bitset caching is automatic. ES maintains a filter cache (node-level, LRU). When the same filter appears in multiple queries, the cached bitset is reused without re-evaluating the condition.

Segment-level granularity. Filter bitsets are cached per Lucene segment. When segments merge (background process), old bitset cache entries are evicted and new ones are computed lazily.

This is why structured filtering belongs in filter, not must. A must: term clause is scored (wasteful, since the term score is meaningless for a category filter) and NOT cached as a bitset. Moving it to filter gets you both: no scoring AND caching.
Takeaway: Move every yes/no condition to filter. Score only what needs scoring. This is the 10x perf win for free.
  • must -- "this must match AND affects ranking"
  • filter -- "this must match but I don't care about its score"
  • should -- "boost if this matches" (in bool with must) or "at least one must match" (in bool without must)
  • must_not -- "exclude, never score"

5. Aggregations -- Bucket vs Metric

Two top-level aggregation types:

  • Bucket aggregations -- group docs into buckets (like SQL GROUP BY). Examples: terms, histogram, date_histogram, range.
  • Metric aggregations -- compute a single value over a doc set. Examples: avg, sum, cardinality, percentiles.

Bucket aggregations can be nested (sub-aggregations) -- bucket per term, then inside each bucket a metric or histogram.

{
  "aggs": {
    "by_category": {
      "terms": { "field": "category" },
      "aggs": {
        "avg_price": { "avg": { "field": "price" } },
        "price_histogram": { "histogram": { "field": "price", "interval": 100 } }
      }
    }
  }
}

Precision Caveats

terms aggregation: each shard returns its local top-N terms; the coordinator merges. This can miss "long-tail" terms when shard distributions differ. Increase shard_size (default: size * 1.5 + 10) for better accuracy at the cost of memory.

cardinality: uses HyperLogLog under the hood -- approximate distinct count (same idea as Redis PFCOUNT). Error margin ~0.5-2%.

percentiles: uses t-digest -- approximate. Accuracy is best at the extremes (p99, p1) and worst in the middle (p50).
Takeaway: Aggregations = the analytics part of ES. terms is approximate at scale (shard_size matters). cardinality is HyperLogLog (approximate). percentiles is t-digest (approximate). Anything "exact" on a large distributed dataset is suspect.

6. Scoring Tuning Levers

When defaults aren't enough. In order of "try this first":

Field Boosting

Multiply a field's score contribution. Title matches matter more than body matches.

{ "multi_match": {
    "query": "phone",
    "fields": ["title^3", "description"]
  }
}
// title match scores 3x

When: obvious field-importance hierarchy. Always the first lever to try.

Function Score

Arbitrary scoring function on top of BM25 -- decay by recency, distance, popularity.

{ "function_score": {
    "query": { "match": { "title": "phone" } },
    "functions": [{
      "gauss": {
        "date": { "origin": "now", "scale": "30d" }
      }
    }],
    "boost_mode": "multiply"
  }
}

When: relevance needs non-textual signals (freshness, geo-distance, popularity score).

Rescore

Cheap query for top-K, then expensive scorer on those K only. Two-phase ranking.

{ "query": { "match": { "title": "phone" } },
  "rescore": {
    "window_size": 100,
    "query": {
      "rescore_query": {
        "match_phrase": { "title": "smart phone" }
      },
      "query_weight": 0.7,
      "rescore_query_weight": 1.2
    }
  }
}

When: expensive scoring (phrase, ML re-rank) on the full result set is too slow.

Synonyms

Index-time vs query-time. Query-time is more flexible (no re-index), but slower per query.

// synonym filter in analyzer config
"filter": {
  "my_synonyms": {
    "type": "synonym",
    "synonyms": [
      "phone, mobile, cell",
      "laptop, notebook"
    ]
  }
}

When: domain-specific vocabulary. Medical, legal, e-commerce all have synonym needs.

Takeaway: Most scoring "problems" are analyzer problems in disguise. Fix the analyzer first, then look at boosting / function score. The hierarchy: analyzer > field boost > function score > rescore > synonyms.

7. Distributed Search Execution

An ES index is split into shards. Each shard is a self-contained Lucene index. A search query hits every shard, and the coordinator merges results.

Query Phase + Fetch Phase

Phase 1: Query

Coordinator sends query to all shards. Each shard runs BM25 locally and returns only doc IDs + scores (top-K per shard). Coordinator merges into global top-K.

Shard 0: [(doc_42, 3.2), (doc_17, 2.8)]
Shard 1: [(doc_99, 3.5), (doc_55, 2.1)]
Shard 2: [(doc_12, 2.9), (doc_78, 2.7)]
Coordinator merges -> [doc_99, doc_42, doc_12, ...]
->

Phase 2: Fetch

Coordinator sends the global top-K doc IDs to the relevant shards. Shards return full documents (_source). Coordinator assembles the final response.

Shard 1: fetch doc_99 -> full _source
Shard 0: fetch doc_42 -> full _source
Shard 2: fetch doc_12 -> full _source
Coordinator returns final results

Why Two Phases?

Bandwidth efficiency. If each shard returned full documents during the query phase, you'd transfer K * num_shards full documents to the coordinator, only to discard most of them. The two-phase approach transfers only IDs+scores first (tiny), then fetches only the final top-K documents (minimal).

Deep pagination trap: requesting page 1000 (from=10000, size=10) means each shard must score and return its local top-10010, and the coordinator merges 10010 * num_shards entries. This is why search_after with a sort tiebreaker (e.g. _shard_doc) exists -- cursor-based, O(1) per page.

IDF skew across shards: each shard computes IDF from its own local doc counts. With small or unevenly distributed shards, the same term can have different IDF on different shards, causing scoring inconsistency. Fix: dfs_query_then_fetch (adds a pre-phase to collect global term stats). Cost: one extra round-trip.
Takeaway: Search is always 2-phase (query + fetch). This is the reason deep pagination is expensive and why search_after exists.
  • Query phase: each shard returns IDs+scores. Coordinator merges.
  • Fetch phase: coordinator retrieves full docs for the global top-K only.
  • from + size pagination: O(from+size) per shard. Avoid deep pages.
  • search_after: cursor-based, O(size) per shard. Use this.
  • dfs_query_then_fetch: global IDF. Fixes scoring skew, costs one round-trip.
