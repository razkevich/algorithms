AWS reference architectures

Five canonical shapes, the service decision matrices behind each box. The senior tell isn't naming services -- it's picking the right one with the right tradeoff.

3-Tier Web Application

The canonical AWS web architecture: DNS resolution, CDN edge caching, L7 load balancing, auto-scaled compute, relational storage with read replicas, in-memory caching, and static asset storage. Takeaways
  • TLS terminates at ALB (or CloudFront) -- compute nodes handle plaintext HTTP internally, reducing CPU overhead and certificate management complexity.
  • Read replicas handle read scaling horizontally; the primary handles writes. Aurora can have up to 15 read replicas with sub-10ms replication lag.
  • ElastiCache (Redis) sits between app and DB: cache-aside pattern. Cache miss goes to DB, populates cache, returns. Cache hit skips DB entirely -- 10x latency improvement.
  • S3 + CloudFront for static assets (JS, CSS, images) offloads compute and provides edge-cached sub-50ms delivery globally.

Async Event Pipeline

Decouple producers from consumers with a durable queue or stream between them. The choice of SQS vs Kinesis vs EventBridge determines ordering, replay, and failure semantics. Toggle the messaging backbone to see how the flow and properties change.

SQS is a durable work queue: at-least-once delivery, no ordering guarantee (unless FIFO), messages deleted after processing. Best for decoupling microservices with independent consumers. Toggle to Kinesis or EventBridge to compare.
Takeaways
  • SQS: at-least-once, no ordering (standard) or exactly-once + FIFO (FIFO queues). DLQ after N failed retries. Best for work queues.
  • Kinesis: ordered within shard, 24h-365d retention, replayable. Checkpoint-based consumption -- stuck checkpoint blocks the shard. Best for streaming analytics.
  • EventBridge: rule-based routing to multiple targets (fanout). Content-based filtering. Best for event-driven architectures with many consumers.
  • The interview tell: "SQS for work queues, Kinesis for ordered streams, EventBridge for event routing" -- know which properties each guarantees.

Multi-Region Active-Active

Both regions serve traffic simultaneously. Route 53 latency-based routing directs users to the nearest region. DynamoDB Global Tables and Aurora Global Database handle cross-region data replication. Kill a region to watch failover.

Both us-east-1 and eu-west-1 serve reads and writes. Route 53 latency-based routing sends users to the closest region. DynamoDB Global Tables replicate writes with last-writer-wins conflict resolution (~1s RPO). Aurora Global Database has one writer region with global readers (~1s replication lag).
Takeaways
  • DynamoDB Global Tables: true active-active writes in all regions. Last-writer-wins conflict resolution. RPO ~1 second. Eventually consistent cross-region.
  • Aurora Global Database: one primary writer region, read replicas in other regions. Planned failover promotes a secondary to writer (~1 min). Unplanned failover RPO ~1s.
  • S3 Cross-Region Replication: async, eventually consistent. Good for static assets, backups, disaster recovery. Not for real-time sync.
  • The hard tradeoff: DynamoDB GT gives you multi-region writes but only eventual consistency. Aurora GDB gives you strong consistency but single-writer. Pick based on your consistency requirement.

Event-Driven Data Lake

Ingest events, land them in S3, transform with ETL, query with serverless SQL or load into a warehouse. Two paths: batch (Firehose + Glue) and real-time (DMS CDC + Lambda). Toggle between them to see how data flows differently.

Batch path: Kinesis Data Firehose buffers events and delivers them to S3 in micro-batches (1-15 min). Glue ETL transforms raw data into curated Parquet/ORC in S3. Athena queries directly on S3 -- serverless, pay-per-query. Good for analytics workloads where minutes of latency is acceptable.
Takeaways
  • Raw zone + curated zone in S3: raw is append-only event log (JSON/CSV), curated is transformed columnar format (Parquet/ORC) partitioned by date/entity for efficient queries.
  • Athena: serverless SQL on S3. No infrastructure. Pay per TB scanned. Partition pruning + columnar format = 90% cost reduction vs full scans.
  • Redshift: managed warehouse for complex joins, aggregations, dashboards. Use when Athena query complexity or concurrency exceeds serverless limits.
  • DMS CDC path: Change Data Capture from RDS streams row-level changes through Kinesis to Lambda for near-real-time analytics. Seconds of latency vs minutes for batch.

Takeaways
  • The senior tell is not naming the service -- it's articulating WHY that service over alternatives. "DynamoDB because we need single-digit-ms reads at 100k QPS with auto-scaling, and our access pattern is pure key-value lookups."
  • Transferable patterns matter: SQS is a work queue (same shape everywhere), Kinesis is a distributed log (same shape as Kafka), S3 is an object store. Name the pattern, then the AWS service.
  • Cost model drives architecture: Lambda is cheap at low QPS but expensive at sustained high QPS. EC2 Reserved/Spot is cheap at steady-state but complex to manage. Match cost model to traffic shape.
