Standalone mongod

A single mongod process. Writes go to memory (WiredTiger cache), then to the journal. Write concern controls when the server acknowledges: w:1 after memory write, j:true after journal sync to disk.

Standalone has no failover. The journal is the durability story. w:1 acks after the memory write; j:true acks after journal sync. MongoDB is multi-threaded -- a slow query does not block other operations (unlike Redis), but it still consumes resources.
Takeaways
  • Use a replica set even for dev -- w:1 standalone has the same latency, no HA loss.
  • j:true adds ~2-5ms latency (journal fsync) but guarantees durability through crashes.
  • MongoDB's WiredTiger engine is multi-threaded: concurrent reads and writes proceed in parallel. A full collection scan does not block other operations, but it pressures cache and I/O.

Replica Set with Elections

3-member replica set: 1 PRIMARY + 2 SECONDARIES. The primary accepts writes and records them in its oplog. Secondaries tail the oplog and apply operations. On primary failure, Raft-pv1 election promotes a new primary.

Replica set = Raft-pv1 election + oplog tail replication. The primary accepts writes, records them in the oplog, and secondaries asynchronously tail and apply. Heartbeats every 2 seconds detect failures.
Takeaways
  • Replica set = Raft-pv1 election + oplog tail replication.
  • w:majority + readConcern:majority = strong consistency, but slower.
  • Rollback can happen -- bound it with w:majority and avoid disastrously losing data.
  • A member with priority:0 or votes:0 can serve reads (analytics secondary) but never becomes primary.

Sharded Cluster

mongos routers at the top, config server replica set in the middle, shard replica sets at the bottom. Each shard owns a set of chunks. The balancer migrates chunks to keep shards even.

Shard key:
Sharded cluster: mongos routers cache the chunk-to-shard mapping from the config servers. Targeted queries include the shard key and route to one shard. Queries without the shard key broadcast to all shards (scatter-gather) -- avoid this in production.
Takeaways
  • Pick hashed shard key when writes are monotonic OR no natural range key.
  • Pick range shard key when locality matters (multi-tenant, time-bucketed).
  • Avoid scatter-gather -- always include the shard key in queries.
  • Compound shard keys give you range locality + better distribution.

Read Concerns + Causal Consistency

Read concerns describe the freshness guarantee of a read. Read preferences route the read to a node. Causal consistency sessions give you read-your-own-writes across secondaries.

Read concerns control what data a read operation returns relative to the cluster's replication state. local returns the node's latest data. majority returns only data confirmed by a majority. linearizable adds a round-trip to confirm the primary still holds the lease.
Takeaways
  • readConcern:majority + writeConcern:majority + causal sessions = the production-grade default.
  • linearizable is rarely needed -- usually causal is enough.
  • Read preferences route the read; read concerns describe the freshness guarantee.
  • Causal consistency is the practical answer between strong and eventual -- read-your-own-writes guarantee with low latency.
