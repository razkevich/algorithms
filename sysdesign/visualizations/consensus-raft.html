Raft consensus -- step by step

Election, log replication, network partitions, snapshots. The fundament behind etcd, ZooKeeper-like systems, Postgres Patroni. Step through the algorithm; build the intuition; survive the depth probe.

Leader Election

A Raft cluster of 5 nodes. Each node is a Follower, Candidate, or Leader. The leader sends periodic heartbeats (AppendEntries with no payload). If a follower's election timeout elapses without hearing from a leader, it starts a new election.

Step 0 / 0
All five nodes start as Followers in term 0. S1 is the current leader, sending periodic AppendEntries heartbeats to maintain authority.
Takeaways
  • Election term increments monotonically. Each peer votes once per term. Random timeouts prevent perpetual split votes. Quorum requires majority -- 3 of 5, not 2 of 5.
  • The leader is the only node that sends AppendEntries. Followers only respond. A candidate that fails to win majority waits for a new random timeout before trying again.
  • Split votes are resolved by randomized election timeouts (typically 150-300ms). The node whose timeout fires first wins the next term.

Log Replication

The leader receives client writes, appends them to its log, and replicates to followers via AppendEntries RPCs. An entry is committed once a majority (including the leader) has it. Committed entries are applied to the state machine.

Step 0 / 0
S1 is the leader in term 1. Its log has 3 committed entries. All followers are in sync. A client is about to send a write request.
Takeaways
  • Replication is per-entry leader-to-followers via AppendEntries. Commit = majority ack. Followers can lag; they catch up via standard replication, no special path.
  • The prevLogIndex / prevLogTerm consistency check ensures logs never diverge: a follower rejects if its log does not match the leader's at the previous entry.
  • Committed entries are never overwritten. Only uncommitted entries from stale leaders can be replaced.

Partition + Leader Change

A network partition splits the cluster. The majority partition elects a new leader and continues serving writes. The minority partition's stale leader cannot commit (no majority). On heal, the stale leader steps down and its uncommitted writes are overwritten.

Step 0 / 0
S1 is the leader in term 5. All five nodes are connected and in sync. We are about to introduce a network partition.
Takeaways
  • Network partition creates two views. Only the majority partition can commit. The minority's stale leader steps down on heal via term comparison. Uncommitted entries are overwritten -- this is by design, not a bug.
  • Clients talking to the minority partition will see their writes time out (no commit acknowledgment). Clients must retry against the new leader.
  • This is Raft's core safety guarantee: no committed entry is ever lost, even across partitions and leader changes.

Snapshot + Log Compaction

Without compaction, the Raft log grows without bound. Snapshots capture the state machine at a point in time, allowing log entries up to that point to be discarded. Far-behind followers receive the snapshot via InstallSnapshot RPC.

Step 0 / 0
A Raft node with a growing log. Each committed entry consumes memory. As the log grows, startup replay time increases and memory pressure mounts.
Takeaways
  • Without snapshots, log grows unbounded. Snapshot is a state machine-level operation; Raft just integrates it via InstallSnapshot.
  • Each node snapshots independently. The leader only sends InstallSnapshot to followers that are too far behind for normal AppendEntries (their next index points to a discarded entry).
  • After applying a snapshot, the follower discards its entire log up to the snapshot index and resumes normal AppendEntries from there.

Membership Change (Joint Consensus)

Changing cluster membership (adding or removing nodes) is dangerous: during the transition, two disjoint majorities could form. Raft solves this with joint consensus -- a transitional config where entries must be committed by a majority of both the old and new configurations.

Step 0 / 0
A 3-node cluster (S1, S2, S3) with S1 as leader. We want to expand to 5 nodes (adding S4, S5). A naive switch could create two disjoint majorities during the transition.
Takeaways
  • Naive membership change can cause split-brain (old and new configs both think they have majority). Joint consensus prevents it.
  • During joint consensus, every commit requires agreement from a majority of the OLD config AND a majority of the NEW config. This eliminates any window where two independent majorities can exist.
  • The transition is: C_old -> C_old,new (joint) -> C_new. Each step is a committed log entry. If the leader crashes mid-transition, the new leader continues from whichever config is in effect.
