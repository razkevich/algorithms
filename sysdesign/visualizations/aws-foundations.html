AWS foundations -- IAM, VPC, costs

Click through the IAM policy evaluator. Watch traffic route through public/private subnets. Memorize the bills that surprise you. The three categories that derail real AWS rounds.

1. IAM Identity Types + Policy Evaluation

Every AWS auth question is the policy evaluator running through these sources in order. The core tuple: Principal + Action + Resource + Condition.

Identity Types

IAM User
Long-term credentials (access key + secret)
Permanent identity with password/keys. Avoid for workloads -- use for break-glass admin only. Keys rotate manually, leak easily.
IAM Role
Short-term assumed credentials (STS)
Preferred for everything. EC2 instance profiles, Lambda execution roles, cross-account access. Credentials auto-rotate via STS (15 min -- 12 hr).
IAM Group
Collection of users
Attach policies to the group, not individual users. Groups cannot be nested. A user can be in up to 10 groups.
Service-Linked Role
AWS-managed, service-specific
Pre-defined by the AWS service (e.g., ElasticSearch, ECS). You can view but not edit the trust policy. AWS manages the permissions.
Federated Identity
External IdP (SAML / OIDC / Identity Center)
SSO via corporate directory (Active Directory, Okta). Maps external groups to IAM roles. IAM Identity Center (formerly SSO) is the modern path.

Policy Evaluation Order

Select a scenario, then click Evaluate to walk through each evaluation source. Default is implicit deny. Any explicit deny at any level is terminal. In same-account, identity-based + resource-based policies are OR (either can grant). Cross-account requires AND (both must allow).

Select a scenario above to see the evaluation setup.
1 Explicit Deny Check
Scan all applicable policies for an explicit Deny on this action+resource. Any explicit deny = DENY (terminal).
2 SCP (Service Control Policy)
Organization-level guardrail. SCPs restrict what member accounts can do. If SCP does not allow this action, DENY.
3 Resource-Based Policy
Policy attached to the resource (S3 bucket policy, SQS queue policy, KMS key policy). In same-account, a resource-based Allow is sufficient alone.
4 Identity-Based Policy
Policies attached to the IAM user/role/group performing the action. Inline policies and managed policies are both checked.
5 Permissions Boundary
A managed policy used as a cap on identity-based permissions. If set, the effective permission is the INTERSECTION of identity policy and boundary.
6 Session Policy
Optional policy passed during AssumeRole or GetFederationToken. Caps the session permissions to the INTERSECTION of the role policy and the session policy.
Takeaway
  • Default = implicit deny. Any explicit deny wins over any allow, at any level.
  • Same-account: identity-based + resource-based = OR (either can grant access).
  • Cross-account: both sides must allow = AND (the trusting account's resource policy AND the trusted account's identity policy).
  • Permissions boundaries and session policies are caps (intersection), not grants.

2. VPC Networking

A 2-AZ VPC with public and private subnets. Public subnets route to the Internet Gateway directly. Private subnets reach the internet only through a NAT Gateway in the public subnet. VPC endpoints bypass NAT entirely -- saving cost and latency.

VPC Architecture (2-AZ)

Click a button above to animate traffic flow through the VPC. Inbound: traffic enters through IGW, hits the ALB in the public subnet, and is forwarded to the app server in the private subnet. Outbound: private instances route through the NAT Gateway to reach the internet. VPC Endpoint: traffic to S3/DynamoDB stays on the AWS backbone, bypassing NAT entirely.

Security Groups vs NACLs

Property Security Group (SG) Network ACL (NACL)
Scope Per resource (ENI level) Per subnet
Statefulness Stateful -- return traffic auto-allowed Stateless -- must explicitly allow return traffic
Rules Allow only (implicit deny all) Allow + Deny, evaluated in number order
Default Deny all inbound, allow all outbound Allow all inbound + outbound
Interview tell Use for service-to-service rules ("ALB SG allows 443 from 0.0.0.0/0; App SG allows 8080 from ALB SG") Use as subnet-level deny list (block known bad IPs, compliance requirements)

Connectivity: VPC Peering vs Transit Gateway

Takeaway
  • Public subnet = route table has 0.0.0.0/0 -> IGW. Private subnet = route table has 0.0.0.0/0 -> NAT GW.
  • VPC endpoints for S3/DynamoDB (Gateway type, free) and other services (Interface type, ENI-based, costs per hour + per GB). Always use them to avoid NAT costs.
  • Security Groups are stateful (track connections); NACLs are stateless (need explicit inbound + outbound rules). SGs for service isolation, NACLs for subnet-level deny lists.
  • VPC Peering is 1:1 and non-transitive. Transit Gateway is hub-and-spoke and transitive. At 3+ VPCs, TGW wins on management overhead.

3. Cost Gotchas

AWS bills happen at the hops you did not model. These are the line items that surprise teams in their first real deployment. NAT Gateway + cross-AZ traffic are the #1 category.

$
NAT Gateway
$0.045/hr + $0.045/GB processed
The per-GB charge is the killer. Private subnets pulling container images, software updates, or large API responses through NAT rack up fast. A single NAT GW processing 10 TB/month = $450 in data charges alone, plus $32 hourly.
Mitigation: VPC Gateway Endpoints for S3/DynamoDB (free). Interface Endpoints for ECR, CloudWatch, STS. Pull container images through ECR endpoint.
$
Cross-AZ Traffic
$0.01/GB each way (in + out = $0.02/GB round-trip)
Every hop between AZs is billed. App server in AZ-1 calling a cache in AZ-2 = $0.02/GB for every request-response. Chatty microservices across AZs compound quickly.
Mitigation: co-locate chatty services in the same AZ. Use AZ-aware routing (ALB cross-zone load balancing can be disabled). Accept reduced availability for cost-sensitive workloads.
$
Cross-Region Traffic
$0.02/GB (varies by region pair)
Replicating data across regions for disaster recovery or multi-region deployments. DynamoDB Global Tables, S3 Cross-Region Replication, Aurora Global Database all incur this.
Mitigation: replicate only what is needed. Compress before transfer. Avoid cross-region in hot paths -- use CDN (CloudFront) for read-heavy global access.
$
Route 53 Queries
$0.40 per million queries (standard), $0.60 per million (latency/geo)
High-volume services with short DNS TTLs generate millions of queries. Each health check = $0.50/month (+ $1.00 for HTTPS + string matching).
Mitigation: set appropriate TTLs (60-300s for most services). Use caching resolvers. Consolidate health checks.
$
DynamoDB Hot Partition
Throttling + on-demand billing spikes from key skew
A single hot partition key can exhaust its share of provisioned capacity (or spike on-demand costs). On-demand mode has no throughput cap but bills per request -- a viral event on a skewed key = surprise bill.
Mitigation: design partition keys for uniform distribution. Use write sharding (append random suffix) for hot keys. Monitor ConsumedCapacity metrics.
$
S3 LIST + GET Requests
$0.005 per 1,000 LIST/GET requests
Listing huge prefixes with millions of objects = thousands of LIST calls. A data pipeline that lists a prefix before processing can cost more in LIST requests than in storage.
Mitigation: use S3 Inventory for bulk enumeration instead of LIST. Structure prefixes for bounded listing. Use S3 Event Notifications instead of polling.
$
CloudWatch Logs Ingestion
$0.50/GB ingested
Log cardinality explosion: a Lambda logging full request/response bodies at scale, or a Kubernetes cluster with verbose debug logging. 100 GB/day = $1,500/month in ingestion alone.
Mitigation: log only what you query. Use log levels in production (WARN+ERROR only). Sample verbose logs. Ship bulk logs to S3 directly, query with Athena.
$
EBS Snapshots
$0.05/GB-month (incremental but cumulative)
Each snapshot is incremental, but the total stored data grows over time. Without lifecycle policies, snapshots accumulate indefinitely. 50 snapshots of a 500 GB volume can store significant unique blocks.
Mitigation: Amazon Data Lifecycle Manager for automated snapshot retention. Tag snapshots. Delete orphaned snapshots from terminated instances.
$
Idle Resources
Varies -- but always more than $0
Stopped EC2 instances still bill for attached EBS volumes. Unattached Elastic IPs bill $0.005/hr. Idle load balancers bill ~$16/month minimum. Unused RDS instances bill full hourly rate. Dev/staging environments left running over weekends.
Mitigation: tag everything. Use AWS Cost Explorer anomaly detection. Schedule dev environments to stop nights/weekends. Audit unattached EBS volumes + EIPs monthly.
Takeaway
  • AWS bills happen at the hops you did not model. NAT GW + cross-AZ are the #1 surprise.
  • Use VPC endpoints. Gateway endpoints (S3, DynamoDB) are free. Interface endpoints cost but are cheaper than NAT for high-volume traffic.
  • Locality matters. Co-locate chatty services. Avoid cross-AZ in hot paths unless availability requires it.
  • Tagging + lifecycle policies are not optional -- they are cost controls.

4. Well-Architected Framework -- 6 Pillars

AWS asks about these in behavioral / architecture rounds. Know each pillar, its one-line ask, and one concrete tell.

Pillar What It Asks Interview Tell
Operational Excellence Run and monitor systems to deliver business value; continuously improve processes and procedures. IaC (CloudFormation/CDK/Terraform), runbooks, automated deployments, observability (CloudWatch dashboards + alarms), post-incident reviews.
Security Protect data, systems, and assets through risk assessment and mitigation. Least privilege IAM, encryption at rest (KMS) + in transit (TLS), VPC isolation, GuardDuty for threat detection, SCPs for org-wide guardrails.
Reliability Ensure a workload performs its intended function correctly and consistently. Multi-AZ deployments, auto-scaling, health checks, circuit breakers, chaos engineering, backup/restore tested regularly, defined RPO/RTO.
Performance Efficiency Use computing resources efficiently to meet system requirements and maintain efficiency as demand changes. Right-sizing instances (Compute Optimizer), caching (ElastiCache/CloudFront), read replicas, purpose-built databases, serverless for bursty workloads.
Cost Optimization Avoid unnecessary costs; understand spending and control fund allocation. Reserved Instances / Savings Plans for steady-state, Spot for fault-tolerant batch, right-sizing, S3 lifecycle policies, VPC endpoints to avoid NAT costs.
Sustainability Minimize environmental impact of running cloud workloads. Right-size to reduce waste, use managed services (higher utilization), Graviton instances (better perf/watt), S3 Intelligent-Tiering, region selection for carbon intensity.
Takeaway
  • In an interview, name the pillar by name, then give one concrete action. "From a Reliability perspective, I would deploy across 3 AZs with auto-scaling and define RPO < 1 hour, RTO < 15 minutes."
  • Security and Reliability are the two most commonly probed in system design rounds. Cost Optimization comes up in "how would you reduce the bill?" follow-ups.

5. Common Interview Probes

When they ask X, the answer should mention Y. These are the most common AWS-specific follow-up questions in system design rounds.

Probe Expected Response Pattern
"How would you handle 10x traffic?" ASG (Auto Scaling Groups) with target tracking policies + ALB to distribute. RDS read replicas for read-heavy. CloudFront for static/cacheable content. ElastiCache for hot data. DynamoDB auto-scaling or on-demand mode. Queue (SQS) to decouple and absorb spikes.
"Multi-region resilience?" Route 53 with health checks for failover routing. DynamoDB Global Tables (active-active, last-writer-wins) OR Aurora Global Database (one writer region, <1s replication). S3 Cross-Region Replication. Define RPO and RTO explicitly. Call out the trade-off: multi-region active-active is complex (conflict resolution, data consistency); active-passive is simpler but has non-zero RTO.
"How does S3 give you 11 9s durability?" Erasure coding across a minimum of 3 AZs within a region (default for S3 Standard). Data is split into fragments, parity fragments added, distributed across physically separate facilities. Can tolerate loss of 2 AZs simultaneously. 99.999999999% = you would lose one object out of 10 billion in 10,000 years.
"Why not Lambda for this?" Cold start latency (100ms-several seconds, language-dependent). 15-minute execution timeout. 10 GB memory cap. 250 MB deployment package (unzipped). 1000 default concurrent executions per region. Connection pooling is hard (no persistent connections between invocations). Good for: event-driven, bursty, short-lived. Bad for: long-running, latency-sensitive, connection-heavy.
"Why DynamoDB over RDS?" Access pattern fits single-table design (known query patterns at design time). No joins required. Need global scale (Global Tables). Need single-digit millisecond latency at any scale. Need auto-scaling with zero operational overhead. Bad for: ad-hoc queries, complex relationships, transactions across items (limited to 100 items / 4 MB), analytics workloads.
"How do you secure data at rest and in transit?" At rest: AWS KMS (managed keys or CMK), S3 SSE-S3/SSE-KMS, EBS encryption, RDS encryption. In transit: TLS everywhere (ALB terminates TLS, internal service mesh with mTLS or VPC-internal). Key rotation via KMS automatic rotation (annual for CMKs). Envelope encryption for large objects.
"How would you reduce the AWS bill by 30%?" Savings Plans / Reserved Instances for steady-state compute (up to 72% savings). Spot Instances for fault-tolerant batch/worker workloads. Right-size instances (AWS Compute Optimizer). S3 Intelligent-Tiering or Glacier for cold data. VPC endpoints to eliminate NAT data processing charges. Shut down non-production environments nights/weekends. Delete unattached EBS volumes, unused EIPs, idle load balancers.
Takeaway
  • Every probe has a "shape" -- name the service, state the trade-off, give a number. "Lambda cold starts are 100ms-seconds; for p99 < 50ms we need a persistent compute layer."
  • Always state RPO/RTO when discussing resilience. "RPO = 0 means synchronous replication; RPO = minutes means async."
  • Cost questions are architecture questions in disguise. "Reduce the bill" = "which architectural choices are wasteful?"
