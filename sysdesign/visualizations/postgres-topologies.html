Single Primary -- WAL and Durability

Postgres durability comes from the Write-Ahead Log (WAL). Every change is written to WAL before the data files. Crash recovery replays WAL forward from the last checkpoint. Multi-process architecture means queries never head-of-line-block writes.

Every write follows the same path: client sends SQL, backend process appends the change to WAL, WAL is fsynced to disk (durability guarantee), then acknowledgment returns to client. Data files are updated lazily at checkpoints.
Takeaways
  • WAL is the durability story -- replication is just shipping WAL. Crash recovery = replay WAL forward from last checkpoint.
  • synchronous_commit = off returns ack before fsync -- faster but risks losing the last few ms of commits on crash (not corruption, just loss).
  • Postgres is multi-process: a long-running SELECT (seq scan) consumes one backend but does not block writes on other backends. No head-of-line blocking like single-threaded Redis.

Streaming Replication -- Sync vs Async

Primary ships WAL to hot standbys over a persistent TCP connection. Each node tracks its position in the WAL stream via a Log Sequence Number (LSN). Replication slots guarantee the primary retains WAL until the standby consumes it.

Primary streams WAL entries to standbys in real time. Each standby replays the WAL to maintain an eventually-consistent copy. The LSN counter tracks how far each node has progressed through the WAL stream.
Takeaways
  • Synchronous = at least 1 standby ack required before commit returns, not all. The primary blocks the committing transaction, not the whole server.
  • Replication slot prevents WAL deletion but can fill primary disk if a standby is gone too long. Always monitor pg_replication_slots.
  • Hot standby = serves reads, but data is eventually consistent. A read might return stale data if the standby has not yet replayed the latest WAL.

Patroni HA -- Automated Failover with etcd DCS

Patroni runs as a sidecar on each Postgres node. It holds a leader lease in etcd (a distributed config store). When the leader lease expires, standbys race to claim it and promote themselves. Self-fencing on network partition prevents split-brain.

Patroni manages Postgres HA using a distributed consensus store (etcd). The primary's Patroni holds a leader lease with a TTL of ~30s, renewing it every ~10s. If renewal stops, standbys detect the expired lease and race to claim leadership.
Takeaways
  • Quorum is in etcd, not Postgres. Patroni delegates split-brain prevention to the DCS -- it does not implement its own consensus.
  • Self-fence on partition = the senior detail. If the primary is alive but partitioned from etcd, Patroni demotes it to read-only. This prevents zombie writes that would diverge from the new primary.
  • RPO/RTO trade depends on synchronous_commit and lease TTL. Sync replication = RPO 0 but higher write latency. Shorter TTL = faster failover (lower RTO) but more false positives.

Logical Replication -- Decoded Changes

Unlike streaming replication (which ships raw WAL bytes), logical replication decodes WAL into row-level changes (INSERT/UPDATE/DELETE tuples) and publishes them per-table. The subscriber applies changes independently -- it can have its own schema, indexes, even local writes.

The publisher decodes WAL entries into logical tuple changes and streams them through a publication. Only tables included in the publication are replicated. The subscriber applies changes via its own subscription -- it can lag, conflict, or fail independently.
Takeaways
  • Logical = ETL with WAL as the source. It decodes physical WAL into row-level changes that any consumer (even a different Postgres major version) can apply.
  • Use for: cross-version upgrades, multi-master patterns, selective replication to analytics databases. Don't use for HA -- physical streaming is the HA path.
  • Conflicts (same PK written on both sides) pause the subscription. Resolution is manual or requires custom conflict handlers. This is why logical replication is not transparent multi-master.

Sharded (Citus) -- Distributed Postgres

Citus extends Postgres with a coordinator that routes queries to worker nodes. Distributed tables are hash-sharded by a distribution column (typically tenant_id). Co-located joins are local; cross-shard joins require network shuffles.

Citus distributes tables across workers by hashing the distribution column. The coordinator rewrites SQL into per-shard fragments, pushes them to workers, and aggregates results. Co-located tables (same distribution column) can join locally on each worker.
Takeaways
  • The right distribution column makes 90% of queries co-located. For multi-tenant SaaS, tenant_id is almost always the answer.
  • Reference tables are the escape hatch for joins on small dimension tables -- they are replicated to every worker so any shard can join against them locally.
  • Citus is row-store sharded Postgres, not a separate engine. Standard Postgres features (transactions, indexes, extensions) work per-shard. Global UNIQUE constraints require the distribution column in the key.
