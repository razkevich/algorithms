Caching patterns -- flow animations

Five patterns side-by-side, controllable. Trigger reads/writes, kill the cache or DB, watch what each pattern actually does. Then transfer to CDNs, outboxes, service workers.

Cache-aside (lazy load)

App talks to both. Cache misses fall through to DB; app writes both.

Most common pattern. App is responsible for both lookups. The cache does not know about the DB. Race window between DB write and cache invalidate is the canonical bug -- order DB-write first, invalidate second.

Tradeoffs

Read latency:
Cache hit in microseconds; miss = DB round-trip + cache write
Write latency:
DB write + cache invalidate (two round-trips)
Consistency:
Eventually consistent; race-prone unless careful invalidation order
Durability if cache dies:
Strong -- cache rebuilt from DB on next miss
Common bug:
Stale cache after concurrent write/read interleaves wrong invalidation order

Read-through

App talks only to cache. Cache fetches from DB on miss.

The cache is the data interface. App is decoupled from the DB at read time. Common in CDNs and ORMs (e.g., Hibernate L2 cache, EhCache). Read-through alone is incomplete -- pair with write-through or cache-aside writes.

Tradeoffs

Read latency:
Cache hit in microseconds; miss = DB round-trip + cache write (same as cache-aside)
Write latency:
Depends on paired write strategy
Consistency:
Depends on the paired write strategy
Durability if cache dies:
Strong -- data lives in DB; cache rebuilds on miss
Common bug:
Forgetting to handle writes -- read-through alone causes silent data loss on write

Write-through

Writes go to cache, cache writes through to DB synchronously.

Strong consistency at the cost of write latency. Cache and DB are always in sync -- no stale-cache bug. Pay for it on every write. Use when reads heavily dominate writes and consistency matters.

Tradeoffs

Read latency:
Cache hit in microseconds; miss fills from DB like read-through
Write latency:
Cache write + synchronous DB write (slower than cache-aside, but no race)
Consistency:
Strong -- cache always reflects DB state
Durability if cache dies:
Strong -- every write already persisted to DB
Common bug:
Write throughput becomes DB throughput -- no buffering benefit

Write-back (write-behind)

Writes go to cache, cache flushes to DB asynchronously.

Fastest writes (cache-only on the hot path). DB writes are batched async -- efficient but lossy if the cache dies before flush. Used in Twitter timeline writes, log buffers, and OS page cache. The "outbox pattern" is the durable cousin: dirty buffer is on the durable side instead of in volatile cache.

Tradeoffs

Read latency:
Cache hit in microseconds
Write latency:
Microseconds (cache only -- DB write deferred)
Consistency:
Eventually consistent; DB lags by flush interval
Durability if cache dies:
Weak -- pre-flush writes are permanently lost
Common bug:
Dirty buffer overflow if writes outpace flush rate; mitigated by back-pressure

Refresh-ahead

Cache pre-emptively reloads hot keys before TTL expiry.

Optimization for predictable hot-key access. Eliminates the "cold miss after TTL expiry" latency spike that hits everyone simultaneously (cache stampede). Predicts access; if prediction is wrong, you wasted DB calls. Used by browser cache headers (stale-while-revalidate), CDN tier-2 caches.

Tradeoffs

Read latency:
Microseconds on hit -- always, by design no miss for hot keys
Write latency:
Depends on paired write strategy
Consistency:
Eventually consistent; refresh interval bounds staleness
Durability if cache dies:
Strong -- data lives in DB
Common bug:
Wrong refresh prediction wastes DB load; missed refresh causes stampede

Where these patterns appear in other systems

  • CDN edge caching -- read-through (origin pulls + caches; cache is the API surface)
  • CDN with stale-while-revalidate (RFC 5861) -- refresh-ahead (serve stale, refresh in background)
  • Service worker / PWA offline cache -- cache-aside (app code decides when to use cache vs network)
  • Outbox pattern (transactional outbox) -- write-back, but the dirty buffer is in the durable DB, so the failure mode is fixed
  • Kafka producer with acks=0 -- write-back (fire-and-forget, lossy on broker death)
  • Kafka producer with acks=all -- write-through (strong durability at write-latency cost)
  • OS page cache -- write-back (fsync is the manual flush)
  • Browser HTTP cache (Cache-Control: max-age + must-revalidate) -- refresh-ahead (revalidation before stale)
  • Hibernate / JPA L2 cache -- read-through (cache is the access layer)
  • Memcached + your app code -- cache-aside (Memcached does not know about your DB)
  • Redis Object Cache for WordPress -- cache-aside
The transfer test. When an interviewer asks "how would you cache X?", picking a pattern is half the answer. The other half is naming the failure mode you are choosing -- "I am picking write-back here because writes dominate and I can tolerate up to 5 seconds of write loss on cache death; if not, write-through." Senior signal: explicit failure-mode tradeoff, not just "use Redis."
