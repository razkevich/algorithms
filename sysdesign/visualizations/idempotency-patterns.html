Idempotency patterns

Idempotency keys, retry semantics, side-effect atomicity, the Stripe-style API contract. The pattern that separates "no double charges" from "we apologize for the inconvenience."

1. HTTP Idempotency by Method

The HTTP spec defines idempotency per method. An operation is idempotent if performing it N times produces the same server-side state as performing it once. Safe means no side effects at all (read-only).

Method Idempotent? Safe? Why
GET YES YES Read-only. No state change regardless of repetition.
HEAD YES YES Same as GET, headers only.
PUT YES NO Replace entire resource. Same body = same state every time.
DELETE YES NO Delete once or delete again: resource is gone either way. (200/204 or 404 -- your API contract.)
POST NO NO Each call creates a new resource. Repeated POST = duplicates.
PATCH DEPENDS NO {"name":"Alice"} is idempotent. {"balance": "+100"} is not. Depends on whether the operation is absolute or relative.

But in real APIs, even POSTs need to be idempotent under retry. A network blip between "server processed" and "client received 200" means the client retries -- and creates a duplicate charge, a duplicate signup, a duplicate order. That is where idempotency keys come in.

Takeaway. RFC says POST is not idempotent; reality says clients retry. Idempotency keys reconcile the two.

2. Idempotency Keys (Stripe-style)

The pattern

Client generates a unique key per logical operation (UUID v4, typically). Sends it in an Idempotency-Key header. Server checks if it has seen the key before. If yes: return the stored response (no re-processing). If no: process normally, then store (key, response).

3. Where Idempotency Goes Wrong

The pattern is simple. The bugs are not. Each failure mode below has been seen in production.

Bug 1: Side effect before key check

Server processes the charge, THEN stores the idempotency key. Crash between the two? Key never stored. Client retries. Card charged twice.

Fix: store key FIRST, atomically with side effect. Or use the idempotency key as PK in the destination table -- INSERT IGNORE on duplicate.

Bug 2: Key reused with different body

Client retries after a long gap. Same key, but the request body changed (different amount, different product). Server returns the cached response for the original request -- wrong result, silent corruption.

Fix: store request_hash = sha256(body) alongside key. On match-key-but-mismatch-hash, return 422 error.

Bug 3: Multi-resource ops with partial idempotency

Payment + email + accounting log. Payment is idempotent (key-based). Email and accounting are fire-and-forget. Retry = one charge, two emails, two ledger entries.

Fix: outbox pattern + downstream idempotency on each consumer. Every service in the chain must handle dedup independently.

Bug 4: TTL too short

Idempotency key stored with 5-minute TTL. Client retries after 10 minutes (mobile app in background, slow user). Key expired, charge re-processed.

Fix: align TTL with realistic retry windows. 24 hours minimum for payment APIs. Stripe uses 24h.

Bug 5: TTL too long / no cleanup

Keys stored forever (or 90-day TTL on high-throughput endpoint). Millions of expired keys accumulate. DB bloat, slow lookups, storage cost.

Fix: TTL that matches retention need (24h-7d). Background cleanup job for DB-backed stores. Redis TTL handles this natively.

Takeaway. The bug is always "state changed before idempotency was guaranteed." Make the idempotency atomic with the side effect.

4. Retry Semantics -- At-Most-Once / At-Least-Once / Exactly-Once

Three delivery guarantees. Every distributed system picks one as its default. The right answer in interviews is almost always "at-least-once + idempotent consumer = practical exactly-once."

Takeaway. Distributed systems are at-least-once by default. Make consumers idempotent; you have got effective exactly-once.

5. Idempotent Operations -- Design Tactics

Six tactics to make naturally non-idempotent operations idempotent. Each shows the same operation executed twice, producing the same final state.

Tactic 1: Use natural idempotent ops where possible

Prefer SET over INCR, PUT over POST, upsert over insert. The operation itself guarantees same-state-on-repeat.

Tactic 2: Embed dedup ID in the request

Include a request_id in every message payload. Consumer keeps a recent-IDs set (Redis SET or DB table). On duplicate ID, skip processing.

Tactic 3: Append-only storage with dedup keys

Insert event with a unique key (event_id). On retry, INSERT fails due to unique constraint. State derived via aggregation over events -- duplicates never enter.

Tactic 4: CAS (compare-and-swap) for state transitions

Conditional update: UPDATE wallet SET balance = balance - 100 WHERE user_id = X AND last_op_id != 'op-42'. If same op retries, the WHERE clause filters it out. Zero rows affected = safe no-op.

Tactic 5: Inbox table on consumer side

Consumer maintains an "inbox" table with event_id as unique key. Before processing, insert the event_id. If it already exists (unique constraint violation), skip. Same pattern as tactic 3 but on the consumer rather than the event store.

Tactic 6: Idempotent aggregates

Design state so duplicate events do not change the result. Use MAX, SET, or boolean flags instead of counters or appends. Example: last_seen = MAX(last_seen, event_ts) -- applying the same event twice does not change state.

Tactic selection guide

Tactic Best for Requires
Natural idempotent ops Any API where you control the contract Design discipline -- prefer PUT/SET/upsert from the start
Dedup ID in request Queue consumers, webhook receivers Recent-ID store (Redis SET or DB table)
Append-only + unique key Event sourcing, audit logs, ledgers Unique constraint on event ID column
CAS / conditional update State machines, balance ops, inventory Versioned rows or operation-tracking column
Inbox table Cross-service event consumers Per-consumer dedup table with unique constraint
Idempotent aggregates Analytics, counters, feature flags State expressed as MAX/SET/UNION (not SUM/APPEND)
Takeaway. Six tactics, one principle: make the final state a function of the input, not a function of how many times you applied it. SET over INCR. Upsert over insert. CAS over blind update.

6. Stripe API Design Example

Stripe's Idempotency-Key header is the de-facto industry standard. AWS, GCP, Square, and Shopify all use the same model. Learn Stripe's contract and you can cite it verbatim in interviews.

The contract

Header Idempotency-Key: <client-generated UUID>
Applies to All POST requests. GET/DELETE are already idempotent by definition.
Key TTL 24 hours. After expiry, same key is treated as new.
Same key + same body Return stored (status_code, headers, body) from first execution. No re-processing.
Same key + different body 400 Bad Request -- "Keys for idempotent requests can only be used with the same parameters they were first used with."
Concurrent same key 409 Conflict -- second request returns immediately while first is still processing.
Key generation Client responsibility. UUID v4 recommended. Stripe does not generate keys for you.

Response cache structure

{
  "idempotency_key": "abc-123-def-456",
  "request_path": "/v1/charges",
  "request_params_hash": "sha256:e3b0c44...",
  "status_code": 200,
  "response_headers": {"content-type": "application/json"},
  "response_body": "{\"id\":\"ch_1abc\",\"amount\":2000,...}",
  "created_at": "2026-05-09T10:30:00Z",
  "expires_at": "2026-05-10T10:30:00Z"
}

Same model used by: AWS SDK (ClientToken parameter), GCP (requestId), Square (Idempotency-Key), Shopify (Idempotency-Key).

Takeaway. Stripe's Idempotency-Key header is the de-facto standard. Adopt the pattern verbatim -- clients already know it.

7. Comparison and Summary

Dimension Redis + TTL Postgres unique index DynamoDB conditional put
Durability Volatile. Cache eviction or restart = key lost = potential re-processing. Durable. Survives restarts. Can be in same txn as the work. Durable. Replicated across AZs.
Speed Sub-ms lookup. Fastest option. 1-5ms (indexed lookup). Fine for most workloads. Single-digit ms. Fast, predictable.
TTL Native. SET key val EX 86400 No native TTL. Requires cleanup job or pg_cron. Native via TTL attribute. DynamoDB auto-deletes expired items.
Typical TTL 24 hours to 7 days. Align with realistic client retry windows.
Atomicity Separate from the side effect (unless side effect is also in Redis). Two-phase risk. Can be in the same transaction as the side effect. Gold standard for atomicity. Conditional put is atomic. Side effect must be in same DDB table or use DDB transactions.
Concurrent retry SET key val NX (SETNX). Second caller sees key exists, knows first is in-progress. Row-level lock. Second caller blocks until first commits. Conditional put fails on second caller. Return 409.
Cross-service Each service handles its own idempotency independently. Use outbox pattern (producer) + inbox table (consumer) for cascade.
Best for High-throughput APIs where occasional re-processing on eviction is tolerable. Payment systems, financial transactions -- where atomicity with side effects is critical. Serverless / AWS-native architectures. Lambda + DDB is a natural fit.
The senior tell. "I would add an Idempotency-Key header per logical request, store key-to-response in Redis with 24h TTL, and make the side effect atomic with the key store via DB unique index in the same transaction. For cross-service, each downstream consumer maintains its own inbox table with the event ID as unique constraint."

That is a one-paragraph senior answer. It covers the mechanism (idempotency key), the storage (Redis + DB), the atomicity guarantee (same transaction), and the cross-service story (inbox pattern). Interviewers hear all four and move on.
Key concepts for the interview.
  • Idempotency key = client-supplied UUID per logical operation. Server stores (key, request_hash, response) and returns cached response on duplicate.
  • Atomicity = the idempotency check must be in the same transaction as the side effect. Otherwise: crash between = double-processing.
  • At-least-once + idempotent consumer = practical exactly-once. This is the answer for every "how do you guarantee no duplicates in a distributed system?" question.
  • Cross-service = outbox pattern on producer, inbox table on each consumer. Each service is independently idempotent.
  • Stripe contract = Idempotency-Key header, 24h TTL, same-key-different-body returns 400, concurrent same-key returns 409.
