API security -- beyond auth

Rate limiting, quotas, RBAC vs ABAC vs ReBAC, secrets, mTLS, the OWASP API Top 10. The defenses you layer between the user and the database.

1. Rate Limiting Algorithms

Same incoming traffic: 200 requests in 1.5 seconds against a 100 req/sec budget. Each algorithm decides differently which requests pass and which get 429 Too Many Requests.

Fixed Window

Waiting...

Count reqs in 1-second buckets. Reset on boundary. Burst vulnerability: up to 2x budget at bucket edge.

Sliding Log

Waiting...

Store timestamp of every request in last 1s window. O(N) memory. Precise but expensive at scale.

Sliding Window Counter

Waiting...

Weighted average of current + previous fixed window count. Cheap approximation, smooth enforcement.

Token Bucket

Waiting...

Bucket holds N tokens, refills at R/sec. Each request takes 1 token. Allows controlled bursts up to bucket capacity.

Leaky Bucket

Waiting...

Requests enter a queue (bucket) that drains at a fixed rate. If queue is full, request is rejected. Smooths bursts to a steady output rate.

2. Quotas vs Rate Limits

Two concepts often conflated. Rate limits protect throughput; quotas cap total consumption. They trigger at different times, for different reasons, and need different alerts.

Rate Limit: 100 req/min

Resets every minute. Blocks bursts; recovers quickly.

Resets at midnight. Blocks at month-end; no quick recovery.

Takeaway. Rate = throughput floor. Quota = absolute cap. Both exist; communicate them separately. Rate limit recovery: wait 1 minute. Quota recovery: wait until billing cycle resets (or buy more).

3. AuthZ Models -- RBAC vs ABAC vs ReBAC

Authentication asks "who are you?" Authorization asks "are you allowed to do this?" Three models, each suited to different relationship complexity.

Role-Based Access Control

Assign Roles to users. Roles contain Permissions. Decision: does the user's role include the required permission?

Pros: Simple mental model. Fast lookup (user -> role -> permission set). Scales well for small, stable role sets.
Cons: Role explosion at scale. "Editor of category X for tenant Y" requires combinatorial roles. No environmental context (time, IP, resource attributes).

Attribute-Based Access Control

Decision based on attributes of the subject, action, resource, and context. Policies are boolean expressions evaluated by a Policy Decision Point (PDP).

Pros: Extremely expressive. One policy handles multi-tenant, time-based, classification-based access without role explosion. Dynamic context (IP, time) supported natively.
Cons: Harder to audit ("who can access X?" requires evaluating all policies). More expensive to evaluate. Policy language learning curve (OPA/Rego, Cedar).

Relationship-Based Access Control (Zanzibar)

Authorization is a graph traversal: "Does a path exist from this user to this resource with the required relation?" Google Zanzibar model, used by Google Drive, Notion, Auth0 FGA, OpenFGA, SpiceDB.

Pros: Naturally models hierarchical sharing (folders, teams, orgs). Adding a team member instantly grants access to everything the team can reach. Scales to billions of relationships (Google Zanzibar serves 10M+ checks/sec).
Cons: Graph traversal cost -- need indexing/caching for performance. Harder to understand "why was access granted?" (path can be deep). Requires a dedicated authz service (OpenFGA, SpiceDB, Authzed).
Takeaway. RBAC for simple cases (small, stable role set). ABAC for expressive, context-aware policies (multi-tenant, time-gated). ReBAC for hierarchical sharing models (Drive, Notion, any "team > folder > document" hierarchy). Pick by relationship complexity, not by trend.

4. Secrets Management

The gap between "we have authentication" and "our secrets are actually secure" is where breaches happen. Anti-patterns on the left, fixes on the right.

Anti-pattern: Env vars in code

Visible in ps aux, leaks to logs and crash dumps, no rotation, no audit trail.

Fix: External secrets store

Load from Vault / AWS Secrets Manager at startup. App never sees raw secret in env; fetched via API with short-lived lease.

Anti-pattern: Hardcoded secrets

const API_KEY = "sk-abc123..." in source code. Discovered by any engineer with repo access.

Fix: Placeholder + injection at deploy

CI/CD pipeline injects from secrets manager. Source code contains only ${API_KEY} references. Secret never exists in the codebase.

Anti-pattern: Secrets in Git history

Even if deleted in HEAD, recoverable from Git history forever. Catastrophic for API keys and DB credentials.

Fix: Pre-commit hooks + immediate rotation

Use gitleaks or trufflehog in pre-commit. If caught post-push: rotate the secret immediately (it is compromised), then scrub history.

Anti-pattern: One static API key forever

Never rotated. If leaked, attacker has permanent access. No way to detect compromise via key age.

Fix: Short-lived credentials + auto-rotation

AWS STS temporary tokens (15 min - 12 hr), GCP workload identity, Vault dynamic secrets with TTL. Rotate static keys every 90 days max.

Takeaway. Never commit secrets. Prefer short-lived credentials over static keys. Use a secrets manager + automation around rotation. The secure default is: app requests credential at startup, gets a lease, lease expires, app re-fetches.

5. mTLS -- Service-to-Service Auth

Regular TLS: the client verifies the server. Mutual TLS: both sides verify each other. The service-to-service identity story in microservices.

Click Animate Handshake to step through the mTLS exchange. Both services present certificates signed by the same organizational CA. Neither side trusts the other until the certificate chain validates.

SPIFFE / SPIRE

SPIFFE (Secure Production Identity Framework For Everyone) defines a standard for workload identity: each service gets a spiffe://trust-domain/workload-id URI embedded in its X.509 certificate. SPIRE is the reference implementation that issues and rotates these identities automatically.

Pros: No shared secrets between services. Identity baked into transport layer. Rotation via short cert lifetime (hours, not months). Compromise of one service does not leak another's credentials.
Cons: Certificate distribution and rotation is operationally complex without automation. PKI infrastructure must be highly available. Debugging cert issues is harder than debugging API keys.
Takeaway. mTLS = the service-to-service identity story. Service mesh (Istio, Linkerd) makes it operationally tractable by automating cert issuance, rotation, and verification in the sidecar proxy. The app code never touches certificates.

6. Common API Attacks -- OWASP API Top 10 (2023)

The ten most critical API security risks, ranked by prevalence and impact. BOLA/IDOR is #1 for a reason.

API1

Broken Object Level Authorization (BOLA / IDOR)

GET /users/123/profile -- does the handler verify user 123 is the requester? Often missed on internal endpoints.
Fix
Check object ownership in every handler. Middleware cannot do this -- it requires business logic context.
API2

Broken Authentication

Weak passwords, missing MFA, predictable tokens, session fixation. The classic auth bypass vector.
Fix
Standard auth library (never roll your own). Password hash with bcrypt/argon2. MFA for sensitive operations. Short-lived JWTs.
API3

Broken Object Property Level Authorization

API returns full object including ssn, salary, internal_notes. Client filters, but attacker reads raw response.
Fix
Explicit allow-list of fields per endpoint per role. Never serialize the full ORM object.
API4

Unrestricted Resource Consumption

No rate limit or query bounds. Attacker sends expensive query (SELECT * JOIN ... JOIN ...), consumes all DB connections.
Fix
Rate limit + quota. Query complexity bounds (GraphQL depth limit). Pagination enforced server-side.
API5

Broken Function Level Authorization

POST /admin/delete-user accessible to any authenticated user. Admin endpoints not gated by role.
Fix
Middleware enforces role per route group. Deny by default; explicitly grant admin routes.
API6

Unrestricted Access to Sensitive Business Flows

Automated abuse of business features: mass account creation, coupon harvesting, ticket scalping via API.
Fix
CAPTCHA, device fingerprinting, behavioral analysis. Rate limit by business action, not just HTTP request.
API7

Server-Side Request Forgery (SSRF)

Server fetches user-supplied URL. Attacker uses http://169.254.169.254/ to hit cloud metadata (IMDS) and steal IAM credentials.
Fix
URL allow-list. Block private IP ranges. IMDS v2 (requires token). Egress firewall rules.
API8

Security Misconfiguration

Default credentials, debug mode in prod, CORS *, verbose error messages exposing stack traces.
Fix
Automated config scanning. Secure defaults. Different config per environment. No debug endpoints in prod.
API9

Improper Inventory Management

Shadow APIs, unversioned endpoints, deprecated endpoints still running. Attacker finds old /v1/users without auth.
Fix
API gateway as the only ingress. Deprecated endpoints removed (not just docs). API catalog enforced.
API10

Unsafe Consumption of APIs

Trusting third-party API responses without validation. Malicious upstream injects data that your service blindly processes.
Fix
Validate all external input. Schema validation on third-party responses. Timeout and circuit break on external calls.

IDOR Attack Demo

The #1 API vulnerability, demonstrated. Alice (user 42) requests Bob's profile (user 123).

Vulnerable Endpoint

// No ownership check!
app.get('/users/:id/profile', auth, (req, res) => {
  const user = db.findById(req.params.id);
  res.json(user);  // serves ANY user's data
});
Alice (user 42) logs in, gets valid JWT
Alice sends GET /users/123/profile
Server checks: valid JWT? Yes
Server returns Bob's profile to Alice
Result: 200 OK -- data leaked

Fixed Endpoint

// Ownership check!
app.get('/users/:id/profile', auth, (req, res) => {
  if (req.params.id !== req.user.id)
    return res.status(403).json({error: 'forbidden'});
  const user = db.findById(req.params.id);
  res.json(user);
});
Alice (user 42) logs in, gets valid JWT
Alice sends GET /users/123/profile
Server checks: valid JWT? Yes
Server checks: req.user.id (42) === params.id (123)?
Result: 403 Forbidden -- access denied
Click Run IDOR Demo to see both flows side by side. The vulnerable endpoint trusts the JWT for authentication but never checks authorization -- whether user 42 should see user 123's data.
Takeaway. BOLA / IDOR is the #1 API vulnerability. Authentication (who are you?) is not authorization (are you allowed?). Every handler that accesses a resource by ID must check: "does the authenticated user own (or have permission for) this object?"

7. Defense-in-Depth Checklist

The senior interview answer to "is this API secure?" is never a single control. It is layers. Each layer assumes the previous one might fail.

Edge
WAF (rule-based + ML anomaly detection). Blocks SQLi, XSS, known attack signatures before they reach your code. Example: AWS WAF, Cloudflare WAF.
Gateway
Rate limit + quota enforcement + authentication (JWT validation, API key check). Central policy point. Example: Kong, AWS API Gateway, Envoy.
Service
Input validation (schema, types, bounds). Authorization check per object (BOLA prevention). Business logic abuse detection. This is where IDOR gets caught -- or missed.
Network
mTLS between services. Network policies (only service A can call service B). Private subnets for data stores. No public-internet path to the database.
Data
Encryption at rest (AES-256) + in transit (TLS 1.3). Secrets in Vault with TTL. Column-level encryption for PII. Key rotation automated.
Audit
Log all auth decisions (allow and deny). Immutable audit trail. Alert on anomalies (spike in 403s, unusual access patterns, off-hours admin activity). SIEM integration.
The senior tell. When asked "is this API secure?", answer in layers. WAF at the edge, rate limiting at the gateway, authorization in the service, mTLS on the network, encryption on the data, audit on everything. Naming each layer signals you have built real systems, not just read OWASP. A single missing layer is a finding; naming all six is the signal.
