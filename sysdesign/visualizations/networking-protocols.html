TCP 3-Way Handshake + Teardown

Every TCP connection begins with a 3-way handshake (1 RTT) and ends with a 4-way teardown. The client who initiates close enters TIME_WAIT for 2 x MSL (typically 60s) to handle straggler segments.

Takeaways
  • 3-way handshake = 1 RTT. Client can send data on the third segment (ACK), but server's first response needs another RTT to arrive.
  • TIME_WAIT (2 x MSL ~60s) = correctness: prevents stale segments from a previous connection arriving on a reused port. On connection-heavy clients, this exhausts ephemeral ports. Fix: SO_REUSEADDR, tcp_tw_reuse.
  • SYN flood: attacker sends SYNs without completing handshake, exhausting server's half-open connection table. SYN cookies: server encodes state in the ISN instead of allocating it -- stateless until ACK arrives.
  • Congestion control: slow start (exponential cwnd growth) then congestion avoidance (linear). On loss: multiplicative decrease (halve cwnd). CUBIC (Linux default) uses a cubic function for recovery; BBR models bandwidth and RTT directly.

TLS Handshake: 1.2 vs 1.3

TLS 1.2 needs 2 RTTs before encrypted data flows. TLS 1.3 collapses that to 1 RTT by sending key share in ClientHello, and enables 0-RTT resumption for returning clients (with replay caveats).

Takeaways
  • TLS 1.3 = 1-RTT handshake (vs 2-RTT for 1.2). Client sends key share in ClientHello, guessing the server's preferred curve.
  • 0-RTT resumption (TLS 1.3): subsequent connections use a PSK from the previous session; client sends application data with the first packet. Caveat: 0-RTT data is replayable -- only safe for idempotent requests (GET, not POST with side effects).
  • Forward secrecy is mandatory in TLS 1.3 (no RSA key exchange). Every session gets ephemeral keys; compromising the server's long-term key does not decrypt past traffic.
  • The senior answer to "how to speed up TLS" is "use 1.3" -- then mention 0-RTT for returning clients, session tickets for distributed servers, and OCSP stapling to avoid certificate revocation round trips.

HTTP/1.1: Keep-Alive and Head-of-Line Blocking

HTTP/1.1 defaults to keep-alive (reuse the TCP connection), but responses must return in request order. Pipelining sends multiple requests without waiting, yet a slow response blocks everything behind it.

HTTP/1.0 opened a new TCP connection per request -- expensive (handshake per request). HTTP/1.1 defaults to keep-alive: reuse the same TCP connection for multiple requests. Select a mode above to see the differences.
Takeaways
  • Keep-alive = the HTTP/1.1 default. Eliminates repeated TCP+TLS handshakes on the same connection.
  • Pipelining sends requests without waiting for responses, but responses MUST return in order. A slow response (e.g., server-side DB query on resource B) blocks faster responses behind it -- this is HTTP-level head-of-line blocking.
  • Browsers work around the single-connection bottleneck by opening up to 6 TCP connections per origin. Domain sharding (serving assets from cdn1.example.com, cdn2.example.com) multiplies this, at the cost of extra DNS lookups and TLS handshakes.
  • HTTP/2 solves HTTP-level HOL with multiplexed streams on a single connection.

HTTP/2: Multiplexed Streams on One Connection

HTTP/2 uses a single TCP connection with multiplexed binary frames. Each request/response pair is a stream with its own stream ID. Frames from different streams interleave freely -- no HTTP-level HOL. But TCP-level HOL remains: a lost packet stalls all streams.

HTTP/2 frames (HEADERS, DATA, SETTINGS, PING) are binary and carry a stream ID. Multiple streams share one TCP connection, with frames interleaved. No HTTP-level HOL -- but TCP's ordered byte stream means a lost packet blocks ALL streams until retransmitted.
Takeaways
  • H/2 = binary framing + multiplexing + HPACK header compression. One TCP connection carries many concurrent streams.
  • HPACK uses a static table (61 common headers) + dynamic table (connection-specific). Repeat headers compress to 1-2 bytes.
  • Server push (PUSH_PROMISE) was rarely used and is deprecated in most browsers. Do not mention it as a benefit in interviews.
  • TCP-level HOL: TCP sees one ordered byte stream. If a packet carrying stream A's data is lost, TCP withholds ALL subsequent data (including stream B's and C's) until retransmission completes. This is HTTP/2's residual problem -- QUIC fixes it.

HTTP/3 over QUIC

QUIC runs over UDP, bakes in TLS 1.3, and provides per-stream reliability. A lost packet on stream A does not block stream B. Connection migration survives IP changes (mobile network handoff).

QUIC combines transport handshake + TLS 1.3 handshake into a single 1-RTT exchange. Connection IDs (not socket 4-tuples) identify connections, enabling migration across network changes.
Takeaways
  • QUIC's three killer features: (1) per-stream HOL avoidance, (2) connection migration via connection IDs, (3) 1-RTT handshake (0-RTT on resumption).
  • Per-stream HOL: QUIC implements reliability per-stream, not per-connection. Losing a packet on stream A only blocks stream A; streams B and C continue unimpeded. This is the fundamental improvement over HTTP/2-over-TCP.
  • Connection migration: QUIC identifies connections by a connection ID, not by (src IP, src port, dst IP, dst port). When a mobile device switches from Wi-Fi to cellular, the IP changes but the connection ID stays -- no re-handshake needed.
  • 0-RTT: returning clients send application data in the first packet using a PSK. Same replay caveat as TLS 1.3 0-RTT: only safe for idempotent operations.

gRPC: HTTP/2 + Protobuf + Streaming

gRPC builds on HTTP/2 for transport and Protocol Buffers for serialization. Four method types cover every service-to-service communication pattern. Browsers cannot speak native gRPC (no HTTP/2 trailer support); use gRPC-Web or REST for browser clients.

gRPC uses HTTP/2 streams for multiplexing and Protobuf for compact binary serialization. Each RPC method maps to an HTTP/2 stream. Metadata travels in HTTP/2 headers; responses end with trailers carrying status codes.
Takeaways
  • gRPC = HTTP/2 + Protobuf for service-to-service. Schema-first (proto files), code-gen for clients/servers, strong typing.
  • Four method types: unary (request/response), server-streaming (one request, stream of responses), client-streaming (stream of requests, one response), bidirectional streaming (both sides stream).
  • Browsers cannot speak native gRPC -- they lack HTTP/2 trailer support. gRPC-Web is a compatibility layer (proxy translates). For browser-facing APIs, use REST or GraphQL; gRPC for backend-to-backend.
  • gRPC uses HTTP/2 under the hood, so it inherits TCP-level HOL blocking. For latency-critical paths, gRPC-over-QUIC is emerging but not yet mainstream.
