Multi-tenancy isolation

Silo / Pool / Bridge -- the cost-vs-isolation curve. Per-layer choices for compute / DB / cache / queue. RLS as the cross-tenant leak defense. The architecture decision behind every B2B SaaS.

1. The Three Models

Every multi-tenant system makes a choice: how isolated are tenants from each other? The spectrum runs from full isolation (silo) through shared everything (pool), with most production systems landing somewhere in between (bridge).

3. The Cost-vs-Isolation Curve

Cost grows roughly exponentially as isolation tightens. Doubling isolation typically means 5-10x cost. The curve forces honest pricing: silo isolation is the enterprise tier.

Illustrative numbers at 1000 tenants: Pool everything ~$0.10/tenant/month. Pool + per-tenant schema ~$1/tenant. Silo DB per tenant ~$50/tenant (RDS instance). Silo VM ~$200/tenant. Silo region ~$500+/tenant.
Sweet spot for B2B SaaS (100s-1000s of tenants): Pool compute + pool small DB + dedicated DB for premium / regulated tenants. The exponential cost curve forces honest pricing. If a tier wants silo isolation, that is the enterprise tier -- price it accordingly.

4. Compliance Considerations

Some workloads force isolation regardless of cost preference. Compliance is the most common reason to break out of pool.

GDPR Data Residency

Data physically in specific region. Forces silo or pool with sharded-by-region routing. EU tenant data cannot leave EU boundary.

Requires silo or regional shard

HIPAA / PHI

Stricter audit trails, encryption at rest, access controls. Usually a separate environment. BAA with cloud provider required.

Typically silo environment

PCI-DSS

Cardholder data in scope. Tokenize to shrink scope OR isolate the PCI footprint. Smaller scope = cheaper audit.

Tokenize or isolate scope

SOC 2 / ISO 27001

Process compliance. Pool is fine if encryption + access controls + audit logs are in place. Shared infrastructure works.

Pool with controls

CMEK / BYOK

Each tenant brings their own KMS key. Encryption layer is per-tenant even if storage is pooled. Key rotation per tenant.

The senior bug: cross-tenant data leak

Forgetting the tenant_id filter on a query means a user from Tenant A sees Tenant B's data. This is the most common multi-tenant vulnerability.

Without RLS -- the leak

-- Developer forgot tenant filter
SELECT * FROM orders
WHERE status = 'pending';
-- No tenant_id filter!
id tenant_id status amount
101 A pending $420
102 B pending $1,200
103 C pending $89
104 A pending $750

Tenant A sees orders from B and C. Cross-tenant data leak.

With Postgres RLS -- the defense

-- Same query, but RLS policy active
SELECT * FROM orders
WHERE status = 'pending';
-- RLS auto-injects: AND tenant_id = current_setting('app.tenant')
id tenant_id status amount
101 A pending $420
102 B pending $1,200
103 C pending $89
104 A pending $750

RLS enforces tenant filter. B and C rows invisible to Tenant A.

RLS setup

-- 1. Enable RLS on the table
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;

-- 2. Create the policy
CREATE POLICY tenant_isolation ON orders
  USING (tenant_id = current_setting('app.tenant'));

-- 3. Set tenant context at connection start
SET app.tenant = 'tenant_A';

-- 4. Every query now auto-filtered — no developer action needed
SELECT * FROM orders;  -- only sees tenant_A rows

Defense layers (defense in depth)

Layer 1 -- API Gateway: Extract tenant from JWT, inject as trusted header. Downstream services NEVER trust user-supplied tenant ID from request body.
Layer 2 -- ORM scope: Global query scope always adds tenant_id filter. Bypass requires explicit @SkipTenantFilter annotation (auditable).
Layer 3 -- Postgres RLS: Database enforces tenant filter on every query, even ad-hoc SQL. The last line of defense.
Takeaway: RLS or ORM-enforced scope is the defense. Trusting tenant_id from request body is the cross-tenant leak waiting to happen.

7. Migration Paths

The reality: most successful SaaS starts pool, evolves bridge as enterprise customers arrive. The migration is inevitable -- the question is whether you planned for it.

Common migration story

Day 1: Pool everything

Single DB, single cluster, tenant_id column on every table. Ship fast. 0-100 tenants, all self-serve.

First enterprise deal

Prospect requires dedicated DB (compliance / contractual). Scramble to extract tenant to separate RDS instance. Manual migration, some downtime.

Bridge architecture

Build tenant-aware routing: small tenants stay in pool DB, large / regulated tenants get silo DB. Shared compute layer routes by tenant ID.

Mature state

Self-serve: pool. Professional: pool with RLS. Enterprise: silo DB. Each tier priced to cover its infrastructure model.

Tools and tactics

Tenant-aware sharding: Shard by tenant ID. Hot tenants get a dedicated shard; cold tenants share a shard. Shard map in config service.

Per-tenant connection pool: Maintain a connection pool per tenant. Large tenants get a bigger pool. Route at the connection-pool level, not the query level.

Migration without downtime: Dual-write to old and new store. Backfill historical data. Verify consistency. Cut reads to new store. Stop writes to old store. Four-phase cutover, zero downtime.

Feature flags per tenant: Tenant config determines which code paths execute. New isolation features roll out to one tenant at a time. Same deployment, different behavior.
The senior tell. "I would start pool with row-level filtering, plan the silo path for enterprise tier from day 1. Per-layer decision: compute pool, DB bridge (shared with per-tenant DB option). RLS in Postgres for the cross-tenant defense. The migration path from pool to bridge is the most important architectural decision -- build the routing layer early so extracting a tenant to a dedicated DB is a config change, not a rewrite."
Takeaway: Start pool. Plan bridge from day 1. Build tenant-aware routing so the migration to silo DB is a config change, not a rewrite. Price enterprise tier to cover silo infrastructure cost.
