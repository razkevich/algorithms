MongoDB data modeling

Embed vs reference -- the decision that owns 80% of MongoDB performance. The bucket pattern, the ESR rule for compound indexes, schema versioning. The interview answer is never "put it in a collection."

1. Embed vs Reference -- Decision Tree

Four axes determine the modeling choice. Toggle each one and watch the recommendation update.

Embed
With low cardinality, co-fetched access, rare child updates, and no size concern, embedding is the clear default. One document fetch returns everything -- no joins, no extra round trips. This is MongoDB's strength: model for the read path.

Side-by-side: User + Address

Embedded
users collection{ "_id": 1, "name": "Alice", "addresses": [ { "type": "home", "city": "Portland", "zip": "97201" }, { "type": "work", "city": "Seattle", "zip": "98101" } ] }
1 query, 1 document fetch
Referenced
users collection{ "_id": 1, "name": "Alice" } // addresses collection { "_id": 101, "user_id": 1, "type": "home", "city": "Portland", "zip": "97201" }
2 queries or $lookup (left-outer join)
Takeaway: The default is embed. Switch to reference only when one of: unbounded growth, access pattern diverges, child update churn would rewrite the parent, or the 16MB cap looms.

2. Three Classic Patterns Visualized

2a. One-to-few -- embed (the default)

Domain: User + Phone Numbers (typically 2-5). Phones are always fetched with the user.

users collection{ "_id": 1, "name": "Alice", "phones": [ { "type": "home", "number": "555-1234" }, { "type": "work", "number": "555-5678" } ] }
Read user = get phones for free. Single document fetch, zero joins. This is the happy path for MongoDB -- embed small, bounded, co-accessed data directly into the parent document.
Anti-case: If phones grow unbounded (e.g., a call log instead of contact numbers), embedding fails -- the document grows without bound, approaching the 16MB BSON limit, and every call-log append rewrites the entire user document. Switch to a reference pattern.

2b. One-to-many -- extended reference (denormalized)

Domain: Order + Customer. A customer can have thousands of orders. Each order shows the customer name without a join.

orders collection{ "_id": 100, "customer_id": 1, "customer_name": "Alice", // denormalized "items": [ { "sku": "WDG-42", "qty": 2 } ], "total": 59.99 }
customers collection{ "_id": 1, "name": "Alice", "email": "alice@example.com" }
Read order = see customer name without fetching customer doc. Trade-off: when Alice's name changes, you must fan out updates to all her orders.

2c. One-to-many -- reference (when access patterns diverge)

Domain: Author + Books. Sometimes you want just the author, sometimes author + books. Separate collections, join with $lookup when needed.

authors collection{ "_id": 1, "name": "Alice", "bio": "Writer of things." }
books collection{ "_id": 200, "title": "Distributed Systems", "author_id": 1 }
Read author alone = 1 query. Read author + books = 2 queries (application-side join) or one $lookup aggregation. $lookup is a left-outer join implemented as a cross-collection traversal -- functional but slow under load. On hot paths, prefer application-side joins with caching, or reconsider whether embedding a subset would serve the read path better.
$lookup pipelinedb.authors.aggregate([ { "$match": { "_id": 1 } }, { "$lookup": { "from": "books", "localField": "_id", "foreignField": "author_id", "as": "books" }} ])
Anti-pattern warning: $lookup on hot paths is a red flag. It forces MongoDB to scan the foreign collection for each input document. In interviews, name this trade-off explicitly: "I would avoid $lookup in the critical read path and use application-side caching or denormalization instead."

3. Bucket Pattern (Time-Series)

Domain: IoT sensor readings, 1 reading per second per sensor. Naive: one document per reading. Better: one document per sensor per hour (bucket).

Anti-pattern: 1 doc per reading
readings collection{ "_id": ObjectId(), "sensor": "s42", "ts": ISODate("2026-05-09T17:00:01Z"), "value": 23.4 } // x 86,400 per sensor per day // x 3,600 per sensor per hour
Bucket pattern: 1 doc per hour
sensor_buckets collection{ "_id": { "sensor": "s42", "hour": "2026-05-09T17" }, "count": 3600, "readings": [ { "ts": "..T17:00:01", "val": 23.4 }, { "ts": "..T17:00:02", "val": 23.5 }, // ... up to 3600 entries ] }

A "last 24 hours of sensor s42" range query touches 24 bucket documents versus 86,400 individual documents. Index is 3,600x smaller. Each bucket doc leverages MongoDB's document-level locking efficiently -- writes append to the current hour's readings array.
Trade-off: The document grows during the hour as readings append. MongoDB pre-allocates space (power-of-2 sizing), but if the bucket exceeds expectations, you hit document moves. Cap bucket size; rotate to a new document when full. For very high-volume sensors, use smaller time windows (per-minute buckets).
Takeaway: Bucket = the time-series pattern. ALWAYS use it for high-volume time-series data. The reduction in document count and index size is usually 100x-3600x, and range queries drop from scanning thousands of documents to reading a handful.

4. Subset Pattern

Domain: User profile with reviews. The profile page shows the top 10 latest reviews. The full review history is rarely accessed.

User doc (hot data embedded)
users collection{ "_id": 1, "name": "Alice", "top_reviews": [ { "_id": 501, "text": "Great product...", "rating": 5, "date": "2026-05-08" }, // ... top 10 only ] }
Profile fetch: 1 doc, 1 query
Full review history (cold data)
reviews collection{ "_id": 501, "user_id": 1, "text": "Great product...", "rating": 5, "date": "2026-05-08", "product_id": 42, "helpful_votes": 17 } // paginated: db.reviews.find({user_id:1}).sort({date:-1}).skip(10).limit(10)
Full history: separate query, paginated

Write path: new review arrives

Takeaway: Subset pattern = embed the frequently-accessed subset, store the full dataset separately. Profile page is a single document fetch; full history is paginated from a separate collection. The cost is a dual-write on insert, but the read-path win is enormous for high-traffic pages.

5. Index Types and Covered Queries

A users collection with six index types. For each: a query that uses the index and one that does not.

Single field: {email: 1}
USES INDEX db.users.find({email: "alice@example.com"})
COLLECTION SCAN db.users.find({name: "Alice"}) -- no index on name
Compound: {tenant_id: 1, status: 1, created_at: -1}
USES INDEX db.users.find({tenant_id: 5, status: "active"}).sort({created_at: -1})
COLLECTION SCAN db.users.find({status: "active"}) -- skips left prefix

Compound left-prefix rule

Index {tenant_id: 1, status: 1, created_at: -1} supports queries on any left prefix of the key sequence, but not arbitrary subsets.

{tenant_id}
Supported (left prefix)
{tenant_id, status}
Supported (left prefix)
{tenant_id, status, created_at}
Supported (full index)
{status}
Not supported (skips tenant_id)
{created_at}
Not supported (skips prefix)
{status, created_at}
Not supported (skips tenant_id)

Covered query

A covered query is one where the index contains all fields the query reads -- both the filter fields and the projected fields. MongoDB returns results directly from the index without touching the document storage.

Index: {tenant_id: 1, status: 1}
COVERED db.users.find({tenant_id:1, status:"active"}, {tenant_id:1, status:1, _id:0})
Projection includes only indexed fields + excludes _id. No document fetch needed.
NOT COVERED db.users.find({tenant_id:1, status:"active"}, {tenant_id:1, status:1, email:1, _id:0})
email is not in the index -- must fetch the document to return it.
Multikey (array field): {tags: 1}
USES INDEX db.users.find({tags: "premium"})
USES INDEX db.users.find({tags: {$in: ["premium", "vip"]}})
MongoDB creates an index entry for each element in the array. Queries on any element use the index.
Text: {name: "text", description: "text"}
USES INDEX db.users.find({$text: {$search: "distributed systems"}})
COLLECTION SCAN db.users.find({name: /distributed/}) -- regex does not use text index
2dsphere: {loc: "2dsphere"}
USES INDEX db.users.find({loc: {$near: {$geometry: {type:"Point", coordinates:[-122,47]}}}})
COLLECTION SCAN db.users.find({"loc.coordinates.0": {$gt: -123}}) -- raw field access, not geospatial query
TTL: {created_at: 1} with expireAfterSeconds: 86400
AUTO-DELETE Documents older than 24h are automatically removed by a background thread.
TTL indexes run a background task every 60 seconds. Not instant -- there is up to a 60-second lag. Use for session expiry, audit logs, temporary tokens.

ESR Rule for compound index field order

Equality, Sort, Range -- order fields in that priority for optimal compound index design.

Violation: Range before Sort
// Query db.orders.find({ "status": "shipped", // equality "total": { "$gt": 100 } // range }).sort({ "created_at": -1 }) // sort // Bad index: {status:1, total:1, created_at:-1} // Range on total breaks sort optimization // MongoDB must in-memory sort after range scan
Correct: Equality, Sort, Range
// Same query, better index // ESR index: {status:1, created_at:-1, total:1} // E: status = "shipped" (equality first) // S: created_at desc (sort next) // R: total > 100 (range last) // MongoDB walks the index in sort order, // skipping entries where total <= 100. // No in-memory sort needed.
Takeaway: ESR. Equality, Sort, Range -- that is the order. Index on {eq_field: 1, sort_field: 1, range_field: 1}. Putting range before sort forces MongoDB into an in-memory sort, which is bounded by 100MB and will fail on large result sets.

The pipeline processes documents sequentially through each stage. $match filters early (uses indexes if available), reducing the work for downstream stages. $group aggregates by key. $sort orders the results. $project reshapes the output.

$lookup: the cross-collection join

$lookup performs a left-outer join: for each input document, it queries the foreign collection and attaches matching documents as an array. This is inherently slower than single-collection operations because it forces cross-collection traversal. On sharded clusters, the foreign collection must be unsharded or on the same shard. In interviews, always flag: "I would avoid $lookup on the hot path."

$facet: parallel sub-pipelines

$facet runs multiple aggregation pipelines on the same input set in parallel, returning a single document with named fields for each sub-pipeline's result. Use case: a dashboard that needs total count, top-N, and category breakdown from the same query -- one round trip instead of three.
$facet exampledb.orders.aggregate([ { "$match": { "status": "shipped" } }, { "$facet": { "totalCount": [{ "$count": "n" }], "topCustomers": [ { "$group": { "_id": "$customer", "spent": { "$sum": "$total" }}}, { "$sort": { "spent": -1 }}, { "$limit": 3 } ], "byMonth": [ { "$group": { "_id": { "$month": "$date" }, "count": { "$sum": 1 }}} ] }} ])
Takeaway: Always push $match first. Use indexes that support the $match stage. $lookup is the join you should question -- name the cost explicitly in interviews. $facet is the tool for "I need multiple views of the same data in one query."

7. Schema Versioning

MongoDB does not enforce schema. When your data model evolves, old documents still exist with the old shape. The canonical pattern: schemaVersion field + migrate-on-read + background fixup.

Evolution: User schema v1 to v2

v1 (legacy)
{ "_id": 1, "name": "Alice Smith", "email": "alice@example.com" } // no schemaVersion field
v2 (current)
{ "_id": 2, "firstName": "Bob", "lastName": "Jones", "email": "bob@example.com", "schemaVersion": 2 }

Read-path branching

application codefunction getUser(doc) { if (doc.schemaVersion === 2) { // v2: use firstName/lastName directly return { first: doc.firstName, last: doc.lastName, email: doc.email }; } else { // v1: split "name" into first/last, migrate on read const [first, ...rest] = doc.name.split(" "); const last = rest.join(" "); // fire-and-forget update to migrate this doc db.users.updateOne( { _id: doc._id }, { $set: { firstName: first, lastName: last, schemaVersion: 2 }, $unset: { name: "" } } ); return { first, last, email: doc.email }; } }

Background migration

Migrate-on-read handles documents as they are accessed. A background batch job handles the rest -- documents that are never read still need migration for consistency and to allow eventual removal of the v1 code path.

v1 name: "Alice Smith" email: "alice@..."
v1 name: "Bob Jones" email: "bob@..."
v2 firstName: "Charlie" lastName: "Brown" schemaVersion: 2
v1 name: "Diana Prince" email: "diana@..."
v2 firstName: "Eve" lastName: "Taylor" schemaVersion: 2
v1 name: "Frank Castle" email: "frank@..."
Migration progress: 2 / 6 migrated
33%
Background migration runs in batches: db.users.find({schemaVersion: {$ne: 2}}).limit(100). For each batch, split name, set firstName/lastName, set schemaVersion: 2, unset name. Process in small batches to avoid lock contention.
Takeaway: MongoDB does not enforce schema, so you must. schemaVersion field + migrate-on-read + background fixup is the canonical pattern. The code path must handle all active schema versions until migration is complete. Only after 100% migration can you remove the v1 branch.
