Cassandra data modeling

Partition keys, hot partitions, denormalize-by-query, tombstones, TWCS for time-series. Cassandra punishes relational instincts -- these are the rules that keep you out of trouble.

1. Primary key anatomy

Every Cassandra table has a primary key with two distinct roles packed into one declaration:

Partition key determines which node(s) own the data. Cassandra hashes it to a token, maps the token to a position on the ring, and routes the request to the responsible node(s). Every efficient query MUST include the full partition key in its WHERE clause.

Clustering key(s) determine sort order within a partition. They enable range scans and ORDER BY. Clustering keys must be used left-to-right in queries -- you cannot skip one.

Interactive example: users_by_country

CREATE TABLE users_by_country (
  country   text,
  signup_at timestamp,
  user_id   uuid,
  name      text,
  PRIMARY KEY ((country), signup_at, user_id)
) WITH CLUSTERING ORDER BY (signup_at DESC);

Physical layout for country = 'US' -- all rows co-located on the same node, sorted by signup_at DESC:

Takeaway: Cassandra is a key-value store with a hierarchical key. Partition key is mandatory in WHERE; clustering keys must be used left-to-right (no skipping). If you skip a clustering key, Cassandra cannot use the index efficiently. If you omit the partition key entirely, the query is rejected or requires a full cluster scan.

2. Hot partition -- the canonical anti-pattern

Domain: time-series sensor readings at 1 Hz.

Bad model: unbounded partition

CREATE TABLE readings (
  sensor_id uuid,
  ts        timestamp,
  value     double,
  PRIMARY KEY ((sensor_id), ts)
);

Every reading for sensor X goes to one partition forever. After a year at 1 Hz: 31.5M rows in one partition, one node bottlenecked, partition well over 100 MB. Cassandra struggles with partitions beyond 100 MB -- GC pauses, compaction stalls, read latency spikes.

Good model: bucketed partition key

CREATE TABLE readings (
  sensor_id uuid,
  day       date,
  ts        timestamp,
  value     double,
  PRIMARY KEY ((sensor_id, day), ts)
);

Now partition = (sensor_id, day). Each day's data is a fresh partition, distributed by hash(sensor_id, day). Each partition is bounded: ~86,400 rows max at 1 Hz.

Range query WHERE sensor_id = X AND day = '2024-01-15' hits 1 partition on 1 node. WHERE sensor_id = X AND day IN ('2024-01-15', ..., '2024-01-21') hits 7 partitions, possibly across 7 nodes -- scatter-gather, but each partition is small and fast.

Takeaway: Time-series ALWAYS bucketed. Pick the bucket size so partitions stay under 100 MB / under 100K rows. Day, hour, week -- depends on write rate. At 1 Hz, day-bucketing gives ~86K rows per partition. At 100 Hz, use hour-bucketing (~360K rows -- still within bounds).

3. Denormalize-by-query

Domain: a chat application with two access patterns:

  • "Show all messages for user X" (sorted by time)
  • "Show all messages in room Y" (sorted by time)

Wrong (relational) approach

-- One table to rule them all (the relational instinct)
CREATE TABLE messages (
  msg_id   uuid,
  user_id  uuid,
  room_id  uuid,
  content  text,
  ts       timestamp,
  PRIMARY KEY ((msg_id))
);

Query "all messages for user X" requires either a secondary index (per-node local scan, scatter to all nodes) or ALLOW FILTERING (full cluster scan). Both are unacceptable at scale.

Right (Cassandra) approach: one table per query pattern

CREATE TABLE messages_by_user (
  user_id  uuid,
  ts       timestamp,
  msg_id   uuid,
  room_id  uuid,
  content  text,
  PRIMARY KEY ((user_id), ts, msg_id)
) WITH CLUSTERING ORDER BY (ts DESC);

CREATE TABLE messages_by_room (
  room_id  uuid,
  ts       timestamp,
  msg_id   uuid,
  user_id  uuid,
  content  text,
  PRIMARY KEY ((room_id), ts, msg_id)
) WITH CLUSTERING ORDER BY (ts DESC);

Write path: app writes both tables on every new message. Storage cost is 2x; read cost is optimal for either query.

Takeaway: Denormalize-by-query is mandatory. Storage is cheap; query latency is the constraint. Each query pattern gets its own table. The write path fans out to all relevant tables. This is the fundamental trade-off Cassandra makes: write amplification for read optimization.

4. Tombstones -- the silent killer

When you DELETE a row in Cassandra, it does not disappear. A tombstone (marker) is written instead. The actual data is removed during compaction -- eventually. Until then, tombstones accumulate and degrade reads.

Anti-pattern: Cassandra as a queue

CREATE TABLE queue (
  shard    int,
  msg_id   timeuuid,
  payload  text,
  PRIMARY KEY ((shard), msg_id)
);

Insert 1000 messages, process 990, delete 990. Result: 10 live rows + 990 tombstones. A range query WHERE shard=1 LIMIT 100 reads through all 1000 cells but returns only 10.

Step through the demo: insert, delete, then query. Watch how tombstones force Cassandra to scan dead cells to find live ones.

Thresholds:

  • tombstone_warn_threshold (default 1000) -- SELECT logs a warning when it scans this many tombstones.
  • tombstone_failure_threshold (default 100,000) -- SELECT fails with TombstoneOverwhelmingException.

Mitigations:

  • Do not use Cassandra as a queue. Use Redis Streams or Kafka for queue semantics.
  • Prefer short TTLs with auto-expire over explicit DELETE -- expired data is cleaned more efficiently.
  • Use TWCS (TimeWindowCompactionStrategy) for time-series with TTL -- drops entire SSTables when all data expires, no tombstone read overhead. See Section 5.
  • Design for append-mostly workloads. Cassandra's storage engine is optimized for writes, not updates/deletes.
Takeaway: Tombstones are the price of decentralized deletes. In a leaderless system, a delete must be propagated as a marker (tombstone) so all replicas know the data is gone. Avoid patterns that create tombstone pressure -- TTLs over DELETEs, append-mostly workloads.

5. TTLs and TWCS for time-series

CREATE TABLE readings (
  sensor_id uuid,
  day       date,
  ts        timestamp,
  value     double,
  PRIMARY KEY ((sensor_id, day), ts)
) WITH default_time_to_live = 7776000  -- 90 days
  AND compaction = {
    'class': 'TimeWindowCompactionStrategy',
    'compaction_window_size': '1',
    'compaction_window_unit': 'DAYS'
  };

TWCS groups SSTables by time window. Writes on day N go to SSTable(day N). After 90 days, the entire day-N SSTable is expired -- compaction drops the file as a unit, no per-cell tombstone scan.

6. Lightweight transactions (LWT) -- when you need strong consistency

Cassandra defaults to eventual consistency. When you need a compare-and-set operation -- INSERT ... IF NOT EXISTS or UPDATE ... IF condition -- it uses Paxos under the hood.

-- Idempotency key: ensure exactly-once payment processing
INSERT INTO payments (idempotency_key, amount, status)
  VALUES ('pay-abc-123', 49.99, 'pending')
  IF NOT EXISTS;

Normal write (1 round-trip)

1
Client → Coordinator → Replicas → ACK

LWT write (4 Paxos round-trips)

1
Prepare -- Coordinator sends prepare(ballot) to replicas, gets promises
2
Read -- Coordinator reads current value from replicas (to check IF condition)
3
Propose -- If condition met, coordinator proposes new value to replicas
4
Commit -- Replicas accept; coordinator commits and returns result
Click "Compare" to visualize the latency difference. Normal writes complete in ~1 round-trip; LWT requires 4 Paxos phases, roughly 10x the latency.

Use cases for LWT (all cold-path):

  • Idempotency keys -- INSERT IF NOT EXISTS to guarantee exactly-once processing.
  • Leader election -- UPDATE ... SET leader = me IF leader = null.
  • Unique constraints -- enforce uniqueness on fields Cassandra normally does not constrain (email, username).
  • Optimistic locking -- UPDATE ... SET version = N+1 IF version = N.
Takeaway: LWT is the escape hatch for strong consistency. It is slow -- 4 Paxos round-trips, roughly 10x normal write latency. Use sparingly, on cold paths only. If you need strong consistency on a hot path, Cassandra is the wrong database.

7. Materialized views and secondary indexes -- careful

Materialized views

Cassandra-managed denormalization: define a view and Cassandra keeps it in sync with the base table.

CREATE TABLE users_by_id (
  user_id  uuid,
  email    text,
  name     text,
  PRIMARY KEY ((user_id))
);

CREATE MATERIALIZED VIEW users_by_email AS
  SELECT * FROM users_by_id
  WHERE email IS NOT NULL AND user_id IS NOT NULL
  PRIMARY KEY ((email), user_id);

Write to users_by_id and the view users_by_email is updated automatically. Sounds great. The caveats:

  • Eventual consistency between base table and MV -- reads from the view may be stale.
  • Performance overhead on writes -- each base table mutation triggers a read-before-write on the view partition.
  • Operational unpredictability -- many production clusters have abandoned MVs as too fragile. They can cause repair issues and build up backlogs.

Secondary indexes

CREATE INDEX ON users_by_id (name);

This creates a local secondary index -- each node indexes only its own data.

Query with only a secondary index (no partition key) forces a scatter query to every node -- each node scans its local index and returns results. This is O(N) in cluster size, not O(1).

Secondary indexes are only efficient when the query also includes the partition key -- then it is just per-partition filtering on one node.

SAI (Storage-Attached Indexes) -- Cassandra 5.x

SAI is a better implementation (attached to SSTables, not separate data structure), but the fundamental limitation remains: without the partition key, the query must scatter to all nodes. Better per-node performance, same distribution problem.

Takeaway: Do not use secondary indexes for the same reason you would not make a Cassandra cluster behave relationally. The right answer is almost always: denormalize into a dedicated table (Section 3). Materialized views automate this but come with reliability trade-offs many teams find unacceptable. When in doubt, manage the denormalization in application code.
