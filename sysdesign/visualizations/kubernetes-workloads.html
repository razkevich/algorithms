Kubernetes -- workloads + rollouts + autoscaling

Pick the right primitive. Roll out without downtime. Scale on the right signal. Probe what matters. The day-2 K8s stuff that real interview rounds dig into.

1. Workload Types -- Decision Tree

Six primitives cover every production workload. The decision tree below narrows to the right one in 4 questions.

Deployment
stateless
Stateless replicas with rolling updates. Each pod is interchangeable -- no stable identity, no persistent storage tied to a specific replica.
Web servers, API gateways, stateless workers, microservices
StatefulSet
stateful
Replicas with stable network identities (pod-0, pod-1) and persistent storage per replica via PVCs. Ordered startup/shutdown.
Kafka brokers, etcd, Postgres replicas, ZooKeeper, Elasticsearch data nodes
DaemonSet
per-node
Exactly one pod per node (or per matching node-selector). The scheduler ensures coverage automatically as nodes join or leave.
Fluent Bit, Node Exporter, CNI plugins, kube-proxy, security agents
Job
batch
Run-to-completion. Retried up to backoffLimit. Pod stays in Completed state for log inspection. Supports parallelism.
Data migrations, ETL batch, ML training jobs, one-off scripts
CronJob
scheduled
Creates Jobs on a cron schedule. Supports concurrencyPolicy (Allow / Forbid / Replace) to control overlap.
Nightly reports, periodic cleanup, scheduled backups, billing aggregation
Operator (CRD + Controller)
advanced
Custom Resource Definition + reconciliation controller. Encodes domain-specific operational knowledge (backup, failover, scaling) into the cluster.
Postgres Operator, Strimzi (Kafka), Cert-Manager, Prometheus Operator

Takeaway: Start from Deployment (the default). You only need StatefulSet when pods must be individually addressable with their own storage. DaemonSet is exclusively for per-node infrastructure. Job/CronJob is for finite work, not services.

Scaler Comparison

Scaler What it scales Signal Use when
HPA Pod replicas (horizontal) CPU, memory, custom metrics Default for stateless services under variable load
VPA Pod resource requests/limits (vertical) Observed usage vs requests Right-sizing over time; not real-time. Do not combine with HPA on same metric
Cluster Autoscaler Nodes Pending pods (unschedulable) Always, if using cloud node groups. Reacts to HPA creating pods that won't fit
KEDA Pod replicas (event-driven) Queue depth, Kafka lag, Prometheus, cron Workers idle most of the time. Supports scale-to-zero
Takeaway:
  • HPA + Cluster Autoscaler = the basic combo. HPA scales pods, CA scales nodes to fit them.
  • VPA = right-sizing tool, not real-time scaling. Run in recommendation mode alongside HPA.
  • KEDA = the queue-driven worker pattern. Scale from Kafka consumer lag or SQS depth. Supports scale-to-zero (HPA cannot).

4. ConfigMaps + Secrets

Four ways to inject configuration. Each has different update-propagation behavior -- a common interview trap.

Method Source Live update? Notes
env.valueFrom.configMapKeyRef ConfigMap No Env vars are set at pod start. Changing the ConfigMap requires pod restart.
envFrom ConfigMap / Secret No Bulk-injects all keys as env vars. Same restart caveat.
volumeMounts ConfigMap / Secret Yes (~1-2 min) Kubelet syncs volume contents periodically. App must watch or re-read file.
CSI Driver (Vault, Secrets Store) External secret manager Yes (configurable) Pulls from Vault / AWS Secrets Manager. Rotation handled externally.

Secrets -- What "Secret" Actually Means in K8s

Kubernetes Secrets are base64-encoded, not encrypted in etcd by default. Anyone with etcd access or kubectl get secret -o yaml permission can read them. This is one of the most common "gotcha" interview questions.
Secret lifecycle -- from plaintext to pod:

Production-Grade Secret Management

For real production systems, the path is: External secret manager (HashiCorp Vault, AWS Secrets Manager, GCP Secret Manager) + External Secrets Operator or Secrets Store CSI Driver. The operator syncs external secrets into K8s Secret objects, or the CSI driver mounts them directly. Either way, the source of truth lives outside the cluster.
Takeaway:
  • ConfigMap updates auto-propagate via volume mount but NOT via env var. Env vars are frozen at pod start.
  • Secrets in etcd are base64, not encrypted. Use KMS envelope encryption at the cluster level, or better yet, an external secret manager.
  • For interviews: "we use External Secrets Operator to sync from Vault/AWS SM into K8s Secrets, mounted as volumes for live rotation."

5. Probes -- Liveness, Readiness, Startup

Three probes, three distinct purposes. Confusing them causes production outages. This is a favorite interview question because the failure modes are subtle.

Probe Question it answers On failure What to check
Liveness "Is this container hung / deadlocked?" Kubelet restarts the container Self-check only: process alive, not blocked. Never call external dependencies.
Readiness "Can this container serve traffic right now?" Service endpoints exclude this pod (no traffic routed). No restart. Downstream deps: DB connection, cache, required services.
Startup "Has the container finished its slow startup?" Liveness + readiness probes don't run until startup succeeds. JVM warmup, large index load, migration completion.

Takeaway:
  • Liveness checks the process, readiness checks dependencies. Most production outages from liveness probes are caused by calling external systems.
  • The classic anti-pattern: HTTP liveness on /health that queries the DB. DB has a 3-second blip. Liveness fails. Kubelet restarts ALL pods. Now you have a cascading failure -- cold starts under load, connection storms, longer recovery.
  • Startup probe protects slow-starting apps (JVM, large indexes). Without it, liveness kills the pod before it finishes initializing.

The Operator pattern encodes operational knowledge into the cluster. Instead of runbooks, you get a controller that watches a Custom Resource and reconciles desired state continuously.

Example: Postgres Operator. You declare a PostgresCluster CR with 3 replicas, 100Gi storage, and daily backups. The operator creates a StatefulSet with 3 pods, provisions PVCs, sets up streaming replication, configures pgBackRest, handles failover, and manages minor version upgrades -- all from that single CR.

When to Use an Operator vs a Helm Chart

Takeaway: Use existing operators for databases and infrastructure components -- don't write your own unless you're building a platform product. For interviews: "for Postgres/Kafka on K8s, I'd use an operator rather than raw StatefulSets because it handles failover, backups, and upgrades that would otherwise need manual runbooks."

7. Common Pitfalls Reference

The six symptoms you'll encounter in production and interviews. Know the mental model: symptom --> event reason --> fix.

Symptom Root Cause Investigation Fix
Pod stuck Pending No node has enough CPU/memory, or taints/tolerations mismatch kubectl describe pod -- Events section shows FailedScheduling with reason Lower resource requests, add nodes (Cluster Autoscaler), or add toleration
Service endpoints empty Readiness probe failing on all pods, or label selector mismatch kubectl get endpoints + kubectl describe pod for probe failures Fix readiness probe, verify Service selector matches pod labels
Rolling update stuck New pods failing readiness; progressDeadlineSeconds exceeded kubectl rollout status shows deadline exceeded. Check new pod logs. kubectl rollout undo to previous revision. Fix image/config, redeploy.
OOMKilled loop Container exceeds memory limit. Exit code 137 in events. kubectl describe pod -- OOMKilled in last state reason Increase memory limit, fix memory leak, or enable VPA for right-sizing
ImagePullBackOff Wrong image name/tag, or missing registry credentials (imagePullSecrets) kubectl describe pod -- Events show pull error with registry URL Fix image reference, create/attach imagePullSecret for private registry
CrashLoopBackOff Application crashing on startup. Kubelet keeps restarting with exponential backoff. kubectl logs --previous to see crash output from last attempt Fix application error (missing config, bad entrypoint, port conflict)
Takeaway: In interviews, the pattern is always the same: kubectl describe pod to read Events, kubectl logs for application output, kubectl get events --sort-by=.lastTimestamp for cluster-wide context. Know these three commands and the six symptoms above.
