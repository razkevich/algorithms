Real-time push -- WebSockets / SSE / long polling

Specific use cases

Live Chat

WebSockets
Typing indicators, read receipts, message send all require client-to-server. Full duplex.

Stock Ticker / Live Dashboard

SSE
One-way push of values. Auto-reconnect with Last-Event-ID handles network blips.

Server Log Tail

SSE
Continuous server-to-client stream. Text-native format is a natural fit for log lines.

Multiplayer Game

WebSockets
Low-latency bidirectional. Player inputs and game state both flow in real time.

Notification Center

Long Polling or WebSockets
Long polling if simple (bell icon count). WebSockets if you need mark-as-read, dismiss, etc.

File Upload Progress

SSE
Server reports percentage/status updates. Client only watches -- no need to send back.
Takeaway: WebSockets if you need duplex. SSE if you don't. Long polling if proxies break SSE. Don't use plain polling for real-time.

3. SSE Deep Dive

Server-Sent Events: a persistent HTTP connection where the server pushes UTF-8 event frames. The browser handles reconnection automatically.

Event format

event: priceUpdate
data: {"symbol":"AAPL","price":192.50}
id: 42

event: priceUpdate
data: {"symbol":"GOOG","price":178.30}
id: 43

Each event has optional event: (type name), required data: (payload), optional id: (for resume). Events are separated by a blank line. The server can also send retry: 5000 to control the client's reconnect interval in milliseconds.

Auto-reconnect and resume

When the connection drops, the browser automatically reconnects after the retry interval (default ~3s). On reconnect, it sends the Last-Event-ID HTTP header with the last received id: value. The server uses this to replay missed events.

JS API

const source = new EventSource('/stream');

// Listen to named events
source.addEventListener('priceUpdate', (e) => {
  const data = JSON.parse(e.data);
  console.log(data.symbol, data.price);
});

// Or catch all unnamed events
source.onmessage = (e) => { /* ... */ };

// Connection lifecycle
source.onopen = () => { /* connected */ };
source.onerror = () => { /* will auto-reconnect */ };

Limits and gotchas

LimitDetailMitigation
6 connections per origin HTTP/1.1 browser limit. Multiple SSE streams from same origin starve other requests. Use HTTP/2 (multiplexed). Or consolidate into one stream with event types.
Text only (UTF-8) No binary frames. Images/audio would need base64 encoding. Use WebSockets for binary data.
Server to client only No upstream channel. Client must use separate HTTP requests for commands. Pair SSE (downstream) with REST (upstream). Or switch to WebSockets.
No IE support Internet Explorer never implemented EventSource. Polyfill or long-polling fallback. Not relevant for modern stacks.

4. WebSocket Deep Dive

Full-duplex communication over a single TCP connection. Starts as HTTP, upgrades to a binary framing protocol.

The upgrade handshake

// Client request
GET /chat HTTP/1.1
Host: server.example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
Sec-WebSocket-Protocol: chat, superchat

// Server response
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
Sec-WebSocket-Protocol: chat

The Sec-WebSocket-Accept value = Base64(SHA1(Sec-WebSocket-Key + magic GUID 258EAFA5-E914-47DA-95CA-5AB5DC85B11)). This proves the server understood the WebSocket protocol, not just any HTTP server.

Frame structure

FieldSizePurpose
FIN1 bitFinal fragment of message
Opcode4 bits0x1 = text, 0x2 = binary, 0x8 = close, 0x9 = ping, 0xA = pong
MASK1 bitClient-to-server frames must be masked
Payload length7/16/64 bits7 bits if <126, 16 bits if 126, 64 bits if 127
Masking key0 or 32 bitsXOR key for payload (client-to-server only)
PayloadvariableApplication data

Minimal overhead: 2-14 bytes per frame vs. ~800 bytes of HTTP headers per request. This is why WebSockets win for high-frequency messaging.

Subprotocols

The Sec-WebSocket-Protocol header negotiates an application-level protocol on top of WebSocket framing:

  • graphql-ws / graphql-transport-ws -- GraphQL subscriptions
  • mqtt -- IoT messaging
  • stomp -- message broker interop (ActiveMQ, RabbitMQ)
  • wamp -- RPC + pub/sub combined

Heartbeat: ping / pong

Server sends a ping frame every ~30s. Client must respond with pong (browser does this automatically). If no pong arrives within timeout, server closes the connection as stale. This detects half-open connections (client crashed, network died silently).

Reconnection

Unlike SSE, the browser WebSocket API has no auto-reconnect. You must implement it in application code. Libraries like Socket.IO, ReconnectingWebSocket, or custom logic with exponential backoff + jitter handle this.

Common libraries

Takeaway: WebSockets = TCP socket with framing. 2-14 byte overhead per frame vs. ~800 bytes for HTTP. Heartbeat (ping/pong) for liveness detection. Reconnect must be done in application code. Subprotocol header for application semantics.

5. Scaling -- The Connection Problem

A WebSocket or SSE connection is long-lived. Every concurrent user = 1 open connection on the server. This changes everything about capacity planning.

Single server limits

ResourceDefaultPractical limitNotes
File descriptors ~1024 (soft) / ~28K (hard) Raise with ulimit -n Each connection = 1 fd. Set to 500K+ for WS servers.
Memory per connection 50-500 KB 100K conns x 200KB = 20GB Framework-dependent. Go/Rust < Node.js < Java/Spring.
Connections per server -- 100K-1M (epoll-based) Node.js, Go, Rust handle 100K+. Java NIO / Netty too. Thread-per-conn = much less.

Scaled architecture: edge + pub/sub backbone

Don't broadcast from a single backend. Don't do fanout in the database. The pattern:

Press Run Scale Demo to see: backend publishes one event to Redis Pub/Sub, all 10 edge servers receive it, each fans out to its 10K connected clients.

Layered architecture

  1. Edge / WS proxy (Cloudflare, AWS API Gateway WebSocket, Envoy, Kong, custom Go gateway): terminates client connections, maintains client identity, subscribes to pub/sub topics.
  2. Pub/sub backbone (Redis Pub/Sub, NATS, Kafka): broadcasts events to all interested edge servers. Backend publishes once; backbone handles fan-out to edges.
  3. Application backend: produces events to the backbone. Does not speak directly to clients. Single point of fanout -- no connection management.

Sticky sessions

Each client must reach the same edge server that holds its open connection. The load balancer must use IP hash or cookie-based session affinity. Without stickiness, a client reconnect hits a different edge and loses its connection state.

Reconnect strategy

Client disconnects, reconnects through CDN/LB to any edge server. The new edge fetches missed events from the backbone's history:

  • SSE style: Last-Event-ID header, server replays from that point.
  • WebSocket style: per-client ack tracking in Redis, replay from last-acked offset.
  • Kafka-backed: each edge consumes from a topic with a per-client offset; replay is built into the consumer group model.
Takeaway: Push at scale = thin edge servers + pub/sub backbone. Don't try to broadcast from a single backend. Don't try to do fanout in the database. Sticky sessions on the edge; replay missed events on reconnect.

6. Common Pitfalls

Quick reference for the failure modes you'll encounter (and interviewers will probe).

SymptomFixWhy
Connection drops every 60s Heartbeats + LB idle timeout Intermediate proxy/LB has idle timeout. Server must send ping before timeout expires. Configure LB idle timeout > heartbeat interval.
Memory grows over time Cleanup on close event Connections leaking -- close handler not removing state. Monitor active connection count as a metric.
All clients reconnect at once after deploy Jittered reconnect delays Thundering herd: all connections drop simultaneously, all retry at once. Add random jitter (0-5s) to reconnect delay.
Lost events on reconnect Track last_seen_id + replay No replay mechanism. Must store per-client last-acked event and replay missed events from a durable source.
WebSockets fail behind corporate proxy Fallback to long polling Some proxies strip the Upgrade header. Socket.IO handles this automatically with transport fallback.
Mobile network: connection churn Aggressive heartbeats + fast reconnect Cell tower handoff, WiFi/cell switches. Short heartbeat interval (15s) + immediate reconnect with backoff.
Head-of-line blocking in multiplexed streams Separate connections or priority frames HTTP/2 multiplexing means one slow SSE stream can block others. Use dedicated connections for critical streams.
Takeaway: The three non-negotiable answers: (1) heartbeat for liveness, (2) jittered reconnect to prevent thundering herd, (3) Last-Event-ID / offset-based replay for missed events. These are what separate "I've built this" from "I've read about this."
