CDC + Transactional Outbox

The dual-write problem; CDC via Debezium; transactional outbox + inbox dedup. The patterns that bridge OLTP databases and event streams without the silent inconsistency bug.

1. The Dual-Write Problem

Your service receives a request, writes to a database, and publishes an event to Kafka. Two separate systems, two separate writes, no shared transaction. This is a dual write, and it fails in two distinct ways.

Click a scenario above to animate the failure mode. The dual-write problem occurs whenever your code performs two writes to different systems without a shared transaction.

Why "just retry" does not work

The request handler has no transactional control over both systems. If the app crashes between the DB write and the Kafka publish, no retry logic runs -- the process is gone. Restarting the service does not replay the half-finished request. You are left in an arbitrary, silently inconsistent state.

Why "publish first, then DB" does not help

Same shape of failure, just inverted. Publish succeeds, DB write fails -- consumers see a ghost event for data that never persisted. Swapping the order changes which failure mode you get; it does not eliminate the fundamental problem.

Takeaway. Two systems with no shared transaction = inevitable inconsistency on failure. The fix is to make ONE durable write that downstream eventually observes. That is what CDC and the transactional outbox both achieve, through different mechanisms.

2. CDC (Change Data Capture)

Instead of the app publishing events, a separate process tails the database's transaction log -- Postgres WAL, MySQL binlog, MongoDB oplog -- parses changes, and publishes them to Kafka. The app only writes to the DB. One write, one system, no dual-write bug.

Tooling

  • Debezium -- Kafka Connect connectors for Postgres, MySQL, MongoDB, SQL Server, Oracle. The standard.
  • wal2json / pgoutput -- Postgres logical decoding plugins (Debezium uses pgoutput by default).
  • Maxwell's Daemon -- MySQL binlog to Kafka/JSON. Lighter than Debezium for MySQL-only shops.
  • AWS DMS, GCP Datastream -- managed CDC for cloud-native stacks.
Click "Animate CDC Flow" to see how data moves from the app through the WAL to Kafka via Debezium. The app never talks to Kafka -- only to the database.

Pros

  • Zero app-code changes -- works on any DB with logical decoding.
  • Captures every change, including manual SQL fixes or migrations.
  • Schema-aware -- Debezium emits typed Avro/JSON with full schema.
  • Single source of truth stays in the database where it belongs.

Cons

  • Requires DB log access. Postgres replication slots can fill disk if the connector lags.
  • Schema changes require care -- dropping a column breaks downstream consumers.
  • 1-2 second typical latency (log polling interval + Kafka batching).
  • Operational complexity: Kafka Connect cluster, schema registry, connector monitoring.
Takeaway. CDC is the platform team's answer. App teams write business code; the data team operates Debezium. Most consistent, lowest app friction, highest infrastructure cost. Name "Debezium" in the interview and say why.

3. Transactional Outbox

Instead of writing to two systems, the app writes to two tables in the same database transaction: the business table and an outbox table. A separate relay process polls the outbox and publishes to Kafka. Because both writes are in one transaction, they either both commit or both roll back -- atomicity for free.

The pattern

BEGIN;
  INSERT INTO orders (id, user_id, amount, status)
    VALUES ('ord-42', 'u-7', 99.99, 'created');

  INSERT INTO outbox (id, aggregate_type, aggregate_id, event_type, payload, created_at)
    VALUES (
      'evt-101',
      'Order',
      'ord-42',
      'OrderCreated',
      '{"orderId":"ord-42","userId":"u-7","amount":99.99}',
      NOW()
    );
COMMIT; -- both rows land, or neither does
Use the buttons above to animate the transactional outbox pattern. "Both commit" shows atomicity: the business row and the outbox row land in one transaction. "Rollback" shows that if either fails, both are rolled back -- no ghost events, no missing events. "Relay publishes" shows the async publishing step.

Relay variants

  • Polling-based relay: simplest implementation. A background process runs SELECT * FROM outbox WHERE processed = false ORDER BY created_at LIMIT N on a timer. Creates DB load proportional to poll frequency. Add an index on (processed, created_at).
  • CDC-on-outbox: Debezium tails the outbox table instead of all tables. Marries the two patterns -- outbox gives the app control over event schema, CDC handles publishing without polling. This is the most common modern approach.

Pros

  • Atomicity for free -- single DB transaction guarantees consistency.
  • App team owns the contract: which events get published, exact schema, versioning.
  • Survives every failure mode of dual-write.
  • Simple to understand and debug -- it is just a table.

Cons

  • App code change required (the outbox INSERT in every write path).
  • Outbox table grows; needs cleanup (DELETE after retention period, or partition by date).
  • Latency = relay poll interval + Kafka publish (seconds, not milliseconds).
  • Polling relay creates DB load; CDC-on-outbox variant eliminates this.
Takeaway. Outbox is the app team's answer. A single DB transaction guarantees consistency. The relay handles async publish; retries are safe because Kafka's idempotent producer deduplicates by producer-id + sequence. Name "transactional outbox" and the CDC-on-outbox hybrid variant.

4. Inbox (Consumer-Side Dedup)

Producer dedup (outbox + idempotent producer) is one half. The consumer side: events may arrive duplicated -- Kafka guarantees at-least-once delivery. A naive consumer applies them twice: double charge, double email, double inventory decrement.

The inbox table

-- Consumer processes each event inside a transaction:
BEGIN;

  -- Attempt to record this event as processed
  INSERT INTO inbox (event_id, processed_at)
    VALUES ($1, NOW());
  -- If PK violation -> already processed, skip

  -- Only if INSERT succeeded: do the business logic
  UPDATE accounts SET balance = balance - $amount
    WHERE user_id = $user_id;

COMMIT;

Alternative: dedup via Redis SETNX with a TTL if you do not need transactional guarantees on the consumer side.

Click "Animate" to watch three events arrive at the consumer -- two unique and one duplicate. The inbox table's primary key constraint catches the duplicate, preventing double-processing.
Takeaway. Outbox handles producer-side consistency; inbox handles consumer-side deduplication. Both are necessary for true exactly-once semantics across the wire. In the interview, mention both halves.

5. Saga + Outbox

Multi-service transactions: each service uses its own outbox to publish step-completion events. An orchestrator (or services in a choreography) reacts to those events. If a step fails, the orchestrator publishes a compensate event via its own outbox. Each service's compensate handler is idempotent (uses inbox).

Animate the happy path (all 3 steps succeed) or the compensation path (step 3 fails, triggering compensating actions in reverse order via outbox events). Each compensation handler uses an inbox table for idempotency.
Takeaway. Outbox + Inbox is the saga's foundation. Without them, sagas have hidden dual-write bugs: the service that "committed step 2" might fail to publish the completion event, leaving the saga stuck. Outbox makes each step's event publication atomic; inbox makes each compensating action idempotent.

The senior tell. When asked "how do you make sure DB write and event publish stay consistent?", the answer is "transactional outbox" or "CDC", not "we retry". Naming the dual-write problem unprompted signals you have hit it in production. Mentioning the outbox+CDC hybrid and the inbox for consumer dedup signals staff-level depth.
