SQS / SNS Messaging Patterns

Competing consumers, fan-out, request-reply, transactional outbox, priority queues. Click "Send Message," watch the flow, internalize the trade-offs.

Competing Consumers

N workers poll the same SQS queue. Each message is delivered to exactly one worker. Workers scale horizontally without coordination — the queue is the implicit load balancer.

Process time 1200ms
Three workers poll the same SQS queue. Send a message and watch exactly one worker pick it up. Burst five messages to see concurrent processing with zero coordination overhead.
Takeaways
  • Visibility timeout as distributed lock substitute: When a worker receives a message, SQS hides it for VisibilityTimeout seconds (default 30s). Other workers cannot see it. If the worker crashes before deleting it, the timeout expires and the message reappears. This is your at-least-once delivery guarantee.
  • Autoscaling: CloudWatch alarm on ApproximateNumberOfMessagesVisible triggers an ASG scale-out. Set alarm at queue depth / max_throughput_per_instance to pre-scale before backlog grows.
  • Delete = commit: Workers call DeleteMessage only after successful processing. If you delete before processing, you lose messages on crash. If processing is idempotent, at-least-once is fine.
  • Long polling (20s) reduces empty receives and API cost by up to 90% compared to short polling.

SNS Fan-out Pattern

One SNS publish fans out to all subscribed endpoints simultaneously. Producers are decoupled from the consumer topology — add a new subscriber without touching the producer.

SNS decouples the publisher from the subscriber topology. Publishing one message to the topic is all the producer ever does — SNS handles fan-out to all subscribers.
Takeaways
  • Why fan-out wins over direct multi-queue publish: Direct publish requires the producer to know every queue and write to each — coupling producer code to consumer topology. SNS fan-out means producer code never changes when you add/remove consumers.
  • SQS + SNS is the canonical durable fan-out: SNS alone (direct Lambda) is brittle — if Lambda is rate-limited or errors, the message is lost. SNS → SQS buffers fan-out delivery, giving each subscriber an independent queue with retry/DLQ.
  • Filter policies (free): Each SQS subscription can have message attribute filters. Fraud detection subscribes with amount > 1000 — SNS only delivers matching messages, reducing queue traffic for subscribers that care about subsets.
  • FIFO SNS + FIFO SQS: Available when ordering matters end-to-end. Fan-out still works but all subscribers must use FIFO SQS.

Request-Reply (Correlation ID)

Asynchronous request-reply over queues. The sender attaches a CorrelationId and a ReplyTo queue address. The worker processes and sends the response to the reply queue. The sender matches response by correlation ID.

Worker latency 1000ms
The sender publishes to the request queue with a CorrelationId and ReplyTo address. The worker consumes, processes, and sends the result to the reply queue. The sender polls its reply queue and matches responses by CorrelationId.
Approach Latency Complexity Use when
Synchronous HTTP Low (direct) Simple Sub-100ms needed, caller blocks OK
Async Queue + CorrelationId 100ms+ (polling) Timeout/cleanup logic Long-running work, decoupled deployment
Temporary queue per request ~same Queue proliferation Strict isolation, low fan-in
Shared reply queue + filter ~same Medium High concurrency, centralized cleanup
Takeaways
  • Temporary queues per request: Simple isolation but creates/destroys a queue per request — expensive at scale (SQS has queue limits). Better as a pattern for low-RPS service-to-service calls.
  • Shared reply queue + CorrelationId filter: All callers share one reply queue. Each caller polls and ignores messages that don't match its CorrelationId. Watch out: a slow or crashed caller accumulates unconsumed messages, growing the queue.
  • Timeout + cleanup: If the worker crashes, the caller must timeout, log the failure, and optionally clean up the temporary queue. Build this into your client wrapper, not ad-hoc.
  • SQS message attributes for routing: Instead of filtering in the consumer, set MessageGroupId (FIFO) or use SNS filter policies to route replies.

Transactional Outbox with SQS

The core problem: DB write and queue publish are two separate operations — they cannot be atomic without distributed transactions. The outbox pattern uses a single DB transaction to solve this.

The transactional outbox stores the event in the same DB transaction as the business write. A relay process polls the outbox and publishes to SQS. This gives you at-least-once delivery without distributed transactions.
Takeaways
  • Why not write to SQS directly in the transaction? DB and SQS are separate systems — if the DB commits but SQS publish fails (network timeout), you lose the event. If you roll back the DB on SQS failure, you need to handle partial failures. The outbox avoids this entirely.
  • At-least-once delivery: The relay may publish the same event multiple times if it crashes after publishing but before marking it sent. Consumers MUST be idempotent (check event ID before processing).
  • Debezium CDC-based outbox: Instead of polling, Debezium tails the DB binlog/WAL and streams changes. Lower latency (milliseconds vs polling interval), zero DB polling load, but requires a Kafka Connect cluster — higher operational overhead.
  • Polling interval trade-off: Short intervals (1s) add DB read load. Long intervals (30s) add latency. Exponential backoff when outbox is empty reduces load at steady state.

Priority Queue & Delay Queue

SQS has no native message priority. The standard workaround: separate queues per priority tier, with worker allocation proportional to priority.

Sim speed 1.0x
Priority simulation: high-priority queue gets 3 dedicated workers, normal gets 2, low gets 1. Workers for high-priority also drain normal when high queue is empty. Send messages and watch allocation in action.

DelaySeconds 0–900s (15 min) per message For longer delays: Step Functions Wait state or EventBridge Scheduler

FIFO queue throughput 300 msg/s (3000 with batching) Standard queue: ~unlimited. FIFO costs ordering.
Message retention 4 days default, max 14 days DLQ retention should exceed source queue retention
Takeaways
  • Priority simulation via worker ratios: 3 queues (High/Normal/Low), 6 workers — allocate 3:2:1. Workers for higher tiers steal from lower tiers when their own queue is empty. This is the SQS-idiomatic priority pattern.
  • Delay queue vs scheduled jobs: DelaySeconds up to 15 minutes. Beyond that, use EventBridge Scheduler (cron expression or one-time) or Step Functions with a Wait state.
  • Batch size vs latency: Batch of 10 cuts SQS costs 10x but adds up to 250ms of "filling time" if traffic is low. Use adaptive batching: fill the batch or fire after 250ms, whichever comes first.
  • Cost model: SQS standard = $0.40/million requests. Each SendMessage = 1 request, each ReceiveMessage (up to 10 msgs) = 1 request. Long-polling + batching are the two levers.
