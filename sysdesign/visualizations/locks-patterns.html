Coordination + concurrency patterns

Mutex, RWLock, semaphore, CAS, leader election, deadlock prevention, barriers, idempotency keys. The toolkit and the failure modes for shared-state coordination across threads, processes, and machines.

1. Mutex / RWLock / Semaphore

Mutex

1 holder at a time

RWLock

Many readers OR 1 writer

Semaphore (3 permits)

N concurrent holders

Takeaway:
  • Mutex -- exclusive access. Simple, safe, can bottleneck.
  • RWLock -- when reads dominate AND writes are rare AND writes must exclude all readers.
  • Semaphore -- bounded concurrency: connection pools, rate limiting, worker slots.

2. Optimistic vs pessimistic concurrency control

Same scenario: two clients update the same bank account balance ($1000). Client A subtracts $200, Client B subtracts $300.

Pessimistic (SELECT ... FOR UPDATE)

Balance: $1000 Lock: FREE

Optimistic (CAS / version column)

Balance: $1000 Version: 1

OCC + MVCC (Postgres snapshot isolation)

Balance: $1000 xmin/xmax tracking active
Takeaway:
  • Pessimistic = block. Guarantees no conflict but reduces throughput.
  • Optimistic = retry. Higher throughput under low contention; retry storms under high contention.
  • MVCC = engine-level optimistic control. No explicit version column needed; the DB checks tuple visibility at commit time.
  • Optimistic wins when most transactions don't collide. Pessimistic wins when they usually do.

3. CAS + lock-free patterns

Takeaway:
  • CAS = the foundation of every lock-free data structure. Read, compute, swap-if-unchanged, retry on failure.
  • ABA: value returns to original between read and CAS -- CAS succeeds incorrectly. Fix: tagged pointers (version + value).
  • Lock-free is faster on the fast path, harder to write correctly. Memory reclamation (hazard pointers, epoch-based) is the real complexity.

5. Deadlock -- detection + prevention

Wait-for graph: 4-thread deadlock

Prevention: canonical lock ordering

Livelock: mutual invalidation

Shared value: 0 Retries: 0
Takeaway:
  • Prevention via lock ordering = always works, requires discipline. Acquire locks in canonical (e.g. lexicographic) order of resource IDs. No cycle possible.
  • Detection + abort = engine-level (Postgres builds wait-for graph periodically, aborts one transaction on cycle). Transparent but costly.
  • Livelock = threads keep retrying CAS, each invalidating the other. Fix: exponential backoff with jitter.

6. Coordination primitives

Barrier (4 workers)

None proceed until all N arrive.

CountDownLatch (count=4)

Countdown to zero, then release. One-shot.

Counter: 4

Condition variable (producer-consumer)

wait() releases mutex + sleeps; notify() wakes + re-acquires.

Buffer: [ ]

Memory barrier (CPU-level)

Ordering guarantees for memory operations.

Store barrier (sfence): all stores before the barrier are visible before any store after it.

Load barrier (lfence): all loads before the barrier complete before any load after it.

Full barrier (mfence): both. Java volatile inserts full barriers. Go sync/atomic likewise.

Rarely managed directly in application code. Relevant when reasoning about volatile, AtomicReference, or sync.Once.

Takeaway:
  • Barrier = rendezvous point. All N must arrive before any proceed. Use: parallel computation phases (MapReduce shuffle boundary).
  • CountDownLatch = one-shot signal. Workers count down; waiters released at zero. Use: "wait for all services to be ready."
  • Condition variable = event subscription paired with a mutex. The fundamental building block for producer-consumer, bounded buffers, thread pools.
  • Memory barrier = CPU-level ordering. You rarely manage it directly, but you must know that volatile / atomics insert them.

7. Practical patterns library

Pattern Use case Primitive
Idempotency key Exactly-once across retries (payment, order creation) DB unique index OR Redis SETNX with TTL
Distributed mutex Cross-process critical section (migration, batch job) etcd lease + fencing token
Resource pool Bounded concurrency (DB connections, HTTP clients) Counting semaphore
Worker pool dispatch Distribute jobs to workers fairly SQS / Postgres FOR UPDATE SKIP LOCKED
Single-leader execution Exactly-once cron, scheduler, singleton service Lease-based leader election
Cross-service ordering Preserve causal order across microservices Partitioning by key (Kafka) OR sequence on resource server
Backpressure Upstream throttle when downstream is saturated Semaphore at gateway / rate-limit token bucket
The two senior signals:
  • Name the failure mode explicitly. Process pause, network partition, GC stop-the-world, clock skew. "What happens when the lock holder pauses for 30 seconds?" -- you should have an answer.
  • Mention fencing tokens whenever distributed locks come up. A lock without a fencing token is not safe: the holder can pause past its lease expiry, another node acquires the lock, and now two nodes think they hold it. The fencing token (monotonically increasing, checked by the storage layer) prevents stale writes. Most engineers don't mention this.
