Probabilistic data structures

Bloom, Cuckoo, HyperLogLog, Count-Min, t-digest. Trade some accuracy for orders-of-magnitude memory savings. The right answer to half the "how do you scale this" interview probes.

1. Bloom Filter

A space-efficient set-membership test. False positives possible; false negatives impossible. Core mechanic: a bit array of m bits and k independent hash functions.

Mechanics

Insert(x): compute h1(x), h2(x), ..., hk(x), each mod m. Set those k bits to 1.

Query(x): compute the same k hashes. If any bit is 0 → definitely not in the set. If all bits are 1 → probably in the set (false positive possible because other inserts may have set those bits).

False positive rate

FP ≈ (1 - e^(-kn/m))^k
Optimal k = (m/n) * ln(2)

Where n = number of inserted items, m = bit array size, k = number of hash functions.

Use cases

  • BigTable / Cassandra SSTable lookups -- skip files that definitely don't contain the key. Each SSTable has a Bloom filter; a miss avoids a disk read.
  • Chrome malicious URL pre-filter -- check a local Bloom filter before making a network request to the safe-browsing API.
  • CDN cache existence check -- avoid origin fetches for objects definitely not in edge cache.
  • Dedup pre-filter -- in a stream processing pipeline, skip the expensive DB lookup for items definitely not seen before.

2. Counting Bloom + Cuckoo Filter

Counting Bloom filter

Replace each bit with a 4-bit counter. Insert increments counters; delete decrements them. Supports deletion -- but at 4x the space of a standard Bloom, and counter overflow (value > 15) is possible under high load.

Trade-off: A standard Bloom at 1% FPR with 1M items needs ~1.2 MB. A counting Bloom needs ~4.8 MB for the same parameters. The extra space buys delete support -- worth it only if deletes are frequent.

Cuckoo filter

Each item maps to two candidate buckets (each bucket holds a small number of fingerprints, typically 4). Insert the fingerprint into either bucket. If both are full, evict a resident fingerprint and re-place it at its alternate bucket. Eviction can cascade (up to a max depth, typically 500 kicks).

Advantages over Bloom: supports proper delete (remove fingerprint), achieves lower FPR for the same space at typical filter loads, and avoids the "k hash functions" overhead.

3. Scalable Bloom Filter

Problem: if n grows beyond the initial sizing, FPR degrades. You either over-provision (waste memory) or accept worse accuracy.

Solution: chain of Bloom filters. When the active filter reaches its capacity, create a new one with 2x capacity and a tighter per-filter FPR (each successive filter uses FPR * r^i where r < 1, typically 0.5). The compounded total FPR across all filters stays near the original target.

Insert

Always insert into the newest (active) filter. When it's full, allocate the next filter.

Query

Check all filters. If any says "probably yes," report present. Only if all say "no" do we report absent. Query cost grows with the number of filters, but the chain typically stays short (log-scale).

4. HyperLogLog (Distinct Count)

Goal: estimate |distinct(stream)| with ~12 KB constant memory at ~1.6% standard error. Exact distinct counting requires O(n) memory; HLL trades accuracy for constant space.

Mechanics

Hash each item to a uniform bit string. Split into two parts:

  1. First p bits: register index (2^p registers, typically p=14 → 16,384 registers).
  2. Remaining bits: count leading zeros + 1. Track the maximum value seen per register.

Intuition: seeing a hash with k leading zeros is a 1/2^k event. If your max leading zeros is 20, the stream probably has ~2^20 distinct items. Multiple registers + harmonic mean + bias correction make it robust.

E = alpha_m * m^2 * (sum of 2^(-M[j]) for j=0..m-1)^(-1)
where m = number of registers, M[j] = max leading zeros in register j

  • Redis PFADD / PFCOUNT -- native HLL support. Count unique visitors with 12 KB per counter.
  • Analytics -- "unique users today" without storing all user IDs.
  • BigQuery APPROX_COUNT_DISTINCT -- HLL under the hood; returns in seconds vs. minutes for exact count.
  • Network monitoring -- count distinct source IPs per destination at line rate.

5. Count-Min Sketch (Frequency Estimation)

A matrix of counters: d rows x w columns. Each row has its own hash function.

Mechanics

Insert(x): for each row i, increment counter[i][hash_i(x) % w].

Query(x): for each row i, read counter[i][hash_i(x) % w]. Return the minimum across all rows.

The minimum is the best estimate because collisions only increase counts, never decrease. So the true count ≤ returned estimate. CMS always over-estimates, never under-estimates.

Error bound: with probability 1 - delta,
estimated_count(x) ≤ true_count(x) + epsilon * N
where w = ceil(e / epsilon), d = ceil(ln(1 / delta)), N = total inserts

Use cases

  • Heavy-hitter detection -- find top-K most frequent items in a stream without storing all items.
  • Rate limiting / throttling -- approximate per-user request counts with fixed memory.
  • Network monitoring -- track per-flow byte counts at router line rate.
  • Trending detection -- identify trending hashtags/terms in a social feed.

6. t-digest (Percentile Estimation)

Goal: streaming p50/p99/p999 estimation with ~1 KB memory and high accuracy at the tails (where it matters most).

Mechanics (high-level)

A t-digest maintains a set of centroids (weighted means). The key insight: bin density adapts to position on the CDF. Bins near the edges (p0, p1, p99, p100) are small and precise; bins in the middle (p40-p60) are large and coarse. This matches interview reality: nobody asks "what's your p50 to three decimals?" -- they ask about p99 and p999.

Merge-friendly: two t-digests can be merged by combining their centroids and re-compressing. This makes t-digest ideal for distributed systems where each node computes a local digest, then merges at aggregation time.

Use cases

  • Distributed metrics aggregation -- M3DB, OpenTSDB, Elasticsearch aggregations.
  • Prometheus histogram alternatives -- t-digest avoids fixed bucket boundaries.
  • Latency monitoring -- compute p99 across thousands of service instances with ~1 KB per counter.
  • A/B testing -- compare percentile distributions without storing all observations.

Bloom alternatives at very low FPR: Xor filters (faster lookup, ~1.23 bits/item overhead, immutable after build) and Ribbon filters (smaller, ~1.005 bits/item overhead, used in RocksDB). Both are static -- no insert after construction.

The senior tell. "I'd front the lookup with a Bloom filter to skip the slow path for misses" -- that's the canonical use. For "unique counts in streams" → HLL. For "is this URL on the malicious list" → Bloom or Cuckoo. For "top-K in a stream" → Count-Min Sketch. For "p99 latency across 1000 nodes" → t-digest. The interview probe is naming the structure for the access pattern.
