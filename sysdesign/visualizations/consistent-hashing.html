Consistent Hashing

The ring, virtual nodes, and the "only 1/N keys move" property — visualized.

A distributed cache or KV store needs to answer two questions: (1) given a key, which node owns it? (2) what happens to ownership when a node joins or leaves? Naive hash(key) % N answers (1) cleanly but makes (2) catastrophic — change N and ~all keys remap. Consistent hashing decouples them: ownership shifts only at the boundary between the new node and its neighbors.

1. The ring (raw, no vnodes)

Hash both keys and nodes into the same fixed-size space. Visualize as a ring (positions modulo the space). Each key is owned by the first node clockwise from the key's position. Below: 4 nodes (A, B, C, D) at the angles they happened to hash to. 12 keys (k1–k12) placed by hash. Each colored arc shows the region of keys owned by one node.

Node A Node B Node C Node D

4 random points on a ring don't divide it into 4 equal arcs. Here C owns 35% of keys while B owns only 14% — a 2.5× spread. With a small N, variance is real and you'll feel it in cache hit rates.

2. Virtual nodes — variance fix

Each physical node owns many ring positions (vnodes). Cassandra's default is 256; below we use 6 per physical for clarity (4 × 6 = 24 vnodes total). Each physical node is colored consistently across all its vnodes. The law of large numbers smooths the distribution: each physical owns ~25% of keys.

Same 4 physical nodes; ownership is now perfectly even by construction. Tune V (vnodes per physical): below ~64, variance shows; above ~512, ring memory grows without further smoothing. Cassandra ships with 256 — the empirical sweet spot.

3. Node add — only 1/N keys move

Back to the simple 4-node ring (no vnodes, for clarity). We add a 5th node E at angle ≈2.5 — landing inside C's big arc. E now owns the keys in (1.2, 2.5]; C shrinks to (2.5, 3.4]. Of the 12 keys, only 3 move (k4, k5, k6 → E). Other arcs are completely undisturbed.

This is the property. When a 100-node cache adds the 101st node, only ~1% of cache entries reshuffle — not 99% as hash(key) % N would force. The cache stays warm during scale events. Same property keeps Cassandra/Dynamo cluster expansions cheap and online.

Variants — pick by use case

Variant Lookup Balance Topology change cost Use case
Plain ring O(log N) Poor with few nodes Cheap, incremental Pedagogical / small clusters
Ring + vnodes (V≈256) O(log NV) Good Cheap, incremental Default for storage: Cassandra, Dynamo, Scylla, Redis Cluster
Bounded-load O(log NV) + retry Bounded max load Cheap, incremental LBs with hot-key skew (Envoy)
Maglev (Google) O(1) Near-perfect Full table rebuild Default for L4/L7 LBs: GLB, Envoy
Bucket-based (Riak, Vitess) O(1) bucket lookup Fixed pre-allocated Per-bucket migration When tooling needs explicit bucket boundaries
