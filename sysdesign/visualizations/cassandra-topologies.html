Cassandra topologies

The ring with vnodes, RF, NetworkTopologyStrategy, R+W>N tunable consistency, multi-DC, gossip + phi accrual. No leader, no master, no single point of anything. Click consistency levels, watch reads return stale or strong.

The Ring (Single DC, Vnodes)

Cassandra uses the Murmur3 partitioner: hash(partition_key) produces a 64-bit signed token in [-2^63, 2^63 - 1]. Tokens are arranged on a ring. Each vnode owns the range from the previous vnode's token (exclusive) up to its own token (inclusive), walking clockwise. Every node is equal -- there is no leader. The coordinator is whichever node the client happens to connect to for this request.

Type a partition key and click "Hash + Route" to trace the path: Murmur3 hash -> token -> vnode -> physical node.
No leader. Every node is equal. The coordinator is whoever the client connects to for this request. With TokenAwarePolicy, the driver picks the coordinator that owns the token -- zero network hops to the right node.
Takeaways
  • Coordinator can be any node -- pick the one closest (TokenAwarePolicy) for fewer hops.
  • Vnodes randomize token placement for balanced load. Default 256 vnodes/node; we show 6 for clarity.
  • Murmur3 distributes evenly because partition keys are usually low-entropy strings -- the hash function compensates.

Replication (RF + Strategies)

Each token's owner is the primary replica. The next RF-1 distinct physical nodes clockwise hold additional replicas. With RF=3, every partition lives on 3 nodes -- losing one node still leaves 2 copies.

Partition key -> replicas

Type a partition key to see which 3 nodes hold replicas.
SimpleStrategy picks replicas by walking clockwise to the next distinct physical nodes. NetworkTopologyStrategy does the same but also ensures replicas land in different racks -- so losing a rack costs at most 1 replica per partition, not all of them.
Takeaways
  • RF=3 with NetworkTopologyStrategy + rack-aware allocation = canonical production setup.
  • Strategy is per-keyspace, not cluster-wide -- different tables can use different strategies.
  • SimpleStrategy is fine for dev/test or single-rack. Production multi-rack always uses NetworkTopologyStrategy.

Tunable Consistency (R + W > N)

Cassandra's killer feature: per-query consistency level (CL). You choose, per read and per write, how many replicas must acknowledge. The magic formula: if R + W > N (where N = RF), you are guaranteed to read the latest write -- at least one replica participated in both the write and the read.

QUORUM = ceil(RF/2) + 1 = 2 for RF=3. With W=QUORUM and R=QUORUM, R+W = 4 > 3 = N. Guaranteed strong consistency. This is the standard production setting -- balanced between fast reads and fast writes.
Takeaways
  • R + W > N = guaranteed read-your-writes. The overlap ensures at least one replica has the latest data.
  • QUORUM + QUORUM = the standard production setting (balanced fast read + fast write + strong).
  • W=ALL + R=ONE = strong but slow writes, fast reads. W=ONE + R=ALL = fast writes, slow reads. Both are R+W=4>3.
  • CL=ANY (write only) = fire and forget -- even hinted handoff counts as ack. Do not use unless you truly mean it.

Multi-DC (NetworkTopologyStrategy + LOCAL_QUORUM)

Two DCs, each with 4 nodes. RF = {DC1: 3, DC2: 3}. Writes to DC1 fan out to local replicas AND async to DC2 replicas. LOCAL_QUORUM requires quorum only within the local DC -- the cross-DC leg is asynchronous, keeping latency low.

Cross-DC delay 120ms
LOCAL_QUORUM: coordinator waits for quorum in its own DC, then returns success. The cross-DC leg is asynchronous. This is the multi-DC default -- low latency for the client, eventual consistency across DCs.
Takeaways
  • LOCAL_QUORUM is the multi-DC default. Do not use cross-DC QUORUM in the hot path.
  • Hinted handoff is best-effort, not durable -- it has a TTL (default 3 hours). If a DC is down longer, run nodetool repair.
  • Repair (nodetool repair) is the maintenance task; read repair is the runtime fix. Both are needed.

Gossip + Failure Detection

Every node picks a random peer once per second and exchanges endpoint state (heartbeat generation, schema version, token ownership). There is no master deciding who is up -- it is emergent from gossip. The phi accrual failure detector tracks inter-arrival times of heartbeats; when time-since-last-heartbeat exceeds a phi threshold (default phi=8), the peer is marked DOWN.

Gossip is Cassandra's membership protocol. Every second, each node picks a random peer and exchanges state. No central authority decides who is alive -- every node independently tracks heartbeat inter-arrival times using the phi accrual failure detector.
Takeaways
  • Gossip = eventually consistent membership view. Convergence in ~1-3 seconds for small clusters.
  • Phi accrual = adaptive failure detector. More robust than simple timeout because it adapts to network conditions -- fewer false positives on transient lag.
  • There is no master deciding who is up -- it is emergent from gossip. Each node independently decides.
