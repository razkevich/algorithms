Thread State Machine

A Java thread moves through six states defined in Thread.State. The JVM enforces these transitions — you cannot skip states.

Press Step to walk through thread state transitions with triggering method calls.

State definitions

StateMeaningHow to enter
NEWThread object created, not startednew Thread(...)
RUNNABLEEligible to run (may or may not be on CPU)t.start()
BLOCKEDWaiting to acquire a monitor lockEntering a synchronized block held by another thread
WAITINGIndefinitely waiting for another thread's signalwait(), join(), LockSupport.park()
TIMED_WAITINGWaiting with a timeoutsleep(ms), wait(ms), join(ms)
TERMINATEDrun() returned or threw unchecked exceptionNormal/exceptional completion
Key insight:
  • BLOCKED vs WAITING: BLOCKED = waiting for a lock; WAITING = voluntarily giving up CPU until notified.
  • interrupt() on WAITING/TIMED_WAITING throws InterruptedException; on BLOCKED it just sets the interrupted flag.
  • A thread can only be started once — calling start() again throws IllegalThreadStateException.

Java Memory Model (JMM)

Each CPU core has its own cache. Without synchronization, writes by Thread A may never be visible to Thread B. The JMM defines happens-before rules that guarantee visibility.

Click Animate Visibility Bug to see Thread A write a value that Thread B never sees due to CPU cache isolation.

Happens-before guarantees

RelationshipGuarantee
Program orderWithin one thread, statement N happens-before N+1
Monitor lockunlock() of a monitor HB lock() of the same monitor by any thread
volatile write → readWrite to a volatile field HB every subsequent read of that field
Thread startt.start() HB any action in thread t
Thread joinAll actions in thread t HB t.join() returning in the joiner
Static initializerClass init HB first use of that class by any thread
Object constructionWrites in a constructor HB a final field read via a reference published safely
Interview line: "The JMM says nothing about memory addresses — it defines a partial order on actions. If action A happens-before B, A's effects are visible to B. Without a HB edge, the JVM and CPU are free to reorder and cache anything."

synchronized — Intrinsic Lock (Monitor)

Every Java object has an intrinsic lock (monitor). synchronized acquires it on entry and releases it on exit — even if an exception is thrown.

synchronized method

public synchronized void increment() {
  count++;  // lock = this
}

Lock object is this. All synchronized methods on the same instance contend on the same lock.

synchronized block

private final Object lock = new Object();
public void increment() {
  synchronized (lock) {
    count++;
  }
}

Explicit lock object — finer granularity, avoids contention across unrelated operations.

Click Animate to see two threads competing for the intrinsic lock, demonstrating mutual exclusion and the BLOCKED state.

Reentrancy

Java's intrinsic lock is reentrant: if the thread that already holds the lock tries to acquire it again, it succeeds (with an internal hold count). This lets synchronized methods safely call other synchronized methods on the same object.

synchronized void outer() {
  inner();  // same thread, already holds lock → succeeds
}
synchronized void inner() { ... }

volatile

volatile gives visibility (write flushes to main memory, read always fetches from main memory) but not atomicity. It is not a lock — no mutual exclusion.

Where volatile suffices

  • Single-writer, multiple readers
  • Simple boolean flags (volatile boolean running)
  • Publishing an immutable object reference

Where volatile is NOT enough

  • Read-modify-write: count++ (read, increment, write — not atomic)
  • Check-then-act patterns
  • Any compound action requiring atomicity

Double-Checked Locking — Bug → Fix

BROKEN (pre-Java 5 or missing volatile): 
private static Singleton instance;
public static Singleton getInstance() {
  if (instance == null) {             // read stale null
    synchronized (Singleton.class) {
      if (instance == null)
        instance = new Singleton(); // partially constructed!
    }
  }
  return instance;
}
Problem: JVM can reorder constructor writes and the assignment. Thread B sees a non-null but incompletely initialized object.
FIX — add volatile: 
private static volatile Singleton instance;
// volatile write creates happens-before with every subsequent volatile read
// → construction completes before reference is published
  • volatile on the reference prevents reordering of constructor writes past the store.
  • Better alternative: initialization-on-demand holder idiom (classloader guarantees safety).

ReentrantLock

Same semantics as synchronized but with more capabilities. Must manually unlock() — always in a finally block.

Key APIs over synchronized

  • tryLock() — non-blocking attempt
  • tryLock(time, unit) — timed attempt
  • lockInterruptibly() — abortable wait
  • newCondition() — multiple condition queues
  • Fair mode: new ReentrantLock(true)

Canonical pattern

Lock lock = new ReentrantLock();
lock.lock();
try {
  // critical section
} finally {
  lock.unlock(); // ALWAYS
}

Fair vs Unfair

Fair (true) = FIFO order → no starvation, lower throughput. Unfair (default) = barging allowed → higher throughput, possible starvation. Default unfair for most use cases.

ReadWriteLock

Multiple readers can hold the read lock simultaneously. The write lock is exclusive — blocks all readers and other writers.

Click to simulate concurrent readers and an exclusive writer contending on a ReadWriteLock.
ReadWriteLock rwl = new ReentrantReadWriteLock();
Lock r = rwl.readLock();
Lock w = rwl.writeLock();

// reader
r.lock(); try { return data; } finally { r.unlock(); }
// writer
w.lock(); try { data = x; } finally { w.unlock(); }
Pitfall: You cannot upgrade a read lock to a write lock without releasing the read lock first (deadlock risk). Use StampedLock for optimistic patterns.

StampedLock (Java 8+)

Non-reentrant lock with optimistic reads. Returns a stamp (long) on acquire; validate the stamp before using the data.

StampedLock sl = new StampedLock();

// Optimistic read — no lock acquired
long stamp = sl.tryOptimisticRead();
int x = field;
if (!sl.validate(stamp)) {        // a write happened?
  stamp = sl.readLock();          // fall back to real read lock
  try { x = field; }
  finally { sl.unlockRead(stamp); }
}
StampedLock payoff: Under read-heavy workloads, optimistic reads incur zero contention — just a stamp validation. Good for CPU-bound hot paths. Not reentrant — never call from synchronized context.

Condition Variables

Condition objects decouple "condition not met" (await) from "condition changed" (signal). One lock can have multiple conditions — unlike a single wait()/notifyAll() queue.

Lock lock = new ReentrantLock();
Condition notFull  = lock.newCondition();
Condition notEmpty = lock.newCondition();

// Producer
lock.lock(); try {
  while (full()) notFull.await();
  enqueue(item);
  notEmpty.signal();
} finally { lock.unlock(); }

// Consumer
lock.lock(); try {
  while (empty()) notEmpty.await();
  T item = dequeue();
  notFull.signal();
} finally { lock.unlock(); }
Two-condition trick: LinkedBlockingQueue uses exactly this — one condition per end of the queue. notifyAll() on a single monitor wakes every waiter (spurious wakeup amplified); two conditions wake only relevant waiters.

Lock-Free Counters — AtomicInteger

The java.util.concurrent.atomic package provides lock-free thread-safe variables backed by CPU-level CAS (compare-and-swap) instructions.

Core operations

AtomicInteger ai = new AtomicInteger(0);
ai.incrementAndGet();   // ++i
ai.getAndIncrement();   // i++
ai.addAndGet(5);         // i+=5
ai.compareAndSet(3,4); // CAS
ai.updateAndGet(x->x*2);

AtomicReference

AtomicReference<Node> head =
  new AtomicReference<>(null);
// Lock-free push
do {
  Node old = head.get();
  newNode.next = old;
} while (!head.compareAndSet(old, newNode));

How CAS works

CAS(addr, expected, desired) is a single atomic CPU instruction: if *addr == expected, write desired and return true; else return false. No lock needed — contention just causes a retry loop.

ABA Problem

ABA: Thread 1 reads value A. Thread 2 changes A→B→A. Thread 1 CAS succeeds (sees A) but misses the intermediate change. 
// Fix: AtomicStampedReference
AtomicStampedReference<Node> ref =
  new AtomicStampedReference<>(node, 0);
int[] stamp = new int[1];
Node n = ref.get(stamp);
ref.compareAndSet(n, newNode, stamp[0], stamp[0]+1);
The stamp (version counter) increments on every write — ABA becomes A(0)→B(1)→A(2), CAS fails correctly.

LongAdder vs AtomicLong

Under high contention, CAS loops on a single cell cause CPU cache-line bouncing. LongAdder uses a striped cell array — threads update different cells; sum() aggregates them.

VarHandle (Java 9+)

VarHandle provides CAS and memory-order operations on plain fields without boxing. Used internally by JDK classes. Replaces AtomicReferenceFieldUpdater — same performance, better API.

VarHandle VH = MethodHandles.lookup()
    .findVarHandle(MyClass.class, "count", int.class);
VH.compareAndSet(obj, expected, newVal);
VH.setVolatile(obj, 42);
Rule of thumb:
  • Simple counters under load → LongAdder
  • Need exact value or CAS semantics → AtomicLong
  • Lock-free data structures → AtomicReference + CAS loop
  • Memory-efficient field updates → VarHandle

Semaphore — Permit Pool

A semaphore holds N permits. acquire() blocks until a permit is available; release() returns one. Perfect for connection pools, rate limiting.

Click Start to simulate 6 threads competing for a semaphore with 3 permits (e.g. a connection pool of size 3).
Semaphore pool = new Semaphore(3); // 3 permits
pool.acquire();
try { // use resource }
finally { pool.release(); }

CountDownLatch — One-Shot Gate

One or more threads wait at a gate until N other threads complete their work. Once count reaches 0, all waiters are released. Cannot be reset.

Click to see 4 worker threads count down a latch — the main thread unblocks when all workers finish.
CountDownLatch latch = new CountDownLatch(4);
// In each worker:
latch.countDown();
// Main thread:
latch.await(); // blocks until count == 0

CyclicBarrier — Reusable Rendezvous

All N parties must reach the barrier before any proceeds. Resets automatically after release — unlike CountDownLatch. Optional barrier action runs once when all parties arrive.

Click to simulate 3 threads running 2 phases — each phase requires all threads to reach the barrier before any advances.
CyclicBarrier barrier = new CyclicBarrier(3, () ->
    System.out.println("Phase complete!"));
// In each thread:
barrier.await(); // blocks until all 3 arrive

Phaser — Dynamic Multi-Phase

Phaser = flexible CyclicBarrier. Parties can register/deregister dynamically. Phase number advances after each barrier. Supports hierarchical phasers for large party counts.

Phaser phaser = new Phaser(1); // 1 registered (main thread)
phaser.register();           // dynamic worker registration
phaser.arriveAndAwaitAdvance(); // wait for phase
phaser.arriveAndDeregister(); // worker done
phaser.arrive();              // don't wait, just signal

Interview heuristic:
  • CDL = "fan-in": many threads → one waiter. Barrier = "synchronize": all threads meet and resume together.
  • Phaser is the generalization of both — but reach for CDL/CyclicBarrier first; they communicate intent clearly.
  • Semaphore is the only synchronizer that works across threads that don't know about each other (acquire in one thread, release in another).
