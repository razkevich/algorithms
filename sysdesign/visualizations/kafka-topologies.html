Kafka topologies

Brokers + KRaft, ISR replication, producer acks, consumer groups, the rebalance protocol that's the source of so many production incidents. Click "kill leader," watch failover. Pick acks=1, watch a message disappear.

Broker Cluster + KRaft Controller Quorum

5 brokers. Topic events with 4 partitions, replication factor 3. Three brokers double as KRaft controller-eligible nodes; one is the active controller leader.

Each partition is a single-writer (leader) replicated log. Brokers 0, 1, 2 are controller-eligible. B0 is the active KRaft controller leader -- it owns metadata changes (partition assignment, leader election, broker membership). The metadata log is replicated via Raft among the controller quorum.
Takeaway
  • Each partition has exactly one leader broker that handles all reads and writes for that partition. Followers replicate via pull (FetchRequest).
  • The cluster has ONE active controller that owns metadata changes. In KRaft mode, metadata lives in an internal Kafka log replicated via Raft -- no external ZooKeeper needed.
  • KRaft wins: simpler ops (no separate ZK cluster), faster controller failover (Raft election vs ZK ephemeral node expiry), better scalability (millions of partitions).

Producer: Partitioning, Acks, Idempotence

3 producers writing to topic events with 4 partitions. Partitioning determines which partition a record goes to. Acks determine durability guarantees.

With a key present, partition = hash(key) % numPartitions -- all records with the same key go to the same partition, preserving ordering per key. The sticky partitioner (default since 2.4) batches keyless records to one partition until the batch fills, then switches -- reducing the number of in-flight batches and network round-trips.
Takeaway
  • acks=all + idempotent producer + min.insync.replicas=2 = no data loss with normal failures. This is the default in modern Kafka stacks.
  • Idempotent producer: each producer gets a PID; each (partition, PID, sequence) is deduped at the broker. Prevents duplicates from retries at zero throughput cost.
  • Compression (lz4/zstd) is per record batch. Compresses on producer, stays compressed on broker disk, decompresses on consumer. Reduces network + disk at the cost of CPU.

Consumer Groups + Rebalance Protocol

Topic with 6 partitions. Consumer group g1 starts with 3 consumers. Each partition is assigned to exactly one consumer in the group. Watch what happens when you add a 4th consumer -- and the difference between eager and cooperative-sticky rebalance.

Consumer group = parallelism unit. Each partition is consumed by exactly one consumer in the group. With 3 consumers and 6 partitions, each consumer handles 2 partitions. Consumers heartbeat to the group coordinator (a broker) to signal liveness.
Takeaway
  • Number of consumers in a group cannot exceed number of partitions -- extras sit idle. This is the scaling ceiling for a single consumer group.
  • Cooperative-sticky rebalance (default in modern Kafka): only the partitions that need to move are reassigned; other consumers keep consuming without pause. Eager rebalance stops ALL consumers for full reassignment -- visible as a "rebalance storm" under high churn.
  • Auto-commit risks duplicate processing: consumer processes records, crashes before commit interval, new consumer re-processes from last committed offset. Manual commitSync after processing gives at-least-once semantics with tighter control.

Replication + ISR (In-Sync Replicas)

One partition with leader on B0 + followers on B1 and B2. Followers fetch from the leader via FetchRequest (pull model). Only data at or below the high watermark (HW) is visible to consumers.

Happy path: producer sends to leader B0. B0 appends to local log. Followers B1 and B2 issue FetchRequests and replicate. Once all ISR members have the record, B0 advances the high watermark (HW). Only records at or below HW are visible to consumers.
Takeaway
  • ISR is the durability set. A follower that lags beyond replica.lag.time.max.ms (default 30s) is removed from ISR. min.insync.replicas blocks producer writes when ISR shrinks below the threshold.
  • Leader election picks from ISR only (by default). The new leader is the ISR member with the highest replicated offset.
  • Unclean leader election (default OFF): if all ISR members are dead and a non-ISR replica is alive, electing it causes data loss -- its log is behind. Keep it OFF unless you explicitly trade durability for availability.

Tiered Storage (KIP-405)

Hot data lives on broker local disk. Cold data (older than the local retention threshold) is offloaded to remote object storage (S3 / GCS / Azure Blob). Same Kafka API -- transparent to clients.

Tiered storage separates retention cost from broker disk capacity. Recent segments stay on fast local disks. Older segments are copied to cheap object storage. Consumers reading recent data see no difference; consumers reading cold data pay higher latency but the data is still accessible through the standard Kafka consumer API.
Takeaway
  • Pro: cheap long retention (compliance, replay-from-archive, ML retraining). Broker disk is no longer the retention bottleneck.
  • Con: read latency on cold tier (S3 GET latency ~50-200ms vs local disk ~1ms). Not suitable for latency-sensitive real-time consumers reading old data.
  • Use case: event sourcing replay, audit logs, regulatory retention (7+ years), training data pipelines. The hot/cold boundary is configured per topic via local.retention.ms.
