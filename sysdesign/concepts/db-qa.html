§ 01  PostgreSQL
Relational · Single-primary · MVCC

PostgreSQL

The default answer that’s correct more often than people admit.

ACID SERIALIZABLE JSONB Vertical-first

Postgres is an ORDBMS with a single primary, MVCC concurrency, full SQL, and an extension model so deep it has become its own ecosystem (PostGIS, pgvector, TimescaleDB, Citus). It’s the system you reach for when you don’t yet know your access patterns, because it can answer almost any query you write tomorrow.

It is not a horizontally-scaled OLTP system out of the box: writes go to one primary, period. You scale reads with replicas, partition large tables, route by tenant, or graduate to a Postgres-compatible distributed engine (Aurora, CockroachDB, Yugabyte) when you actually need it.

The 30-second pitch: “Postgres for the source of truth. Replicas for read scale. Partitions and BRIN for time-series. JSONB + GIN where the schema is genuinely sparse. Reach for distributed Postgres only when a single primary can’t hold the write load.”

Q&A drills

Walk me through what happens when you run SELECT * FROM users WHERE email = ?.

One sentence: the parser produces an AST, the planner enumerates plans by cost, the executor pulls tuples through nodes, and visibility is filtered by MVCC.

Concept: Postgres’ query lifecycle is parse → rewrite → plan → execute. The planner uses statistics from pg_statistic (collected by ANALYZE) and chooses among Seq Scan (read every page), Index Scan (random heap fetches via index), and Bitmap Index Scan (collect TIDs in memory, then sort and read pages sequentially — the win when an index returns many but not all rows).

Nuance: the planner picks Bitmap when selectivity is in the awkward middle (~1–10% of rows). Seq Scan beats Index Scan when nearly all rows match because random I/O kills throughput. EXPLAIN (ANALYZE, BUFFERS) is the correct tool; BUFFERS tells you cache vs. disk.

EXPLAIN (ANALYZE, BUFFERS, VERBOSE)
SELECT * FROM users WHERE email = 'a@b.com';
What is MVCC and why does VACUUM matter? When does autovacuum fall behind?

One sentence: MVCC keeps multiple versions of each row so readers never block writers, and VACUUM reclaims dead versions once no transaction can see them.

Concept: every tuple has xmin (creating txn) and xmax (deleting txn). An UPDATE writes a new tuple version and marks the old one dead. Without VACUUM, dead tuples accumulate (bloat): tables grow, sequential scans slow down, and indexes get fat. Autovacuum runs in the background based on autovacuum_vacuum_threshold + a fraction of table size.

Nuance: autovacuum falls behind when a long-running transaction (or replication slot) holds the visibility horizon back — vacuum can’t reclaim tuples that any live snapshot might still see. Symptoms: monotonically growing tables, n_dead_tup climbing in pg_stat_user_tables. Fix: kill the long txn, set idle_in_transaction_session_timeout, monitor pg_stat_activity for old xact_start, drop unused replication slots.

Wraparound: xid is 32-bit; if VACUUM never runs, you eventually hit transaction-id wraparound and Postgres shuts down to save you. Real outage cause; autovacuum mostly handles it now but the boogeyman is real.

Difference between Read Committed, Repeatable Read, and Serializable. Which is default?

One sentence: Read Committed (default) sees each statement’s own snapshot; Repeatable Read sees one snapshot for the whole txn; Serializable adds true serialization via SSI.

Concept: in Read Committed, two SELECTs in the same txn can see different data — non-repeatable reads happen. Repeatable Read in Postgres is implemented as snapshot isolation: stable view, but vulnerable to write skew (two txns each read data the other hasn’t modified yet, then both write). Serializable = SSI (Serializable Snapshot Isolation), which detects rw-dependency cycles and aborts one txn with 40001 serialization_failure.

Nuance: SSI is one of the few production-grade serializable implementations. Cost: aborts under contention — you must retry the transaction. Saying “Postgres is fully ACID” without picking the level is a yellow flag at staff level. The right answer cites a use case: “Default is Read Committed; for a transfer between accounts I’d use Serializable and a retry loop.”

BEGIN ISOLATION LEVEL SERIALIZABLE;
-- ... reads, writes ...
COMMIT;  -- may raise 40001; retry on the client
Streaming replication vs logical replication — when each?

One sentence: streaming ships raw WAL byte-for-byte (physical, whole-cluster); logical decodes WAL into per-row change events and replicates per-table.

Concept: streaming gives you a binary clone — same OS, same Postgres major version, no schema flexibility. Logical (built on pgoutput + replication slots since 10) lets you replicate selected tables, do zero-downtime major-version upgrades, run cross-version replicas, and feed CDC pipelines (Debezium).

Nuance: logical has gotchas — replication slots can pin WAL on the primary forever if a subscriber falls behind, filling disk. DDL is not replicated. Sequences are not advanced on the subscriber until a write triggers them. Large transactions are buffered until commit (Postgres 14+ supports streaming-in-progress).

-- on primary
SELECT pg_create_logical_replication_slot('cdc', 'pgoutput');
-- monitor lag and disk
SELECT slot_name, pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn))
FROM pg_replication_slots;
Index types: when do you reach for B-tree, GIN, GiST, BRIN, hash?

One sentence: B-tree for ordered equality/range, GIN for sets/JSONB/FTS, GiST for geometric/fuzzy, BRIN for huge sequential tables, hash almost never.

Concept: B-tree is the default — equality, range, ORDER BY. GIN (generalized inverted index) maps each element to the docs that contain it — perfect for jsonb containment (?, @>), arrays, and tsvector. GiST is a generalized search tree for geometric (PostGIS), nearest-neighbor, and trigram similarity (pg_trgm). BRIN stores min/max per block range — tiny index, great for naturally-clustered time-series; useless if data is unordered.

Nuance: hash indexes finally became WAL-logged in PG 10, but B-tree on the same column is almost always a better default. Partial indexes (WHERE deleted_at IS NULL) and covering indexes (INCLUDE (col)) are massive wins most candidates forget. pgvector adds ivfflat and hnsw for ANN search.

How do you scale Postgres horizontally? When does sharding actually become necessary?

One sentence: you don’t scale Postgres horizontally for writes natively — you scale reads with replicas, partition by range/hash, route by tenant, and graduate to Citus or a distributed-Postgres engine when one primary genuinely can’t hold the write rate.

Concept: a modern primary on decent hardware does 50–100k+ TPS comfortably. Most “we need to shard” conversations are actually about: hot tables that need partitioning, missing indexes, connection storms (fix with PgBouncer in transaction-pooling mode), or vacuum bloat.

Nuance: when you do need horizontal write scale, the choices are: Citus (multi-tenant, distributed tables by hash), app-level sharding (own the routing, accept the pain on cross-shard queries), or distributed Postgres-compat (Aurora Limitless, CockroachDB, Yugabyte, Spanner-style). The interview answer: “I’d exhaust vertical + replicas + PgBouncer + partitioning before I shard. Most teams shard prematurely.”

When does JSONB beat a normalized schema, and when does it bite?

One sentence: JSONB wins for sparse, polymorphic, or rapidly-evolving payloads; it bites when those fields become first-class query targets.

Concept: JSONB is decoded, indexable (GIN), supports operators (->, ->>, @>, ?). Great for “config blob” or “catalog with optional attributes.” Bad when you start filtering, aggregating, joining on inner keys at scale — the planner has limited stats on JSONB internals, and you lose the type system.

Nuance: the right pattern is hybrid: promote frequently-queried keys to columns (with constraints, indexes, FK), keep the rest in JSONB. Generated columns (GENERATED ALWAYS AS (data->>'k')) materialize a JSON path into an indexable column. Don’t treat Postgres-with-JSONB as “Mongo with SQL” — that loses both worlds.

CREATE INDEX idx_doc_tags ON docs USING GIN ((data->'tags'));
SELECT * FROM docs WHERE data @> '{"tags":["sale"]}';
Connection pooling: why does Postgres need it, and what’s the difference between PgBouncer modes?

One sentence: Postgres uses a process per connection — ~10MB each — so 1000 app connections = 10GB of RAM and a context-switching nightmare; PgBouncer multiplexes thousands of clients onto a small pool of server connections.

Concept: PgBouncer modes: session (client owns a server connection until disconnect — safe for everything but no benefit), transaction (server connection released at COMMIT — the workhorse), statement (released after each statement — restrictive).

Nuance: transaction mode breaks anything that uses session state — SET, prepared statements, LISTEN/NOTIFY, advisory locks across statements, temp tables. Most ORMs work fine if you turn off named prepared statements. PG 14+ has built-in support for protocol-level prepared statements that survive transaction pooling. pgcat and the new pg_bouncer features narrow the gap further.

Design a high-write audit log table that needs to retain 2 years of data and answer time-range queries fast.

One sentence: declarative range partitioning by month, BRIN index on created_at, B-tree on actor_id, drop old partitions instead of deleting rows.

Concept: a single 2-year table with B-tree on time would have a 50+GB index and slow vacuum. Range partitioning by month gives you ~24 child tables; old months can be detached and archived in O(1). BRIN on created_at is tiny because rows are naturally ordered.

Nuance: use pg_partman to automate partition creation and retention. Watch out for partition pruning — queries must include the partition key in the WHERE for pruning to work; EXPLAIN tells you which partitions were scanned. For really high write rate, also batch inserts (COPY or multi-row INSERT) and consider unlogged tables for the staging step.

CREATE TABLE audit (
  id BIGSERIAL, actor_id BIGINT, action TEXT,
  created_at TIMESTAMPTZ NOT NULL
) PARTITION BY RANGE (created_at);

CREATE INDEX ON audit USING BRIN (created_at);
-- monthly partitions managed by pg_partman
What does SELECT ... FOR UPDATE actually lock, and how does it differ from FOR UPDATE SKIP LOCKED?

One sentence: FOR UPDATE takes a row-level write lock on every selected row, blocking conflicting writers until commit; SKIP LOCKED silently skips already-locked rows — the building block for a job queue.

Concept: Postgres locks tuples by writing a special hint into the row header (no in-memory lock table for row locks). Other transactions trying to update the row block. NOWAIT raises an error instead of waiting; SKIP LOCKED just doesn’t return them.

Nuance: SKIP LOCKED is the canonical Postgres job queue: SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1 hands each worker a different row. No need for Redis or RabbitMQ for low-volume work. The trade is you don’t get pub/sub semantics — workers must poll. Pair with LISTEN/NOTIFY for low-latency wakeups.

SELECT id FROM jobs WHERE status='pending'
ORDER BY created_at FOR UPDATE SKIP LOCKED LIMIT 1;
Logical decoding for CDC: how does Debezium stay correct across failures?

One sentence: Debezium reads from a logical replication slot that pins WAL on the primary, tracks LSN as the offset, and replays from the last committed LSN on restart.

Concept: a replication slot guarantees the primary keeps WAL until the consumer has confirmed receipt — the “backpressure” that prevents data loss but also the disk-fill risk if the consumer dies. Each event carries an LSN; Debezium commits offsets to Kafka so it can resume.

Nuance: at-least-once by default; consumers must dedupe on (table, PK, LSN). Snapshot-on-startup uses repeatable-read or pg_export_snapshot to be consistent with the slot start. Schema changes are tricky — DDL isn’t in the logical stream; Debezium uses heartbeats and a schema history topic. Watch pg_replication_slots.confirmed_flush_lsn like a hawk.

Why do indexes degrade over time, and what does REINDEX CONCURRENTLY do?

One sentence: B-tree indexes accumulate empty pages from deletes and HOT-broken updates; REINDEX CONCURRENTLY rebuilds them online without taking a lock that blocks reads/writes.

Concept: a B-tree page split leaves half-empty pages; deletes mark slots dead but don’t reclaim. Over months, an index doubles in size while data hasn’t. Symptoms: index scans slower than expected, pg_relation_size on the index inflated. HOT (heap-only-tuple) updates avoid index churn when no indexed column changes.

Nuance: REINDEX CONCURRENTLY (PG 12+) builds a new index alongside, then swaps. It briefly takes a strong lock at the swap. pg_repack does the same for tables. Don’t do this during peak; schedule it like a vacuum.

Famous footguns
  • “Postgres scales horizontally with replicas.” No — replicas scale reads. Writes go to the primary. Confusing the two is a yellow flag.
  • Default isolation is Read Committed, not Serializable. Don’t claim “Postgres is fully ACID” without naming the level.
  • Long-running transactions silently break vacuum and replication. Set idle_in_transaction_session_timeout; alert on pg_stat_activity.
  • Replication slots fill the primary’s disk when a subscriber dies. Always monitor slot lag; consider max_slot_wal_keep_size in PG 13+.
§ 02  Apache Kafka
Distributed log · Partitioned · Replayable

Apache Kafka

An immutable, partitioned log that the world treats like a database.

Log-based Replayable Exactly-once (with care) Not a queue

Kafka is a distributed, partitioned, replicated commit log. Producers append records to a topic; the topic is split into ordered partitions; each partition is an append-only file with a leader and N followers. Consumers track their position via an offset. The log is retained by time or size, not by “was it acked” — which is why it’s replayable.

It is not a message queue. There’s no per-message ack to the broker, no priority, no per-message TTL, no fanout-by-routing-key. The trade is enormous throughput (millions of msgs/sec on commodity hardware) and the ability to replay history.

The 30-second pitch: “Kafka is a durable, partitioned event log. We use it as the integration spine: services publish events, downstream services subscribe and maintain their own materialized views. Order is per-partition; throughput scales with partitions; durability is configurable per topic.”

Q&A drills

Explain the difference between consumer groups, partitions, and offsets. Who commits the offset and where?

One sentence: a partition is the unit of parallelism, a consumer group is a set of consumers that cooperatively read a topic with each partition assigned to exactly one consumer in the group, and the offset is the consumer’s bookmark stored in the __consumer_offsets topic.

Concept: if a topic has 12 partitions and a consumer group has 4 members, each member owns 3 partitions. Add a 5th consumer — rebalance redistributes. Add 13 consumers — one sits idle. So partition count = max parallelism for a single consumer group.

Nuance: the consumer commits its offset (default every 5s with auto-commit, or explicitly via commitSync/commitAsync). At-least-once means: process the record, then commit. If you commit first and crash, you lose work. Cooperative rebalancing (KIP-429) reduces the “stop-the-world” pause.

props.put("enable.auto.commit", "false");
// in poll loop:
records.forEach(r -> process(r));
consumer.commitSync();
What does “exactly-once semantics” actually require end-to-end?

One sentence: exactly-once is not a single feature — it requires an idempotent producer, transactional writes spanning produce + offset commit, and a read_committed consumer; and even then it’s only end-to-end if the downstream sink is idempotent or transactional.

Concept: the producer adds enable.idempotence=true + a producer ID + sequence numbers, so the broker dedups retries within a session. Transactions (transactional.id) let you atomically write to multiple partitions and commit consumer offsets — the “read-process-write” pattern Kafka Streams uses. Consumers must set isolation.level=read_committed to skip records from aborted txns.

Nuance: “exactly-once” refers to processing, not delivery. If your sink is a database, you still need an idempotent upsert or a 2PC. Saying “Kafka does exactly-once” without explaining this is the staff-level red flag.

producer.initTransactions();
producer.beginTransaction();
producer.send(new ProducerRecord<>("out", k, v));
producer.sendOffsetsToTransaction(offsets, groupMetadata);
producer.commitTransaction();
How does Kafka achieve durability and what do acks=all, min.insync.replicas, and replication factor really mean?

One sentence: a record is durable when it’s appended to the leader and replicated to min.insync.replicas in-sync followers; acks=all makes the producer wait for that.

Concept: RF=3 means the partition has 3 replicas. ISR (in-sync replica set) is the subset that’s caught up to the leader. min.insync.replicas=2 + acks=all means the producer waits until 2 of 3 replicas have the record. If only 1 is in-sync, the producer gets NotEnoughReplicasException — correct behavior, because acking when ISR is too small risks data loss on leader failure.

Nuance: acks=1 trades durability for latency — the leader can crash before replication. unclean.leader.election.enable=false prevents an out-of-sync replica from becoming leader (which would lose data). For maximum durability: RF=3, min.insync.replicas=2, acks=all, unclean.leader.election.enable=false.

Walk through the write path. What’s the page cache’s role?

One sentence: producer batches records, sends to the partition leader, leader appends to its log segment file, the OS page cache absorbs the write, followers fetch and replicate, then fsync happens lazily based on configuration.

Concept: Kafka leans on the Linux page cache — it doesn’t maintain its own. Writes go to memory; the kernel flushes to disk in the background. Zero-copy reads (sendfile syscall) push pages straight from page cache to socket without copying through user space — the secret to Kafka’s read throughput.

Nuance: by default, Kafka does not fsync on every write — it relies on replication for durability (“if 3 brokers crash simultaneously, you have bigger problems”). You can force flush.messages=1 for fsync-per-record, but throughput collapses. The right answer: “Durability comes from replication, not fsync. Page cache is the speed.”

What did KRaft replace, and why does it matter?

One sentence: KRaft replaces ZooKeeper for Kafka’s metadata (topic configs, ACLs, partition assignments) with a self-managed Raft quorum of controller nodes — one fewer system to operate.

Concept: historically, Kafka stored metadata in ZK and elected a controller via ZK ephemeral nodes. ZK was a separate cluster with its own ops burden, sized for low write rates. KRaft (KIP-500) makes 3 or 5 Kafka brokers act as controllers using Raft directly, storing metadata in an internal Kafka topic (__cluster_metadata).

Nuance: KRaft scales to millions of partitions (ZK choked around 200k). Cold-start is faster (controller failover is seconds, not minutes). Kafka 3.3+ marked KRaft production-ready; 4.0 removed ZK entirely. If asked “why?”, the cleanest answer is operational: “One system, one consensus protocol, faster recovery, more partitions.”

Why is the partition the unit of ordering, and what happens when you need global ordering?

One sentence: Kafka guarantees order within a partition (because a partition is one append-only file with one leader); for global ordering you need a single partition, which caps throughput at one consumer’s speed.

Concept: producers route records to partitions by hash(key) % numPartitions by default. Same key → same partition → ordered. No key → round-robin (or sticky in newer clients). Multiple partitions = multiple parallel writers and readers.

Nuance: “I need global ordering” is usually wrong. What people usually need is per-entity ordering — route by entity ID and order is preserved within that entity. If you genuinely need global order (e.g., a single financial ledger), accept the throughput ceiling and use partition 0 of a single-partition topic. Repartitioning by changing the partition count breaks ordering for existing keys (hash(k) % N changes); use a custom partitioner or pre-pick a generous partition count.

What is log compaction and when do you use it?

One sentence: log compaction retains at least the latest record per key, deleting older versions of the same key, turning the log into a database-like changelog.

Concept: default retention is time/size based (e.g., 7 days). With cleanup.policy=compact, a background thread (log cleaner) periodically rewrites segments, keeping only the newest record per key. A null value is a tombstone — eventually removes the key entirely.

Nuance: compacted topics power Kafka’s own metadata, Kafka Streams state stores (changelog topics), and CDC patterns where you want “current state per key” recoverable from the topic. They’re not free: compaction is I/O-intensive, and you must pick keys carefully (a compacted topic with no key is just … broken). Time-based + compact (cleanup.policy=compact,delete) is valid for “last N days of latest-per-key.”

Design exactly-once for a service that reads from Kafka, processes, and writes to Postgres.

One sentence: use the transactional outbox pattern — write your DB row and an outbox row in one Postgres transaction, then a CDC connector publishes the outbox to Kafka with idempotent producer; on the consume side, dedupe by record key in your Postgres upsert.

Concept: Kafka transactions don’t span Kafka + Postgres. The two-database problem is unsolved without 2PC, which Postgres-Kafka don’t share. The outbox pattern brackets the boundary: Postgres txn is atomic, Debezium reads the outbox via logical replication, idempotent producer dedups retries.

Nuance: on the consumer side, store (topic, partition, offset) alongside the application row, and use INSERT ... ON CONFLICT DO NOTHING or check the offset before applying. This gives effectively-once processing — the only thing that’s actually achievable when crossing systems.

-- producer side: transactional outbox
BEGIN;
INSERT INTO orders (...) VALUES (...);
INSERT INTO outbox (event_type, payload) VALUES ('OrderPlaced', ...);
COMMIT;
-- Debezium ships outbox -> Kafka with idempotent producer
Consumer rebalancing keeps stalling our service. What’s happening and how do you fix it?

One sentence: rebalancing happens whenever group membership changes — a consumer joins, leaves, or fails to heartbeat in time — and during a rebalance, all partition processing pauses (in eager mode) until assignments are recomputed.

Concept: the consumer sends heartbeats every heartbeat.interval.ms (default 3s) and must call poll() within max.poll.interval.ms (default 5min). Long processing per record — a slow DB write, an external API call — makes poll() miss its deadline; the broker considers the consumer dead and rebalances.

Nuance: fixes: (1) reduce max.poll.records so each poll loop is shorter; (2) move slow work out of the poll thread; (3) increase max.poll.interval.ms; (4) enable cooperative rebalancing (partition.assignment.strategy=CooperativeStickyAssignor) so only affected partitions pause; (5) use static membership (group.instance.id) to skip rebalances on transient pod restarts.

When should you NOT use Kafka?

One sentence: when you need per-message ack semantics, low-volume request/reply, complex routing rules, or message-level priority — reach for a queue (RabbitMQ, SQS) instead.

Concept: Kafka’s simplicity is its constraint. There’s no per-message ack to the broker (the consumer just moves the offset); no “dead letter” built in (you build it as a separate topic); no priority queue; no fanout by routing key (you put it in a topic and consumers ignore what they don’t care about). Latency floor is a few ms; tail is “whatever the consumer’s poll interval is.”

Nuance: the giveaway use cases for Kafka: high throughput, replay needed, multiple independent consumers of the same data, “event log as integration spine.” The giveaway use cases for RabbitMQ/SQS: task queues, request/reply with TTL, fanout routing, low volume but per-message reliability matters more than throughput.

Tiered storage and how it changes Kafka’s economics.

One sentence: tiered storage (KIP-405, GA in 3.6) offloads cold log segments to object storage (S3) while keeping recent ones on local disk, decoupling retention from broker disk size.

Concept: historically, retention was capped by broker disk — 7-day retention on TB/day = enormous local disk. Tiered storage lets brokers move closed segments to S3 transparently; consumers reading old offsets pay a small latency cost but get the data. Confluent Cloud, MSK, Aiven, Redpanda all expose this.

Nuance: reading from object storage is much slower (hundreds of ms per fetch); replay-from-the-beginning patterns become I/O-expensive on cloud egress. The big economic win: long retention without overprovisioned brokers; the trade is occasional consumers paying for cold reads.

How do you size a Kafka cluster for 1 GB/s sustained ingestion?

One sentence: at 1 GB/s sustained with RF=3, you write 3 GB/s to disk + ~3 GB/s replication network; budget ~6–9 brokers with NVMe and 25 GbE NIC, plus retention-driven storage.

Concept: per-broker throughput on commodity hardware is roughly 250–500 MB/s sustained write before tail latency degrades. RF=3 multiplies the disk + network requirement. Network is usually the first bottleneck on cloud (instances cap at 10–25 Gbps). For 1 GB/s with headroom, plan ~6–9 brokers, partition count in the low thousands across topics, and replication-throttle for rebuilds.

Nuance: the answer interviewers want is structured: ingest rate × RF = disk write; ingest × (RF-1) = replication network; consumer fanout × ingest = read network; partition count >= max parallelism per topic; pick instance type that keeps each broker under 70% CPU/network at peak. Numbers matter less than the structure.

Famous footguns
  • “Exactly-once means the broker dedups end-to-end.” No — it requires idempotent producer + transactions + read_committed consumer, and even then end-to-end demands an idempotent sink.
  • “More partitions = always faster.” Partitions cost open file handles, controller memory, and replication bandwidth. Tens of thousands per cluster start to bite.
  • Auto-commit + slow processing = silent data loss. Auto-commit advances the offset on a timer; if the consumer crashes mid-batch, you lose messages. Always commit after processing.
  • Repartitioning a topic breaks key ordering. Old records are at hash(k) % oldN, new ones at % newN. Pick partition count generously up front; resharding is migration, not config.
§ 03  MongoDB
Document · Replica sets + sharding · WiredTiger

MongoDB

Document-shaped data and a shard key you’d better get right.

ACID (multi-doc) Causal consistency Shard-key-sensitive 16 MB doc cap

MongoDB stores BSON documents in collections. A replica set = one primary + N secondaries with an oplog; primaries handle writes, secondaries tail and replay. A sharded cluster adds mongos routers and config servers to spread documents across multiple replica sets by shard key.

It is not a schemaless free-for-all. The schema lives in the application, and Mongo enforces it via JSON Schema validators if you ask. It’s also not a great fit for highly relational data with cross-document transactions at scale — multi-shard ACID exists since 4.2, but it’s a tool, not a pattern.

The 30-second pitch: “Mongo for document-shaped data and fast schema iteration. Replica sets give HA out of the box. Sharding works once you’ve modeled access patterns around the shard key. Default consistency is causal-on-primary; tighten it via write concern + read concern.”

Q&A drills

What changes when you go from a replica set to a sharded cluster?

One sentence: routing moves to mongos, queries need a shard key strategy or they broadcast, multi-doc transactions become 5–10× more expensive when they cross shards, and uniqueness across shards is only enforced on the shard-key prefix.

Concept: mongos is a stateless router that consults config servers (a replica set storing chunk metadata) to direct queries. Queries with the shard key go to one shard (targeted); queries without it go to all shards (scatter-gather). Aggregations gain a coordinate-and-merge phase.

Nuance: a common mistake is sharding without revisiting indexes. An index that worked on a replica set might not have the shard-key prefix, so every query becomes scatter-gather. The right answer: “Sharding is an architecture, not a config flag. The shard key is the design.”

How do you choose a shard key?

One sentence: high cardinality, even write distribution, and a shape that lets your hottest queries target one shard.

Concept: three properties at once: cardinality (enough distinct values), uniformity (writes spread evenly — no hot shard), locality (queries can be answered by hitting one or few shards). Hashed shard key spreads writes; ranged supports range queries but risks hot shards on monotonic keys (e.g., timestamps, ObjectIds).

Nuance: compound shard keys are usually right. {tenantId: "hashed", createdAt: 1} spreads tenants and keeps each tenant’s data range-queryable within its shard. Zone sharding pins ranges to nodes (e.g., region locality for GDPR). Resharding is online since 4.4 but expensive; pick well the first time.

sh.shardCollection("app.events",
  { tenantId: "hashed", createdAt: 1 });
Explain write concern, read concern, and how causal sessions fit in.

One sentence: write concern controls when the primary acks (durability), read concern controls which data the read sees (consistency), and causal sessions chain operations so “read-your-writes” works across primary/secondary boundaries.

Concept: w:1 — primary only (fast, can lose on failover). w:majority — majority of replica set acked (durable). j:true waits for journal sync. Read concerns: local (whatever’s here), majority (won’t roll back), linearizable (primary only, slowest), snapshot (used inside transactions).

Nuance: default for new drivers is w:majority. Causal sessions let you write to primary then read from a secondary and still see your write — the driver passes a cluster time, the secondary waits until it has caught up. The right answer: “Match the concern to the operation. Money operations are w:majority, j:true + linearizable read. Profile reads are local on a secondary.”

Multi-document transactions: what’s the cost, and when do you actually use them?

One sentence: multi-doc transactions are real ACID since 4.0 (replica sets) and 4.2 (sharded), but they hold locks longer, cost coordinator round trips on sharded clusters, and abort under contention — treat them as the escape hatch, not the default.

Concept: Mongo encourages embedding related data in one document so you don’t need transactions. When you do (e.g., transferring money between accounts in separate docs), wrap in a session with snapshot isolation. Sharded transactions use a 2PC-like coordinator; latency goes from ~ms to tens of ms.

Nuance: the rule of thumb: if your transaction spans documents because the schema is wrong, fix the schema. If it spans documents because they’re genuinely independent entities, use a transaction sparingly. Default txn timeout is 60s; long txns block oplog progression on secondaries.

How does the WiredTiger storage engine work, and why does it matter for capacity planning?

One sentence: WiredTiger is a B-tree storage engine with document-level locking, MVCC for snapshot reads, and snappy/zstd compression — document-level locking is why Mongo isn’t bottlenecked on a global lock the way it was pre-3.0.

Concept: WT keeps a write-ahead journal, periodic checkpoints (default 60s), and an in-memory cache (default 50% of RAM minus 1GB). Reads hit cache; misses go to disk; writes update in-memory then journal. MVCC makes reads non-blocking on writes.

Nuance: working set must fit in cache for good performance — the working set is the indexes + hot documents, not the whole database. If db.serverStatus().wiredTiger.cache shows high eviction rates and pages read from disk, you’re cache-starved. Compression typically gives 3–7× on text-heavy data; pick zstd on 4.2+ for better ratio at slightly higher CPU.

What’s the oplog, and how does its window affect operations?

One sentence: the oplog is a capped collection on the primary that records every write; secondaries tail it and replay; the oplog window is how far back in time the oplog still has entries.

Concept: default size is 5% of free disk. A secondary that falls behind the oplog window must do a full initial sync — copy every doc from a healthy node. Long-running secondary downtime = re-sync.

Nuance: alert on oplog window dropping below your max-tolerable-secondary-downtime + safety margin. db.getReplicationInfo() shows the window. Resize with replSetResizeOplog. Watch for write-heavy bursts shrinking the window unpredictably.

Indexing in Mongo: when do you reach for compound, multikey, partial, wildcard, or text?

One sentence: compound indexes for multi-field queries (order matters — ESR rule), multikey when an indexed field is an array, partial to skip soft-deleted rows, wildcard for catch-all on dynamic schemas, text for basic full-text.

Concept: the ESR rule for compound index field order: Equality, Sort, Range. Indexed range scans break sort-using-index, so range comes last. Multikey is automatic on array fields, but compound multikey is restricted (only one indexed field per doc can be an array per index).

Nuance: partial indexes save huge space on “active rows only” tables (partialFilterExpression: { deleted: false }). Wildcard indexes ({ "$**": 1 }) are tempting but expensive at write time and not useful for most queries — reach for them only on truly dynamic catalog data. Atlas Search bridges to Lucene for real text/relevance.

How does primary election work, and what’s the failover timeline?

One sentence: on primary failure, secondaries vote (Raft-like protocol since 3.4), the most up-to-date eligible node becomes primary, and clients with retryable writes silently retry — default failover budget is ~10–30s.

Concept: electionTimeoutMillis (default 10s) is the heartbeat timeout before secondaries call an election. Priority and lag determine who can win. An odd number of voting members is critical to avoid split-brain; arbiters exist but harm durability and should be avoided when possible.

Nuance: drivers retry idempotent operations once during failover. Stepdown can be triggered manually for maintenance. Watch for “rollback”: if a primary takes writes that aren’t replicated and then loses election, those writes are rolled into a rollback file — lost in practice. Avoid by using w:majority.

Aggregation pipeline: how do you write performant pipelines on large collections?

One sentence: filter early with $match + index, project early to shrink documents, push $sort before $group when an index can serve it, and watch for blocking stages that buffer everything in memory.

Concept: stages flow records through. $match + $sort can use indexes if they appear before any stage that transforms documents ($group, $project reshapes). Blocking stages ($group, $sort without index, $lookup without index) hit the 100MB memory limit by default; allowDiskUse: true spills, but slowly.

Nuance: $lookup is “left outer join” but slow at scale — consider denormalization or computing on the client. Use explain() with executionStats to see which stages used indexes (IXSCAN vs COLLSCAN). On sharded clusters, push as much work as possible into the per-shard phase before merge.

You’re storing user-generated comments. Embed or reference?

One sentence: embed when comments are bounded and read together with the parent; reference when they’re unbounded, mutated independently, or queried separately.

Concept: Mongo’s document model rewards co-locating data that’s read together. If a post has <100 comments and you always show them with the post, embed. If a post can have 100k comments, embedding hits the 16 MB doc cap and forces every read to drag all comments.

Nuance: the hybrid pattern: embed the latest N (say 10) comments in the post for fast first paint, store all comments in a separate collection, denormalize the count back to the post. The interview tell: a candidate who answers “always embed” or “always reference” hasn’t modeled this in production.

Why isn’t Mongo “schemaless”?

One sentence: the schema exists, it just lives in your application code — and that’s often worse than a declared schema because no two services agree on it.

Concept: Mongo accepts arbitrary BSON; your readers and writers must agree on field names, types, and shapes. Without enforcement, you get drift: one service writes email as a string, another as {primary: ..., backup: ...}, and queries silently miss documents.

Nuance: use JSON Schema validators at the collection level (validator: { $jsonSchema: ... }) for hard guarantees, and a typed DTO layer in code (Mongoose, MongoEngine, BSON codecs). The right interview answer: “Document-shaped data, application-owned schema, validators where invariants matter.”

Famous footguns
  • Bad shard key = forever pain. Resharding online is real but expensive; teams have spent quarters fixing a poor key. Pick once, model first.
  • 16 MB document cap is hard. Activity feeds, comment lists, time-series — embedding unbounded arrays will eventually break. Use bucketing or a separate collection.
  • Default isolation pre-4.0 wasn’t ACID across docs. If you reference an old article on Mongo’s consistency, check the version.
  • Aggregation memory limit (100 MB) bites silently. Without allowDiskUse, big $group just errors. With it, performance falls off a cliff.
§ 04  Apache Cassandra
Wide-column · Masterless · LSM

Apache Cassandra

Linear-scale writes, gossip-coordinated, opinionated to the bone.

Linear write scale Tunable per query Query-first modeling No joins

Cassandra is a masterless, peer-to-peer ring of identical nodes. Data is placed on the ring by consistent hashing of the partition key; the replication factor (RF) determines how many copies. Storage is an LSM tree: writes hit a commit log + memtable, flush to immutable SSTables, and merge through compaction.

It is not a relational database. No joins, no foreign keys, no aggregations beyond the partition, weak secondary indexes. Data is modeled per query, often with the same data duplicated across multiple tables.

The 30-second pitch: “Cassandra for write-heavy, time-series, multi-region workloads where I can model around partition keys. RF=3, LOCAL_QUORUM, query-first tables. The trade is no ad-hoc queries and write amplification through duplication.”

Q&A drills

What does R + W > RF guarantee, and what does it not?

One sentence: R + W > RF guarantees that any read overlaps with any write on at least one replica, so the read sees the latest write — provided writes are linearizable per replica, which they aren’t under concurrent writes.

Concept: with RF=3, R=W=QUORUM=2, R+W=4 > 3, so reads always intersect the latest write. Cassandra uses last-write-wins by timestamp on conflicts — readers see the row with the highest timestamp.

Nuance: what it doesn’t guarantee: linearizability across writes. Two concurrent writes to the same cell with the same timestamp resolve by some tiebreaker; one is silently lost. For real CAS you need LWT (Lightweight Transactions) using Paxos — expensive (4 round trips) and partition-scoped only. The senior answer: “R+W>RF gives strong reads under sequential writes; for concurrent writes to the same row, use LWT or accept LWW.”

SELECT * FROM users WHERE id = ? -- with CL=QUORUM
INSERT INTO users (id, email) VALUES (?, ?) IF NOT EXISTS;
-- the IF NOT EXISTS triggers Paxos (LWT)
Walk through the write path. Why are Cassandra writes so fast?

One sentence: a write hits the commit log (sequential append, fsync on a schedule) and an in-memory memtable, then immediately acks — no in-place update, no random I/O on the hot path.

Concept: the memtable is an in-memory sorted structure (per table). When it fills, it flushes to disk as an immutable SSTable. Reads merge candidates across SSTables + memtable. Compaction (size-tiered, leveled, or time-window) merges SSTables periodically, removing tombstones and obsoleted versions.

Nuance: the LSM trade is read amplification (a read may consult multiple SSTables; bloom filters avoid most of them) and write amplification through compaction. Compaction strategy choice: STCS (default, write-favored), LCS (read-favored, more I/O), TWCS (time-windowed, ideal for time-series with TTL).

How does a partition key + clustering columns work, and why do they matter for performance?

One sentence: the partition key determines which node holds the row (via hash), and clustering columns determine the sort order within that partition — so range scans within a partition are cheap, but cross-partition queries are expensive or illegal.

Concept: PRIMARY KEY ((tenant_id, day), event_time, event_id) means: partition key is (tenant_id, day), clustering is event_time, event_id. All events for a tenant on a day live on the same set of replicas, sorted by time. WHERE tenant_id=? AND day=? AND event_time > ? — one partition, one disk seek, lots of sequential reads.

Nuance: querying without the full partition key is illegal (or requires ALLOW FILTERING, which is a slow scan-and-filter you should never use in production). The right modeling: compound partition keys to bound partition size and spread load.

What are tombstones, and why can they kill reads?

One sentence: a tombstone is a marker recording “this cell or row was deleted”; reads must scan tombstones along with live data, so partitions full of tombstones get linearly slower.

Concept: Cassandra is append-only. A delete writes a tombstone with a timestamp; the actual data is removed only by compaction after gc_grace_seconds (default 10 days). The grace period exists to ensure all replicas converge before tombstones are dropped — otherwise a missed delete could resurrect data.

Nuance: common cause: writing-then-deleting many cells in a wide partition (e.g., a queue table). Reading 10k tombstones to find 100 live rows is a real production failure. Symptoms: tombstone_warn_threshold warnings (default 1000) and tombstone_failure_threshold errors (default 100k). Fix: rethink the model, use TTLs with TWCS, never use Cassandra as a queue.

Repair: what is it, why is it mandatory, and what does it cost?

One sentence: repair is the anti-entropy process that compares Merkle trees of data across replicas and streams missing/divergent ranges to bring them into sync — mandatory because hinted handoff and read-repair only cover the easy cases.

Concept: when a replica is down, the coordinator may store a hint (a deferred write); when the replica returns, hints replay. But hints have TTL and storage limits. Read repair fixes inconsistencies on the path of a read at QUORUM+. Neither catches every miss. Full repair (nodetool repair) is the backstop — must run within gc_grace_seconds or deleted data can resurrect.

Nuance: repair is expensive — it streams data and competes with live traffic. Reaper (open source) schedules incremental repairs across the cluster. Skipping repair = data resurrection bugs. The interview tell: a candidate who can’t describe repair has run small Cassandra clusters but not production ones.

Multi-DC: how does NetworkTopologyStrategy + LOCAL_QUORUM actually work?

One sentence: NTS places replicas across racks within each DC, gossip propagates between DCs, and LOCAL_QUORUM means “quorum of replicas in the local DC only” — cross-DC writes happen but don’t block the ack.

Concept: { 'us-east': 3, 'eu-west': 3 } means RF=3 in each DC, total 6 replicas. A write at LOCAL_QUORUM needs 2 of 3 local replicas to ack; the cross-DC writes are async via the coordinator. Reads at LOCAL_QUORUM stay in the local DC entirely.

Nuance: this is the right pattern for multi-region apps — reads/writes serve from local DC, replication is eventually-consistent across regions. Conflict resolution is LWW; for counters or strict ordering, this is wrong. EACH_QUORUM waits on quorum in every DC — correctness for cross-region invariants, latency cost is the WAN round trip.

Why are secondary indexes weak, and what do you do instead?

One sentence: secondary indexes are local per node — a query has to fan out to every node to find matching rows — so they only work well when the index lookup also includes the partition key.

Concept: in a relational DB, an index points from value to row anywhere in the table. In Cassandra, an index lives on each node and only sees that node’s data. A query like WHERE email = ? across a 100-node cluster requires touching all 100 nodes — latency = slowest node.

Nuance: the right pattern is denormalized lookup tables: a separate table keyed on the alternate access pattern (users_by_email with email as partition key). You write to both tables; you read targeted. SAI (Storage-Attached Indexes, 5.0) materially improves on the old 2i, but the “duplicate the table” pattern is still preferred for hot paths.

Design a time-series table for IoT sensor readings at 1M writes/sec.

One sentence: partition by (sensor_id, day_bucket), cluster by reading_time DESC, use TWCS compaction with TTL matching retention, and pre-warm partitions on the client side.

Concept: partition key bounds the partition size — one sensor’s daily readings (typically <100 MB) is the right magnitude. TWCS (Time-Window Compaction) groups SSTables by time window so old data ages out cleanly when TTLs expire — no read amplification on cold data, no compaction storms.

Nuance: 1M writes/sec needs 20+ nodes; spread by sensor_id (high cardinality — check). Day bucket prevents wide partitions for chatty sensors. TTL the data at the row level so old days self-evict. The senior answer also mentions materialized rollups (1-min, 1-hour aggregates) in separate tables for dashboard queries.

CREATE TABLE readings (
  sensor_id UUID, day DATE,
  reading_time TIMESTAMP, value DOUBLE,
  PRIMARY KEY ((sensor_id, day), reading_time)
) WITH CLUSTERING ORDER BY (reading_time DESC)
  AND default_time_to_live = 2592000
  AND compaction = {'class':'TimeWindowCompactionStrategy',
                    'compaction_window_unit':'DAYS',
                    'compaction_window_size':1};
What is gossip and how does the cluster discover topology?

One sentence: gossip is a periodic peer-to-peer protocol where each node exchanges state (heartbeat, schema version, load, status) with a few randomly-chosen peers per second; full cluster state converges in O(log N) rounds.

Concept: there’s no master to ask. Each node maintains its view of the cluster; gossip messages carry vector-clock-like versions so nodes can merge each other’s views. Adding a node: it bootstraps from seeds, gossip propagates, ranges are streamed.

Nuance: seed nodes are bootstrap helpers, not coordinators — they’re only contacted on startup. Schema disagreements between nodes (nodetool describecluster shows different schema versions) are real outages waiting to happen, often caused by concurrent DDL during partitions.

What do vnodes solve, and what do they cost?

One sentence: vnodes (virtual nodes) let each physical node own many small token ranges instead of one large one, which makes rebalancing on node add/remove smooth instead of catastrophic.

Concept: classic Cassandra (one token per node): adding a node forces one neighbor to stream half its data. With num_tokens=16 (modern default; 256 was the old default), each node owns 16 random ranges; adding a new node steals slices from many nodes simultaneously, parallelizing the stream.

Nuance: too many vnodes (256) hurt repair and bootstrap (more SSTables, more streaming sessions). Too few weaken the rebalance smoothness. Modern guidance: num_tokens=16, with allocation algorithm token_allocation set to balanced. For analytical workloads with heavy range scans, fewer vnodes can perform better.

When would you NOT use Cassandra?

One sentence: small datasets, ad-hoc analytics, multi-row transactions, anything that needs joins, and any workload where the team won’t commit to query-first modeling.

Concept: Cassandra punishes generality. Without joins or aggregations, every query needs a table designed for it. Without ACID across rows, you can’t do “transfer money between accounts” safely. Without strong indexing, you can’t add new query patterns without ETL.

Nuance: the giveaway: if you’d describe the workload as “mostly reads, lots of joins, schema evolves frequently” — that’s Postgres. If you’d describe it as “massive write fan-out, time-series, multi-region with regional locality, well-known access patterns” — that’s Cassandra. The senior answer names the runner-up: “ScyllaDB if I want C* semantics with shard-per-core efficiency; DynamoDB if I want managed.”

Famous footguns
  • Using Cassandra as a queue. Tombstones from deletes destroy read performance. Anti-pattern, full stop.
  • Wide partitions. A single sensor with no time bucket = a 100 GB partition = OOM on read. Bound your partitions.
  • ALLOW FILTERING in production. It’s a confession that the data model is wrong.
  • Skipping repair. Deleted data resurrects after gc_grace_seconds without repair. Schedule it; alert on it.
§ 05  Amazon DynamoDB
Managed · Auto-partitioned · Serverless-friendly

Amazon DynamoDB

No knobs, no servers, no second chances on your key design.

Single-digit ms Multi-region active-active Hot partition risk No ad-hoc queries

DynamoDB is AWS’s fully-managed KV/document store. Items live on partitions hashed by the partition key; each partition is replicated 3× across AZs with internal consensus. The whole engine is opaque — you see only the API: GetItem, PutItem, Query, Scan, TransactWriteItems.

It is not a general-purpose database. There’s no SQL, no joins, no GROUP BY, no full-text search, no schema migration. Every access pattern must be modeled into a primary key or a secondary index before data lands.

The 30-second pitch: “Dynamo for predictable single-digit-ms key access at any scale, especially in serverless AWS. Single-table design with composite keys covers most patterns. Global Tables for multi-region active-active — with LWW conflict resolution as the trade.”

Q&A drills

Walk through single-table design. When would you NOT use it?

One sentence: single-table design packs multiple entity types into one table behind generic PK/SK keys with typed prefixes, so common access patterns are answered by a single Query on a co-located item collection — you skip it when the team can’t commit to upfront modeling or access patterns are still evolving.

Concept: typical layout: PK = USER#42, SK = PROFILE for the user; PK = USER#42, SK = ORDER#001 for one of their orders. Query(PK = USER#42) returns profile + all orders in one call. GSI overloading uses generic GSI1PK/GSI1SK to serve multiple alternate access patterns over the same table.

Nuance: the win is predictable, low-cost reads — one network round trip serves a screen. The cost is mental load, evolution pain, and easy footguns (a missing index = a Scan, which is expensive). Don’t do it for: small apps where simplicity matters, exploratory schemas, anything that will need ad-hoc analytics — pipe to S3/Athena instead.

// PK            SK              data
// USER#42       PROFILE         {name:"Ada"}
// USER#42       ORDER#2024-001  {total:42}
// USER#42       ORDER#2024-002  {total:99}
Query: PK=USER#42 -> profile + all orders, one RCU each
What’s the difference between LSI and GSI, and when does each make sense?

One sentence: LSI shares the partition key (alternate sort key, must be created at table create, eventually consistent for non-key projections); GSI has its own partition + sort key, eventually consistent, can be added/removed online — the workhorse for alternate access patterns.

Concept: an LSI lets you sort items within a partition by a different attribute. A GSI is effectively a separate table that DynamoDB maintains in the background, with its own RCU/WCU. Up to 5 LSIs and 20 GSIs per table.

Nuance: LSIs constrain partition size to 10 GB total (because they’re collocated). GSIs don’t share that limit but cost double the writes (every update also updates the GSI). Sparse GSIs (only items with the indexed attribute appear) are a powerful pattern: filter to “rows that need processing” without scanning the whole table.

Explain RCUs and WCUs. Why does on-demand cost so much more than provisioned?

One sentence: 1 RCU = 1 strongly-consistent read of an item up to 4 KB; 1 WCU = 1 write up to 1 KB; on-demand is auto-scaled but priced ~7× per unit, paying for elasticity.

Concept: eventually-consistent reads cost half (0.5 RCU). Transactional reads cost 2×. Items larger than the unit consume proportionally more (a 12 KB item = 3 RCU strong, 1.5 RCU eventual). At provisioned, you pay for capacity reserved per second; auto-scaling adjusts based on utilization but lags spikes.

Nuance: on-demand wins for spiky/unpredictable workloads, sandboxes, and development. Provisioned with auto-scaling wins above ~30% sustained utilization — the per-unit price is much lower. Mixing — on-demand for some tables, provisioned for the always-hot ones — is common.

What’s a hot partition, and how does adaptive capacity actually help?

One sentence: a hot partition is a single partition receiving disproportionately more traffic than others; adaptive capacity redistributes some capacity to the hot partition, but a truly hot key still throttles.

Concept: a single partition tops out around 3000 RCU / 1000 WCU / 10 GB. If your workload concentrates on one PK, you’re capped at that throughput regardless of total table capacity. Adaptive capacity rebalances unused capacity from cold partitions to hot ones (within limits); helpful for skewed-but-not-pathological access.

Nuance: the fix for a genuine hot key is write sharding: append a random suffix (USER#42#1 through USER#42#16) and read all 16. Or pre-split using calculated suffixes. Adaptive capacity buys you 30s of slack on a moderate spike, not a structural fix.

Strongly consistent reads vs eventually consistent — what’s the trade?

One sentence: strongly consistent reads always reflect the latest committed write but cost 2× the RCU and add a few ms of latency by hitting the leader replica; eventually consistent reads can be served by any replica and are usually fresh within ~1s.

Concept: Dynamo replicates each partition 3 ways across AZs with multi-Paxos. A strong read goes to the leader; an eventual read can hit any replica. GetItem defaults to eventual; pass ConsistentRead=true for strong.

Nuance: GSIs are always eventually consistent — even a strong base-table read followed immediately by a GSI query may return stale results. For read-after-write across a GSI, you have to query by the base key. Streams + a Lambda can compensate for downstream materializations.

Transactions in Dynamo: TransactWriteItems vs conditional writes. When each?

One sentence: TransactWriteItems gives ACID across up to 100 items (4 MB total) at 2× cost; ConditionExpression on a single item is optimistic concurrency at no extra charge — use the latter wherever possible.

Concept: conditional writes (PutItem + ConditionExpression: "attribute_not_exists(id)") implement compare-and-set on a single item, atomically. Transactions are needed when you need atomicity across multiple items (e.g., transfer between two accounts).

Nuance: transactions use a coordinator and 2PC under the hood; latency is higher (~10ms typical), and they’re idempotent only if you pass a client request token. They abort on conflict; the client retries. Tens of thousands per second are fine; millions need careful design.

UpdateItem PK=ACCT#A
  UpdateExpression: "SET balance = balance - :amt"
  ConditionExpression: "balance >= :amt"
// no transaction, just CAS
How do Streams work, and what are they for?

One sentence: DynamoDB Streams emit a time-ordered, partition-keyed log of changes (insert/update/delete with old + new images), retained for 24h, consumable by Lambda, Kinesis, or KCL workers — the canonical CDC mechanism for Dynamo.

Concept: enable on a table; pick what to capture (NEW_IMAGE, OLD_IMAGE, BOTH, KEYS_ONLY). The stream is sharded the same way as the table; downstream consumers process at-least-once with checkpoints.

Nuance: Streams are how you implement materialized views, search index sync (push to ES/OpenSearch), notifications, audit logs, and aggregations Dynamo can’t do natively. For Kinesis-style higher throughput / longer retention, use Kinesis Data Streams for DynamoDB instead.

Global Tables: how do conflicts resolve, and when is that wrong?

One sentence: Global Tables replicate writes across regions asynchronously and resolve concurrent writes to the same item with last-writer-wins by timestamp — correct for “independent regional writes”, wrong for counters, balances, or anything that should accumulate.

Concept: each region accepts writes locally and ships them to peers via internal Streams. Reads in any region serve from local replica. Conflicts are detected by per-item version vectors; LWW picks the higher timestamp.

Nuance: what breaks: UpdateItem ... ADD count :1 in two regions on the same item — the later write replaces, doesn’t accumulate. The fix is to scope writes to one region per item (e.g., partition key includes the region) or use a CRDT-style design (sum across per-region counters).

What’s the 400 KB item limit really doing to your design?

One sentence: Dynamo’s 400 KB cap forces you to split large entities — either across multiple items in an item collection, or by storing the blob in S3 with the key in Dynamo.

Concept: 400 KB is generous for a typical “user with embedded preferences” but small for “all comments on a popular post”. The pattern: store the metadata + recent items in Dynamo, the full blob in S3, and the S3 key as an attribute.

Nuance: S3 latency (tens of ms) is the trade. DAX caches Dynamo in front for read-heavy paths; doesn’t help cross-region. Compressed JSON or binary attribute formats save room. Don’t fight the cap — it exists to keep partitions healthy.

Design a multi-tenant SaaS with predictable per-tenant performance. Why Dynamo?

One sentence: tenant ID is the partition key prefix; access patterns are modeled into the table or GSIs; on-demand or auto-scaled provisioned with per-table limits caps blast radius from a noisy tenant.

Concept: single-table design with PK = TENANT#42#USER#7 spreads tenants across many partitions automatically. GSIs serve cross-tenant reporting. Streams + Lambda emit per-tenant events for usage metering.

Nuance: two pitfalls. (1) A whale tenant can monopolize a partition — mitigate with write sharding on tenant ID. (2) Cross-tenant analytics is impossible in-place; pipe to S3/Athena via Streams. The senior framing: “Per-tenant performance is bounded by per-partition limits, not table limits. Whales need their own partition strategy.”

What’s the worst thing you can do in DynamoDB?

One sentence: use Scan in a hot path — it reads every item, costs proportional to table size, and ignores the entire reason you picked Dynamo.

Concept: Scan is for ETL or one-off ops, never for user-facing reads. Every Scan consumes RCU for every item in the table (or scanned segment); on a multi-TB table, this is hundreds of dollars per call.

Nuance: if you find yourself reaching for Scan, your access pattern wasn’t modeled. The fix: add a GSI for the alternate access pattern, or reshape the table. Parallel Scan helps for ETL but doesn’t help cost. The interview tell: a candidate who proposes Scan + filter has not internalized Dynamo’s economics.

Famous footguns
  • Hot partition + adaptive capacity = silent throttling. Adaptive helps moderately; a true hot key still 4xx’s. Shard writes proactively.
  • GSIs are eventually consistent. Read-after-write through a GSI is not safe within ~1s. Read by base key for that.
  • Scan in production code. Costs scale with table size, not result size. Always model around Query.
  • LWW on Global Tables for counters. Two regions both increment, one increment is lost. Use per-region counters or scope writes to a single region per item.
§ 06  Redis
In-memory · Single-thread per shard · Cluster slots

Redis

A toolbox of data structures that happens to be a server.

Sub-ms latency Atomic ops Async repl by default RAM-bounded

Redis is an in-memory data structure server. Everything happens in RAM through a single-threaded event loop per shard, which is why operations on data structures (sorted sets, hashes, streams) are atomic without locks. Persistence is optional via RDB snapshots and/or AOF (append-only file).

It is not a general-purpose database in the “source of truth” sense without explicit durability design. Async replication is the default; WAIT approximates sync but doesn’t guarantee it.

The 30-second pitch: “Redis for cache, sessions, leaderboards, rate limiting, ephemeral counters, and as a queue (Streams). Cluster scales linearly across hash slots. Durability is opt-in — AOF for crash safety, RDB for fast restart.”

Q&A drills

Why is Redis single-threaded, and how can it still hit millions of ops/sec?

One sentence: a single-threaded event loop avoids locks and context switches, so each command runs to completion atomically; throughput comes from extremely fast in-memory operations and pipelining.

Concept: Redis processes commands in order on a single thread per shard. No mutexes around data structures; every op is implicitly atomic. Pipelining batches commands over one connection, amortizing network latency. Multi-threaded I/O (since 6.0) parallelizes parsing and response writing, not command execution.

Nuance: a slow command (KEYS *, large SUNIONSTORE, big HGETALL) blocks every other client. Use SCAN instead of KEYS; profile with SLOWLOG. To use more cores, run multiple shards (Redis Cluster) or multiple processes per host.

Explain Redis Cluster: hash slots, MOVED/ASK, and why multi-key ops have constraints.

One sentence: Cluster maps the keyspace to 16,384 hash slots via CRC16(key) mod 16384; each slot lives on one master + N replicas; clients are slot-aware and follow MOVED/ASK redirects during resharding.

Concept: MOVED means “permanently, this slot lives there now — update your map.” ASK means “during migration, this specific key has moved temporarily.” Multi-key commands (MSET, SUNION, transactions) require all keys in the same slot.

Nuance: hash tags force colocation: {user:42}:cart and {user:42}:wishlist hash on user:42 only, landing in the same slot. Lua scripts and transactions across multiple keys must use this. Resharding moves slots between nodes online; clients with stale maps follow redirects until they refresh.

SET {user:42}:cart "..."
SET {user:42}:wish "..."
MULTI
LPUSH {user:42}:cart "item"
INCR {user:42}:counter
EXEC
RDB vs AOF: pick a persistence strategy and defend it.

One sentence: RDB is a periodic point-in-time snapshot (fast restart, minutes of data loss); AOF is an append-only command log (durable, slow restart, large file); most teams enable both.

Concept: RDB forks the process and dumps memory; cheap CPU spike but disk-friendly. AOF appends every write command; fsync policy is always (every cmd), everysec (default, ~1s window), or no (kernel decides). AOF rewrites compress the log periodically to bound size.

Nuance: everysec is the right default — you can lose up to 1s of writes on a hard crash. always drops throughput by 10×+. Restart from AOF replays every command (slow on TB-scale data); RDB loads as a memory image (much faster). Production: AOF for durability, RDB for fast restart, both kept.

How would you implement a distributed lock? Where does Redlock fail?

One sentence: single-node lock is SET key value NX PX 30000 (atomic set-if-not-exists with TTL); release with a Lua script that checks the value before deleting; Redlock coordinates across N independent masters with a quorum and clock-skew bound, but Kleppmann’s critique — GC pauses or clock jumps can violate mutual exclusion — is real.

Concept: the value is a unique token so the holder is identifiable. Without it, lock A’s release could delete lock B if A held until expiry. Redlock acquires a majority within a clock-bounded window; releases everywhere on done.

Nuance: the staff-level answer: “For best-effort mutexes (cache stampede protection, rate-limited triggers), Redlock is fine. For correctness-critical locks (financial transfers, inventory deductions), use a fencing token from a strongly-consistent store like etcd or a SQL transaction — the lock is just for fairness.”

SET lock:job1 <uuid> NX PX 30000
-- release atomically
EVAL "if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) end" 1 lock:job1 <uuid>
Design a leaderboard with Redis. What data structure, what operations, what scale ceiling?

One sentence: a sorted set (ZADD/ZINCRBY for updates, ZRANGE WITHSCORES for top-N, ZREVRANK for “your rank”) on a single key — sub-ms reads, but ceiling is one master’s memory and CPU.

Concept: a sorted set is a skiplist + hashtable combo, giving O(log N) inserts and O(log N + M) range scans. ZRANGEBYSCORE gives bracketed slices (e.g., scores between 100 and 200). ZREVRANGEBYSCORE handles descending order.

Nuance: for tens of millions of players on one leaderboard, one key works. For per-region or per-time-window boards, key per board (lb:global, lb:eu:weekly). When you outgrow one master, shard by region, then merge top-N at read time. Don’t cluster a single hot key — the slot lives on one master.

ZINCRBY lb:global 10 user:42
ZRANGE lb:global 0 9 REV WITHSCORES  -- top 10
ZREVRANK lb:global user:42           -- user's rank
What are Streams, and how do they compare to Kafka?

One sentence: Redis Streams (5.0+) are an append-only log with consumer groups, pending-entry lists, and at-least-once delivery — like a tiny Kafka, scoped to one Redis cluster, with millisecond latency and gigabyte-scale retention.

Concept: XADD appends; XREAD/XREADGROUP consumes; consumer groups track positions. PEL (pending entries list) tracks delivered-but-not-acked entries per consumer; XCLAIM reassigns ownership when a consumer dies.

Nuance: Streams are great for low-latency task queues, sensor ingest, ephemeral event buffers. They’re bounded by Redis’s RAM (use MAXLEN to cap) and don’t replay a year of history the way Kafka does. Pick Streams when you want Redis ergonomics and Kafka when you want long retention + distributed durability.

How do TTL and eviction policies actually work, and which do you pick for a cache?

One sentence: TTL on a key triggers passive expiration on access + active expiration in a sampled background job; when memory hits maxmemory, the eviction policy decides what to drop — allkeys-lru or allkeys-lfu are usually right for caches.

Concept: Redis doesn’t actively expire all keys on a timer (too expensive). It samples ~20 keys with TTL every cycle, expires those that are due, and repeats if more than 25% were expired. LFU tracks access frequency with logarithmic decay; LRU approximates recency by sampling.

Nuance: use volatile-lru if some keys have TTL (cache) and some don’t (config); allkeys-lfu if Redis is purely a cache and access patterns are skewed; noeviction if every key matters and you’d rather get OOM errors than lose data. Set maxmemory-policy explicitly — the default noeviction is a footgun for caches.

What does WAIT guarantee, and what does it not?

One sentence: WAIT N timeout blocks until the write has been acknowledged by N replicas or the timeout passes; it gives best-effort synchronous-like replication, not a guarantee.

Concept: Redis replication is async by default. WAIT gives the producer feedback on replication lag for a specific write. It doesn’t change replication’s underlying mechanics — if the master fails after the client’s WAIT returned but before fsync, you can still lose the write.

Nuance: the staff-level distinction: WAIT is a feedback mechanism, not a durability mechanism. Pair with AOF fsync everysec or always if you need durability. For real synchronous replication, use a different system (Postgres with synchronous standby).

How does Redis Sentinel differ from Cluster, and when do you pick which?

One sentence: Sentinel provides leader election + failover for a single master/replica setup (no sharding); Cluster shards across many nodes with built-in gossip-based failover — pick Sentinel when one master’s capacity is enough, Cluster when you need horizontal scale.

Concept: Sentinel runs alongside Redis as a separate process; a quorum of Sentinels detects master failure and promotes a replica. Clients query Sentinels for the current master. Cluster nodes gossip directly with each other; clients are slot-aware.

Nuance: Sentinel preserves all Redis features (multi-key transactions, Lua across keys). Cluster restricts multi-key ops to same-slot keys (use hash tags). Most teams under 100GB stay on Sentinel; sharded workloads or >100GB usually need Cluster.

Cache stampede / thundering herd: what is it, and how do you avoid it?

One sentence: when a popular cache key expires, many clients miss simultaneously and slam the source — mitigate with single-flight locks, probabilistic early refresh, or stale-while-revalidate.

Concept: on miss, set a short-lived lock (SET stampede:foo 1 NX PX 5000); only the lock holder regenerates; everyone else waits + reads. Or use probabilistic early expiration: when remaining TTL is < some threshold, a random fraction of requests refreshes early.

Nuance: for catastrophic stampedes (cache flush, mass eviction), the mitigation must include rate-limiting traffic to the source DB, circuit breakers, and serving stale data with a label. The senior framing: “Cache stampede is a coordination problem at the edge; the fix is at the application, not Redis.”

Design rate limiting in Redis. Sliding window, token bucket, or fixed window?

One sentence: sliding-window log with a sorted set is most accurate but storage-heavy; token bucket via Lua is the common production choice; fixed window with INCR + TTL is the simplest but has edge bursts.

Concept: Fixed window: INCR counter:userId; EXPIRE counter:userId 60. Edge case: 100 requests at 0:59, 100 more at 1:00 = 200 in two seconds. Sliding window log: ZADD log:userId <ts> <ts>; ZCOUNT log:userId <now-60> <now>. Accurate; storage is one entry per request. Token bucket: Lua atomic update of (tokens, last_refill_ts).

Nuance: for high-volume APIs, token bucket via Lua atomically wins on cost. For audit trails (“who hit me when?”), the log pattern doubles as audit. redis-cell module implements GCRA (a fancier token bucket) with one command.

-- token bucket Lua snippet
local tokens = tonumber(redis.call('hget', KEYS[1], 'tokens') or capacity)
local last   = tonumber(redis.call('hget', KEYS[1], 'last') or now)
local refill = math.min(capacity, tokens + (now - last) * rate)
if refill < 1 then return 0 end
redis.call('hset', KEYS[1], 'tokens', refill - 1, 'last', now)
return 1
When would you NOT use Redis?

One sentence: as a primary store for data you can’t afford to lose without a thorough durability + ops design, for datasets larger than your RAM budget by a wide margin, or for workloads dominated by random large objects.

Concept: Redis is RAM-bounded. A 500GB working set means 500GB of RAM × replicas. Disk-backed alternatives (KeyDB, DragonflyDB, or just “use Postgres for that”) win on cost when access patterns aren’t latency-critical.

Nuance: the right answer cites use cases: “Redis for hot path; cold path on disk-backed store; reconcile via Streams or app-level invalidation. Don’t put your only copy of irreplaceable data in Redis.”

Famous footguns
  • KEYS on a production cluster. Blocks the event loop; thousands of users wait. Use SCAN.
  • Hot key kills one master. Redis Cluster doesn’t help — the slot lives on one node. Shard the key, randomize, or precompute.
  • maxmemory-policy=noeviction on a cache. Default. Cache fills, you OOM. Pick allkeys-lru or allkeys-lfu explicitly.
  • Redlock for correctness-critical locks. Best-effort only; pair with fencing tokens from a strongly-consistent store for money/inventory.
§ 07  Elasticsearch
Search · Lucene · Inverted index

Elasticsearch

A search engine that some teams pretend is a database.

Full-text + vector Near-real-time Reshard = reindex Not a system of record

Elasticsearch wraps Lucene with a distributed, JSON-over-HTTP cluster model. An index is split into primary shards (fixed at creation) plus replicas; each shard is a Lucene index made of immutable segments. Writes go to a primary shard, then replicate; index changes become visible on refresh (default every 1s).

It is not a system of record. It’s eventually consistent, can’t do multi-document transactions, gets slow under heavy mutation, and reshards by reindexing. Use it as a derived index over your real source of truth.

The 30-second pitch: “Elasticsearch for full-text search, log/metric observability, and vector retrieval. Source of truth lives elsewhere; we sync via CDC. Shard count is a permanent commitment per index; we use aliases to evolve.”

Q&A drills

Why is the shard count fixed at index creation? How do you reshard?

One sentence: documents are routed to a shard by hash(_routing) mod num_primary_shards; changing the modulus would relocate every document, so Elasticsearch makes you create a new index and reindex.

Concept: reindexing is the canonical operational pattern: create idx_v2 with new shard count or mapping; run the _reindex API (or push from the source again); flip the alias from idx=v1 to idx=v2 atomically.

Nuance: the shrink API can reduce shard count (must be a divisor) without full reindex by hard-linking segments; the split API multiplies. Both have constraints. Aliases are the contract apps use; never point apps at a raw index name in production.

PUT idx_v2 { "settings": { "number_of_shards": 12 } }
POST _reindex { "source":{"index":"idx_v1"}, "dest":{"index":"idx_v2"} }
POST _aliases { "actions":[
  {"remove":{"index":"idx_v1","alias":"idx"}},
  {"add":{"index":"idx_v2","alias":"idx"}}]}
How do query phase and fetch phase work, and why does deep paging break them?

One sentence: in query phase each shard returns its top-K matching doc IDs + scores; the coordinator merges into a global top-K; fetch phase pulls the actual documents — deep paging (from=10000) forces every shard to materialize 10000+K hits, and the coordinator sorts millions in memory.

Concept: with N shards and from=F, size=S, each shard returns F+S hits. The coordinator picks the global top S. Cost is N×(F+S) memory + sort. At F=100k, this is brutal.

Nuance: the fix is search_after (cursor-based, stateless) or PIT (point-in-time + search_after, consistent across paging). Both have O(K) cost per page regardless of depth. Deep paging is rejected by default beyond max_result_window=10000 — raise the limit only as a temporary workaround.

Why are heavy updates an anti-pattern?

One sentence: Lucene segments are immutable, so an “update” writes a new doc version and tombstones the old one; segment merges reclaim the space, but heavy churn means continuous merges that compete with queries.

Concept: every update = delete + insert. The deleted doc lives until merge. _id lookups still work because Lucene tracks them. But indexing throughput drops under heavy updates because you’re always merging; p99 search latency rises because merges contend for CPU and disk.

Nuance: the happy path is append-only (logs, events). For mutable entities, sync deltas from your source of truth on a schedule rather than per-write. Time-based indices (one per day/month) avoid mutation entirely — close old indices, never update them.

Explain mappings and why dynamic mapping at scale is dangerous.

One sentence: a mapping defines field types, analyzers, and indexing options — dynamic mapping infers from the first doc that contains a field, and a careless producer can explode the mapping with thousands of fields and crash the cluster.

Concept: Lucene stores per-field state in memory. 10k fields = 10k bits of overhead per doc + per shard. Mapping explosions happen when a producer puts user-controlled keys into a JSON object (e.g., "attributes": { "anything_user_typed": "..." }).

Nuance: mitigations: explicit mappings with dynamic: strict or dynamic: false; flattened field type for true catch-all (single inverted index, no per-key state); index-level index.mapping.total_fields.limit (default 1000). The senior answer: “Treat the mapping as a schema. Validate at ingest. Don’t let users define fields.”

What does the refresh interval actually do, and how does it affect “near-real-time”?

One sentence: refresh writes the in-memory buffer to a new searchable Lucene segment (default every 1s) — that’s why a doc is searchable ~1s after indexing, not synchronously.

Concept: writes go to a buffer + the translog (durability). Refresh creates a new searchable segment; flush (every 30 min or 512 MB translog by default) fsyncs and clears translog. Refresh = visibility; flush = durability.

Nuance: for bulk ingest, set refresh_interval=-1 (or 30s) to reduce segment churn; restore on completion. For “immediate” reads (test code), pass ?refresh=true on the index call — expensive, never use in production hot path. The interview tell: a candidate who confuses refresh and flush hasn’t debugged ES at scale.

Hot/warm/cold/frozen tiers: when do you use each?

One sentence: hot tier serves fresh, frequent-read indices on SSD with replicas; warm holds older read-only indices on cheaper storage; cold has searchable snapshots on object storage; frozen partially-mounts S3 directly — ILM (Index Lifecycle Management) automates the transitions.

Concept: log/metric workloads have a natural age curve: hot data is queried 1000s of times/min, week-old data once a day, year-old data almost never. Tiering matches storage cost to access frequency. Frozen tier is partly-mounted S3 — queries are slow but data costs near-zero.

Nuance: ILM policy: rollover at 50 GB or 7 days → warm at 30 days → cold at 90 days → delete at 365 days. Searches across tiers work but cold/frozen are 10–100× slower; design dashboards to bias hot.

How do you tune for log/metric ingest at 1 TB/day?

One sentence: append-only time-based indices, refresh interval bumped to 30s, sized shards 30–50 GB, ILM policy with hot/warm/cold tiers, and a queue (Kafka) buffering ingest so backpressure doesn’t lose data.

Concept: at 1 TB/day with 7-day retention, you have 7 TB live. With RF=1 replica = 14 TB primary shards. At 50 GB/shard = 280 shards primary. Plan ~10–15 hot data nodes with NVMe; replicas can live on warm tier later.

Nuance: ingest pipelines (Logstash, Filebeat, OTel) batch and pre-process. Refresh interval matters: 1s default gives 1s search latency but high segment count; 30s gives more I/O efficiency. Use ingest pipelines in ES for transformations (parse, enrich) so producers don’t need to.

Explain the inverted index, doc values, and BM25 scoring at a high level.

One sentence: the inverted index maps each term to the docs that contain it (term → postings list); doc values are a column-oriented per-field structure for sorts/aggregations; BM25 scores docs by term frequency × inverse document frequency, normalized for doc length.

Concept: “find docs containing ‘cat’” consults the postings list for ‘cat’. Sorting/aggregating on a field means scanning many docs by ID, which the row-oriented inverted index is bad at — doc values store the same data column-wise so it’s cheap. BM25 (default since 5.0) replaced TF-IDF; it caps the contribution of repeated terms and accounts for doc length.

Nuance: if you don’t need to sort/aggregate on a field, set doc_values: false to save disk. If you don’t need full-text on a field (only exact match), use keyword instead of text. Misusing text for IDs is a common mistake — analyzers tokenize the ID, queries don’t match.

Vector search: how does kNN actually run, and what are the trade-offs?

One sentence: ES uses HNSW (Hierarchical Navigable Small World graphs) per segment for approximate nearest neighbor; query latency is O(log N) per segment, but recall depends on graph parameters (m, ef_construction) and the number of segments.

Concept: HNSW builds a layered graph where higher layers are sparser. Search starts at the top, navigates greedily, drops a layer, repeats. The num_candidates parameter controls breadth at query time. Each segment has its own graph, so segment count affects latency.

Nuance: recall vs latency is the trade. Higher m & ef_construction = better recall, larger index, longer build. Hybrid search (BM25 + kNN, combined via RRF or weighted sum) is typically what you want, not pure vector. Quantization (int8, BBQ) shrinks the vector index 4–32× with modest recall loss.

You hit a hot shard. How do you diagnose and fix it?

One sentence: check shard-level stats (_cat/shards, _nodes/stats/indices) for query rate / time skew, then trace to either skewed routing (custom _routing values), poor shard count vs node count, or an oversized shard.

Concept: default routing distributes by _id hash. Custom routing (e.g., ?routing=tenant_id) co-locates a tenant’s data on one shard — brilliant for read concentration, lethal if one tenant is 10× bigger than others.

Nuance: fixes: increase shard count via reindex; remove custom routing if it’s skewed; use routing partitions (a tenant spans K shards) for whales; raise replicas to spread read load. Search slowlog + indexing slowlog + node hot threads are the diagnostic toolkit.

What does the cluster master do, and what changed in ES 7?

One sentence: the master node manages cluster state — mappings, shard assignments, node membership; ES 7 rewrote discovery + master election to use a Raft-like consensus protocol, eliminating the split-brain footgun of earlier versions.

Concept: only one master is active; data nodes apply cluster state updates pushed by the master. Pre-7, you had to manually set minimum_master_nodes based on quorum math; getting it wrong caused split-brain (two masters). 7+ uses voting configurations and computes the quorum automatically.

Nuance: master-eligible nodes should be 3 or 5, ideally dedicated (no data, no ingest); they should be small (16 GB heap) but stable. The cluster state grows with shard count; very large clusters (10k+ shards) need careful master sizing.

Design product search with filters, facets, and relevance ranking.

One sentence: a query is a bool with must for the user’s search terms (BM25 scored), filter for category/price (no scoring, cacheable), and aggregations for facets; relevance is tuned with field boosts, function_score, and learning-to-rank.

Concept: separate scoring (text query) from filtering (filter clauses). Filters live in a cache and are virtually free on repeat queries. Aggregations on keyword fields backed by doc values give counts per facet. function_score blends in business signals (popularity, freshness, margin).

Nuance: for serious relevance, use learning-to-rank (LTR plugin) trained offline on click data — rerank top-N from BM25. Hybrid with vectors (semantic search via embeddings) for queries that don’t match terms exactly. Synonyms and analyzers at indexing time are where most relevance wins live.

Famous footguns
  • Treating ES as source of truth. No multi-doc transactions, eventually consistent, reindex-prone. Real source elsewhere; ES is the derived index.
  • Heavy updates. Each update is delete + insert + merge. Use append-only or sync deltas.
  • Mapping explosions. User-controlled JSON keys + dynamic mapping = thousands of fields. Set dynamic: strict or use flattened.
  • Deep paging. from=100000 kills a coordinator. Use search_after or PIT.
§ 08  Coordination Stores: ZooKeeper / etcd
Consensus · Strongly consistent KV · Watch primitives

ZooKeeper & etcd

A small, strongly-consistent KV for the things that must be true.

Linearizable Watches + leases Tiny payloads only Not a database

Coordination stores are small, strongly-consistent key-value systems built on a consensus protocol — Zab (Atomic Broadcast) for ZooKeeper, Raft for etcd. They expose primitives that distributed systems need: leader election, distributed locks, configuration, service discovery, and watches/notifications on key changes.

They are not databases. Payloads are tiny (KB, not MB). Throughput is in the thousands of writes per second, not hundreds of thousands. They’re sized for “the truth about the cluster”, not application data.

The 30-second pitch: “ZooKeeper or etcd for coordination — leader election, locks, config, service discovery. Tiny payloads, linearizable reads, ephemeral nodes / leases for liveness. Pick etcd for new systems (Raft, gRPC, Kubernetes’ choice); ZK if you’re already in the JVM ecosystem.”

Q&A drills

What problem do these systems actually solve? When would you reach for one over a regular DB?

One sentence: they solve distributed agreement on small mutable state — “who’s the leader?”, “what’s the current config?”, “is this lock held?” — with linearizable reads and writes, which a regular DB can’t guarantee across nodes without similar machinery.

Concept: the consensus core (Raft, Zab, Paxos) elects a leader, replicates a log of state-machine commands across a quorum, and ensures every node applies the same commands in the same order. The cost is that every write needs majority ack — latency = WAN RTT in multi-DC, throughput is single-leader-bounded.

Nuance: you reach for them when correctness across distributed processes matters. A regular DB serves the data plane; ZK/etcd serves the control plane. Examples: Kafka used ZK for controllers; Kubernetes uses etcd for cluster state; HDFS uses ZK for the active NameNode; Vault uses Consul/etcd for HA.

How does Raft actually work?

One sentence: Raft has three roles (leader, follower, candidate); the leader replicates an append-only log to followers; entries become committed once a majority has them; followers apply committed entries to a state machine in order.

Concept: Each term has at most one leader. Followers vote in elections triggered by leader timeout. The leader sends AppendEntries RPCs (heartbeats + log entries). Safety property: a committed entry is in the log of all future leaders. Liveness: requires a majority of nodes alive.

Nuance: Raft splits the consensus problem into leader election + log replication + safety, deliberately making it more teachable than Paxos. The most subtle parts: ensuring leaders only commit their own term’s entries (the “previous-term commit” bug), and the log-completeness check during voting.

Zab vs Raft vs Paxos — what’s the practical difference?

One sentence: all three solve consensus with majority quorums; Paxos is the foundational theory, Raft is a deliberately simpler reformulation, Zab is ZooKeeper’s atomic-broadcast protocol that ensures FIFO order from the leader.

Concept: Paxos (Lamport, 1998) is notoriously hard to understand; Multi-Paxos and variants (EPaxos, Mencius) extend it. Raft (Ongaro & Ousterhout, 2014) was explicitly designed for understandability. Zab is an atomic broadcast that gives ZooKeeper its primary-order guarantee for state changes.

Nuance: for engineering purposes the differences are minor — all give linearizable writes, majority quorums, leader-driven replication. Pick Raft for new systems (clearer literature, more implementations: hashicorp/raft, etcd/raft, openraft). Zab is just “ZooKeeper’s thing”.

How do you implement leader election with these systems?

One sentence: in ZK, candidates create an ephemeral sequential znode under a leader path; the lowest sequence is leader; others watch the predecessor; on death, the ephemeral node disappears and the next candidate is notified.

Concept: ephemeral znodes are tied to a session; when the session expires (heartbeat lost), they vanish. Sequential numbering gives a deterministic order. The watch-on-predecessor pattern avoids a stampede when the leader dies (only one candidate gets notified).

Nuance: in etcd, the equivalent uses a lease (a TTL'd token) and the elect primitive (or roll your own with a key + lease + compare-and-swap). The pitfall in both systems: session expiration during a long GC pause — you think you’re leader, but the cluster has elected someone else. Pair with fencing tokens downstream.

// ZK leader election
create /election/n_ EPHEMERAL|SEQUENTIAL "host:1234"
list /election sorted -> if I'm first, I'm leader
else watch the predecessor
What are watches in ZK / etcd, and where do they go wrong?

One sentence: watches are server-side notifications fired when a key/znode changes — in ZK they’re one-shot (must re-register after firing), in etcd they’re streaming (open a gRPC stream, get every change).

Concept: watches let clients react to state changes without polling. ZK guarantees the watch fires before the corresponding read sees the new value, so “notify-then-read” is correct. etcd uses a global revision and streams events from a starting revision, so you can replay missed events on reconnect.

Nuance: ZK’s one-shot model is a footgun: you can miss the second event between firing and re-registering. The fix: read the current state right after the watch fires, and re-register. etcd’s streaming model is much friendlier; just track the last-seen revision.

How do distributed locks work, and what are fencing tokens?

One sentence: a lock is a key/znode held by one client; on acquire you get a unique fencing token (a monotonically increasing number, typically the consensus log index); downstream resources accept writes only with a higher token than the last seen, so a stale lock holder can’t cause damage.

Concept: the canonical Kleppmann argument: any lock without fencing is unsafe under GC pauses or network delays. The lock holder pauses for a minute, the lock TTL expires, another client acquires, the original wakes up and acts — both think they hold the lock. Fencing prevents the late writer.

Nuance: ZK’s session model + ephemeral nodes give some safety, but fencing is still recommended for shared resources. etcd lease + CAS on the protected resource gives the same property. The senior answer: “Locks are advisory; fencing tokens are how you make them correct.”

ZooKeeper vs etcd vs Consul: practical differences.

One sentence: ZK is mature, JVM-based, tree-shaped data model with sessions and watches; etcd is gRPC, Raft, key-value with leases — the Kubernetes choice; Consul adds service discovery and a multi-DC gossip layer on top of Raft.

Concept: ZK’s znode tree is a hierarchical name space; clients walk paths, watch children. etcd is flat key-value with key prefixes; revisions track every change. Consul exposes Raft-backed KV plus health checks, DNS interface, and multi-DC.

Nuance: picking: Kubernetes ecosystem → etcd (it’s already there). Hadoop / Kafka old setups → ZK. Service mesh + multi-DC service discovery → Consul. New green-field: etcd, almost always. ZK is being phased out (Kafka KRaft, recent HBase versions).

Why do these systems cap throughput and payload size so aggressively?

One sentence: consensus is leader-bounded — every write must be replicated to a majority and applied in order — and any single big payload bloats the log and slows replication for everyone, so the systems push back hard on misuse.

Concept: typical throughput: ZK/etcd handle ~5–30k writes/sec on good hardware. Payloads default to 1 MB max in ZK (znode size), 1.5 MB max in etcd (request size). These limits aren’t cosmetic — a 100 MB payload would block the leader for seconds.

Nuance: if you find yourself wanting to store “the config blob for service X” and it’s 50 MB, the answer is to put a pointer (S3 URL) in the coordination store, not the blob. Same with secrets — Vault references stored in etcd; secrets themselves elsewhere.

How do you size the cluster, and why is it always 3 or 5?

One sentence: consensus tolerates ⌊(N-1)/2⌋ failures — 3 nodes survive 1 failure, 5 survive 2, 7 survive 3 — and odd numbers maximize fault tolerance per node added; beyond 5 the latency cost outweighs the fault tolerance gain.

Concept: 4 nodes tolerate 1 failure (same as 3) but require 3 acks instead of 2; even numbers strictly hurt. 5 is the sweet spot for production critical systems. 3 is fine for less critical clusters where 2 simultaneous failures are unlikely.

Nuance: spread across 3 AZs (3 nodes = one per AZ; 5 nodes = 2/2/1). Avoid “all 3 in one rack” — that defeats the point. Learner / non-voting members in etcd let you add a node without it counting toward quorum during catch-up.

What goes wrong when you put too much in etcd?

One sentence: etcd’s default DB size limit is 2 GB; beyond that, compaction lags, defrag is required, leader changes get slow, and the whole control plane stalls — Kubernetes operators see this when CRDs or events accumulate without cleanup.

Concept: etcd MVCC keeps every revision until compacted. Without compaction, the DB grows unbounded. Compaction removes old revisions; defrag reclaims space (but locks the leader briefly). Both must run on a schedule.

Nuance: Kubernetes runs auto-compact on a 5-min cadence. Symptoms of an over-stuffed etcd: rising apply latency, frequent leader changes, kube-apiserver 5xx’s. Recovery: trim event TTLs, defrag, and bump the size limit only as a stopgap.

etcdctl defrag --cluster
etcdctl compaction $(etcdctl endpoint status --write-out=json | jq '.[].Status.header.revision')
Design service discovery for a microservices platform. Why coordination, not DNS?

One sentence: use etcd or Consul as the source of truth for healthy instances + their addresses; clients (or a sidecar) watch for changes and update their connection pool; DNS is a fallback / interop layer.

Concept: DNS works but TTLs are blunt — a 30s TTL means 30s of stale lookups on a deregister. A coordination store with watches gives sub-second propagation. Each service registers a key with a lease; if the lease expires (instance dies), the entry is auto-removed.

Nuance: the modern stack: a service mesh (Istio, Linkerd) reads from xDS (often backed by etcd) and pushes routing rules to data-plane proxies. The mesh gives you health checks, circuit breakers, retries, mTLS — richer than just discovery. The senior answer mentions blast radius: a flaky etcd takes the whole platform down; treat it like the most critical system you have.

What’s the most common operational mistake with these systems?

One sentence: running them on slow disks. Consensus replicates to disk before acking; fsync latency directly determines write latency, and a slow disk turns a 5ms cluster into a 500ms cluster.

Concept: ZK and etcd both fsync the WAL on every committed transaction. Network-attached storage (EBS gp2, slower NFS) has fsync latencies in the tens of ms. NVMe local SSD is the right baseline; gp3 with provisioned IOPS works.

Nuance: other classics: putting them on the same disk as the workload (I/O contention from kafka or DB), running them in containers without resource limits (GC pauses cause leader flapping), letting clock skew get out of hand (Raft tolerates skew but health checks don’t).

Famous footguns
  • Storing application data. ZK/etcd are coordination stores. Tens of MB is too much. Use a pointer.
  • Locks without fencing tokens. GC pauses violate mutual exclusion. Always fence the protected resource.
  • Slow disks. Every committed write hits fsync. NVMe or fast cloud SSD; never network-attached without provisioned IOPS.
  • Even-numbered clusters. 4 nodes don’t survive more failures than 3 but cost more latency. Always odd: 3, 5, 7.
§ 09  RabbitMQ
AMQP broker · Smart routing · Per-message ack

RabbitMQ

A smart router with per-message acks — queue-shaped, not log-shaped.

Per-message ack Flexible routing Throughput ceiling No replay

RabbitMQ is an AMQP-based message broker. Producers publish to exchanges; exchanges route to queues by binding rules; consumers ack or nack each message individually. Messages persist on disk if marked durable, sit on a queue until consumed, and are deleted on ack.

It is not a log. There’s no replay (without effort), no per-partition order across many consumers, no “rewind to last week.” The trade is per-message handling: priorities, TTLs, dead-lettering, fanout by routing key — expressive in ways Kafka isn’t.

The 30-second pitch: “Rabbit for task queues, RPC, fanout by routing key, complex ack flows. Per-message reliability matters more than raw throughput. We use Quorum Queues for HA. For event logs and replay, we use Kafka instead.”

Why RabbitMQ over NATS / SQS in this guide: RabbitMQ is the most-asked “non-Kafka broker” in interviews because its concept model (exchanges, bindings, per-message acks) is the canonical contrast to Kafka’s log model. NATS is excellent but appears less in design loops; SQS is essentially a managed queue that doesn’t exercise the same protocol-level questions. If interviewers ask about “a queue,” they almost always mean RabbitMQ.

Q&A drills

Explain exchanges, queues, and bindings. Walk through routing for a message.

One sentence: producers publish to exchanges (not queues directly); exchanges route to queues based on bindings (rules tied to routing keys or headers); a single message can land in zero, one, or many queues based on the routing logic.

Concept: exchange types: direct (exact routing-key match), topic (wildcard match: orders.*.eu), fanout (every bound queue), headers (match on AMQP headers), x-consistent-hash (load-balance to one of several bound queues).

Nuance: the indirection is the point. Producers don’t know about queues; consumers subscribe by creating queues + bindings. New consumer types attach without producer changes. Compare to Kafka where the producer picks the topic and the consumer picks how to interpret — Rabbit is more expressive at the cost of more concepts.

// publish
basic_publish(exchange='orders', routing_key='orders.created.eu', body=...)
// bindings
queue_bind('shipping_eu', 'orders', 'orders.created.eu')
queue_bind('analytics',   'orders', 'orders.*.*')
Why does RabbitMQ struggle at very high throughput compared to Kafka?

One sentence: Rabbit’s design optimizes for per-message reliability and routing flexibility — per-message acks, per-message TTLs, conditional dispatch — which adds CPU + I/O overhead per message; Kafka batches sequentially and pushes most coordination to consumers, so it scales an order of magnitude higher.

Concept: a Rabbit message round-trip involves: persist to disk (if durable), index in queue structure, deliver to consumer, await ack, remove from queue. Each of these is a per-message cost. Kafka appends to a log file in a batch and lets consumers track their own offset.

Nuance: Rabbit handles ~50k msg/s per node comfortably; tuned Quorum Queues hit ~100k. Kafka does millions per node. The senior framing: “Rabbit is queue-shaped: per-message reliability. Kafka is log-shaped: batched throughput. Pick by what your messages need, not just by load.”

Classic Mirrored Queues vs Quorum Queues — what changed?

One sentence: classic mirrored queues used a leader/replica pattern with non-deterministic failure modes (synchronization bugs, lost messages on partition); Quorum Queues (3.8+) use Raft for replication with deterministic semantics — in 3.10+, mirrored queues are deprecated.

Concept: Quorum Queues replicate via Raft to 3 or 5 members; writes commit on majority ack. Failover is fast and consistent. Trade: higher per-message overhead than non-replicated, slightly less throughput than classic.

Nuance: for new clusters, default to Quorum Queues. Transient/non-critical work can use classic non-replicated queues for cheaper throughput. Streams (also 3.9+) add a Kafka-like log with replay — if you need both AMQP and replay, Streams + Quorum is the modern stack.

How do publisher confirms and consumer acks actually work?

One sentence: publisher confirms ack the producer that the broker has accepted (and persisted, for durable + persistent messages) the message; consumer acks tell the broker the consumer has finished processing — both are required for at-least-once delivery.

Concept: on the producer, confirm_select opens confirm mode; the broker sends basic.ack per message (or per batch via multiple). On the consumer, basic.consume with ack=manual means messages stay on the queue until the consumer sends basic.ack.

Nuance: auto-ack on the consumer is a footgun — messages are removed from the queue as soon as delivered, so a consumer crash mid-processing loses them. Prefetch (basic.qos) limits unacked messages per consumer; without it, a slow consumer hoards messages from the queue. The right pattern: prefetch 10–100, manual ack after processing, with idempotent handlers because retries can deliver duplicates.

What’s a dead-letter exchange and when do you use it?

One sentence: a dead-letter exchange (DLX) is where messages go when they expire (TTL), are rejected (basic.reject with requeue=false), or exceed a queue’s length limit — the canonical way to isolate poison messages and route them for inspection or retry.

Concept: set x-dead-letter-exchange on the queue; rejected messages re-publish to that exchange, where you can route them to a “poison” queue for ops review or to a retry queue with TTL that eventually republishes.

Nuance: the “retry with backoff” pattern: queues with increasing TTLs (5s, 30s, 5min) all DLX-back to the original work queue. Each failed message gets a header counter; after N retries it goes to permanent DLQ. This is how production-grade Rabbit pipelines handle transient failures without overwhelming downstream systems.

How do you do RPC over RabbitMQ, and is it a good idea?

One sentence: client publishes to a request exchange with reply_to set to its own callback queue and a unique correlation_id; the server processes and replies to reply_to; the client matches replies by correlation ID.

Concept: the pattern works and is documented. Direct reply-to (reply_to=amq.rabbitmq.reply-to) avoids creating per-request queues. Tornado/Spring/etc. have helpers.

Nuance: is it a good idea? Sometimes — for cross-language, fire-and-process workloads where the request takes seconds. For sub-second RPC, gRPC or HTTP is leaner: no broker hop, no fanout overhead. The real win for AMQP RPC: built-in retries, visibility into queue depth, and the natural decoupling of producer from consumer scaling.

Design a task queue for image processing: each job takes 10s, you need at-least-once, dead lettering, and per-tenant isolation.

One sentence: a per-tenant queue (or a sharded set) bound to a topic exchange, durable + persistent messages, manual ack with prefetch=1 per worker, DLX with retry queue (TTL backoff) and a permanent DLQ after N failures.

Concept: per-tenant queues prevent one noisy tenant from starving others. Prefetch=1 on long jobs ensures even distribution across workers. Persistent + durable + publisher confirms = at-least-once durability. Workers are idempotent (deduplicate by job ID).

Nuance: for huge tenant counts (10k+), per-tenant queues become a queue management problem — consider consistent-hash exchange to distribute work to a fixed pool of queues with hash-based affinity. Add metrics on queue depth + age of oldest message; alert before SLA bites.

What’s the difference between a lazy queue and a regular queue?

One sentence: lazy queues store messages on disk by default, holding only metadata in memory — great for queues that occasionally back up huge (millions of messages); regular queues keep recent messages in memory for low-latency dispatch.

Concept: regular queues page to disk under memory pressure but at high cost (sync flush). Lazy queues skip the cache and write directly — consistent throughput regardless of depth, at the cost of slightly higher per-message latency.

Nuance: use lazy when queues might back up to millions (work queues with bursty producers, deferred jobs). Use regular when latency matters and queues stay small. Quorum queues are effectively lazy (everything is on disk + Raft log).

What happens during a network partition? How does “pause-minority” work?

One sentence: in classic clustering, a partition can split the cluster; the cluster_partition_handling mode decides what happens — pause_minority stops the smaller side until partition heals (preserves consistency, costs availability).

Concept: options: ignore (let both sides accept writes; reconcile manually), pause_minority (CP-leaning), autoheal (the cluster picks a winning partition automatically). Quorum queues internally use Raft and don’t need this knob — minority partitions just can’t commit.

Nuance: pause_minority + odd cluster size is the safe default. With Quorum Queues, partition handling is per-queue (Raft majority required for writes), which is much cleaner than the cluster-wide setting.

How do you handle backpressure when consumers can’t keep up?

One sentence: Rabbit applies flow control automatically when memory or disk thresholds are exceeded — producers see slowed acks; combine with TTL, max-length, and lazy queues to bound damage.

Concept: AMQP’s connection.blocked notification tells producers the broker is throttling. Queue-level x-max-length + DLX bounds queue size and routes overflow elsewhere. x-message-ttl ages messages out automatically.

Nuance: don’t let queues grow unbounded — you’ll OOM the broker. The right pattern: cap queue length, send overflow to DLQ for visibility, scale consumers by depth metrics. Senior framing: “Backpressure is a property of the system, not just the broker. The broker tells you where the bottleneck moved.”

When does Kafka beat RabbitMQ, and vice versa?

One sentence: Kafka wins for high-throughput event streams, multi-consumer fanout with replay, and event-sourced architectures; Rabbit wins for task queues, complex routing, per-message TTL/priority, RPC, and lower-volume workloads where per-message control matters more than throughput.

Concept: Kafka is a log: append, retain, replay, partitioned ordering. Rabbit is a queue: route, deliver, ack, delete. Different shapes; different problems.

Nuance: the “both” pattern is common: Kafka for the event spine (CDC, audit, analytics streams) and Rabbit for task queues (image processing, email, cleanup). Don’t pick one for both jobs unless one shape really doesn’t apply — you’ll bend it badly.

RabbitMQ Streams: what are they and why do they exist?

One sentence: Streams (3.9+) are a Kafka-like append-only log built into RabbitMQ — replay, multi-consumer fanout, high throughput — bridging the gap so teams already on Rabbit don’t need a second system for log-shaped use cases.

Concept: Streams use a custom binary protocol (faster than AMQP for this workload), support consumer offsets, and reach Kafka-class throughput on appropriate hardware. AMQP clients can still consume via a compatibility layer.

Nuance: Streams are not a Kafka killer — Kafka’s ecosystem (Connect, Streams API, Schema Registry, KRaft) is mature. But for organizations already running Rabbit who want replay-capable feeds, Streams avoids adding a whole new system. Worth knowing about if you’re defending Rabbit against “but Kafka...”

Famous footguns
  • Auto-ack on the consumer. Crash mid-processing = lost message. Always manual ack with prefetch.
  • Unbounded queue depth. Producers outpace consumers, broker OOMs. Set x-max-length + DLX.
  • Mirrored queues in 3.10+. Deprecated. Migrate to Quorum Queues; the replication semantics are night-and-day better.
  • RabbitMQ as Kafka. Trying to do replay, partitioned event log, cross-region streaming. Use Streams, or just use Kafka.
§ 10  Cross-Cutting

The questions that compare engines.

Anyone can recite a single engine’s docs. Staff signal lives in the “why this and not that” calls. Drill these until the trade-off comes out unprompted.

When would you pick Cassandra over DynamoDB?

One sentence: Cassandra wins when you need on-prem or non-AWS deployment, predictable cost at huge sustained scale, and tunable per-query consistency; Dynamo wins when you want zero ops, deep AWS integration, and serverless billing.

Concept: they have similar shapes — partition key + clustering, LWW conflict resolution, query-first modeling, no joins, no ACID across rows by default. The differences are operational. Cassandra: you run it, you tune it, you pay flat per node, you can deploy anywhere. Dynamo: AWS runs it, you pay per RCU/WCU, you can’t leave AWS.

Nuance: at huge sustained throughput (>1M ops/s), Cassandra is often cheaper than Dynamo provisioned (and dramatically cheaper than on-demand). At small/medium scale, Dynamo wins on ops cost — you’re not running a 12-person SRE team. ScyllaDB is the third option: Cassandra-compatible API, shard-per-core, 5–10× better hardware utilization. The senior answer names it.

Why isn’t Redis a database?

One sentence: it can be one if you accept the constraints — AOF + replication + persistence policies make Redis as durable as anyone else — but the design center is “in-memory data structures with optional persistence”, not “system of record with optional caching.”

Concept: Redis defaults are tuned for speed: async replication, no fsync per write, single-node failover via Sentinel. Run as a database means: fsync everysec AOF, RF replicas, sized RAM for full dataset, monitored failover, capacity planning around RAM cost.

Nuance: teams that do use Redis as a primary store usually have niche access patterns (sub-ms latency required, dataset fits in RAM economically, ops team that knows AOF tuning). For most workloads, the right framing: “Redis as cache + ephemeral state, durable store on Postgres or Dynamo behind it.”

When does Kafka beat RabbitMQ?

One sentence: Kafka beats Rabbit when you need replay, very high throughput, multi-consumer fanout over the same data, or an event log as integration backbone; Rabbit beats Kafka for task queues, RPC, complex routing rules, per-message TTL or priority.

Concept: the shape distinction: Kafka is a partitioned log retaining all messages for a window; Rabbit is a queue that deletes messages on ack. Replay, audit, “reprocess everything for a new consumer” — only Kafka. Per-message ack with retry counter, dead-letter routing, priority queue — only Rabbit.

Nuance: use both in many real systems: Kafka for the event spine, Rabbit for the task queue layer. Beware the “we’ll just use Kafka for queues” design — you end up reimplementing acks, retries, and dead-lettering on top.

Is Postgres + logical replication a valid alternative to Kafka?

One sentence: for low-to-moderate event volumes (~tens of thousands/sec), an outbox table + Debezium + a downstream consumer is a perfectly fine Kafka replacement; at higher volumes, Postgres logical replication becomes the bottleneck before Kafka would.

Concept: the outbox pattern: write your business row + an outbox row in one transaction; Debezium reads the WAL via logical replication slot; events go wherever (Kafka, Rabbit, HTTP). You get atomic publish-with-write without 2PC.

Nuance: limits: the outbox table grows; you need a vacuum strategy. A single replication slot pins WAL on the primary, so a stuck consumer = full disk. At 100k+ events/sec, Postgres logical replication starts to lag and the slot disk usage becomes a real burden — that’s when you graduate to Kafka. The senior answer: “Outbox + CDC for early-stage systems; Kafka for scale-out.”

When would you pick MongoDB over Postgres + JSONB?

One sentence: Mongo wins when documents are the dominant data shape, you need horizontal sharding for write scale, and access patterns rarely cross documents; Postgres + JSONB wins when you need transactions, joins, strong typing on most fields and a few flexible ones.

Concept: Postgres + JSONB gives you SQL + ACID + GIN indexes on JSON paths. It’s shockingly capable. You can model 80% of “document” workloads with no compromise. The 20% Mongo wins: when you actually need horizontal write scale (Postgres won’t shard natively); when document size routinely exceeds a few KB and you’d rather not stress JSONB; when you want a managed cluster that already speaks documents (Atlas).

Nuance: the failure mode of “Mongo because flexible”: schema drift, no transactions across documents, sharding pain. The failure mode of “Postgres + JSONB everywhere”: planner statistics on JSON are weak, deeply nested JSON aggregates are slow. The senior framing: “Default to Postgres. Move to Mongo when sharding becomes the bottleneck.”

Elasticsearch vs Postgres FTS — when does ES actually pay off?

One sentence: Postgres FTS (tsvector + GIN) handles up to ~tens of millions of docs with simple ranking very well; ES wins when you need analyzers, multi-field weighting, faceted search with sub-second aggregations, vector search, or scale beyond a single Postgres node.

Concept: Postgres FTS is “real” full-text — tokenization, stemming, ranking with ts_rank. It struggles when you want per-field analyzer configuration, complex relevance tuning, multi-language analyzers, autocomplete with custom analyzers. ES gives all of that, plus aggregations on doc values for facets, plus vector search.

Nuance: the underrated tier between them is Meilisearch / Typesense — lighter than ES, more capable than PG FTS. The decision tree: small (<10M docs, simple ranking)? PG FTS. Mid (need facets, complex relevance)? ES or a search-dedicated managed service. Big (logs, observability, multi-tenant search at scale)? ES with proper tiering.

ZooKeeper vs etcd vs Consul — practical differences?

One sentence: ZK is the legacy choice tied to JVM ecosystems (Hadoop, older Kafka, HBase); etcd is the Kubernetes-era default with cleaner APIs and Raft; Consul adds service discovery and multi-DC gossip on top of Raft.

Concept: all three give linearizable reads, majority quorums, leader-driven replication, watches/notifications, and small-payload constraints. They’re largely interchangeable for the consensus core; the differences are API, ecosystem, and added features.

Nuance: for new green-field, etcd is almost always right — gRPC API, well-supported, Kubernetes brought it everywhere. ZK if you’re in a JVM stack already running it. Consul when you specifically want service-mesh-adjacent features (health checks, DNS interface, multi-DC). Avoid “all three” in one stack — it’s a coordination problem about coordination tools.

Why is exactly-once so hard to get right?

One sentence: “exactly-once delivery” across two systems is impossible without distributed atomic commit (which has its own problems); what’s achievable is effectively-once processing via idempotent operations on the receiver.

Concept: the canonical example: send a message to Kafka and write to a database. Kafka transactions don’t span Kafka. 2PC has well-known liveness issues (TM crash leaves participants blocked). The pragmatic alternative: assign every message a unique ID; the receiver checks “have I seen this ID?” before processing.

Nuance: “exactly-once” in Kafka Streams is real, but it’s scoped to the Kafka-to-Kafka path (idempotent producer + transactions covering produce + offset commit). The moment you sink to a non-Kafka system, you’re back to idempotent operations or the outbox pattern. The senior interview answer: “Exactly-once processing requires idempotent consumers. The broker can deduplicate within itself; the world won’t.”

What’s the difference between log-based and statement-based replication?

One sentence: statement-based ships SQL statements to replicas (re-executes them); log-based ships the resulting row changes (applies them) — log-based is deterministic and faster, statement-based handles non-deterministic functions (like NOW()) badly.

Concept: Postgres streaming replication is binary log-based (WAL byte-for-byte). MySQL has both modes; default is now row-based binlog. Mongo’s oplog is a statement-like document operation log. Cassandra ships mutations row-wise. Replicas applying logs deterministically is the only way to get consistent replicas.

Nuance: classic statement-based bug: UPDATE x SET t = NOW() — primary and replica disagree because NOW() evaluates differently. Row-based binlog records the actual values written. Logical replication (Postgres pgoutput, MySQL row-based) is the modern default and the foundation for CDC pipelines.

Why does sharding break things you didn’t expect?

One sentence: sharding turns single-node guarantees (transactions, joins, unique constraints, secondary indexes, aggregates) into distributed problems — each requires either a coordinator (latency cost) or a redesign (denormalization, app-side joins).

Concept: a unique constraint across shards needs a global index (Mongo enforces uniqueness only on the shard-key prefix). A join across shards becomes scatter-gather. A transaction across shards becomes 2PC. SUM across shards needs an aggregator. None of these are impossible, all are slower and more failure-prone.

Nuance: the right design when sharding: pick a shard key that keeps every important query within one shard (tenant ID is usually right). Accept that a few queries become cross-shard and design for it. Don’t pretend sharding is “just config” — it’s an architecture.

How do you decide between strong, causal, and eventual consistency?

One sentence: pick the weakest model that satisfies the use case — strong for money/inventory/locks, causal for user-facing flows (read-your-writes, monotonic reads), eventual for caches, analytics, and feeds where slight staleness is invisible.

Concept: linearizable = single global timeline (most expensive). Causal = if A happened before B, everyone sees A first; concurrent ops can reorder. Eventual = converges “eventually”, no timing guarantee. Most user-facing apps need causal, not linearizable; most engineers reach for linearizable by default and pay too much.

Nuance: the trade-off compounds: stronger consistency = higher latency + lower availability under partition. The senior framing names it explicitly: “The cart total is causal — my reads see my writes. The inventory deduction is linearizable — we can’t oversell. The product feed is eventual — it’s fine if it’s 30s stale.”

If I told you we have one OLTP database, one cache, one queue, and one search index, which engines do you pick?

One sentence: Postgres for OLTP (default), Redis for cache (no real competitor at sub-ms), Kafka or RabbitMQ for queue depending on shape (log vs queue), Elasticsearch or Postgres FTS for search depending on scale.

Concept: defending each: Postgres — ACID, mature, JSONB for flexibility. Redis — sub-ms ops, rich data structures, well-known operational profile. Kafka if events need replay, Rabbit if tasks need per-message reliability. ES if search needs analyzers + facets, PG FTS if simple.

Nuance: the staff-level move is naming the tradeoff in each pick: “I’d default to Postgres + Redis + Rabbit + PG FTS for a startup; swap PG FTS for ES once we hit relevance complexity, swap Rabbit for Kafka once we need replay, and shard Postgres or move to Aurora when single primary doesn’t fit.” A picker that can articulate when to upgrade beats one that picks the most powerful engine for everything from day one.

What’s the rubric for the “30-second database defense” in a system design interview?

One sentence: four-part structure: workload (access pattern, scale, consistency, geography) → candidate engines (the 2–3 with matching shape) → trade-off you’re accepting → failure mode (what breaks, what we monitor, what the runbook does).

Concept: interviewers want to hear that you’ve thought about the failure case before the happy case. “The database is Dynamo because the access pattern is key-based, single-digit-ms, multi-region. We accept LWW on Global Tables; we don’t use it for counters. Failure mode is hot partition; we shard high-traffic keys with a write-suffix; we alert on throttle metrics.”

Nuance: not naming the runner-up is a yellow flag. Saying “Postgres” without explaining when you’d move off it is the same. The structure is: here’s what I picked, here’s the second choice, here’s when I’d switch. That’s the answer that signals staff.
