§ 01  Distributed systems fundamentals

The fallacies, the failures, and the lies the clock tells.

Every distributed system is a meditation on three lies: the network works, time advances uniformly, and processes are alive when you can’t reach them. Senior engineers don’t just know these lies — they instinctively design around them.

Concept · The three hard truths (1) The network is a liar. Packets reorder, drop, duplicate, arrive late, or never. You cannot tell “dead” from “slow” from a single observation — this is the foundation of every distributed-systems pain point.

(2) Time is a fiction. Wall clocks drift, jump backward (NTP), and disagree across nodes by milliseconds. Logical clocks (Lamport, vector) preserve happens-before without trusting wall time. HLC (hybrid logical clocks) sneak physical time back in for human readability.

(3) Coordination is expensive. Every linearizable operation costs at least one round-trip through a quorum. Most data doesn’t need linearizability — the staff-engineer move is knowing which operations actually do.
What are the 8 fallacies of distributed computing?

Coined by L. Peter Deutsch & James Gosling at Sun. The eight things engineers wrongly assume:

  • The network is reliable — it isn’t. Drops, partitions, asymmetric failures.
  • Latency is zero — cross-region RTT is 60–200ms; even intra-AZ is 0.5–1ms.
  • Bandwidth is infinite — egress charges, NIC saturation, TCP head-of-line.
  • The network is secure — assume hostile, even inside the VPC (zero trust).
  • Topology doesn’t change — nodes come and go; routes flip; ASGs scale.
  • There is one administrator — multi-team, multi-cloud, multi-vendor.
  • Transport cost is zero — serialize/deserialize, encryption, framing all cost.
  • The network is homogeneous — mix of L2/L3 hops, MTUs, NICs, congestion algos.
Probing: Which fallacy bit you in production? “We assumed Region A reaching Region B implied B reaching A — partial partition” is a great war story.
Define partial failure, gray failure, and Byzantine failure.

Partial failure: some components fail while others continue. The defining property of distributed systems — in a single process, you crash or you don’t; in a cluster, half the nodes might be unreachable from the other half. Mitigation: timeouts, retries, circuit breakers, idempotency.

Crash-stop (fail-stop): a node either runs correctly or stops; once stopped, it stays stopped. The friendly failure model.

Gray failure: the node is “up” by health check but degraded — high latency, dropped packets, half-broken disk, GC death-spiral. Worse than a crash because load balancers keep sending traffic. Detection requires differential observation (Gray Failure paper, MSR).

Byzantine failure: nodes can act arbitrarily — lie, send conflicting messages, collude. Required by blockchains, consensus across trust boundaries. Most enterprise systems assume crash-stop and accept that compromised nodes break invariants. PBFT, HoneyBadger, Tendermint handle Byzantine; Raft/Paxos do not.

Probing: “Byzantine” is the trap word. Most candidates over-claim. The right answer is “we assume crash-stop, so a malicious node breaks safety — here’s the trust boundary.”
Lamport clocks vs vector clocks vs HLC — when which?

Lamport clock: single integer per process; on send, attach L; on receive, set L = max(local, received) + 1. Preserves causal order (if a happened-before b, then L(a) < L(b)) but not the converse — concurrent events may have ordered timestamps. Cheap, total order via tiebreak on node ID.

Vector clock: a vector with one entry per node. Increment own slot on local event, take element-wise max on receive. Detects concurrency — two events are concurrent iff neither vector dominates. Used by Dynamo for conflict detection. Cost: O(N) bytes per timestamp where N = nodes.

HLC (hybrid logical clock): combines physical time with a logical counter. The high bits track wall-clock (so timestamps are human-readable / monotonic across long pauses), the low bits resolve ties when wall clocks tie. Used by CockroachDB, MongoDB. Bounded skew from physical time means you don’t need TrueTime hardware.

// Lamport receive
on_receive(msg):
    local_clock = max(local_clock, msg.clock) + 1

// Vector clock receive (V[i] is this node's slot)
on_receive(msg):
    for i in nodes:
        V[i] = max(V[i], msg.V[i])
    V[self] += 1
Gotcha: Vector clocks grow with cluster size. Dotted version vectors and bounded variants exist; Riak uses dotted version vectors specifically to bound them.
What is Spanner’s TrueTime and why does it matter?

Google Spanner uses GPS + atomic clocks in every datacenter to bound clock uncertainty. TrueTime returns an interval [earliest, latest] — not a point. The bound (epsilon) is typically <7ms. Spanner exploits this: to commit a transaction at time t, it waits out the uncertainty (commit-wait) so any later transaction’s now() is guaranteed to exceed t. This delivers external consistency (linearizability across the entire global system) without paying coordination on every read.

The hardware is the secret sauce. CockroachDB approximates without atomic clocks via HLC + uncertainty intervals; reads in the uncertainty window restart, which is cheaper than commit-wait but bounded only probabilistically.

Probing: “could you build Spanner without TrueTime?” The honest answer: you can get close (CockroachDB does), but you give up some operations or accept restart-on-uncertainty. The hardware is what makes Spanner’s SLA defensible.
Explain the two generals problem.

Two armies on opposite hills must attack at the same time to win; messengers between them can be captured. No finite exchange of acknowledgments achieves common knowledge of agreement — if A sends “attack at dawn”, A doesn’t know B got it. If B acks, B doesn’t know A got the ack. Add a third ack, A doesn’t know B got that. Recursion never terminates.

The takeaway is foundational: over an unreliable channel, you cannot achieve guaranteed agreement. Real systems work around this with probabilistic agreement (more rounds = lower failure odds), idempotency (it’s safe if both happen, or neither), and timeouts (declare failure and reconcile).

This is why distributed transactions are hard, why exactly-once is a coordination problem, and why every reliable-delivery system has at-least-once + dedup as its actual guarantee.

State CAP and PACELC. Where are they overstated?

CAP (Brewer): in the presence of a network Partition, you must choose between Consistency (linearizable reads) and Availability (every request gets a non-error response). Most production systems are CP with bounded availability OR AP with eventual consistency.

PACELC (Abadi): the more honest framing. If Partition: trade A vs C; Else (normal operation): trade Latency vs C. Spanner is CP/EC (consistent always, accepts latency); Dynamo is AP/EL (eventual when partitioned, low-latency normally). PACELC captures the latency cost of consistency that CAP elides.

Overstated: CAP is a coarse model. Real systems offer per-operation tunables (Cassandra ONE/QUORUM/ALL, DynamoDB consistent reads). Saying “we’re a CP system” is rarely true at the operation level.

Probing: name a system that violates the CAP triangle — trick question. None do. But many sit between corners and dial per-query.
What is the consistency lattice? Define linearizable, sequential, causal, eventual.

From strongest to weakest:

  • Strict serializability: serializable and respects real-time order. Spanner. The gold standard, expensive.
  • Linearizability: single-object real-time consistency. Once a write completes, all later reads see it. Most consensus-backed key-value stores. Per-key, not cross-key.
  • Sequential consistency: all clients see the same global order, but it need not match real time. Java’s volatile within a process; rare in distributed systems.
  • Causal consistency: if A causally precedes B (read-before-write or same client), all clients see A before B. Concurrent writes can disagree across clients. COPS, Riak with vector clocks.
  • Read-your-writes / monotonic reads: session guarantees — weaker still, but enough for many UIs.
  • Eventual consistency: if updates stop, replicas converge. No bound on when. The default of every AP system.

The lattice exists because the cost gap between linearizable and causal is large — linearizable requires a coordination round-trip; causal can be delivered with just metadata propagation.

Gotcha: “strong consistency” is a vendor word; ask which level. DynamoDB’s “strongly consistent reads” are linearizable per-item, not serializable across items.
FLP impossibility — what does it actually say, and why does Raft “work”?

Fischer-Lynch-Paterson (1985): in a fully asynchronous system, no deterministic consensus protocol can guarantee both safety and liveness in the presence of even a single crash failure. No timing assumptions, no bound on message delay.

Raft / Paxos “work” because real networks are partially synchronous — messages eventually arrive, clocks eventually advance. They sacrifice liveness during pathological partitions (the cluster won’t make progress) to preserve safety (it never commits conflicting values). FLP is satisfied: progress is not guaranteed; it’s overwhelmingly likely.

The practical implication: under partition, your Raft cluster may be unavailable for writes. That’s the C in CAP showing up.

What is exactly-once delivery, and why is it controversial?

Exactly-once message delivery over an unreliable network is impossible (two generals). Exactly-once processing semantics is achievable as the composition: at-least-once delivery + idempotent or deduplicated processing.

Kafka’s “exactly-once” (EOS) is implemented via idempotent producers (sequence numbers per partition) + transactional writes (atomic commit across topic-partitions + offset commits). Flink offers exactly-once via two-phase-commit sinks and checkpoint barriers. Both work end-to-end only if every sink supports the protocol; a Kafka-to-S3 pipeline is not exactly-once unless S3 writes are idempotent (e.g., deterministic object keys).

The pragmatic answer in interviews: design for idempotency. Make consumers tolerant to replays via dedup keys. Exactly-once-as-marketed is a closed-world property.

Probing: can you describe a real failure mode where Kafka EOS doesn’t hold? Producer crashes after sending the commit message but before client gets the ack → client resends → producer epoch fences old transaction — this kind of detail signals depth.
What is “tail latency amplification”?

If a request fans out to N backends and the response requires all of them, the user sees the maximum of N latencies. Even if each backend has p99 of 10ms, with N=100 the request’s p99 looks like the max-of-100 — close to the original p999, often 10× worse. This is “the tail at scale” (Dean & Barroso, CACM 2013).

Mitigations:

  • Hedged requests: fire to two replicas, take whichever returns first. Cuts tail at 2× cost.
  • Tied requests: fire to two, cancel the slow one. Same idea, less wasted work.
  • Backup requests with quorum: fan out to N+f, accept the first N. Used by Spanner, Bigtable.
  • Adaptive retries: Envoy / gRPC retry with deadline propagation.

Knowing this is the difference between “p99 is fine in our backends” and “our gateway p99 is awful and here’s why.”

What is idempotency and how do you implement it?

An operation is idempotent if applying it once or multiple times produces the same result. HTTP: GET/PUT/DELETE are idempotent by spec; POST is not. Real systems implement idempotency via:

  • Idempotency keys: client supplies a UUID; server records (key, response) and replays the response on retry. Stripe’s pattern.
  • Deterministic IDs: derive primary key from request content; INSERT-IF-NOT-EXISTS makes the operation idempotent.
  • Compare-and-set / version checks: “set X to v2 if current version is v1”.
  • Outbox pattern: write the side-effect record transactionally with the state change; a separate process delivers it. Retries replay from the outbox.

Idempotency-key TTL is the underrated detail: too short and a slow retry creates a duplicate; too long and you hold infinite state. 24h is a common middle.

How do gossip protocols work and where do they shine?

Each node periodically picks a random peer and exchanges a piece of state (membership, key updates, epidemic data). Information propagates exponentially — logarithmic rounds to reach all N nodes with high probability. Robust to failures because there’s no central coordinator.

Variants: push (sender pushes), pull (receiver pulls), push-pull (both, fastest convergence). SWIM (Scalable Weakly-consistent Infection-style Membership) uses gossip for failure detection: indirect probes via random peers reduce false positives. HashiCorp Serf / Consul uses SWIM. Cassandra, Akka Cluster, Redis Cluster all gossip membership.

Sweet spot: large clusters (hundreds to thousands of nodes) where centralized coordination would be a bottleneck, and the data is small + non-critical (membership, soft state). Anti-pattern: gossiping large state — bandwidth blows up.

§ 02  Sharding, partitioning & replication

Where the data lives, and how many copies.

Two levers: split (partitioning) and copy (replication). Every horizontal-scale system pulls them differently. The wrong choice shows up months later as “why is one node hot?” or “why is the resharding taking three weeks?”

Concept · The locality-replication trade Partitioning distributes data across nodes for write scalability and storage. Replication creates copies for read scalability, durability, and locality. The interesting question is never “do we shard?” — it’s “what’s the partition key?” The partition key determines which queries are fast (single-shard) and which are slow (scatter-gather), how data balances, and how painful resharding will be.

The fundamental tension: good locality (related data on same shard) makes single-key queries fast but creates hot partitions. Aggressive randomization spreads load but turns every interesting query into a fan-out.
Compare range, hash, and consistent hashing as partitioning strategies.

Range partitioning: sort by key, assign contiguous ranges to nodes. Pros: efficient range scans, ordered queries. Cons: hot spots if writes cluster (timestamps in particular — today’s data hammers one shard). HBase, BigTable, CockroachDB use ranges.

Hash partitioning: hash the key, modulo N nodes. Pros: uniform distribution, no hotspots from sequential keys. Cons: destroys locality — range scans become full scatter-gather. Adding a node remaps almost every key. Cassandra (with murmur3) is hash-based.

Consistent hashing: hash both keys and nodes onto a ring; each key goes to the next node clockwise. Pros: adding/removing a node only affects neighbors (1/N keys move, not all). Cons: uneven load with few nodes — mitigated by virtual nodes (each physical node owns many ring positions, smoothing distribution). Used by Dynamo, Cassandra, ScyllaDB, Riak.

Directory (lookup) partitioning: a metadata service maps key → shard. Maximum flexibility, the cost is the metadata service is now a critical dependency. Used by HDFS NameNode, Vitess, MongoDB’s config servers.

// Consistent hashing with vnodes
ring = []
for node in nodes:
    for i in range(256):  // 256 vnodes per physical node
        ring.add(hash(node.id + str(i)) → node)

find_node(key):
    h = hash(key)
    return ring.first_clockwise_after(h)
Probing: “why virtual nodes?” tests if you understand variance — with 10 physical nodes and no vnodes, the ring is unbalanced. With 256 vnodes each, the law of large numbers smooths it.
What is a hot key, and how do you mitigate it?

A hot key is a partition that receives disproportionate traffic — a celebrity user, a viral product, “today’s date” in time-series data. Symptoms: one shard at 100% CPU, others idle; tail latency on a specific operation; throttle errors that look targeted.

Detection: per-shard metrics, RUM, slow-query logs grouped by key. DynamoDB exposes hot-partition metrics directly; Kafka has consumer-lag-by-partition.

Mitigations:

  • Key salting: append a random suffix to the key for writes (user:42:shard:7). Reads must scatter-gather across all salt values. Worth it for write-hot keys; bad for read-hot.
  • Caching the hot read: for celebrity reads, push to a CDN or Redis. The hot key becomes the cache key.
  • Sub-keying: split the entity itself (per-day buckets for time-series, sub-shards for high-fanout chats).
  • Adaptive partitioning: DynamoDB silently splits hot partitions; Vitess does manual splits.
Gotcha: the worst hot key is the one created by your schema. (tenant_id, created_at) as a partition key time-bombs — the latest tenant’s recent data is always hot. Reverse the dimensions or bucket the timestamp.
Single-leader, multi-leader, leaderless — trade-offs.

Single-leader (primary-replica): all writes go to one node; replicas pull. Postgres streaming replication, MySQL, MongoDB replica sets. Pros: simple consistency, easy reasoning, no write conflicts. Cons: leader is a write bottleneck and SPOF; failover is non-trivial (split-brain risk).

Multi-leader: multiple writable replicas; writes propagate between them. Used cross-region (each region’s leader serves locally) and in active-active setups. Pros: low write latency for geo-distributed users, regional independence. Cons: conflict resolution — concurrent writes to the same key in different regions need merging (LWW, CRDTs, manual). Cassandra’s multi-DC, CouchDB, BDR for Postgres.

Leaderless (Dynamo-style): any node accepts writes; clients (or a coordinator) write to multiple replicas, read from multiple, and use quorum to resolve. Pros: no leader to fail; uniform load; survives partitions gracefully. Cons: read repair & anti-entropy needed; writes are eventually consistent unless you tune R+W>N. Cassandra, Riak, Dynamo.

Explain quorum reads and writes. What does R+W>N actually buy you?

With N replicas, read quorum R and write quorum W: writing returns success when W replicas ack; reading returns the value seen by R replicas. If R+W > N, every read overlaps with every write — you’re guaranteed to see at least one replica that has the latest write, and conflict-resolution (latest timestamp wins, or vector clock) yields the right answer. This is “strong consistency” in Dynamo-speak.

Common settings: N=3, W=2, R=2 — R+W=4 > 3, tolerates one failed replica per operation. N=3, W=1, R=1 is “fast” but eventually consistent. N=3, W=3 is durable-but-fragile (any failure blocks writes).

Sloppy quorum / hinted handoff: when the “real” replicas are down, Dynamo writes to other nodes with a hint to forward later. Preserves availability but breaks the R+W>N guarantee transiently — you’re trading consistency for liveness.

// Cassandra QUORUM
SELECT * FROM users WHERE id=? USING CONSISTENCY QUORUM;
// QUORUM = floor(RF/2) + 1; with RF=3 that's 2 replicas
What is chain replication?

Replicas are arranged linearly: head → middle(s) → tail. Writes enter at the head, propagate down the chain; the tail acks. Reads go to the tail (which has the latest committed value). Variant: CRAQ (Chain Replication with Apportioned Queries) lets non-tail nodes serve reads when they’re known to be in sync, with fallback to query the tail.

Pros: linearizable reads with simple invariant; reads scale by adding replicas (in CRAQ); failure handling is just chain reconfiguration. Cons: write latency = chain length; head/tail failure requires coordinator (e.g., ZooKeeper). Used by Microsoft Azure Storage, FAWN, Hibari, RecoverX.

Probing: chain replication is the “deeply read” signal — most candidates only know primary-replica and quorum. Bringing up CRAQ shows you’ve actually read distributed-systems literature.
Sync vs async replication — durability vs latency.

Synchronous: the primary waits for at least one replica ack before returning. Durability is high — the write survives primary failure. Latency includes the slowest sync replica’s round-trip. Postgres synchronous_commit, MySQL semi-sync, AWS Aurora’s 4-of-6 quorum.

Asynchronous: primary returns as soon as its WAL is durable locally; replicas catch up later. Lowest write latency, but a primary crash can lose un-replicated transactions (RPO > 0).

Semi-synchronous / chain semi-sync: wait for one ack but proceed if the closest replica is slow. Used in MySQL group replication, MongoDB w:1 + journal.

The dial: how much data are you willing to lose on primary failure? For payment ledgers: zero, pay the latency. For analytics events: a few seconds is fine, take the speed.

What is read-your-writes consistency, and how do you implement it?

A session guarantee: a client that writes then reads should see at least its own writes, even if the system is asynchronously replicated. Without it, “updated my profile, refreshed, the change is gone” UI bug.

Implementations:

  • Sticky reads to primary: after a write, route reads to the primary for some window. Simple, works.
  • Replica timestamps: the write returns a token (LSN, version); the read attaches it; the replica blocks until it’s caught up. MongoDB causal consistency, Postgres logical replication slots.
  • Client-tracked vector: client maintains a high-water-mark; reads request “at least version v”.

This is the most-undervalued consistency model in production — users have causal mental models. Eventual consistency without read-your-writes feels broken to humans.

How do you do online resharding?

The pain is moving terabytes while writes continue. Standard playbook:

  • Dual-write window: writes go to both old and new shard layout; reads still serve from old.
  • Bulk backfill: stream historical data from old to new (snapshot + CDC tail).
  • Cutover read traffic: shadow reads to verify, then flip.
  • Stop dual-write: remove the old path.

DynamoDB does this transparently via adaptive splitting (and the new on-demand resharding). MongoDB has resharding built in since 5.0 (“reshardCollection”). Vitess has VReplication. Cassandra resharding is famously painful — the token range layout is fixed at table creation; people typically dual-write into a new keyspace and migrate.

The hard part is rarely the move — it’s the new key choice. Reshard once, choose the wrong key, you’re back in 18 months.

Gotcha: dual-writing has subtle ordering issues across shards. Use idempotent writes keyed by version, or you risk applying a stale write to the new layout after a fresher one already arrived.
Multi-region replication — latency, locality, consistency triangle.

You can’t have all three simultaneously. The corners:

  • Sticky-region (single-leader-per-region): users pinned to home region; writes are local, reads are local; cross-region reads are stale. Easy. The implicit choice for most SaaS.
  • Free-write multi-master: any region accepts writes; conflicts resolve via LWW or CRDTs. Lower write latency for mobile users, but you accept anomalies on shared data.
  • Globally synchronous (Spanner / Cosmos strong): writes coordinate across regions via consensus; cross-region quorums → 100–200ms write latency, but linearizable reads from anywhere.

Operational details that bite: failover RTO/RPO between regions, network egress costs, regulatory data residency (GDPR, China, India). The architecture often gets dictated by data sovereignty, not technical preference.

Why is cross-shard transactional consistency so hard?

A transaction touching multiple shards needs all participants to commit together or all to abort. The classic answer is two-phase commit (2PC): coordinator asks “prepared?”, all participants reply yes/no, coordinator broadcasts commit/abort.

2PC’s problems: blocking (if coordinator dies after a participant prepared, that participant holds locks indefinitely); availability (every shard must be up to commit); latency (two extra round-trips). For these reasons, 2PC is rare in scaled systems; the typical replacements:

  • Saga pattern: sequence of local transactions with compensating actions on failure. Eventual consistency, no global lock.
  • Outbox + event-driven: each shard’s commit emits events; downstream eventually catches up.
  • Spanner-style: Paxos per shard + 2PC across shards, with TrueTime making the coordinator failover safe. Expensive but truly transactional.

The senior answer: avoid cross-shard transactions through schema design (co-locate related data via the partition key), or accept eventual consistency through sagas.

Probing: can you describe a saga’s compensation gone wrong? “What if the compensation itself fails?” The answer is dead-letter queues, manual reconciliation tools, or designing for no-compensation (use only naturally reversible operations).
What are CRDTs and when do they shine?

Conflict-free Replicated Data Types: data structures with merge operations that are commutative, associative, and idempotent. Two replicas that’ve received different updates can merge without coordination — the result is independent of order or duplication.

Common types: G-Counter (grow-only counter, merge by max per node), PN-Counter (increment + decrement), OR-Set (observed-remove set), LWW-Register (last-write-wins by timestamp), RGA / WOOT (sequence types for collaborative text). State-based (CvRDT) ships full state and merges; operation-based (CmRDT) ships ops with delivery guarantees.

Sweet spot: collaborative editing (Figma uses CRDTs; Google Docs historically used OT), shopping carts (Riak/Dynamo), presence/availability data, IoT counter aggregation. Anti-pattern: anything requiring global invariants (uniqueness, account balance non-negative) — CRDTs converge, but not to constraints.

Compare Dynamo’s and Cassandra’s replication models.

Both are leaderless, consistent-hashing, quorum-based. Differences in the details:

  • Conflict resolution: Dynamo uses vector clocks & sibling resolution at read time (clients merge concurrent versions). Cassandra uses last-write-wins by timestamp — simpler, but lossy on concurrent updates.
  • Read repair: both repair stale replicas during reads; Cassandra also has scheduled anti-entropy (Merkle tree comparison via nodetool repair).
  • Hinted handoff: both keep hints for unavailable replicas; Cassandra has tunable hint TTL.
  • Multi-DC: Cassandra natively supports per-DC consistency levels (LOCAL_QUORUM, EACH_QUORUM); Dynamo (the AWS service) handles this via global tables.

The shared limitation: neither offers cross-row transactions. Both expose linearizable single-row operations via lightweight transactions (Cassandra LWT uses Paxos under the hood) at significant latency cost.

§ 03  Distributed consensus

Agreement under asynchrony & failure.

Consensus is the most expensive primitive in distributed systems. The senior move is recognizing where you actually need it — metadata, leader election, locks — and where you don’t (most data, most of the time).

Concept · What problem consensus solves A set of nodes must agree on a single value, even if some nodes fail or messages are delayed arbitrarily. Required properties: safety (no two nodes decide different values), liveness (eventually a value is decided when conditions allow), and fault tolerance (tolerate up to f failures with 2f+1 nodes).

Where you need it: leader election, configuration changes, distributed locks, transaction commit coordination, primary key allocation, namespace metadata.

Where you don’t: the actual data plane. Run consensus over a small metadata store; let the data flow through cheaper protocols (chain, quorum, replication).
Walk through Raft’s leader election.

Each node is in one of three states: follower, candidate, leader. Time is divided into terms (monotonic integer); each term has at most one leader. Followers expect periodic heartbeats from the leader.

If a follower’s election timeout (randomized, e.g. 150–300ms) expires without a heartbeat, it becomes a candidate: increments term, votes for itself, and broadcasts RequestVote RPCs. Each node votes for at most one candidate per term, granting the vote only if the candidate’s log is at least as up-to-date as its own (last log index/term comparison). A candidate that receives a majority becomes leader and starts heartbeating; otherwise it times out and re-election begins (with new random delay to break ties).

Safety property: the candidate-log-completeness check ensures a leader cannot be elected unless it has every committed entry — so a new leader never overwrites committed history.

// Raft RequestVote RPC handling (simplified)
on_request_vote(req):
    if req.term < current_term: return reject
    if voted_for in [null, req.candidate_id]
       and req.log_at_least_as_up_to_date(my_log):
        voted_for = req.candidate_id
        return grant
    return reject
Probing: “why randomized timeouts?” tests whether you understand that simultaneous timeouts cause split votes. “What happens to a network-partitioned old leader?” tests if you know about the term-stepdown rule.
How does Raft replicate a log entry?

Client sends a command to the leader. The leader appends to its log, then sends AppendEntries RPCs to all followers in parallel. Each AppendEntries carries the new entries plus the leader’s commit index and a prevLogIndex/prevLogTerm for log-matching consistency check. Followers append if their log matches at prevLogIndex; otherwise they reject and the leader decrements its nextIndex for that follower and retries (eventually rebuilding from a common prefix).

Once a majority of followers ack the entry, the leader marks it committed, applies it to the state machine, returns to the client, and informs followers via the next AppendEntries (which propagates the new commit index). Followers then apply the entry to their state machines.

The log-matching property — if two logs share an entry at the same index/term, all preceding entries match — is what makes Raft’s safety proof tractable.

Gotcha: Raft can’t commit entries from a previous term by majority replication alone — the leader must commit at least one entry in its own term before old entries are safe (the “noop on election” pattern). Etcd does this; if you implement Raft yourself and skip it, you can lose committed data after a leader change.
Compare Raft and Paxos.

Paxos (Lamport, 1990): the original. Defines a single-decree protocol (Basic Paxos) where proposers propose values, acceptors accept, and learners learn. Multi-Paxos chains them with a stable leader to amortize the prepare phase. Famously hard to teach — the original paper presented it as a fictional Greek parliament; the “simple” explanation came years later.

Raft (Ongaro & Ousterhout, 2014): redesigned for understandability. Strong leader (no concurrent leaders), explicit log, decomposed into leader election + log replication + safety. The log-matching property is enforced rather than emergent.

  • Equivalent power: both solve consensus with 2f+1 nodes tolerating f failures.
  • Raft is easier to implement — fewer corner cases, clearer specification. Almost all new consensus systems (etcd, CockroachDB, Consul, TiKV) use Raft.
  • Paxos still wins on flexibility: Multi-Paxos can have multiple leaders for different keys, Fast Paxos can commit in fewer round-trips when there’s no contention. Google’s Chubby and Megastore use Paxos.

If asked “which would you use?”: Raft, unless you have a specific reason. The implementation simplicity dominates the small flexibility loss.

What is ZAB and how does ZooKeeper use it?

ZAB (ZooKeeper Atomic Broadcast) is the consensus protocol underlying ZooKeeper. Like Raft, it’s leader-based with an epoch (analog of term) and an ordered log. Differences: ZAB has explicit phases (discovery, sync, broadcast) and was designed primarily for primary-backup replication of state-machine updates rather than general consensus.

ZAB guarantees: FIFO order per client (one client’s ops are applied in order), total order across the cluster (all servers see the same sequence). This is why ZooKeeper can support things like fenced locks, leader election, and watches with consistent ordering.

Modern usage: ZooKeeper still backs HDFS HA, HBase, older Kafka deployments (pre-KRaft), Solr Cloud. New systems trend toward etcd or built-in Raft.

What is the Multi-Paxos “leader lease” trick for fast reads?

Naively, a linearizable read in a consensus system requires going through the log (a no-op append) to verify the leader is still authoritative — otherwise a partitioned old leader could serve stale data. That’s a full quorum round-trip per read.

Lease-based reads: the leader gets a time-bounded lease from a quorum (“you are leader until time T”); during the lease, it can serve reads from local state without coordinating, because no other leader can be elected until T passes. Followers refuse votes within the lease window. Reads are now ~free — just a clock check.

Caveat: requires bounded clock skew. If the leader’s clock advances faster than followers’, it might serve reads after a new leader was elected. Spanner uses TrueTime to bound this; etcd / CockroachDB use conservative skew assumptions and step-down on timeout.

Probing: the lease-based-reads question separates “I read the Raft paper” from “I’ve operated etcd in production.”
What does FLP impossibility mean for production systems?

Restated: in pure async, no deterministic protocol guarantees consensus liveness with even one failure. Real systems escape FLP by adding assumptions:

  • Partial synchrony: messages eventually arrive within some bound; clocks drift but bounded. This is the model Raft/Paxos work in.
  • Failure detectors: use timeouts as a probabilistic oracle. Eventually-perfect ◇P detectors are sufficient for consensus.
  • Randomization: Ben-Or’s algorithm achieves consensus in expected finite time using coin flips. Used in some Byzantine protocols.

The operational reality: when networks misbehave badly enough (e.g., asymmetric partitions where A→B works but B→A doesn’t), Raft will flap leaders and stop committing. That’s FLP cashing the check — you didn’t lose safety, you lost liveness.

Why doesn’t every distributed system just use Raft?

Raft is a hammer; not everything is a nail.

  • Throughput ceiling: single-leader Raft tops out at ~10K–100K ops/sec depending on payload size. Datasets with millions of QPS need partitioning — Raft per shard, not one global Raft group.
  • Latency cost: every commit needs majority round-trip. For high-volume data ingestion (logs, events), eventual consistency at 10ms beats consensus at 100ms.
  • Geo-distribution: a global Raft group requires cross-region quorum — 100–300ms commit latency. Use Raft regionally; use replication or async between regions.
  • Operational complexity: 5 nodes minimum for tolerating 2 failures. Cluster membership changes are tricky (joint consensus).

Senior architecture: Raft for the metadata service / control plane (small dataset, infrequent writes); cheaper replication for the data plane.

What is a snapshot in Raft, and why is it needed?

The Raft log grows forever otherwise. A snapshot is the serialized state machine plus the last log index/term it covers. After snapshotting, the leader truncates its log up to that index. Followers that fall too far behind receive an InstallSnapshot RPC instead of incremental AppendEntries.

Snapshot frequency is a tuning knob: too often = wasted I/O; too rare = log bloat and slow recovery. Etcd snapshots every 100K log entries by default. Snapshot creation must not block the main loop — etcd uses copy-on-write of its boltdb.

Gotcha: a follower receiving a snapshot must atomically replace its state — partial application after a crash leaves it inconsistent. Most implementations write to a temp file and rename atomically.
etcd vs Consul vs ZooKeeper — where each fits.

etcd: Raft-based KV store, optimized for Kubernetes (which is its primary user). Strict watch semantics, lease-based TTL keys, MVCC. Best fit: K8s control planes, internal config services, distributed locks via leases. ~10K writes/sec ceiling per cluster.

Consul: Raft (per-DC) plus gossip (across DCs and for membership). Built-in service discovery + health checking + KV + multi-DC ACL. Best fit: service mesh control plane, multi-DC service discovery, Vault backing. Less consistent than etcd in non-essential paths to favor availability.

ZooKeeper: ZAB-based, hierarchical namespace (znodes), ephemeral nodes, watches. Older, more verbose API. Best fit: legacy stacks (HBase, older Kafka, HDFS HA), where it’s the standard. Operational pain — harder to run than etcd.

In 2026, default to etcd for new projects unless you need Consul’s multi-DC or ZK’s ecosystem fit.

What is “split brain” and how does Raft prevent it?

Split brain: two nodes simultaneously believe they’re the leader, accepting writes that diverge. Possible in naive primary-replica systems when failover triggers without confirmation that the old primary is dead.

Raft prevents this through three mechanisms:

  • Term numbers: each leader is associated with a unique term. Higher term wins; old leaders see they’re obsolete and step down.
  • Quorum elections: a candidate needs majority support to become leader. With 2f+1 nodes, at most one majority exists at a time, so at most one valid leader per term.
  • Pre-vote / leader stickiness: followers don’t initiate elections while receiving heartbeats; partitioned-but-running old leaders detect they’re isolated when AppendEntries fail with higher term.

The remaining edge case: an old leader has already accepted a write the new leader hasn’t. Raft handles this via the log-completeness check — the new leader must have all committed entries to be elected. Uncommitted entries on the old leader are simply discarded.

What is Byzantine fault tolerance and when do you need it?

BFT protocols tolerate arbitrary failures — nodes lying, double-voting, sending different values to different peers. Required when participants don’t trust each other (blockchain) or when running across security domains (cross-organization consortia).

BFT consensus needs 3f+1 nodes to tolerate f Byzantine faults (vs 2f+1 for crash-fault Raft/Paxos). PBFT (Practical BFT, Castro & Liskov 1999) is the foundational protocol; modern variants include HoneyBadger (asynchronous), Tendermint (used by Cosmos blockchain), HotStuff (linear comm complexity, Facebook Diem).

Cost: more nodes, more messages per decision (PBFT is O(n²) communication). Justified only when trust is genuinely a question. Most enterprise systems are Crash-Fault and assume operators have control over their nodes — BFT is overkill.

Probing: if a candidate insists on BFT for an internal service, push back — you’re paying real performance for a threat model that doesn’t apply.
How would you build a config service from etcd primitives?

Etcd offers: KV with revisions, watches, leases, atomic compare-and-swap. A simple config service:

  • Storage: /config/<service>/<key> as KV.
  • Reads: etcdctl get or watch for live updates. Cache locally with revision tracking.
  • Writes: txn with revision check (CAS) for concurrent safety.
  • Validation: a separate admission service that watches the config tree and emits violations to a status path.
  • Audit log: use etcd’s revision history; periodically snapshot to S3 for retention beyond etcd’s compaction window.

The watch-and-cache pattern is the secret — clients are eventually consistent locally but never poll. Each cached client tracks its highest seen revision; on reconnect, it asks for everything > that revision and catches up.

// etcd client pseudo-code
revision = local_cache.last_revision()
for ev in client.watch("/config/", start_rev=revision+1):
    cache.apply(ev)
    cache.last_revision = ev.kv.mod_revision
§ 04  Coordination, locking, leader election

Locks lie. Use fencing tokens.

Distributed locks are the hello-world of coordination — and the most-misimplemented primitive in distributed systems. The lock holder might be GC-paused; the lock service might lose state on failover; the network might lie. The senior answer involves fencing tokens.

Concept · Why distributed locks are tricky A “lock” in a distributed system is a hint, not a guarantee. The classic failure: client A acquires the lock, GC-pauses for 30s, lock TTL expires, client B acquires it, A wakes up and proceeds — both think they hold the lock and write conflicting data.

The fix is fencing tokens: the lock service issues a monotonically-increasing token on each acquisition. The protected resource (storage, queue) checks the token and rejects writes from older holders. Locks alone are insufficient; locks + token checks at the storage layer are correct.
Implement a distributed lock with ZooKeeper.

The canonical recipe uses ephemeral sequential znodes:

  • To acquire: create an ephemeral sequential znode under /locks/<resource>/.
  • List all children. If your znode has the lowest sequence number, you hold the lock.
  • Otherwise, watch the znode immediately preceding yours (not the lowest — avoids the “herd effect” on release). When that watch fires, recheck.
  • To release: delete your znode. Subsequent waiter is notified by its watch.
  • If your client dies: the session expires, ZK auto-deletes the ephemeral znode — lock auto-released.

Caveat: session timeout is the visible TTL of the lock. If the session is > timeout from server’s view but the client thinks it’s still alive (long pause, network blip), you can have a phantom lock. Use fencing tokens (the znode’s zxid or sequence number).

// ZK lock acquisition (pseudo)
my_node = zk.create("/locks/L/lock-", ephemeral=true, sequential=true)
while true:
    children = zk.get_children("/locks/L/").sort()
    if my_node == children[0]: return ACQUIRED
    prev = children[children.index(my_node) - 1]
    if zk.exists(prev, watch=true): zk.wait_for_event()
Why is Redlock controversial?

Redlock (Redis distributed lock, by antirez) acquires a lock by writing to N independent Redis instances; success requires a majority. Sounds robust. Martin Kleppmann’s 2016 critique: Redlock’s safety depends on bounded clock drift — specifically, the lock’s expiry time must be reliable across nodes. With clock jumps (NTP step, VM migration), or with GC pauses on the client, two clients can simultaneously hold the lock without violating any single Redis instance’s view.

antirez’s rebuttal: “just use fencing tokens to harden the resource layer.” Which is true, but Kleppmann’s point stands: if you need fencing tokens anyway, you don’t need a fancy distributed lock — a single etcd lease is sufficient and cheaper.

Pragmatic answer: for non-critical mutual exclusion (preventing two cron jobs running concurrently, where the worst case is wasted work), Redlock or even single-Redis SETNX is fine. For correctness-critical paths, use a real consensus system (etcd/ZK) and fence at the resource.

Probing: “is Redlock safe?” isn’t a yes/no question. The right answer is “safe for this category of use, not safe for that one, and here’s the failure mode.”
Explain fencing tokens with the canonical GC-pause example.

Scenario: Client A acquires a lock with TTL 10s and starts writing to S3. Halfway through, A’s JVM stops the world for a 20s GC pause. The lock expires. Client B acquires the lock, writes to S3. A wakes up, finishes its write — overwriting B’s data. Both thought they held the lock.

Fix: the lock service returns a fencing token (e.g., a monotonic counter or the lock acquisition’s revision number). Every write carries the token. The storage system tracks the highest token seen and rejects any write with a lower token.

// On lock acquisition
token = lock_svc.acquire("resource")  // returns 33

// On every write
storage.write(data, fence=token)
// Storage logic:
if incoming.fence < max_fence_seen: reject
else: max_fence_seen = incoming.fence; apply

Now after A’s GC pause, A’s write has token 33; B has token 34; storage already saw 34, so A’s 33 is rejected. The lock service alone can’t guarantee correctness — the resource must participate.

What is a session in ZooKeeper / etcd, and why does it matter?

A session is the client’s logical connection to the cluster, with a TTL kept alive by heartbeats. Ephemeral nodes (ZK) and leases (etcd) are tied to sessions: when the session expires, all session-scoped state vanishes.

This is the foundation of distributed locks — if the client crashes, its session times out, its ephemeral node disappears, and the next waiter takes over. Without sessions, you’d need explicit lease renewal or risk dead-client locks holding forever.

Critical: the client SDK must surface session expiration as an error. A client that loses its session and reconnects gets a new one — any locks/watches from the old session are gone. Many subtle bugs come from clients that don’t handle session-expired correctly.

What is total order broadcast and how does it relate to consensus?

Total order broadcast (atomic broadcast): deliver messages to all correct processes in the same order. Equivalent to consensus — you can build one from the other.

From consensus to total order: each message becomes a consensus decision on “what comes next.” From total order to consensus: the first delivered message becomes the agreed value. ZooKeeper’s ZAB literally is atomic broadcast; the underlying protocol commits each operation to a total order.

Other order types:

  • FIFO order: messages from one sender delivered in send order. Cheap, just sequence numbers.
  • Causal order: if A precedes B (causality), deliver A first. Vector clocks suffice; no consensus needed.
  • Total order: all processes see same sequence. Requires consensus.

Most messaging systems offer FIFO per partition (Kafka). Cross-partition total order requires consensus on every event — expensive, used sparingly.

Compare leader election strategies: Bully, Raft-based, lease-based.

Bully algorithm: classic algorithmic textbook leader election. Each process has an ID; the highest-ID process wins. On detecting failure, a process broadcasts “election”; higher-IDs respond and one of them takes over. Works in symmetric networks but doesn’t handle partitions well — both sides may elect their own “bullies.”

Raft-based: use Raft’s built-in leader election for the workload itself. The Raft cluster is the leader-electing entity. Used implicitly when your service runs on top of etcd / Consul.

Lease-based (most common in cloud): use a coordination service (etcd, ZK, DynamoDB conditional writes). Candidates race to acquire a lease; whoever wins is leader until lease expires. Renew via heartbeat. K8s controllers use this pattern with the coordination.k8s.io/Lease resource.

// K8s leader-election pattern
lease = client.acquire_lease(name="my-controller", ttl=15)
if lease.holder == my_id:
    do_leader_work()
    while running:
        client.renew(lease)  // every 5s

Use lease-based unless you have a specific reason to do otherwise. Cheap, well-understood, integrates with cloud-native stacks.

What is SWIM and why does it scale?

SWIM (Scalable Weakly-consistent Infection-style Membership): a gossip protocol for failure detection and membership. Each node periodically picks a random peer and sends a ping; if no ack, it asks k other random peers to ping-req the suspect indirectly. If they all fail, the node is marked suspect, then dead, and the gossip propagates.

Why it scales: O(1) work per node per round regardless of cluster size. Direct + indirect probes reduce false positives caused by single-link failures. Membership changes spread epidemically — every node learns of a join/leave in O(log N) rounds.

Used by HashiCorp Serf (and thus Consul), Cassandra (its gossip is SWIM-like), Akka Cluster. The alternative — centralized health checks — collapses at scale because the central node becomes the bottleneck and a partition-exposed SPOF.

How does Kafka use ZooKeeper / KRaft?

Pre-Kafka 2.8: ZooKeeper held all cluster metadata — broker registry, partition assignments, topic configs, controller election. Every broker watched ZK paths and reacted. The controller (one elected broker) was the only writer to most paths.

KRaft mode (Kafka Raft, GA in 3.3+, default in 4.0): Kafka runs its own internal Raft quorum among “controller” brokers. Metadata is now a log, not a ZK tree. Benefits: no separate cluster to operate, faster failover (~1s vs ~30s with ZK), 10× more partitions supported (the old ZK metadata limit was the scaling bottleneck), simpler ops.

The lesson is meta: ZooKeeper, the consensus service, was being used as an expensive metadata store. Replacing it with Raft directly on Kafka’s own metadata log yields better performance — the consensus is the same, the integration is tighter.

Probing: “why move off ZooKeeper at all?” tests whether you understand that Kafka’s scaling pain wasn’t Kafka itself — it was ZK’s metadata throughput.
What is a barrier, latch, and semaphore in distributed terms?

Distributed latch: N processes wait for some condition to be reached, then all proceed. Cassandra repair coordinator uses one to wait for all nodes to ack. Implementable as a counting znode in ZK or a counter in etcd.

Distributed barrier: like a latch but reusable — all members reach the barrier, all proceed, barrier resets. Used in big-data / scientific computing for phased computation. Hadoop’s combine phases used barriers conceptually.

Distributed semaphore: permit-counting. N permits available; acquirers consume, releasers replenish. Used for rate limiting (only 5 concurrent migrations) or throttled access (only 10 connections to legacy DB). Can be built on top of a counter primitive in etcd with CAS or Redis with Lua scripts.

All three depend on a coordination service for state. The performance ceiling of the underlying service (etcd ~10K ops/sec) is the ceiling for these primitives. For high-throughput rate limiting, prefer per-process token buckets with periodic central reconciliation.

What is the “thundering herd” problem in coordination?

When a single event triggers many clients to react simultaneously: a leader change wakes up every follower; a lock release wakes every waiter; a config update fires every watch. The coordination service gets hammered, and the workload has a synchronized stampede.

Mitigations:

  • Sequential watches (the ZK lock recipe): each waiter watches only its predecessor, so only one waiter wakes per release.
  • Jittered backoff: on watch fire, sleep random delay before reacting.
  • Hierarchical fan-out: coordination service notifies a small set; they propagate to leaves.
  • Coalescing: in K8s, controllers use rate-limited workqueues so rapid events get debounced.

The K8s controller pattern is a good study: every watch event goes through a delta FIFO, then a workqueue with rate limiting. The reconcile loop sees the latest state, not every transition — intentional debouncing.

Where do you actually need a global lock, vs idempotent operations?

Most engineers reach for locks too early. Ask first: is this a uniqueness constraint, an ordering constraint, or genuinely mutual exclusion?

  • Uniqueness: use a database unique constraint (or DynamoDB conditional put). No lock needed; the storage gives you atomicity.
  • Ordering: use a single-partition log (Kafka topic with one partition keyed by entity). Consumers process in order without locks.
  • Mutual exclusion of side effects: often replaceable by idempotency. Make the operation safe to repeat.
  • Genuine resource exclusivity (only one process compacting this directory): yes, use a lock. With fencing.

The senior signal: arriving at “no lock needed” through schema or idempotency. Junior pattern: reaching for ZooKeeper for everything.

Gotcha: “exactly one cron job” is the most common bad lock case. Use a scheduler with leader election (K8s CronJob with concurrency policy, or a singleton-mode workload with a Lease). Don’t spawn N pods that race for a Redis SETNX every minute.
How do you do leader-elected work in Kubernetes?

The standard pattern uses coordination.k8s.io/v1.Lease. Multiple replicas of a controller race to update a Lease object with their identity and a TTL. Whoever wins is the leader; others sit idle. Renew every few seconds; on failure, others detect via timeout and elect a new leader.

The client-go leader-election package implements this. Configure renewDeadline (e.g., 10s) and leaseDuration (15s) — the gap is the safety margin for clock skew and renewal latency.

apiVersion: coordination.k8s.io/v1
kind: Lease
metadata:
  name: my-controller
  namespace: kube-system
spec:
  holderIdentity: pod-abc123
  leaseDurationSeconds: 15
  renewTime: "2026-03-28T10:00:05Z"

This is the same primitive kube-controller-manager and kube-scheduler use to ensure only one is active. Run 3 replicas for HA; only one does work; failover is <15s.

§ 05  Networks & protocols

From frames to gRPC.

A staff engineer reads a tcpdump without flinching, knows why HTTP/2 doesn’t solve everything, can explain how QUIC sidesteps TCP’s sins, and can make the load-balancer choice that doesn’t silently lose 0.1% of requests at p99.

Concept · The OSI ladder, where it actually matters L2 (data link): MAC addresses, ARP, switches. Surfaces when debugging same-subnet weirdness or VLANs in K8s overlays.
L3 (network): IP, ICMP, routing. The layer the cloud cares about — subnets, route tables, BGP.
L4 (transport): TCP, UDP, QUIC. Connection state, congestion control, head-of-line blocking.
L7 (application): HTTP, gRPC, DNS. Where API gateways, ingresses, and request routing live.

L5/L6 (session/presentation) are mostly absorbed into L7 in modern stacks. Good interview answer: “OSI is a teaching model; TCP/IP is what runs.”
TCP vs UDP — what does TCP buy and what does it cost?

TCP: connection-oriented, reliable in-order byte stream, congestion-controlled, flow-controlled. Costs: 3-way handshake on connect (1.5 RTT), explicit teardown (FIN), retransmit-on-loss (extra latency for dropped packets), head-of-line blocking (later packets wait while a lost packet is retransmitted), per-connection state on both ends.

UDP: fire-and-forget datagrams. No connection, no ordering, no retransmit, no congestion control. Use when you can tolerate loss (DNS query: just retry), need multicast (UDP supports it natively), or build your own reliability on top (QUIC, WebRTC, custom protocols like Aeron for trading).

Modern apps that look like “UDP is back”: HTTP/3 (QUIC over UDP), DNS-over-QUIC, WebRTC for media. The takeaway: when you need partial reliability or want to avoid TCP’s HoL blocking, UDP gives you the canvas.

Probing: “why doesn’t HTTP/2 fix HoL blocking entirely?” tests if you understand that HTTP/2’s stream-level multiplexing is undone by TCP’s packet-level ordering. One lost packet stalls every stream until retransmitted.
Walk through the TCP handshake, including SYN cookies.

Three-way: client sends SYN with its initial sequence number; server replies SYN-ACK with its own ISN and acks the client’s; client acks the server’s. Connection established, both sides have ISNs and can begin data transfer. 1.5 RTT latency before any payload.

SYN cookies: defense against SYN-flood DoS. Without cookies, the server allocates state on the SYN-ACK; an attacker fires SYNs and exhausts memory. With cookies, the server stuffs the connection state into the SYN-ACK’s ISN itself (encoded with a hash of the 5-tuple + secret + timestamp); state is allocated only on the final ACK. Linux enables this under load.

TCP Fast Open (TFO): piggybacks data on the SYN, skipping the handshake’s second RTT for repeat connections via a server-issued cookie. Adopted in mobile / CDN contexts; not universal because middleboxes mangle it.

Compare HTTP/1.1, HTTP/2, HTTP/3.
  • HTTP/1.1: text-based, one request per connection at a time. Pipelining exists but rarely works (broken middleboxes). Workaround: 6 parallel connections per origin. Header compression: none. The web ran on this for 20 years.
  • HTTP/2: binary framing, stream multiplexing over a single TCP connection (many concurrent requests/responses interleaved), HPACK header compression (incremental dictionary), server push (deprecated — never delivered the promise). Pain point: TCP head-of-line blocking. Mandatory TLS in practice.
  • HTTP/3 (QUIC): runs over UDP with QUIC providing TLS 1.3, stream multiplexing, congestion control. Eliminates TCP HoL blocking — each stream has its own ordering, so a dropped packet in stream A doesn’t stall stream B. 0-RTT connection resumption. Connection migration (mobile changes IP, connection survives).

Adoption: HTTP/2 is universal; HTTP/3 is ~30% of web traffic in 2026, dominant for CDN edges (Cloudflare, Google). For your internal services, HTTP/2 over TLS is fine; pivot to HTTP/3 if you have lossy mobile clients or geographic users where TCP retransmit hurts.

How does the TLS handshake work? 1.2 vs 1.3.

TLS 1.2: 2-RTT handshake. Client → ClientHello (cipher list, random, SNI). Server → ServerHello + Certificate + ServerKeyExchange + ServerHelloDone. Client → ClientKeyExchange + ChangeCipherSpec + Finished. Server → ChangeCipherSpec + Finished. Then encrypted application data. Key derivation uses RSA or DHE; cipher suite negotiation is verbose.

TLS 1.3: 1-RTT handshake. Client sends ClientHello with key share already (assuming the server’s key exchange method); server replies with its share + cert + Finished; client immediately sends Finished + data. Removes RSA key transport (always ECDHE for forward secrecy), removes weak ciphers. 0-RTT resumption for repeat connections (replay risk for non-idempotent requests — servers must mitigate).

Session resumption: session tickets (server-encrypted state given to client) or session IDs (server-side cache). Reduces handshake to 1 RTT in 1.2; to 0 RTT in 1.3.

mTLS: server requests client cert during the handshake (CertificateRequest). Both sides authenticate. Standard for service-to-service in zero-trust (SPIFFE/SPIRE issue short-lived certs to workloads).

Explain DNS internals: recursion, caching, anycast.

Two server roles: recursive resolvers (your ISP’s, 8.8.8.8, 1.1.1.1) walk the chain on your behalf; authoritative servers own zones and respond. The walk: query root (returns TLD authority), query TLD (returns zone authority), query authority (returns answer). Each result is cached up to its TTL.

TTL strategy: low TTL = fast failover but higher resolver load and worse caching; high TTL = bad for failover, great for cache hit rate. CDN A records often have 30-60s TTL; static infrastructure uses hours/days.

Anycast: the same IP is announced from multiple geographic locations via BGP; routing delivers each query to the closest instance. How 1.1.1.1, 8.8.8.8, and root nameservers achieve global low-latency. Also used by AWS Route 53, Cloudflare DNS, Google Public DNS.

Routing policies (Route 53): weighted, latency-based, geolocation, geoproximity, failover, multivalue. Most production systems combine latency-routing with health-checked failover.

Gotcha: JVM caches DNS forever by default (networkaddress.cache.ttl=-1). On AWS, where instances rotate, this causes the “why is the app talking to a dead IP?” bug. Set the cache TTL to 30s or use a service-discovery client.
What does BGP do, and why does it matter to app engineers?

BGP (Border Gateway Protocol) is how autonomous systems (ASes — ISPs, clouds, enterprises) announce reachability to each other. Each AS says “I can reach prefix X via path Y, Z, ...”; routers prefer shortest AS-paths (with policy overrides). The whole internet is held together by ~75K AS announcements.

Why app engineers should care:

  • Outages aren’t your fault but look like yours: Facebook’s 2021 outage was a BGP withdrawal. AWS Route 53 has had BGP-leak incidents.
  • BGP hijacks: an AS announces a prefix it doesn’t own; traffic gets redirected. Mitigated by RPKI (signed announcements) but adoption is partial.
  • Anycast routing: your CDN’s edge selection is BGP-driven. Suboptimal paths happen.
  • Cross-cloud / hybrid: Direct Connect + BGP is the production path; misconfigured route maps cause asymmetric routing.

Don’t need to operate BGP, but understand it’s the substrate — “the internet just routes” is a fallacy.

L4 vs L7 load balancing — when each.

L4 (transport-layer): balances on IP + port; doesn’t inspect payload. Connection is forwarded; the LB doesn’t terminate TCP. Examples: AWS NLB, IPVS, HAProxy in TCP mode, Linux kernel kube-proxy. Pros: high throughput (millions of conns/sec), low latency, cheap. Cons: can’t do path-based routing, header manipulation, TLS termination (without SNI tricks).

L7 (application-layer): terminates the connection, inspects HTTP, can route by host/path/header, do auth, retry, rate-limit. Examples: ALB, Envoy, NGINX, HAProxy in HTTP mode. Pros: rich routing, observability per request, per-user features. Cons: 10× less throughput per box, more memory per connection, becomes a stateful component.

Algorithms:

  • Round-robin: simple; bad with heterogeneous backends.
  • Least-connections: good when request duration varies; default in many L7 LBs.
  • Consistent hashing: sticky routing without session state — user X always hits backend Y. Bounded-load consistent hashing handles hot keys.
  • EWMA / least-loaded: exponentially-weighted moving average of latency; sends to fastest. Smart but susceptible to oscillation.

Real architecture: L4 in front of L7 in front of services. NLB → ALB or Envoy → pods. Each layer does its specialty.

API gateway vs reverse proxy vs service mesh — what does each own?

Reverse proxy (NGINX, Envoy standalone): the dumb forwarder. Terminates TLS, routes by host/path, forwards to backends. Single component, no policy engine.

API gateway (Kong, AWS API Gateway, Apigee, Tyk): reverse proxy plus authn/z, rate limiting, transformation (REST↔GraphQL), API key management, developer portal. North-south traffic (client → cluster). Used by external API products.

Service mesh (Istio, Linkerd, Consul Connect, Cilium Mesh): infrastructure layer for east-west traffic (service → service). mTLS for service identity, observability (golden signals per call), traffic shaping (canary, retry, circuit breaker), policy. Two flavors: sidecar (Istio classic, Linkerd) where Envoy runs alongside each pod, and sidecar-less (Cilium, Istio Ambient) where eBPF or per-node proxies handle the mesh layer.

Overlap: all three can do TLS termination and routing. The right way: service mesh for in-cluster traffic, API gateway for external entry, reverse proxies as components within either.

Opinionated take: the sidecar mesh is in decline. Per-pod sidecars cost real CPU/memory and complicate every deployment; eBPF-based meshes (Cilium) and ambient mesh do the same job at the node level. Sidecar mesh has a 3–5 year ceiling.

Probing: “why a service mesh at all?” tests if you understand the alternative is putting mTLS, retries, and observability in every service’s code or library — which is what people did before meshes and what they’ll do again with library-based approaches like gRPC’s built-in features.
What is consistent hashing for load balancing?

Maps requests to backends by hashing a request key (user ID, session ID, cache key) onto a ring shared with backend identifiers. Each request goes to the next clockwise backend. Adding/removing a backend only reassigns 1/N of keys (vs mod N hashing which reassigns nearly all).

Critical for stateful services: cache servers (Memcached, Redis sharding clients), in-memory session stores, sticky-session fronting. Variants:

  • Virtual nodes: each backend owns many ring positions for balanced distribution.
  • Bounded-load consistent hashing (Mirage, Vimeo, used by Envoy): caps each backend at (1+ε)×avg load; overflow goes to the next backend on the ring. Eliminates pathological hot-backend cases.
  • Maglev hashing (Google): generates a fixed-size lookup table from a permutation per backend; constant-time lookup, minimal disruption on changes. Used by Envoy and GLB.

Use case match: cache fronting, gRPC client-side LB with state-affinity, GeoDNS routing where you want stable mapping despite backend churn.

What is gRPC and where does it beat REST?

gRPC is HTTP/2 + Protobuf + a client/server code-gen framework. The wins over JSON REST:

  • Binary: Protobuf is 3–10× smaller than JSON, faster to (de)serialize, stable schema with explicit version compatibility.
  • Streaming: client-streaming, server-streaming, bidirectional streams over a single connection.
  • Strongly typed contracts: .proto files generate idiomatic clients in 10+ languages. No more “does this field exist? what type?”
  • HTTP/2 features: header compression, multiplexing, all by default.

Where REST still wins: public APIs (every language has an HTTP client; proto tooling has friction), browser-facing (gRPC needs gRPC-Web or Connect), human-readable debugging, evolution flexibility (REST tolerates schemaless additions; Protobuf is stricter).

Sweet spot for gRPC: internal service-to-service in microservice meshes — throughput, type safety, polyglot support all win. Internal east-west traffic is gRPC-dominant in 2026.

What happens when MTU mismatch hits an overlay network?

Underlying network has MTU 1500. An overlay (VXLAN, IPIP, WireGuard) wraps each packet in another header; if you don’t reduce the inner MTU, packets exceed 1500 and either get fragmented or dropped (DF bit set + ICMP unreachable, or just dropped if ICMP is filtered — PMTU black-hole).

Symptom: small requests work, large ones hang. SSH connects, but ls -la /large/dir blocks. Database connections succeed, large query results stall.

Fixes:

  • Reduce inner MTU by the overlay header size (VXLAN: 50 bytes; WireGuard: 80 bytes). Set on the pod/container interface.
  • TCP MSS clamping: set TCP option to advertise smaller MSS, so endpoints don’t generate oversized segments. Most CNIs do this automatically.
  • Allow ICMP fragmentation-needed through firewalls; most clouds drop ICMP, breaking PMTUD.

This is a top-3 K8s networking debugging story; nearly every cluster operator has hit it.

Why does TCP slow start matter for short-lived connections?

TCP starts each new connection with a small congestion window (cwnd, typically 10 segments today, was 4 historically) and doubles per RTT until loss. Short-lived connections never escape slow-start — a 50KB response over a 100ms-RTT link delivers in slow-start, taking 4–5 RTTs instead of 1.

Mitigations:

  • Connection reuse: HTTP/1.1 keepalive, HTTP/2 multiplexing, gRPC channel reuse.
  • BBR congestion control (Google, Linux 4.9+): models bottleneck bandwidth and RTT, doesn’t treat loss as the only congestion signal. Better steady-state throughput on lossy / bufferbloated paths.
  • Initial cwnd tuning: some servers raise cwnd to 30 for known low-latency paths.
  • 0-RTT (TLS 1.3, TCP Fast Open): piggyback data with the handshake.

Why it shows up in interviews: “why are short requests slower than I’d expect from raw RTT?” The answer is slow-start, and the fix is connection reuse.

§ 06  AWS networking & resource hierarchy

VPCs, accounts, and the wires between them.

AWS is the canonical cloud in interviews not because it’s best, but because it’s the most complete vocabulary. Knowing the AWS vocabulary translates to GCP and Azure with name changes and minor semantic differences.

Concept · The AWS hierarchy from the top Organization (a tree of accounts) → Organizational Units (logical groupings, used for SCP attachment) → Accounts (the unit of billing, blast radius, and IAM trust) → Regions (geographic isolation; no resources cross by default) → Availability Zones (independent failure domains within a region; physically separate datacenters connected by low-latency fiber) → VPCs (your private network within a region) → Subnets (per-AZ slices of a VPC).

The implicit lesson: AWS’s primary isolation boundary is the account, not the VPC. Multi-account is the modern best practice; a single “prod” account with everything inside it is a 2015 architecture.
How do AWS Organizations, OUs, and SCPs interact?

An Organization has a single management (payer) account and N member accounts. Accounts are arranged in a tree of OUs (e.g., Root → Workloads → Production → PaymentService). SCPs (Service Control Policies) attach to OUs or accounts and act as guardrails — they don’t grant permissions; they restrict what IAM in those accounts can do.

SCP example: deny all iam:* outside us-east-1 to enforce regional governance. Even a root user in a member account can’t escape an SCP; only the management account is exempt.

Modern multi-account pattern (Control Tower / Landing Zone):

  • One management account: billing, SCPs, never run workloads.
  • One log archive account: centralized CloudTrail, immutable.
  • One audit/security account: GuardDuty, Security Hub aggregator.
  • Per-environment / per-team workload accounts: prod, staging, dev, sandbox.

Why: blast radius. A compromised workload account doesn’t have CloudTrail to delete; a runaway dev experiment can’t cost more than its account’s budget.

Probing: “why per-environment accounts and not just per-environment VPCs?” Account boundary is harder to escape than VPC boundary — IAM trust, S3 bucket policies, KMS keys all default-deny across accounts.
Region, AZ, Local Zone, Wavelength, Outpost — when which?
  • Region: a geographic location (us-east-1, eu-west-1) with multiple AZs. Most resources live within one region. Cross-region traffic is internet-priced unless you use Global Accelerator or Direct Connect.
  • Availability Zone: a logically isolated datacenter within a region. Independent power, cooling, networking. AZs are connected by low-latency fiber (~1ms). Multi-AZ is the basic HA pattern.
  • Local Zone: AWS infra in a metro area for ultra-low-latency to nearby users. Typically one AZ; intended for media production, gaming, sub-10ms latency. Subset of services available.
  • Wavelength: AWS infra inside telco 5G networks. Latency to mobile devices on that carrier <10ms. AR/VR, autonomous vehicles, real-time gaming.
  • Outpost: AWS hardware in your datacenter, managed by AWS. Same APIs as cloud, but local. For data-residency requirements, low-latency to legacy on-prem systems, regulated workloads.

Practical answer: 99% of workloads use Region + multi-AZ. Local Zone for latency-sensitive consumer apps in specific cities. Outpost when regulators require on-prem.

Walk through a VPC’s components.

A VPC is a logically isolated virtual network with a CIDR block (e.g., 10.0.0.0/16). Components:

  • Subnets: per-AZ CIDR slices. Public = has a route to an Internet Gateway; private = only internal routes; isolated = not even NAT.
  • Route tables: one per subnet (or default for the VPC); rules like “0.0.0.0/0 → igw-xxx” or “peer-vpc-cidr → pcx-xxx”.
  • Internet Gateway (IGW): bidirectional internet access for public subnets. One per VPC, free.
  • NAT Gateway: outbound-only internet for private subnets (instances can fetch updates, callers can’t reach in). Hourly + per-GB price; cross-AZ NAT traffic costs extra.
  • Security Groups: stateful firewall on ENIs (instance / Lambda / ALB). Default-deny; rules are allow-only. Returns traffic auto-allowed.
  • NACLs (Network ACLs): stateless firewall on subnets. Both allow and deny rules; both directions explicit. Rare to customize — use SGs.
  • VPC Endpoints: private connections to AWS services without traversing internet (covered separately).
  • VPC Flow Logs: 5-tuple flow records for forensics, network analysis.

    public-az2:   10.0.2.0/24

    private-az2:  10.0.12.0/24

VPC Peering vs Transit Gateway vs VPN vs Direct Connect.
  • VPC Peering: 1:1 link between two VPCs. CIDRs must not overlap. Doesn’t transit — if A peers B and B peers C, A can’t reach C through B. Cheap, simple, doesn’t scale beyond a handful.
  • Transit Gateway (TGW): a hub-and-spoke router. Attach VPCs (and VPNs, Direct Connect) to it; transitive routing via route tables. Up to thousands of VPCs. Hourly + per-GB; cross-AZ for the TGW costs extra. The right answer for multi-VPC architectures.
  • Site-to-Site VPN: IPsec over the internet to your on-prem. ~1.25 Gbps per tunnel; encrypted but unpredictable latency. Acceptable for low-volume control-plane connectivity.
  • Direct Connect: dedicated fiber from AWS to your on-prem (or colo). 1/10/100 Gbps, predictable latency, lower egress prices. Production hybrid pattern — expensive setup, cheaper steady state.

Decision matrix: 2–3 VPCs talking? Peering. 5+ VPCs? TGW. On-prem <1 Gbps and not latency-sensitive? VPN. Heavy hybrid traffic? Direct Connect (with VPN as failover).

Gotcha: Direct Connect doesn’t encrypt by default. For regulated traffic, run VPN/MACsec over Direct Connect, or use AWS Direct Connect with MACsec on supported ports.
Gateway VPC Endpoints vs Interface Endpoints (PrivateLink).

Gateway Endpoints: for S3 and DynamoDB only. They’re free; you add an entry to your route table that targets the endpoint. Traffic goes to AWS’s service over the Amazon backbone, never the internet. No DNS changes needed.

Interface Endpoints (PrivateLink): for almost every other AWS service (and your own custom services). An ENI is created in your subnet with a private IP; AWS provides a DNS name resolving to that IP. Per-hour + per-GB priced. Used by SQS, SNS, KMS, Secrets Manager, ECR, etc.

PrivateLink for SaaS: the same mechanism lets you (the SaaS provider) expose a service to a customer’s VPC privately — no internet, no peering. Customer creates an Interface Endpoint to your service. This is the gold-standard private-SaaS connectivity. Snowflake, Datadog, MongoDB Atlas all support this.

Why use endpoints at all: keep traffic off the internet (security, compliance), avoid NAT Gateway egress charges (significant for high-volume apps).

What is Route 53’s routing-policy menu and when each?
  • Simple: one record, one or more values. No advanced behavior.
  • Weighted: distribute by percentage. Used for canary, A/B, gradual rollout.
  • Latency-based: route to the AWS region with lowest latency to the resolver. Default for multi-region apps.
  • Geolocation: route by user’s country / continent. Compliance (data residency), localized content.
  • Geoproximity: route by physical distance with bias. Like geolocation but distance-based and tunable.
  • Failover: primary + secondary, with health check. If primary fails, traffic shifts.
  • Multivalue answer: returns up to 8 healthy records to client; client picks. Health-checked round-robin.

Real production: latency-based + health-checked + alias to ALB. Combine policies hierarchically — latency-based at top, geolocation at country level, failover within each region.

What is Global Accelerator and how does it differ from CloudFront?

CloudFront: CDN. Caches HTTP content at edge POPs (~600 globally). Origins are S3, ALB, EC2, custom HTTP. Best for static + cacheable content. SSL terminated at edge.

Global Accelerator: NLB-style anycast. Provides 2 static anycast IPs that route to your nearest edge POP, then over AWS’s backbone to the closest healthy regional endpoint. Not a CDN — doesn’t cache; it improves the connection’s first-mile latency by getting traffic onto AWS’s backbone fast. Good for: gaming, VoIP, streaming, anything non-HTTP, multi-region failover with stable client IPs.

Decision: cacheable HTTP/HTTPS → CloudFront. Non-HTTP, low-latency, multi-region with stable IPs → Global Accelerator. They can also stack — CloudFront in front of GA endpoints — for hybrid cases.

Explain the IAM trust model: principals, roles, role assumption.

Principal: who is acting (a user, role session, AWS service, federated identity).

User: long-lived identity with credentials (access keys). Mostly antipattern in 2026 — use SSO + roles.

Role: set of permissions; no credentials of its own. Anyone allowed to assume it gets short-lived credentials via STS. Trust policy specifies who can assume; permission policy specifies what they can do.

Role assumption: via sts:AssumeRole — you trade your principal’s identity for time-limited (15min–12hr) credentials with the target role’s permissions. Audit log records both the original principal and the assumed role.

Instance profile: a role attached to an EC2 instance; the instance metadata service (IMDS) hands out short-lived creds. Used by SDKs automatically.

IRSA (IAM Roles for Service Accounts): the K8s on EKS pattern. Pod’s ServiceAccount is annotated with a role ARN; the EKS pod identity webhook injects a JWT projected volume; AWS SDK exchanges the JWT for STS creds. One role per workload — the right granularity.

apiVersion: v1
kind: ServiceAccount
metadata:
  name: payment-service
  namespace: prod
  annotations:
    eks.amazonaws.com/role-arn: arn:aws:iam::123:role/payment-service
Probing: “how does a pod get AWS credentials?” Wrong answer: instance role (everything on the node has the same access). Right answer: IRSA / EKS Pod Identity, with a role-per-workload.
What’s the difference between resource policies and identity policies?

Identity (principal) policy: attached to a user, group, or role. Says “this principal can do X on Y.”

Resource policy: attached to a resource (S3 bucket, KMS key, SNS topic). Says “this resource can be accessed by principal X for action Y.”

For most actions, the principal needs both permissions (identity allows AND resource allows). For cross-account access, you must use a resource policy because identity policies don’t cross account boundaries by themselves.

Cross-account S3 example: Account A’s role assumes; Account B’s S3 bucket has a bucket policy granting access to A’s role ARN; A’s role’s identity policy also allows the action. Both must permit; either deny is fatal.

Gotcha: implicit deny is the default. Permissions Boundaries and SCPs further restrict. The evaluation order: explicit deny > SCP > permissions boundary > identity + resource policies. An IAM admin might be blocked by an SCP they can’t see — trace the deny chain.
What is KMS and how does envelope encryption work?

KMS holds customer master keys (CMKs) — the actual encryption keys never leave KMS. To encrypt large data, you don’t use the CMK directly — envelope encryption:

  1. Ask KMS to GenerateDataKey; KMS returns a plaintext data key + an encrypted-with-CMK version of that data key.
  2. Encrypt your large data with the plaintext data key locally (AES-GCM, fast).
  3. Store the encrypted data alongside the encrypted-with-CMK data key.
  4. To decrypt: ask KMS to decrypt the data-key blob (returns plaintext), then locally decrypt the data.

Why: KMS request rate limits + cost. Encrypting a 1GB blob with envelope is one KMS call (for the data key); without envelope it’d be 16M calls (encrypting per chunk). S3 SSE-KMS, EBS encryption, RDS encryption all use envelope under the hood.

Multi-region keys: same key material in multiple regions, useful for active-active multi-region workloads. Key policies are critical — lose access to a CMK and your encrypted data is unrecoverable.

What is AWS Backbone and why does it matter for cross-region traffic?

AWS operates a private global network connecting its regions and edge POPs. Inter-region traffic between AWS services (S3 cross-region replication, RDS cross-region read replicas, Transit Gateway cross-region peering) traverses this backbone — not the public internet. Lower latency, more bandwidth, no transit-AS hops.

This affects design: cross-region S3 replication is fast enough to be operationally viable; cross-region RDS read replicas have predictable lag. If you tried to do this over public internet between two cloud providers, you’d have BGP-routed paths with congestion, jitter, and 30–100% worse latency.

Pricing: AWS-to-AWS cross-region is <$0.02/GB; AWS-to-internet outbound is $0.05–$0.09/GB. Designing for backbone usage saves real money at scale.

Explain Security Groups vs NACLs in one breath.

Security Group (SG): stateful, allow-only, applied to ENI (instance/Lambda/ALB level). Default outbound allow-all, default inbound deny-all. Returns auto-allowed. Multiple SGs can attach to one ENI; rules are union-OR. Use SGs for everything.

NACL (Network ACL): stateless, allow + deny, applied to subnet level. Both directions explicit. Rules processed by number, lowest first. Default NACL allows all; custom NACLs deny by default.

When to use NACLs: subnet-wide deny-list (“no instance in this subnet can ever talk to that bad IP”), defense-in-depth, regulatory requirements that demand subnet-level controls. The 99% answer: leave NACLs at default-allow, use SGs.

§ 07  Kubernetes deep dive

Reconciliation, all the way down.

Kubernetes is fundamentally control theory: declare desired state, run controllers that drive actual state toward desired. The cleverness is everywhere — in the scheduler’s priority functions, in kubelet’s pod sandbox lifecycle, in the API server’s admission chain. Knowing one layer is not enough; staff loops test the joins.

Concept · The control plane API server: the only component that talks to etcd. Everything else (controllers, scheduler, kubelet) reads/writes through the API. RESTful CRUD over types defined by CRDs and built-ins.
etcd: the consistent, watchable KV store. Holds all cluster state.
Scheduler: watches for unscheduled pods, picks a node, sets pod.spec.nodeName. Doesn’t actually start the pod.
controller-manager: runs many controllers (Deployment, ReplicaSet, Job, Endpoints, etc.) that watch resources and reconcile.
cloud-controller-manager: runs cloud-specific controllers (LoadBalancer creation, node lifecycle, route programming).
On each node: kubelet (watches pods assigned to its node, manages container runtime), kube-proxy (programs Services), container runtime (containerd, CRI-O).
How does the API server enforce admission? Walk through the request flow.

Each request goes through:

  1. AuthN: identify the caller (cert, token, OIDC, webhook). Failure → 401.
  2. AuthZ: can this caller perform this action on this resource? RBAC, ABAC, webhook. Failure → 403.
  3. Mutating admission webhooks: webhooks that modify the resource. Sidecar injection (Istio), default values, label injection. Run in order, each sees the previous’s output.
  4. Schema validation: the resource matches its OpenAPI schema (built-in or CRD).
  5. Validating admission webhooks: webhooks that accept or reject. Policy enforcement (OPA Gatekeeper, Kyverno), org-specific rules.
  6. Persist to etcd: the resource is stored. Watches notify.

This pipeline is per request. A misbehaving webhook (slow, down) can stall every API operation. Webhooks have timeouts (default 10s) and can be marked failurePolicy: Ignore for non-critical paths.

apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingWebhookConfiguration
metadata:
  name: enforce-labels
webhooks:
- name: labels.example.com
  rules:
  - apiGroups: [""]
    apiVersions: ["v1"]
    operations: ["CREATE"]
    resources: ["pods"]
  failurePolicy: Fail
  timeoutSeconds: 5
Probing: “a webhook is misconfigured and times out, what breaks?” If failurePolicy: Fail, every Pod creation in scope blocks. Recovery: delete the webhook config (one of the few times you bypass normal change control).
What is the reconciliation loop, and why is it the core idea?

Every Kubernetes controller follows the same pattern: watch → diff → act. The controller observes the current state of resources it cares about, compares to desired state in spec, and takes idempotent actions to converge.

This is control-theoretic in form — the desired state is the setpoint, the actual state is the process variable, the controller is the feedback element. Properties:

  • Idempotent: running the same reconcile twice does nothing the second time. Crashes don’t corrupt state.
  • Eventually consistent: reconciles converge over time, not instantly. A 3s delay is normal.
  • Edge-triggered with periodic re-sync: watches deliver change notifications (efficient); periodic full re-list (every 10 minutes typically) catches missed events.
  • Workqueue + rate limiting: batched events, exponential backoff on errors, retries with cap.

This is also why operators (CRD + custom controller) work: the same loop, but for your custom resource. Write a controller, watch your CRD, drive external state to match. PostgresOperator runs Postgres clusters this way; cert-manager issues certificates this way.

How does the scheduler decide where to place a pod?

Two phases:

  • Filtering (predicates): eliminate nodes that can’t run the pod. Resources fit, taints tolerated, node selector matches, volume zones compatible, affinity rules satisfied. Output: candidate node set.
  • Scoring (priorities): rank candidates. Built-in scorers consider: balanced resource allocation, image locality (pulled images on this node?), spread across nodes / zones, inter-pod (anti-)affinity, taints/tolerations preferred. Highest score wins; ties broken randomly.

The scheduler runs as a control loop: watch unscheduled pods, run filter+score, set spec.nodeName. It doesn’t enforce; kubelet on the chosen node sees the assigned pod and starts it.

Customization: scheduler profiles, custom plugins (kube-scheduler is plugin-based since 1.19), pod priority + preemption (high-priority pods can evict lower-priority ones), pod topology spread constraints (spread evenly across zones, hostnames, custom domains).

Karpenter (AWS) bypasses the traditional cluster autoscaler model: when pods are unschedulable, Karpenter reads them, picks the right instance type (size, generation, spot vs on-demand), and provisions. Faster than Cluster Autoscaler, better packing.

Explain the pod lifecycle, including init containers, sidecars, ephemeral containers.

Pending → Running → Succeeded/Failed (or Unknown for lost-contact). Inside Running, containers can be restarting per their restartPolicy.

Container categories:

  • Init containers: run sequentially before main containers. Setup tasks — database migrations, secret fetching, dependency waits. Each must succeed before the next runs.
  • Main containers: run in parallel; the pod is “ready” when all are ready. Failure restarts per restartPolicy.
  • Sidecar containers (since 1.28 GA): a special main container with restartPolicy: Always at the container level. Started before regular main containers, kept running across regular containers’ lifetimes. Examples: log shipper, mesh proxy. Replaces the old “multi-container with hand-rolled lifecycle” pattern.
  • Ephemeral containers: debug containers attached to a running pod for troubleshooting. Don’t restart, don’t mutate the pod spec. Used via kubectl debug.

Probes: liveness (restart container if fails), readiness (remove from service endpoints if fails), startup (longer-grace probe for slow starters; once it passes, liveness/readiness take over). Get the timing wrong on liveness probes and you’ll thrash containers under load.

Gotcha: a slow Java app with a default liveness probe (1s timeout, 3 failures, 10s period) can be killed mid-warmup. Use a startupProbe with generous initialDelaySeconds for slow-starting workloads.
Deployment vs StatefulSet vs DaemonSet vs Job — when which?
  • Deployment: stateless replicas. Pods are interchangeable, randomly named, can be replaced freely. Rolling updates with maxSurge / maxUnavailable. The default for HTTP services, workers without state.
  • StatefulSet: ordered replicas with stable identity. Pod-0, pod-1, pod-N. Each gets a stable hostname and a persistent volume. Started in order, deleted in reverse. Use for clustered storage (Kafka, Cassandra, Postgres, etcd) where pod identity matters.
  • DaemonSet: one pod per node (subject to node selectors). Use for node-level agents: log shippers (Fluent Bit), metric collectors (node-exporter), CNI agents, storage drivers.
  • Job: run-to-completion. Configurable parallelism and completion count. Use for batch work, migrations, one-shot tasks.
  • CronJob: Job on a schedule. Use for periodic batch (cleanup, backups, reports). Watch concurrency policy; default Allow can pile up if jobs run longer than period.

Common error: using StatefulSet for “I want stable hostnames” when you only have stateless workers. StatefulSet has slow rolling updates and ordered restarts — if you don’t need ordering, you’re paying for nothing.

Resource requests vs limits, and the QoS classes.

Requests: guaranteed resources; what the scheduler reserves on the node. Limits: hard ceiling enforced by the kernel (CFS for CPU, OOMKill for memory).

QoS classes (assigned by Kubernetes from your resource spec):

  • Guaranteed: requests == limits, both set, for every container, both CPU and memory. Scheduled with strong affinity, last to be evicted on node pressure.
  • Burstable: requests < limits, or only some resources specified. Most workloads.
  • BestEffort: no requests or limits set. Eviction first. Use only for genuinely tolerant workloads.

The CPU limits debate: setting CPU limits causes throttling under load even when the node has spare CPU — the kernel enforces the limit per scheduler period. For latency-sensitive workloads, this introduces “throttle stalls” that show up as p99 spikes. Modern practice: set requests, skip CPU limits. Memory limits still required (no graceful throttling for memory).

Eviction order under node pressure: BestEffort first, then Burstable exceeding requests, then Guaranteed last. Within tier, by priority and order of usage above request.

HPA, VPA, Cluster Autoscaler, Karpenter — how they fit.
  • HPA (Horizontal Pod Autoscaler): scales replica count by CPU, memory, or custom metrics (Prometheus, external). Scales a Deployment / StatefulSet up and down. Reaction time: ~1 minute.
  • VPA (Vertical Pod Autoscaler): recommends or applies resource requests based on observed usage. Updater mode evicts pods to apply new sizes. Doesn’t play well with HPA on the same metric.
  • Cluster Autoscaler: watches for unschedulable pods, adds nodes to the underlying node group (ASG, MIG). Scales down nodes whose pods can be scheduled elsewhere. Slow (~minutes for new nodes), tied to node-group templates.
  • Karpenter: Cluster Autoscaler replacement. Watches unschedulable pods directly, picks instance types optimal for the workload, provisions in <1 min, supports diverse instance types and Spot natively. Default for new EKS clusters in 2026.

Compose: HPA scales pods, Karpenter scales nodes when pods can’t fit. VPA is rare in production — it conflicts with HPA, and right-sizing is more often a one-time analysis than continuous tuning.

What is the operator pattern, and when do you write a CRD + controller?

An operator codifies the operational expertise for managing a stateful application as a Kubernetes-native automation. Pattern: define a CustomResourceDefinition (CRD) for your domain (e.g., PostgresCluster), write a controller that watches CRD instances and reconciles real-world state.

Examples: cert-manager (Certificates, Issuers, ClusterIssuers), Postgres Operator (Zalando, CrunchyData), Strimzi (Kafka), etcd-operator, Argo Rollouts (canary/blue-green).

When to write one: when your stateful workload has multi-step lifecycle ops (cluster bootstrapping, version upgrades, backup/restore, failover) that you’d otherwise document in a runbook. The operator is the runbook, executable.

When NOT to write one: stateless services don’t need it. Helm + a Deployment + an HPA covers 80% of workloads. Operators are for Cassandra, Kafka, Postgres, Elasticsearch — things with non-trivial lifecycle.

Frameworks: kubebuilder / operator-sdk generate the boilerplate. controller-runtime is the underlying library. Most production operators are written in Go.

How does kubelet talk to the API server? What about the container runtime?

kubelet → API server: mTLS over HTTP/2. kubelet has a client cert (issued via the certificates.k8s.io API or by a kubeadm bootstrap token). It watches pods assigned to its node (fieldSelector=spec.nodeName=<me>) and updates pod status (Ready, Phase, conditions). On a healthy cluster, kubelet maintains a long-lived watch — few RPCs, mostly just status updates.

kubelet → container runtime: via CRI (Container Runtime Interface), gRPC over a Unix socket. Operations: RunPodSandbox (create the pod sandbox — the namespace + cgroup + network), CreateContainer, StartContainer, StopContainer, RemoveContainer. Pulls images via ImageService.

Modern runtimes: containerd (default, lightweight, used by AKS, EKS, GKE), CRI-O (OpenShift default, lightweight). Docker Engine removed in 1.24 — the dockershim was deprecated in 1.20 and removed in 1.24. Older clusters still in transition use cri-dockerd as a translator.

Kata Containers, gVisor: CRI-compatible runtimes that add a VM (Kata) or user-space kernel (gVisor) for stronger isolation. Use for multi-tenant clusters running untrusted code.

How does PodDisruptionBudget interact with node draining?

PDB: a policy saying “at most N replicas of this app can be disrupted simultaneously” or “at least M must remain running.” Defines voluntary disruption tolerance.

When you kubectl drain a node (or cluster-autoscaler does), the eviction API checks PDBs: if evicting this pod would violate any PDB, the eviction is rejected. The drain operator must wait or retry. Without PDBs, drain proceeds aggressively — you can lose all replicas of a service if they’re all on the draining node.

Common PDB: minAvailable: 50% for a 3-replica deployment ensures at most 1 pod down during voluntary disruption. For singletons (single-leader StatefulSets), maxUnavailable: 0 means “don’t evict me, ever” — node drain blocks until manual intervention.

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: api-pdb
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: api
Gotcha: PDBs apply only to voluntary disruption (drain, update). They do nothing against involuntary (node hardware failure, kernel panic, cluster autoscaler termination if not gracefully draining).
What is the difference between a Deployment’s rolling update and a StatefulSet’s?

Deployment: creates a new ReplicaSet, scales up the new while scaling down the old per maxSurge (extra pods allowed) and maxUnavailable (pods that can be down). Pods are interchangeable; ordering doesn’t matter.

StatefulSet: updates pods in reverse ordinal order (N, N-1, ..., 0) one at a time by default. Each pod must become ready before the next is updated. partition field allows canary updates — pods with ordinal < partition stay at old version. OnDelete strategy disables auto-update entirely; you delete pods manually to trigger update.

Why the difference: StatefulSet pods may have stable identity (Cassandra node-N, Kafka broker-N) and replication relationships that require ordered update. A Postgres primary should update last; replicas first. Most CRDs/operators implement update logic that’s smarter than StatefulSet defaults.

How does etcd’s scaling profile constrain Kubernetes cluster size?

etcd is a Raft consensus cluster — every write is a quorum round-trip. Its throughput is ~10K writes/sec and storage is bounded (default 2GB; max recommended 8GB). Every Kubernetes resource is an etcd entry.

This drives the scale ceilings:

  • ~5,000 nodes per cluster (kube-up tested).
  • ~150,000 pods (with proper API-server tuning).
  • ~300,000 total objects.
  • API server LIST operations stress etcd; cluster operators use etcd-defrag, watch caches, and api-priority-and-fairness to manage.

Scale-out strategies: multi-cluster federation (Karmada, Cluster API), virtual clusters (vcluster runs a control plane inside a host cluster). For really large fleets, multiple K8s clusters with traffic / state federation beats one giant cluster.

Probing: “why not run K8s with 10K nodes?” etcd. The scheduler. The controllers’ informer caches. Each is fine at 5K, painful at 10K, broken at 20K. Multi-cluster is the architectural answer.
§ 08  Kubernetes networking

Flat networks, CNI, and why eBPF won.

Kubernetes networking starts with a deceptively simple promise: every pod gets an IP, all pods can talk to each other without NAT. Underneath: CNI plugins, kube-proxy, conntrack tables, iptables that grow into hundreds of thousands of rules, and an industry pivot toward eBPF.

Concept · The Kubernetes networking model Four invariants:
  • Every pod gets a unique IP, reachable from every other pod (in the cluster), with no NAT in between.
  • Every node can reach every pod, no NAT.
  • Pods see their own IP as the same one others see (no Docker-style NAT to a host port).
  • Services provide a virtual IP (VIP) backed by pod endpoints; service IPs are not real network destinations — they’re translated by kube-proxy.
The CNI plugin (Calico, Cilium, AWS VPC CNI, Flannel) is responsible for making the first three true. kube-proxy implements the fourth.
Compare AWS VPC CNI, Calico, Cilium, and Flannel.
  • AWS VPC CNI: each pod gets a real VPC IP from a secondary ENI on the node. Pros: pods are first-class VPC citizens — security groups, route tables, VPC flow logs all work. No overlay overhead. Cons: ENI/IP limits per instance type bound max pods (m5.large → 29 IPs across 3 ENIs); IPAM complexity. Default for EKS.
  • Calico: uses BGP to route pod CIDRs to nodes; no overlay needed in supported environments (or uses IPIP/VXLAN as fallback). Strong NetworkPolicy support, mature. Works on bare metal, VMs, on-prem.
  • Cilium: eBPF-based. Replaces iptables-based kube-proxy with eBPF datapath, does identity-aware NetworkPolicies (L7-aware: HTTP method, path), service mesh capabilities (Cilium Service Mesh), Hubble for observability. The strongest momentum in 2026.
  • Flannel: simple overlay (VXLAN by default). No NetworkPolicy. Used in small / dev clusters, k3s. Reasonable choice for “just give me pod networking, nothing fancy.”

Opinionated take: for new clusters, Cilium. eBPF datapath outperforms iptables at scale, identity-based policy is cleaner than label selectors, and observability is built-in. Calico is solid; AWS VPC CNI is the default if you’re on EKS and don’t need policy.

What is eBPF and why is it eating the networking stack?

eBPF (extended Berkeley Packet Filter): a Linux kernel facility for running sandboxed programs at hook points (XDP, tc, kprobes, uprobes, syscalls). Programs are verified for safety (no infinite loops, no out-of-bounds memory) at load time, then JIT-compiled to native code. They run with kernel-level performance and can read/write kernel state via maps (shared data structures with userspace).

Why it matters for K8s:

  • kube-proxy replacement: eBPF programs intercept packets at the socket / driver level, do service VIP translation, and skip iptables entirely. iptables performance degrades linearly with rule count; eBPF is constant-time.
  • Network policies: per-flow filtering with no syscall overhead, identity-based (using pod labels mapped to numeric IDs), L7-aware.
  • Observability: capture flow events, latency distributions, dropped packets without a sidecar tap. Hubble (Cilium) and Pixie (now defunct) both exploit eBPF.
  • Security: Falco, Tetragon, Tracee instrument syscalls, file access, network connects without modifying applications.

The bet: iptables-based networking is end-of-life. Even Red Hat’s OVN-Kubernetes is moving toward eBPF helpers. The transition will take 3–5 more years for laggards but the direction is set.

Probing: “Why does iptables get slow?” The packet path traverses chains rule-by-rule. With 5K services × 3 endpoints × 5 rules each, you have 75K rules per packet path. Lookup is O(N). eBPF maps are O(1) hashmap lookups.
kube-proxy: iptables vs IPVS vs eBPF.

iptables mode (default): kube-proxy programs DNAT rules to translate ServiceIP+port to a random pod endpoint. Random selection via probability rules. Performance degrades with service count (linear rule traversal); rule updates serialize through a lock. Mature, ubiquitous.

IPVS mode: kube-proxy programs the IPVS kernel module (a separate, hash-based load balancer). O(1) lookup regardless of service count. Supports multiple algorithms (round-robin, least-connection, source-hashing). Better at scale (5K+ services), but conntrack tables can still overflow.

eBPF (Cilium kube-proxy replacement): bypasses iptables and IPVS entirely; service translation happens in eBPF programs at the socket layer (for outbound) or XDP/tc (for inbound). Constant-time lookups, native sessionAffinity, can do health-aware routing. Removes conntrack pressure for pod-local traffic.

Migration path: most production EKS clusters in 2026 either run iptables (legacy) or have transitioned to Cilium with kube-proxy replacement. IPVS is a middle ground that didn’t see broad adoption.

ClusterIP, NodePort, LoadBalancer, ExternalName — what each does.
  • ClusterIP (default): a virtual IP within the cluster. Accessible only from inside the cluster. kube-proxy DNATs to backend pods. The most-used service type.
  • NodePort: the service is exposed on a port (30000–32767) on every node. External traffic to node:nodePort reaches the service. Implementations: just for dev/test; production uses LoadBalancer or Ingress.
  • LoadBalancer: the cloud-controller creates a cloud LB (AWS ALB or NLB, GCP Forwarding Rule). Each LB Service in EKS creates a separate LB — expensive at scale. Pattern: use one LB Service for an ingress controller, then route internally.
  • ExternalName: a CNAME-like alias. my-svc.cluster.local → rds-prod.amazonaws.com. Used to make external services look local for migration / abstraction.
  • Headless service (clusterIP: None): no VIP; DNS returns pod IPs directly. Used by StatefulSets so each pod is addressable by its ordinal name (cassandra-0.cassandra.default.svc.cluster.local).

Modern pattern: one Ingress (or Gateway API) in front, with LoadBalancer Service on the ingress controller; internal services are ClusterIP.

Ingress vs Gateway API — why the change?

Ingress (v1): a single resource that handles HTTP routing — hosts, paths, TLS. Limitations: vendor-specific annotations balloon the config (nginx.ingress.kubernetes.io/... for every advanced feature), no role separation (whoever creates the Ingress controls the LB), poor TCP/UDP support, awkward extensions.

Gateway API (GA in 1.30): a tiered resource model that fixes Ingress’s flaws.

  • GatewayClass (cluster-admin level): defines a controller (e.g., envoy-gateway, aws-load-balancer-controller).
  • Gateway (infra-team level): a deployable LB instance bound to a GatewayClass. Defines listeners (port, protocol, TLS).
  • HTTPRoute / TCPRoute / GRPCRoute (app-team level): the routing rules attached to a Gateway. Per-route filters, traffic splitting, header manipulation.

Benefits: role-oriented (admin/infra/app separation), extensible (typed extensions instead of annotations), protocol-aware (HTTP, TCP, gRPC, UDP all first-class), traffic splitting / canary built into HTTPRoute.

Implementations: Envoy Gateway, Istio Gateway, Cilium Gateway, AWS Load Balancer Controller (since v2.7), GKE Gateway. Ingress is now in maintenance mode — new features go to Gateway API. Plan to migrate.

apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: api-route
spec:
  parentRefs:
  - name: prod-gateway
  hostnames: ["api.example.com"]
  rules:
  - matches:
    - path: { type: PathPrefix, value: /v1 }
    backendRefs:
    - name: api-v1
      port: 80
      weight: 90
    - name: api-v2
      port: 80
      weight: 10  # 10% canary to v2
Explain CoreDNS, the cluster DNS, and how pods resolve names.

CoreDNS runs as a Deployment in kube-system (typically 2 replicas). Its Service IP is set as clusterDNS in kubelet config, so every pod’s /etc/resolv.conf points at it.

CoreDNS’s Corefile defines plugin chain: kubernetes plugin watches Service / Endpoint / Pod resources and builds an in-memory zone (cluster.local); forward plugin sends external queries upstream (e.g., to /etc/resolv.conf nameservers or 8.8.8.8); cache plugin caches.

Resolution: a pod queries my-svc; the resolver applies search domains from /etc/resolv.conf (my-ns.svc.cluster.local, svc.cluster.local, cluster.local), so my-svc → my-svc.my-ns.svc.cluster.local → clusterIP.

Common issues:

  • NDOTS > 5: pod with FQDNs that don’t end in dot trigger search-domain expansion (5 lookups for one external name). Set dnsConfig.options: ndots: 1 for high-volume external clients.
  • NodeLocal DNSCache (DaemonSet caching DNS on each node) reduces CoreDNS load and tail latency.
  • CoreDNS pods crashing or evicted → cluster-wide DNS failure. Run with PriorityClass and ensure adequate resources.
What does a NetworkPolicy do, and what doesn’t it do?

A NetworkPolicy is a Kubernetes resource that specifies allowed pod-to-pod (and pod-to-namespace) traffic at L3/L4. The CNI plugin (Calico, Cilium) implements them. Without a policy-enforcing CNI, NetworkPolicies are silently ignored.

Selector-based: podSelector + namespaceSelector match source/destination by labels. Default behavior: if any policy matches a pod, traffic not explicitly allowed is denied. Without any policy, pods accept all traffic.

Common patterns:

  • Default-deny in a namespace: empty podSelector + empty policyTypes → nothing allowed unless explicitly permitted.
  • Service-to-service allowlist: “app=frontend can hit app=backend on port 8080.”
  • Egress restrictions: pods can only reach the database namespace.

What NetworkPolicies don’t do: L7 inspection (HTTP method, path, headers) — need Cilium NetworkPolicy or service mesh. Encryption / mTLS — need a mesh. Egress to specific FQDNs (only IPs/CIDRs by default) — need Cilium FQDN policies.

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: db-allow-api
spec:
  podSelector:
    matchLabels: { app: postgres }
  policyTypes: [Ingress]
  ingress:
  - from:
    - podSelector:
        matchLabels: { app: api }
    ports:
    - port: 5432
How do Services find pods? The Endpoints / EndpointSlice mechanism.

Each Service has a label selector. The Endpoints controller (in kube-controller-manager) watches pods matching the selector and maintains a corresponding Endpoints object listing IPs and ports of ready pods.

kube-proxy watches Endpoints and programs the dataplane (iptables / IPVS / eBPF) to translate Service VIP → backend pod. When a pod becomes unready (failed readiness probe, terminating), it’s removed from Endpoints; kube-proxy stops sending it traffic.

EndpointSlice (1.21+, default in 1.25+): replaces single Endpoints object with sharded slices of 100 endpoints each. Solved the “giant cluster, one huge Endpoints update on every pod change” scalability problem.

Latency between “pod becomes unready” and “kube-proxy stops sending traffic”: typically 1–5 seconds. For graceful shutdown of a service receiving real traffic, the pod should: (1) fail its readiness probe, (2) sleep through the propagation delay, (3) drain in-flight requests, (4) exit. PreStop hook + sleep is the canonical pattern.

Gotcha: 502s on rolling deploy without preStop sleep are this exact race. Endpoint update is async; the LB still sends to the dying pod. preStop: sleep 15 usually fixes it.
What is Topology Aware Routing / Topology-aware hints?

Cross-AZ traffic costs money on AWS ($0.01/GB each direction). For a Service routing requests to randomly-selected pods, ~2/3 of traffic goes cross-AZ in a 3-AZ cluster. Topology Aware Hints (1.27+) annotates EndpointSlices with hints saying “prefer endpoints in zone Y if you’re in zone Y.” kube-proxy uses these hints to prefer same-zone endpoints.

It’s a soft hint — if the local zone has no healthy endpoints, traffic falls back to other zones. Activated by the service.kubernetes.io/topology-mode: Auto annotation. For balanced topology and adequate redundancy, the saving is 60–90% of cross-AZ traffic for chatty services.

Doesn’t replace zone-aware load balancers entirely — AWS LBs already do this for ingress. This is for internal Service-to-Service traffic.

What is a Headless Service, and when do you use it?

A Service with clusterIP: None. Instead of allocating a VIP, DNS for the Service returns A records for each pod IP directly. Combined with StatefulSets (which give pods stable DNS names), you can address individual pods.

Use cases:

  • Distributed databases: Cassandra, Kafka, MongoDB — each node needs to know peer addresses for replication / consensus. Headless Service + StatefulSet gives them cassandra-0.cassandra, cassandra-1.cassandra, etc.
  • Direct pod-to-pod connections: when you don’t want load balancing — e.g., SSE/WebSocket where you want to address a specific instance.
  • Service discovery for clients that do their own LB: gRPC clients with round_robin resolution; just give them DNS that returns all pod IPs.

Skip kube-proxy translation entirely — clients connect directly to pods. No conntrack, no DNAT.

How does service mesh mTLS get bootstrapped?

The mesh control plane runs a CA. Each workload (pod or sidecar) authenticates to the control plane via its Kubernetes ServiceAccount token (a JWT signed by the cluster). The control plane validates the token via the K8s TokenReview API, then issues a short-lived (1–24h) X.509 certificate with the workload identity (SPIFFE ID like spiffe://cluster.local/ns/prod/sa/api) in the SAN.

The sidecar (or eBPF-based mesh datapath) uses this cert for mTLS to peers. Peers verify the cert chain (rooted in the mesh CA) and the SPIFFE ID against allowed-source policies. Identity is the workload, not the IP — pods can move, IPs can recycle, the identity stays consistent.

Renewal: sidecars renew before expiry; the control plane handles cert rotation transparently. SPIRE (independent of any mesh) implements the same pattern as a generic identity provider.

This is what “zero trust within the cluster” actually means in 2026: no IP-based ACLs, identity-based mTLS for every pod-to-pod call.

Why is east-west traffic (in-cluster) the hardest scaling problem?

North-south (client → cluster) is bounded by your edge LB capacity and is well-understood. East-west (service → service) scales with services squared in the worst case — M services calling N services with average request rate R yields M×N×R flows. At microservice scale, this dominates by 100×.

Specific pain points:

  • Conntrack explosion: every new connection adds a conntrack entry. Default Linux conntrack table ~262K entries; chatty meshes overflow this.
  • kube-proxy latency: with 10K services and iptables, programming updates takes seconds; eBPF helps.
  • Sidecar cost: a sidecar mesh doubles the connection count per pod (in + out via sidecar). Each mTLS handshake costs ~1ms CPU.
  • Observability data volume: tracing every east-west call generates terabytes of trace data.

Mitigations: connection pooling, gRPC multiplexing (one conn handles thousands of RPCs), eBPF datapath, sampling for tracing, sidecar-less meshes (Cilium Mesh, Istio Ambient).

Probing: “why are you advocating Cilium Mesh over Istio?” Sidecar overhead is real at scale. A 1000-pod cluster with sidecar mesh has 1000 extra Envoy processes burning ~100m CPU each. Eliminate them and the cluster gets ~10% of capacity back.
§ 09  Data architecture, pipelines, ETL

Bronze, silver, gold — and the contracts in between.

Modern data architecture is converging: object storage as the system of record, columnar formats (Parquet) as the encoding, table formats (Iceberg, Delta, Hudi) as the transactional layer, and dbt + Airflow as the orchestration glue. The pipeline shape changed; the questions changed too.

Concept · ELT, lakehouses, and the medallion The classic pipeline was ETL: extract from source, transform in flight (Spark / Informatica / SSIS), load into warehouse. Compute was expensive; the warehouse was the only place with cheap query.

ELT reversed it: extract, load raw into the warehouse / lakehouse, transform with SQL inside (dbt). Drove by cheap object storage and warehouse compute (Snowflake, BigQuery, Databricks SQL).

Medallion architecture: bronze (raw, append-only), silver (cleaned, conformed, joined), gold (business-ready aggregates). Each stage is a transformation from the previous. Re-runnable, debuggable, version-controlled (dbt models).
ETL vs ELT — why ELT won.

Three changes flipped the economics:

  • Storage got cheap: S3 at $0.023/GB-month means storing raw history is trivial. Pre-cloud, you couldn’t afford to keep raw — transformation was lossy by necessity.
  • Cloud warehouses got fast: Snowflake / BigQuery / Databricks SQL can run terabyte-scale SQL in seconds. Transform inside the warehouse is now competitive with dedicated ETL frameworks.
  • Schema drift and reprocessing: ELT lets you fix a bug in transformation logic and rerun against raw bronze. ETL throws away the input; you’d need to re-extract.

ETL still wins when: data must be transformed before it touches the warehouse (PII redaction for compliance), the volume is too high to land raw (some IoT), or the transformation is non-SQL (ML feature extraction).

Hybrid (ETLT or reverse ETL): light transformation on the way in (PII masking, deduplication), then ELT for the rest. Common in regulated industries.

Lambda vs Kappa architecture.

Lambda (Marz, ~2014): two parallel paths — batch (Hadoop / Spark) processes the historical truth; speed (Storm, Samza) processes incoming events for low-latency views. A serving layer merges. Pros: batch correctness wins eventually, even if speed has bugs. Cons: two codebases, two failure modes, hard to keep in sync.

Kappa (Kreps, 2014): one path. Reprocess from the event log (Kafka with retention) when needed. Streaming engines (Flink, Spark Structured Streaming) provide the “batch” semantics by replaying. Pros: single code path, simpler ops. Cons: reprocessing TB of historical data through a streaming engine is expensive and slow.

Modern reality: mostly Kappa-ish. Kafka with 7–30 day retention; periodic offload to a lakehouse (S3 + Iceberg) for “truly historical” data. Streaming for live; batch SQL on the lakehouse for backfills and ad-hoc.

What is CDC, and how does log-based CDC compare to polling?

CDC (Change Data Capture): stream a database’s changes (inserts, updates, deletes) as events to downstream systems. Used to populate data warehouses, search indexes, caches, replicas without dual-writes from the application.

Polling-based CDC: periodic SELECT * WHERE updated_at > last_seen. Pros: simple, no DB privileges needed beyond read. Cons: misses deletes (no row to find), misses intermediate updates (only sees latest), depends on a reliable updated_at column, adds query load.

Log-based CDC: read the database’s replication log (Postgres WAL via logical replication, MySQL binlog, MongoDB oplog, SQL Server CDC). Captures every change including deletes, in commit order, with no impact on the primary’s query workload. Tools: Debezium (the canonical), AWS DMS, Fivetran (managed).

  • Ordering: per-table or per-key, FIFO. Cross-table ordering requires single-partition consumption.
  • Replication slots (Postgres) accumulate WAL until consumed — abandoned slots = disk full incident.
  • Schema evolution: column adds typically transparent; renames and drops break consumers.

Outbox pattern: instead of CDC’ing the business tables, the app writes both business state and an outbox row in one transaction. CDC streams only the outbox. Cleaner schema, tighter contract.

// Outbox row example
INSERT INTO outbox (id, event_type, aggregate_id, payload, created_at)
VALUES (gen_random_uuid(), 'order.placed', $1, $2::jsonb, now());
What is a lakehouse, and why is Iceberg / Delta winning over raw Parquet?

Lakehouse = warehouse-grade SQL semantics on top of cheap object storage (S3, GCS, ADLS). Key components: columnar files (Parquet) + table format (Iceberg, Delta, Hudi) + query engine (Spark, Trino, Snowflake, Databricks SQL).

Just Parquet gives you compression and column pruning — that’s it. No transactions, no schema evolution, no time travel, no concurrent writers, no partition spec versioning. You’re reimplementing the warehouse’s control plane on a filesystem.

Table formats add:

  • ACID transactions via metadata files (atomic commit by renaming a manifest pointer).
  • Schema evolution with version history.
  • Time travel (query the table as of a past snapshot).
  • Hidden partitioning (Iceberg partitions by transformations of columns; queries don’t need to know).
  • Concurrent multi-writer via optimistic concurrency on the manifest.
  • Vectored reads + min/max statistics for partition / file skipping.

Apache Iceberg is winning the format war — vendor-neutral (Snowflake, BigQuery, Databricks all read it), open governance, REST catalog spec for cross-engine compatibility. Delta is Databricks’s flavor; Hudi has streaming-upsert focus. If choosing now: Iceberg.

Probing: “why not just use Hive metastore + Parquet?” Hive’s partition-as-directory model is rigid (changing partition keys requires rewriting), no atomic multi-file commits, no row-level deletes. Iceberg is what you’d build if Hive didn’t exist.
Schema registry & data contracts — what does “backward compatibility” mean?

A schema registry (Confluent Schema Registry, AWS Glue Schema Registry, Apicurio) stores Avro / Protobuf / JSON Schema definitions and enforces compatibility on writes. Producers register a new schema; the registry checks compatibility against the current and rejects breaking changes.

The compatibility matrix:

  • Backward compatible: new schema can read data written with old schema. Producers upgrade first; consumers can keep using old schema. Allowed: adding optional fields, removing required fields with defaults.
  • Forward compatible: old schema can read data written with new schema. Consumers upgrade first; producers can keep using old schema. Allowed: adding required fields with defaults, removing optional fields.
  • Full compatible: both. Strictest. Allowed: only optional field additions/removals.
  • None: no checks. Bad idea except for genuinely throwaway topics.

The right default: backward for most topics — producers can be deployed independently. Forward when consumers move first (rarely). Full when you can’t coordinate — cross-team, cross-org, third-party consumers.

Data contracts elevate this concept to a formal agreement between producer and consumer teams: SLOs on freshness, schema evolution policy, ownership, deprecation timelines. Often expressed as YAML in a contract repo, validated in CI.

Avro vs Protobuf vs JSON Schema — trade-offs.
  • Avro: binary; schema must travel with data (or be looked up by ID via schema registry). Self-describing files possible. Strong evolution semantics. Built for the Hadoop / Kafka era. Default in many Confluent shops.
  • Protobuf: binary; schema separate (compiled into client code). Field numbers are the protocol; renaming a field doesn’t break compatibility, removing a number does. gRPC’s serialization. Fast, compact, type-safe codegen across languages. Default for service-to-service in 2026.
  • JSON Schema: human-readable, ubiquitous tooling. Verbose on the wire (no compression, no field shortening). Schema validation at parse time. Use for config, REST APIs, anywhere debug-friendliness matters more than throughput.
  • Apache Thrift: Facebook’s pre-Protobuf. Still in use at large scale (Pinterest, Twitter), but new projects rarely choose it.

For event streams: Avro is the streaming/lakehouse standard, Protobuf is the service-to-service standard. Pick one per platform; don’t mix.

What is Airflow, Dagster, Prefect — what do they own?

All are workflow orchestrators. Schedule, retry, monitor, alert on dependent tasks (DAGs). Differences in philosophy:

  • Airflow: the incumbent. Python DAGs, scheduler + executors, web UI. Imperative DAG definition (you write the topology). Operator zoo for every cloud / DB. Pain points: backfills are clunky, dynamic DAGs awkward, the UI shows tasks but not data.
  • Dagster: assets-first. You declare data assets (tables, ML models, files); Dagster figures out the dependency graph. Strong typing, integration with dbt, asset lineage in the UI. Better fit for data lakehouse work.
  • Prefect: Python-native, “tasks as functions.” Hybrid execution (control plane in Prefect Cloud, workers anywhere). Cleaner Python ergonomics than Airflow.
  • Argo Workflows: K8s-native, container-per-step. Used for ML pipelines (Kubeflow), platform automation. YAML-defined, less developer-friendly for complex logic.

What they don’t do: actual data transformation. They orchestrate — the work happens in dbt, Spark, or a Python container they invoke.

What is dbt, and why has it eaten the transformation layer?

dbt (data build tool) is a CLI that compiles SQL files into a DAG of CREATE TABLE AS SELECT / MERGE / INSERT statements run in your warehouse. Models are .sql files with Jinja templating; dbt resolves ref() calls into the dependency graph.

Wins:

  • SQL-first: data engineers + analysts can both contribute. The transformation lives where the data lives (warehouse).
  • Version control: models are git-tracked; PRs review transformation changes.
  • Tests: built-in tests (not_null, unique, accepted_values) and custom SQL tests. Run as part of CI.
  • Documentation: auto-generated lineage graphs and per-column docs.
  • Incremental models: materialize as “append since last run” or “upsert” with simple syntax.

What dbt doesn’t do: ingest data (you need an EL tool: Fivetran, Airbyte, custom CDC), transform outside the warehouse, ML feature engineering at scale (use Spark / Snowpark for that). dbt + warehouse is the silver-and-gold layer of the medallion.

How would you design a CDC pipeline from Postgres to Snowflake?

Standard architecture:

  1. Postgres logical replication: create a publication, configure wal_level=logical, replication slots for the consumer.
  2. Debezium Postgres connector reads the WAL, emits per-row change events to Kafka topics (one per table, keyed by PK).
  3. Kafka retains events (7 days typical) so consumers can replay. Schema Registry holds Avro schemas with backward compatibility.
  4. Snowpipe Streaming (or Snowflake Connector for Kafka) consumes from Kafka and writes to bronze tables in Snowflake — one row per change event with op type (c/u/d).
  5. dbt models in Snowflake transform bronze (events) → silver (current state via window/qualify) → gold (business aggregates).

Key concerns:

  • Schema evolution: when Postgres adds a column, schema registry sees a new Avro version; downstream models need a new column or null tolerance.
  • Initial snapshot: Debezium does a first-time full table snapshot before tailing WAL. For huge tables this is hours and locks slot.
  • Backpressure: if Snowpipe lags, Kafka retention must be longer; otherwise events drop.
  • Replication slot bloat: dead consumer = WAL accumulates = primary disk full. Alert on slot lag.
  • Tombstones: delete events should propagate to silver as soft-delete or hard-delete depending on policy.
Probing: “what happens if Debezium crashes?” The replication slot retains WAL until Debezium reconnects and acks. Slot lag is a critical alert.
Data quality — Great Expectations, dbt tests, contracts.

Layers of defense:

  • Schema validation at ingestion (schema registry). Catches structural drift.
  • Row-level constraints on landing: not_null on required fields, range checks on numerics, regex on identifiers.
  • Test suites in dbt: schema.yml declares not_null, unique, accepted_values, relationships (foreign-key checks). Custom tests for business rules.
  • Profiling tools (Great Expectations, Soda, Monte Carlo): statistical assertions over time. “User signups today is within 2σ of 7-day average.” Catches anomalies that schema can’t.
  • Data contracts with SLAs: producer commits to freshness, completeness, schema stability; violations trigger paging, not silent breakage.

The pragmatic stack: dbt tests for in-pipeline correctness (run in CI on every PR), Great Expectations or Soda for ongoing quality monitoring (run on a schedule, alert on drift). Contracts as the social/process layer.

What is OpenLineage and why does data lineage matter?

OpenLineage is an open spec for emitting lineage events — what process produced what dataset, from what inputs, with what code version. Implementations integrate with Airflow, dbt, Spark, Flink and emit to a backend (Marquez, Datahub, OpenMetadata).

Why lineage matters:

  • Impact analysis: “if I change column X in table A, what downstream models break?”
  • Incident debugging: “the dashboard is wrong — trace upstream to find the bad join.”
  • Compliance: “does this user data flow into any model that’s exported to a third party?”
  • Cost attribution: “which downstream consumers justify the expensive ingestion of source X?”

For SQL transformations (dbt), lineage is essentially free — ref() calls produce a DAG. For Spark / Python, lineage is parsed from job metadata; coverage is patchier.

How do you handle late-arriving / out-of-order data?

In streaming, events arrive with a timestamp but no guarantee of order. Watermarks are a streaming engine’s estimate of “event time progress” — a watermark of T says “we believe no more events with timestamp < T will arrive.” Windows close based on watermarks, not wall clock.

Handling late events:

  • Allowed lateness: keep windows open for X minutes past watermark; late events still fall in. Memory cost.
  • Side outputs / dead-letter: events arriving after lateness threshold go to a separate stream for manual reconciliation.
  • Recompute downstream: bronze layer accepts everything; periodic batch jobs in silver/gold reconcile.
  • Idempotent updates: design aggregations as upserts keyed on event ID; replay reapplies.

In batch, “late” is a different problem — data was missing in yesterday’s run; today’s data includes it. Solution: incremental models with backfill. dbt’s incremental materializations let you re-run a date range to fix a gap.

The hard truth: if your business demands exact aggregates over event-time windows, you need late-arrival tolerance, you must monitor watermark lag, and you must accept some delay for “final” results.

§ 10  Big data processing

Spark, Flink, Kafka Streams — what each runs.

The processing-engine landscape clarified in the last five years: Spark for batch & micro-batch streaming, Flink for true low-latency streaming, Kafka Streams for lightweight in-app processing, and the lakehouse query engines (Trino, Databricks SQL) for interactive. Knowing which tool for which job is the staff signal.

Concept · The processing-engine matrix
  • Batch SQL on lakehouse: Trino, Databricks SQL, BigQuery, Snowflake. Best for ad-hoc, dashboards, BI.
  • Batch / micro-batch ETL: Spark. The standard for terabyte-scale transformations and ML feature engineering.
  • True streaming (sub-second): Flink. Event-time processing, exactly-once via checkpoints + 2PC sinks.
  • Lightweight in-app streaming: Kafka Streams, ksqlDB. No separate cluster, JVM-only.
  • ML training: Ray, Spark MLlib for tabular; PyTorch / TF for deep learning — usually outside this stack.
How does Apache Spark execute a query?

Spark splits work into jobs → stages → tasks. The driver:

  1. Receives a query (DataFrame ops or SQL); the Catalyst optimizer rewrites the logical plan (predicate pushdown, projection pruning, join reordering, constant folding).
  2. Generates a physical plan with operators (HashAggregate, SortMergeJoin, BroadcastHashJoin, ShuffleExchange).
  3. Splits at shuffle boundaries into stages; within a stage, operators are pipelined per partition (tasks).
  4. Schedules tasks to executors on cluster nodes; each task processes one partition.
  5. At stage boundaries, data is shuffled — written to local disk, fetched by reducers based on partition key.

Tungsten (the off-heap memory + bytecode-generated operators) makes Spark’s in-memory processing fast. Adaptive Query Execution (AQE) (Spark 3+) re-optimizes mid-query based on runtime stats — coalesce small partitions, switch join strategies, handle skewed joins.

Where Spark struggles: tiny tasks (overhead dominates), deeply skewed joins (one task takes 99% of the time even with AQE), low-latency streaming (micro-batch is 100ms+).

RDD vs DataFrame vs Dataset — which to use?
  • RDD (Resilient Distributed Dataset): the original Spark abstraction. Distributed collection of Java/Scala objects. Functional ops (map, filter, reduce). No optimizer — you write what you want, Spark runs it. Use for unstructured / non-tabular data or when you need fine-grained partition control.
  • DataFrame: distributed table with named typed columns. Catalyst optimizes; Tungsten code-generates. Works in PySpark with SQL-like ergonomics. The default in 2026. ~5× faster than RDD for typical workloads.
  • Dataset (Scala/Java only): typed DataFrame — row class is a case class. Adds compile-time type safety but loses some optimization opportunities (Catalyst sees the case class as a black box for some ops). Not available in Python.

The trend: structure your data as DataFrames, fall back to RDD only when ergonomics demand it. Datasets are a Scala-shop preference, not strictly better.

Spark Structured Streaming vs Flink — when which?

Spark Structured Streaming: micro-batch (Spark 3+ also has continuous-processing mode but it’s feature-limited). Latency floor ~100ms, typically 1–10s. Processes batches of input every trigger. Same DataFrame API as batch — one team, two workloads.

Flink: true streaming — one event at a time through the operator graph, sub-millisecond latency possible. Sophisticated state management (RocksDB-backed, queryable), event-time + watermarks first-class, exactly-once via Chandy-Lamport-style barrier checkpointing + transactional sinks.

Choose Spark when: you already run Spark for batch, latency requirements are seconds (not milliseconds), the team is more SQL/DataFrame than Java/Scala-runtime-savvy. Most analytics ETL.

Choose Flink when: sub-second p99 matters, you need rich stateful processing (joins on long-running windows, sessionization, complex event processing), exactly-once with transactional sinks is required. Fraud detection, real-time personalization, anomaly detection.

Operationally, Flink is harder — tuning RocksDB state backend, sizing checkpointing, reasoning about backpressure. Spark is easier to run for non-experts.

Probing: “why not just use Spark for everything?” Latency. The 100ms floor is fundamental to micro-batch. If your SLO is “event to action in 50ms,” Spark Structured Streaming can’t hit it; Flink can.
What is event-time vs processing-time? Why do watermarks matter?

Event time: when the event happened (the timestamp on the event). Processing time: when the streaming engine sees the event. They differ — events from a mobile client might arrive 30 minutes late after a network outage.

For meaningful aggregations (“clicks per minute by event time”), event time is usually correct. But events arrive out of order, so the engine doesn’t know when a window can “close.”

Watermark: the engine’s estimate that “no event with timestamp < T will arrive.” Once the watermark passes a window’s end + allowed-lateness, the window emits its result. Watermarks advance based on observed event timestamps with a delay heuristic.

Trade-offs:

  • Aggressive watermark (small delay) = fast emission but more late events excluded.
  • Conservative watermark = more accuracy but higher result latency.
  • Allowed lateness keeps windows open longer; cost = state retention.

Watermarks are per-source by default; aggregating multiple sources uses the minimum (slowest) watermark, which means a stalled source can hold up the whole pipeline. Idle-source detection mitigates.

What windowing types exist, and what does each do?
  • Tumbling window: fixed-size, non-overlapping. “Count events per 1-minute interval.” Each event belongs to exactly one window.
  • Hopping (sliding) window: fixed-size, overlapping. “Count events in any 5-minute window, computed every 1 minute.” Each event belongs to multiple windows (5 in this example).
  • Sliding window (Flink-strict): some systems distinguish “sliding” (advances per-event) from “hopping” (advances by fixed step).
  • Session window: dynamic, gap-based. “Group events from the same user separated by < 30min idle.” Window grows as events arrive; closes after idle gap.
  • Global window: all events in one logical window; needs custom triggers to emit (e.g., on count or processing time).

Real use cases: tumbling for “hourly reports,” hopping for “current 5-min trend updated each minute,” session for user activity sessionization, global with custom trigger for streaming joins.

How does Flink achieve exactly-once semantics?

Two pieces:

(1) Checkpointing (Chandy-Lamport): the JobManager periodically injects a barrier into source streams. Operators snapshot their state when they receive barriers from all upstream channels (alignment). Snapshots are written to durable storage (S3, HDFS). On failure, Flink restores from the latest checkpoint — sources reset to the recorded offsets, operator state restored. Internal exactly-once.

(2) Two-phase commit (2PC) sinks: for end-to-end exactly-once, the sink must support transactional writes that can be aborted. Flink’s TwoPhaseCommitSinkFunction implements: preCommit (write data to a staging area, e.g., Kafka transaction or unflushed file), commit (atomically make visible after checkpoint completes), abort (discard on failure). Kafka producers, Iceberg, JDBC with proper drivers all support this.

The combination: source offsets are committed atomically with sink writes via the checkpoint. A failure replays the checkpoint; in-flight transactions are aborted; the system converges to a consistent state with no duplicates.

What can break it: sinks that aren’t transactional (a generic HTTP sink) — you’re back to at-least-once. The sink determines the end-to-end guarantee.

Gotcha: exactly-once is per-checkpoint. Inside a checkpoint window, an aborted transaction is invisible. But if your sink is a streaming consumer (e.g., Kafka topic), readers must use read_committed isolation to skip aborted transactions — otherwise they see the un-committed data.
Kafka Streams vs ksqlDB — what each is for.

Kafka Streams: a Java library, not a separate cluster. You write a stream-processing app; it runs as just-another-JVM-app, scaling horizontally by partition rebalancing within a consumer group. Stateful operations use embedded RocksDB (replicated to a Kafka changelog topic for fault tolerance). Exactly-once via Kafka transactions.

ksqlDB: a SQL layer on top of Kafka Streams. You declare streams (immutable event logs) and tables (derived materialized state) in SQL; ksqlDB compiles to Streams topologies. Runs as a server cluster you manage.

When to choose Kafka Streams: simple-to-medium streaming logic, want to embed in your service, no separate cluster. Microservices doing event-driven work.

When ksqlDB: streaming SQL is the right vocabulary, you have non-Java users, you want a managed/cluster surface.

When Flink instead: you outgrow Streams — complex windowing, true low-latency, multi-stream joins beyond what Kafka topics can naturally express, you don’t want all state in Kafka topics.

Streams is great for “join two topics, do stateful aggregation, write a third topic” in 50 lines. Beyond that complexity, you’re reinventing Flink with extra steps.

What is Apache Beam and the “write once, run anywhere” pitch?

Beam is a programming model + SDK for batch + streaming, with runners that execute the same pipeline on Spark, Flink, Google Dataflow, or Samza. Pipelines are PCollections (parallel collections) and PTransforms; the model abstracts over engine specifics like windowing, triggers, and state.

Pitch: write your pipeline once; if you change engines, you change the runner config. In practice the abstraction leaks — engine-specific runner capabilities differ (which windowing types, which sinks, what state APIs), and performance characteristics vary widely. The “portable runner” story is real but caveat-laden.

Where Beam shines: Google Cloud Dataflow. Beam is Dataflow’s native SDK; if you’re on GCP, Beam is the right choice. Outside GCP, Beam adoption is modest — Flink+Java and Spark+Python or SQL-via-dbt dominate.

How would you handle a skewed join in Spark?

Skew = one or a few keys having vastly more rows than others. After the shuffle, those keys’ tasks take 100× longer than the rest; the stage is bottlenecked.

Mitigations:

  • Adaptive Query Execution (AQE) (Spark 3+): detects skew at runtime and splits the heavy partition into sub-partitions; the other side gets duplicated for the split. Default-on; usually sufficient.
  • Broadcast hash join: if one side is small (<~10MB), broadcast it — no shuffle at all. Spark’s default if size hint is right; force with broadcast(smallDF).
  • Salting: append random salt to the hot key on both sides (e.g., user_id + "_0" through user_id + "_99"); join on the salted key. Distributes the heavy key across 100 tasks. Manual but effective.
  • Pre-aggregation: if the join is for aggregation, group on the heavy side first (reducing rows) before joining.
  • Skew hints: Spark accepts SKEW hints in SQL to direct AQE.

Diagnosis: Spark UI’s task duration histogram per stage. If you see 99 tasks at 1s and 1 task at 5min, that’s skew.

What is a stream-stream join, and what are temporal windows?

Joining two streams isn’t the same as joining two tables — both sides are unbounded. You can’t materialize and full-scan; you must define a window of relevance.

  • Interval join (windowed): match left event with right events whose timestamps fall in [L.ts - lower, L.ts + upper]. State is bounded by the window size + allowed lateness. Examples: “join click events with impressions within the past 5 minutes.”
  • Temporal table join (event-time enriched lookup): for each event, look up the “current” value of a slowly-changing dimension as of the event’s time. Used to enrich a stream with versioned reference data — e.g., events with currency conversion rates as of the trade time.

State management: each side maintains a window-bounded buffer of recent events keyed by the join key. The state size determines memory + checkpoint cost. Engineering for skew on the join key is critical — one hot user can blow up state.

Backpressure in streaming — what is it and how is it handled?

Backpressure: the consumer can’t keep up with the producer; without flow control, queues fill, memory blows up, latency spikes. In a healthy streaming system, backpressure propagates upstream — the slow operator slows down its producers, which slow down theirs, all the way to the source.

Flink: backpressure is built in via the network buffer system. If a downstream operator can’t accept, the upstream blocks on writes; sources stop polling Kafka. Visible in the Flink UI as backpressure indicators per operator.

Spark Structured Streaming: rate limiting at the source (maxOffsetsPerTrigger for Kafka). No automatic propagation — you tune for the slowest operator’s throughput.

Kafka Streams: consumer poll throughput naturally throttles upstream — the consumer commits offsets when done, so producers don’t over-supply.

The unhealthy alternative to backpressure is shedding — dropping events when the system can’t keep up. Acceptable for some use cases (sampling, log analytics) but you must commit explicitly to it.

Probing: “your Flink job is showing backpressure on the sink — what do you do?” First identify which operator (sink). Likely sink is the bottleneck (slow downstream system). Solutions: increase sink parallelism, batch writes, or scale the downstream system.
Why is end-to-end exactly-once so hard, even with Kafka EOS and Flink?

Exactly-once requires coordination across every step of the pipeline. Each component must support transactional / idempotent writes that can be aborted alongside source offsets. Failure modes that break it:

  • Non-transactional sink: the most common. A REST API call, an SMTP send, a webhook — you can’t abort “I already sent the email.” At best, idempotent at the receiver.
  • Two-system commits: writing to Postgres + Kafka in one transaction — only achievable via outbox pattern (write both to Postgres, CDC propagates to Kafka).
  • Consumer-side replay: Kafka offsets advance as part of EOS, but if your consumer reads + writes to a non-transactional system, you re-process on restart.
  • Cross-pipeline: if Pipeline A writes to topic X with EOS, and Pipeline B reads X with EOS, end-to-end works. If anywhere in the chain breaks isolation, you fall back to at-least-once.

The pragmatic engineering answer: design every consumer to be idempotent. Use deterministic IDs, upsert semantics, dedup on a unique event ID. EOS is a useful guarantee within the streaming engine; cross-system, idempotency is what saves you.
