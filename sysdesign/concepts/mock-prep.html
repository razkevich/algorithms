Day 1 Recap

The 5-Stage Framework

The structure that determines pass/fail. Memorize the stages, the caps, the artifacts each must produce.

The single rule: finish a working end-to-end system within the time box. Most candidates fail not from weak technical knowledge but because they get stuck in details and never reach Deep Dive. Time discipline > depth.

The 5 stages at a glance

1
Requirements 5 min cap
Produce: 3 functional + 3-5 quantified non-functional + out-of-scope.
Drive it: ask the PM (interviewer) clarifying questions. You synthesize, you don't invent.
Tools: SCALDS + COO scan checklist. Tab 2.
2
Core Entities 2 min cap
Produce: bulleted nouns. "v1, will iterate."
Why it matters: vocabulary alignment + becomes API resources + DB tables.
Watch for: conflating attributes (`shortcode`, `longUrl`) with entities (`Mapping`). The mapping is the entity; those are its fields.
3
API Design 5 min cap
Produce: endpoints with paths, methods, body shape. REST default; deviate only with reason.
Conventions: plural resource names (/mappings); path params for required IDs; identity from auth token (never request body).
Skip: obvious pagination/metadata endpoints unless they fork the design.
4
High-Level Design 10-15 min cap
Produce: boxes + arrows + schema annotations.
Discipline: simplest design that satisfies functional reqs. Walk each API endpoint through the system, narrate the data flow.
Don't sidetrack: when you spot a cache/queue need, note it and defer to Stage 5. Mid-HLD cache discussion = rabbit hole.
Vocab: logical-first. Tab 4.
5
Deep Dive 10 min cap
Produce: address each non-functional requirement; identify bottlenecks & SPOFs; handle edge cases.
Drive it: walk your locked NFRs. "We said <200ms — here's how we hit it."
Self-volunteer: hot-key handling, replication topology, observability. Don't wait for prompts. Tab 6.

Closing each stage — the verbal sign-off

The handoff phrase

Before opening the next stage, formally close the current one: 
"Locking these — [artifact 1], [artifact 2], [artifact 3]. Moving to Stage X."
For Stage 1 specifically, see Tab 5. Without an explicit close, the interviewer can't grade the stage against your stated targets in the critique.

Latency reference numbers (memorize)

OperationTypical latency
Cache (in-memory / Redis)1-5 ms
Relational DB simple query30-50 ms
Web server simple request10-20 ms
Target end-to-end p99 (no heavy compute)< 100 ms
Cross-continent network round-trip~150 ms

Implication: anything spanning continents on the hot path blows a 200ms p99 — note multi-region implications during Stage 1 — these are deployment-context constraints, called out separately from the SCALDS attribute scan.

Anti-patterns that tank interviews

  • Long requirements list. Looks broad; actually a commitment trap. Pick top 3.
  • Premature estimation. Burning 5 min on math that doesn't change the design.
  • Sidetracking into caches/queues during HLD. Mark them, return in Deep Dive.
  • Silent diagramming. No narration = no signal for the interviewer.
  • Schema bloat. Listing every column with types wastes time.
  • Talking over the interviewer. You miss the hints they drop.
  • Trusting user input for sensitive identity. User ID from request body = security red flag.
  • Designing for non-functional reqs you didn't actually state. "We made it highly available" without the requirement = noise.
  • Vendor-specific naming. EKS / API Gateway / Deployment instead of logical components. Tab 4.
  • Skipping HLD because "I have the optimized design." Reads as memorization. Use accelerated HLD instead.

SCALDS + COO — the Quality-Attribute Scan

Two distinct lists, two purposes. SCALDS to commit, COO to volunteer. Memorize both; recite both before every mock until automatic.

SCALDS — Stage 1 commitment set

Pick 3-5 to commit and quantify. Each one becomes a target Stage 5 will be graded against.

Letter Attribute Probe yourself URL Shortener example
S Scalability Peak QPS? Data volume? Growth rate? Hot-key skew? "100M creates/mo → 40 w/s avg, 4K r/s avg. Peak 10× → 400 w/s, 40K r/s. Hot key 10× per-key."
C Consistency Strong / eventual / causal / read-your-writes — per-operation, not blanket. "Eventual on resolve — read-after-create gap acceptable. Strong on shortcode uniqueness (DB unique constraint)."
A Availability Uptime SLO? Failure modes? Failover time? (absorbs "Fault Tolerance" — same axis from the user's view) "99.95% (~4h/yr). Postgres single-master with hot standby + Patroni for sub-30s failover."
L Latency p99 per operation? End-to-end vs single-hop? Cold-cache vs warm? "Read p99 <200ms (NA region), write p99 <1s."
D Durability How much data loss is acceptable? Per record-type — different answer per type. "Mapping = no loss (broken links forever). Click events = lossy OK (analytics is approximate)."
S Security AuthN/Z, data protection, rate limits, abuse prevention, regulatory? (absorbs "Compliance" — GDPR/SOC2 is a security/regulatory constraint) "Out of scope for v1 (anonymous service, no PII). Production: rate-limit POST, abuse-detection on long-URL patterns."

+ COO — Stage 5 must-volunteer set

Address all three unprompted in Deep Dive, even if not in your locked SCALDS. These are the items that separate Senior from Staff+.

Letter Attribute Probe yourself URL Shortener example
C Cost TCO at current scale? At 10×? What dominates the bill? When does the design break the budget? "Postgres + Redis fits a startup budget. Reaching for Spanner / global tables would 10× the bill — defer until international expansion warrants it."
O Observability Metrics, logs, traces, SLO/SLI definitions. "How would you know it's broken?" "Per-endpoint p99 latency + error rate as RED-method dashboards. Trace IDs propagated app→cache→DB. Alert on p99 > 200ms breach over 5-min window."
O Operability Deploy strategy, rollback, RPO/RTO, schema migrations on hot DBs. "Blue-green deploy with health-check gating. Postgres schema migrations via expand-then-contract pattern (dual-write, backfill, switch reads, drop old col). Daily backups → S3; PITR via WAL for last 7 days."

The mental model

"SCALDS to commit, COO to volunteer."

Stage 1: walk SCALDS as a mental scan; pick 3-5; quantify each.

Stage 5: walk your locked SCALDS items first (you committed; you must defend); then proactively touch all three COO items even if interviewer didn't probe them.

How to use it in Stage 1

  1. Run a 30-second mental scan through SCALDS. (COO is a Stage 5 list, not Stage 1.)
  2. Pick 3-5 to commit. The ones that fork the design or earn business signal.
  3. Quantify each. "Highly available" is useless. "99.95% availability (~4h/year downtime)" is a target.
  4. Explicitly skip with reason. Don't silently omit. Say "Security N/A for v1 — anonymous service, no PII." Better signal than skipping.

+ COO recital (Stage 5)

Goal: 30 seconds for SCALDS, 15 seconds for COO. Then practice walking each with a one-line probe + generic example. Muscle memory target: Day 3.

Deployment context (call out separately, not in mnemonic)

Things that aren't true quality attributes but constrain the design — surface in the Stage 1 PM conversation, before SCALDS:

  • Geographic scope — global / regional / single-region? (load-bearing for latency targets — cross-continent RT alone is ~150ms)
  • Client environment — mobile / battery / low-bandwidth?
  • Deployment — cloud / on-prem / air-gapped / hybrid?
  • Compliance regime — GDPR / HIPAA / SOC2 / PCI-DSS — drives Security depth.

Common stumbles

  • Skipping COO. Day 1 didn't have COO; you only did the Stage 1 set. From now on, all three COO items must surface in every Stage 5.
  • Conflating Durability with Availability. Different axes. Durability = data loss; Availability = uptime.
  • Hand-waving Scalability. "Should scale" is not an answer. State peak QPS, data volume, growth.
  • Letting Compliance hide. If the domain is regulated (fintech, health, EU), Security expands to include compliance — don't omit.
  • Treating Cost as out-of-scope. Even if not in your locked SCALDS, mention TCO trade-offs in Stage 5. Staff+ candidates always do.

Why this isn't FCC + SLEDS anymore

The migration story (read once, then forget)

Day 1 used FCC + SLEDS: Fault Tolerance, CAP, Compliance, Scalability, Latency, Environment, Durability, Security. Three problems with that framework:

  1. Two C's and two S's were confusable — F vs A vs CAP overlap; Compliance vs Security overlap.
  2. No slot for Cost, Observability, Operability — the three areas that separate Senior from Staff+.
  3. Environment is a deployment constraint, not a quality attribute. Belongs in the PM conversation, not the NFR list.

SCALDS + COO is one-letter-per-attribute, covers the three gaps, and uses real words ("scalds" + "coo") for memorability. Compliance folds into Security; Environment moves to deployment-context probes.

Math Canon

The conversions you should write cold on paper without thinking. Goal: fluency, not precision. Round aggressively.

The single magic number

10⁵ — seconds in a day

86,400 ≈ 10⁵. Burn this in. DAU × actions/user ÷ 10⁵ = average QPS.
  • 1B DAU × 1 action = 10K QPS avg
  • 100M DAU × 10 actions = 10K QPS avg
  • 10M DAU × 100 actions = 10K QPS avg
Once 10⁵ is muscle memory, every QPS estimate is one division.

Year31,536,0003 × 10⁷5-year capacity planning

Day 1 trap

During the URL Shortener mock, said "45 chars". Wrong. Alphanumeric = 62 (not 45). 45⁶ ≈ 8B; 62⁶ ≈ 57B. Conclusion was right (6 chars is enough), but the math was off — caught the eye of the interviewer.

Worked example — URL Shortener (the canon)

Step-by-step

Prompt: 100M new short URLs/month, 100:1 read:write, 5-year horizon.

Writes:
100M / month / 2.5 × 10⁶ s = 40 writes/sec average
With peak 10×: ~400 writes/sec peak

Reads:
40 × 100 = 4,000 reads/sec average
With peak 10×: 40,000 reads/sec peak
⚠️ Day 1 stumble: said 38,000 reads. That's 1000:1 ratio applied. Re-derive cleanly: average × 100 = 4K, peak × 10 = 40K.

Storage:
Per row ≈ 500 B (shortcode + long URL + metadata)
Monthly: 100M × 500B = 50 GB
5-year cumulative (no growth): 50 GB × 60 mo = 3 TB
With 3× replication + 1.5× index overhead: ~14 TB total

What forks the design:

  • 400 w/s, 40K r/s peak → single Postgres handles writes, reads need cache
  • 14 TB → well within sharded Postgres or DynamoDB; no exotic store needed
  • Read-heavy 100:1 → Redis in front of DB, near-100% cache hit on hot keys

Multipliers — the defaults

MultiplierDefaultWhen to bump
Replication factor×3×5+ cross-region
Index overhead×1.5-2heavy secondary-index workloads
Peak QPS / avg QPS×2-3 (typical) / ×10 (spiky)×5-10 for sports/news/sales
Hot-key skew×100celebrity fanout / trending

Vendor-Neutral Vocabulary

The single biggest senior-vs-mid signal in HLD. Lead with logical components; translate to vendor only as an optional aside.

Why it matters

  • Interviewer is grading architecture knowledge, not AWS familiarity. Naming products tells me you've used a tool; describing roles tells me you understand systems.
  • Vendor names invite vendor probes. "What does API Gateway do that an LB doesn't?" — easy bog.
  • Cross-cloud interviewers grade you down. Google, Azure, on-prem shops — they want to know you understand the role, not just AWS's product catalog.
  • Locks you out of pivot space. If interviewer says "we're on-prem", vendor-named designs re-architect from scratch.
  • The discipline of starting logical IS the senior signal. Counterintuitive but true.

Phrasing — bad vs good

❌ Vendor-first
"I'd put EKS Deployments behind an ALB, with API Gateway in front. Postgres on RDS, ElastiCache for Redis."
✓ Logical-first
"Stateless app tier behind a load balancer + API gateway. Relational primary, with an in-memory cache in front. On AWS this would be EKS + ALB + RDS + ElastiCache; same shape on GCP / Azure."
❌ Vendor-first
"We'd dump click events to SQS, have a Lambda consume them, batch-write to RDS."
✓ Logical-first
"Async work queue absorbs click events; consumer service batches and flushes to the relational store. SQS + Lambda is the AWS-native shape; Kafka + a worker pod is the OSS shape."
❌ Vendor-first
"Use DynamoDB Global Tables for multi-region writes."
✓ Logical-first
"Multi-region active-active KV store with last-writer-wins conflict resolution. DynamoDB Global Tables is the canonical AWS-managed version; the open-source equivalent is Cassandra with a global cluster."

The pattern in interviews

  1. Always lead with the logical role. "Stateless app tier", "in-memory cache", "durable event log".
  2. Translate to vendor as an optional aside only when (a) you're asked, or (b) it adds material precision.
  3. If interviewer pushes you to a vendor ("we're on AWS"), respond with the AWS analog — but lead with the logical role. "Right — for the relational primary, RDS Multi-AZ for the auto-failover; the role is still relational primary with hot standby."
  4. If you don't know the vendor name, just say the role. "I'd want a managed search index with refresh interval <1s — equivalent to Elasticsearch / OpenSearch on AWS." That's still senior.

Drill

Take any HLD you've designed. Re-narrate it aloud, banning vendor names entirely. Then re-narrate again, adding vendor analogies as optional appendices. The fluency you build is the muscle memory. Target: 5 minutes of HLD without slipping into vendor-first.

Stage 1 Closing Ritual

The verbal sign-off that locks Stage 1 against the rest of the mock. Without it, the interviewer can't grade your design against your stated targets.

The three artifacts

Before you can advance to Stage 2 (Entities), you must produce all three:

1. Top-3 Functional

"Users will be able to ___, ___, and ___."

Exactly 3. Not 5. Strategic prioritization > breadth. Every requirement is a commitment to design for it.

2. 3-5 Quantified Non-Functional

SCALDS scan visible. Each one quantified.

"99.95% availability" not "highly available". "<200ms p99 read" not "fast".

3. Out-of-Scope

Explicit list of what you're not designing for in this round.

Auth, custom features, multi-region, security — say so. Otherwise they leak into design pressure later.

The closing template

"Before I move to Stage 2, locking these:

   Functional — top 3:
     1. ___
     2. ___
     3. ___

   Non-functional — quantified:
     • Latency: ___
     • Availability: ___
     • Scalability: ___ (peak QPS, hot-key skew)
     • Consistency: ___
     • Durability: ___
     [+ Environment, Compliance, Security — explicit N/A or in-scope]

   Out of scope:
     • ___
     • ___

  Confirmed?  Moving to Core Entities."

Sloppy close vs clean close

❌ Sloppy (Day 1 baseline)
"Yeah, latency is one. Let's say 99.9% availability. Let's keep custom aliases out. Now let's talk about entities."

— No top-3 functional list, NFRs not quantified consistently, OOS scattered, no verbal sign-off, no SCALDS scan visible. Interviewer has to backtrack you.

✓ Clean
"Locking Stage 1.
Functional: create short link, resolve to redirect, public click stats.
Non-functional: read p99 <200ms NA, write <1s; 99.95% availability; 40 w/s avg / 4K r/s avg with 10× peak; eventual consistency on resolve; no data loss on mappings; single-region for v1; compliance N/A; security out of scope.
OOS: custom aliases, frontend, auth, security, multi-region, compliance.
Moving to entities."

Why the ritual matters

  • Critique calibration. End-of-mock grading is "did you hit X" — needs an explicit X.
  • Stops scope creep. If "click stats" wasn't on the list, you don't have to design for it. Force the interviewer to bring it up explicitly.
  • Forces SCALDS scan. The recital structure makes the missing letters glaring.
  • Process signal. Senior+ candidates close stages cleanly. Mid candidates blur boundaries.

Common stumbles

  • "Let's also have ___" mid-Stage 4. If it wasn't on the locked list, push back: "I locked OOS for ___ — do you want me to swap it in for one of the locked items?" Forces tradeoff conversation.
  • Quantification skipped under pressure. "We need it to be available" — caught instantly. Always pair every NFR with a number.
  • SCALDS half-scanned. Skipping D (Durability) and S (Security) silently is the most common pattern. Walk each letter aloud.

Stage 3 — API Design

5-min cap. Three or four endpoints is the right count for most problems. Endpoints become the spine of HLD; spec them so each one is independently designable.

Protocol pick

ProtocolWhenWhy
REST default The default. Deviate only with a reason. Caching, browser-native, infra-native, stateless. 95% of problems pick this.
GraphQL Heterogeneous clients needing different data shapes (mobile vs web vs partner) One endpoint, client-driven query shape; downsides: caching is harder, n+1 fanout risk.
gRPC / RPC Internal service-to-service, perf-critical hot paths Binary protobuf, multiplexed HTTP/2, schema-first. Mention if interview is backend-platform-flavored.
WebSockets / SSE Real-time bidirectional / push (chat, notifications, live feeds) Still design REST for create/read; layer push for updates.

Endpoint conventions — the rules you'll be graded on

RuleWhyExample
Plural resource names REST convention; the resource is the collection; specific items are accessed by id within it. /v1/mappings, /v1/users — not /v1/mapping
Path params for required identifiers Identity of the resource being acted on goes in the path. /v1/mappings/{shortcode} — not ?shortcode=
Query params for filters / pagination / time ranges Optional or query-shaped inputs. /v1/mappings/{shortcode}/stats?from=&to=&page=
Sub-resources under their parent Hierarchical data lives hierarchically. /v1/mappings/{shortcode}/stats > /v1/analytics/{shortcode}/stats
Use IDs not user-facing data in path params Full URLs / strings with special chars don't URL-encode cleanly. {shortcode} — not {shortUrl} or {longUrl}
Auth identity from token, never request body The single non-negotiable security rule. The endpoint doesn't take an authorId; it comes from the JWT. POST /v1/mappings { longUrl } — not { longUrl, ownerId }
Body for input data; response for output data Don't put data in headers (except auth); don't omit response shape. Include the response JSON shape, not just the status code.

The 301 vs 302 trap (URL Shortener canonical question)

If your design needs analytics, you must pick 302

301 = browser remembers the redirect forever. After one click, the browser bypasses your server and goes straight to the destination. Your click counter never sees subsequent clicks.

302 = browser asks every time. Every click hits your server. Analytics work. Cost: you pay one network round-trip per click instead of zero.

This is a load-bearing trade-off — own it.

The operational-vs-business-analytics trap

Operational metricsBusiness analytics
WhatServer p99, error rate, throughput, queue depth"How many users clicked my link?"
AudienceSRE / on-callEnd users
ToolPrometheus / Datadog / CloudWatchREST endpoint backed by your DB
Day 1 trapSaid "analytics served via Prometheus/Datadog" — conflated the two. Prometheus doesn't serve user data. Functional req #3 needs a real REST endpoint.

Typical 3-4 endpoint pattern (URL Shortener as template)

POST  /v1/mappings                                     { longUrl }                  → 201 { shortcode, shortUrl }
GET   /{shortcode}                  [short domain]                                  → 302 redirect to longUrl
GET   /v1/mappings/{shortcode}/stats?from=&to=                                      → 200 { totalClicks, dailyClicks: [...] }

Three endpoints cover create, redirect, stats. Pagination and metadata endpoints are skipped unless they fork the design.

Anti-patterns (caught in Day 1)

  • Saying "300 something" for the redirect. Pick 301 / 302 / 307 specifically and defend.
  • Putting full URLs in path params. Use the resource identifier ({shortcode}), not the full URL.
  • Designing a "POST /v1/users/{userId}/mappings" while auth is OOS. Auth identity comes from token even when auth is "OOS" — pretend it would.
  • Skipping the stats endpoint and saying "Prometheus handles it". Operational vs business analytics conflation.
  • Two endpoints for what could be one. Defensible (different cache TTLs) but you must say the defense.

Stage 5 — Deep Dive Walks

10-min cap. The stage that grades depth. Drive it by walking your locked NFRs in order; each one has canonical moves. Self-volunteer; don't wait for probes.

The seniority ladder (this stage is where you place)

LevelBehavior in Stage 5
JuniorWaits for interviewer to point at improvement areas. Answers when asked.
Mid-SeniorSelf-identifies some optimization spots. Mixed depth.
SeniorSelf-identifies all the obvious spots. Leads the discussion. Names trade-offs.
Staff+Same as Senior + makes decisive trade-off calls and defends them under pushback. Pre-empts the interviewer's next probe.

You're targeting Senior / Staff+ → drive Stage 5 proactively.

The walk pattern — NFR by NFR

Stage 5 isn't free-form. Walk your locked NFRs in the order you stated them; for each, deliver the canonical moves below.

L — Latency

  • State your hot-path latency budget (e.g., redirect <200ms = LB 5ms + cache 5ms + redirect 10ms = 20ms typical).
  • Cache strategy: read-through pattern, TTL choice, invalidation, hit-rate target (90%+ for power-law).
  • Read replicas to absorb cache misses — count derived from QPS math, not hand-waved.
  • Cross-region implications if E said multi-region — multi-region replica routing.

F — Fault Tolerance / Availability

  • Walk every component: what fails → blast radius → recovery.
  • Stateless app tier: behind LB, K8s/orchestrator handles spinup. ✓
  • Database: hot standby + automated failover. Name the tool — Patroni, Stolon, RDS Multi-AZ.
  • Cache: replication factor for HA cache cluster (Redis Sentinel or Cluster mode).
  • Async queue: at-least-once delivery + idempotent consumers; dead-letter for poison messages.

S — Scalability (and the hot-key reflex — see Tab "Hot-Key Reflex")

  • Peak QPS handling at each tier: app, cache, DB.
  • Hot-key handling — three layers (CDN / cache / DB) — self-volunteer.
  • Scale-out story: how would you 10× this? 100×? Sharding strategy + when you'd reach for it.

C — Consistency (CAP)

  • What's eventually consistent vs strong? Which operations? Which reads tolerate stale?
  • Replication lag implication: bounded staleness vs unbounded.
  • Cache coherence: TTL-based vs event-based invalidation.

D — Durability

  • Per-record-type tolerance: mappings = no loss; click events = lossy OK.
  • Backup cadence + restore RTO/RPO. Point-in-time recovery (Postgres WAL).
  • Cross-region backup if the data is critical.

E — Environment

  • Multi-region implications already declared in Stage 1; honor them here.
  • If global, name the strategy: read-local-write-anywhere, active-active with conflict resolution, etc.
  • If single-region, acknowledge the SLA boundary (Day 1: NA-only 200ms).

Self-volunteer items (don't wait for the interviewer)

  • Observability. Metrics (Prometheus), logs (structured + aggregator), traces (OpenTelemetry). Senior+ never forgets to mention.
  • Security & rate limiting. Even if S is OOS, mention rate-limit on creates briefly.
  • Edge cases. What if user deletes a mapping? What if the long URL is malicious? What if shortcode collides on custom alias?
  • Operational concerns. How do you deploy without downtime? How do you roll back a bad release?
  • Cost. Briefly: which component dominates spend? When does the design break the budget?

The "don't talk over the interviewer" rule

Senior+ candidates often over-monologue. Mistake.

Pause periodically. Let the interviewer probe. They have expectations you'll miss if you're filling all the air.

Soft-skill grading happens here too. Talking through follow-ups with the interviewer beats lecturing at them.

Pattern: after each NFR walk, pause for 2-3 seconds. Check if interviewer wants to probe before moving to the next.

Hot-Key Reflex

When you hear "viral / popular / burst / hot / celebrity / trending" in a non-functional requirement, this entire checklist fires unprompted in Stage 5. Senior+ self-volunteers; mid-level waits to be probed.

Trigger words

If the prompt or your locked NFRs contain any of these words, hot-key handling is on the menu:

viral popular burst hot celebrity trending spike power-law skew read-heavy

The mental model — three layers

Hot keys can hammer any of three layers. Identify which one(s) and apply the layer-specific mitigation.

1. CDN / edge

Trigger: static / cacheable response.

Mitigation: serve from CDN edge with TTL. But: caching breaks any analytics that needs to count clicks.

URL Shortener trap: CDN-cached redirects bypass server → no click counts.

2. Cache layer (Redis)

Trigger: single shortcode hit by 10K+ QPS — single key, single Redis node.

Mitigations:
L1 in-process cache + key-replication-with-suffix + probabilistic refresh + single-flight

3. Database (Postgres)

Trigger: single row updated 10K+/sec (the click counter).

Mitigations:
Write coalescing / async queue + batched aggregation + sharded counters

Cache-layer mitigations — depth

PatternWhat it doesWhen to use
L1 (in-process) cache Each app server keeps an LRU of N most-popular keys in memory. Hot keys served from app process; never hits Redis. Read-heavy with strong power-law (URL shortener fits perfectly). N = 10K-100K entries typical.
Key replication with suffix Hot key abc123 stored as abc123:0, abc123:1, ..., abc123:9. Client picks suffix at random; load distributes across 10 Redis nodes. Single-key concentration — one key gets disproportionate share of load.
Probabilistic early refresh Each request, with probability p × (now − last_refresh) / TTL, refresh the cache before TTL expires. Spreads stampede across time. Cache stampede on TTL expiry of a hot key.
Single-flight / request coalescing On cache miss, only one request hits the DB. Concurrent requests for the same key wait for the first. Library-level (Go: singleflight; Java: Caffeine.refreshAfterWrite). Cache stampede protection + DB load reduction.
Mutex-on-miss On miss, acquire a Redis lock to populate; concurrent misses wait or serve stale. Same goal as single-flight; cluster-wide instead of process-local.
Stale-while-revalidate Serve stale value past TTL while async refresh runs. Hot keys never appear "missing". Hot keys in read-heavy systems; eventual consistency acceptable.

DB-layer mitigations — depth

PatternWhat it doesWhen to use
Async queue + batched flush Write events go to Kafka/SQS; consumer aggregates in 1-min windows; flushes summary to DB. Counter-style updates (click counts, view counts, like counts).
Sharded counters Single counter row split into N shards: (shortcode, shard_id, count). Increment a random shard. Read = SUM all shards. Hot single-row UPDATE contention. Fast write, slightly slower read.
Write coalescing in app tier App accumulates updates in-memory (1-sec window), writes one consolidated update. When async queue is overkill; small bounded windows.
Partition by time Counter table partitioned by date; today's hot row in one partition, historic queries elsewhere. Time-series-ish counters (per-day click counts).

DB Drill Facts

Day 1 pre-mock recital surfaced specific factual gaps and terminology slips per database. Drill these so they're cold for Day 2's mock and beyond.

Full reference is in concepts/db-toolbox.md. This tab is the minimum facts to recall under interview pressure, with the Day 1 corrections highlighted.

Postgres

  • Single-master writes. WCU ceiling on a beefy node ≈ 10K writes/sec. Reads scale via streaming replicas (no native write replication).
  • Replication: streaming (physical, byte-for-byte WAL shipping) for HA; logical (per-table) for selective replication and CDC.
  • Failover automation: name these Patroni, Stolon, repmgr; on AWS = RDS Multi-AZ (sub-30s failover with auto promotion).
  • MVCC + isolation: Read Committed default. Repeatable Read = snapshot. Serializable = SSI.
  • Sharding: Citus extension (now Azure Cosmos DB for Postgres), or app-level by partition key.
  • Partitioning: declarative (PARTITION BY RANGE/LIST/HASH), built-in. Use this for archival (the cleaner version of two-table tiering).
  • Connection pooling: PgBouncer is mandatory at scale. Postgres scales OUT poorly (one process per connection); pool aggressively.
  • Indexes: B-tree (default), GIN (full-text, JSONB), BRIN (huge sequential), partial (WHERE clause), expression, covering (INCLUDE).

DynamoDB

  • Transactions: Day 1 gap TransactWriteItems / TransactGetItems — up to 100 items, single account+region, ACID.
  • Conditional writes: CAS for optimistic concurrency (PutItem ConditionExpression).
  • Read consistency: eventually consistent default; strongly consistent read available at 2× RCU cost.
  • Single-partition limit: ~3,000 RCU / 1,000 WCU. Hot key = throttle. Mitigation: write-shard via key suffix.
  • Capacity: on-demand (pay-per-request) or provisioned (with auto-scaling).
  • GSI/LSI: Global Secondary Index = eventual consistency, separate capacity; Local SI = strong consistency, max 5 per table.
  • Single-table design (Rick Houlihan): composite keys encoding multiple entity types in one table.
  • Streams: change-data feed for Lambda triggers / cross-region replication.
  • Cost: predictable but expensive at high QPS — can be 10× Postgres TCO. State this trade-off.

MongoDB

  • Terminology — get these right: Day 1 gap
    • Shard key (NOT "partition key" — that's Cassandra/DDB) — determines distribution across shards.
    • Replica set — unit of replication. 1 primary + N secondaries (typically 2). Async replication. Election on primary failure.
    • mongos — stateless query router. Clients talk to mongos; it consults config servers and dispatches to shards.
  • ACID transactions since 4.0 (replica set) / 4.2 (sharded). Don't claim Mongo lacks transactions — it doesn't.
  • Read preferences: primary / secondary / nearest — tune the C in CAP per-query.
  • Read concerns: local / majority / linearizable.
  • Write concerns: w:1 / w:majority / w:0 — durability vs latency.
  • Schema validation is optional (per-collection JSON Schema). "Schema-on-read" is a 2015 framing; updated.
  • Aggregation pipeline: $match, $group, $lookup ("join lite," not Postgres-grade).

Redis

  • Day 1 gap — "tunable consistency" was wrong. Redis is single-primary per shard with async replication. There is no Cassandra-style tunable consistency.
  • What IS tunable: persistence — AOF (append-only log) / RDB (snapshot) / hybrid; durability vs perf trade-off.
  • Single-threaded execution loop — atomic by default; Lua scripts for compound atomicity.
  • Eviction policies: allkeys-lru, allkeys-lfu, volatile-ttl, noeviction.
  • Replication: primary-replica async; Sentinel for HA (auto-failover); Cluster mode for sharding (16,384 hash slots).
  • Streams: the data structure (XADD / XREAD / XGROUP) — Kafka-lite. name this when discussing logs.
  • Distributed locks: SET NX EX for most cases. Redlock is contested (Kleppmann's critique). For correctness-critical locks: Postgres advisory lock or ZK/etcd, not Redis.
  • Sorted sets (ZADD/ZRANGE): leaderboards, time-bucketed sliding-window rate limiting.

Kafka

  • Terminology: Day 1 gap
    • Topic = logical category. Partition = unit of parallelism + storage; lives on a broker.
    • Partition key determines which partition a message lands in. Same key → same partition → ordered.
    • Ordering is per-partition only, never across partitions.
  • Default: at-least-once. Exactly-once is opt-in: idempotent producer + transactional producer + read_committed consumer.
  • Producer acks: 0 (fire-and-forget) / 1 (leader ack) / all (ISR ack — durable).
  • Consumer offsets: stored in the special __consumer_offsets topic by default (Kafka itself). Offset commit cadence tunable.
  • Consumer groups + rebalance strategy (sticky / cooperative-sticky to reduce churn).
  • ISR (in-sync replicas). Unclean leader election trade-off: availability vs durability.
  • Retention: time-based / size-based / compacted (latest-value-per-key, for changelog topics).
  • Hot partition: if one shortcode tweets viral, partition keyed on shortcode is hot. Mitigation: include random suffix in key; or hash-distribute.

Elasticsearch

  • Near-real-time, NOT real-time. Day 1 nuance Default refresh interval = 1 second. Newly-indexed docs aren't searchable for ~1s.
  • Lucene inverted index; sharded + replicated; BM25 scoring.
  • Sharding fixed at index creation; can't reshardd without reindexing. Capacity planning matters up-front.
  • Mapping: dynamic (schema-on-write, but inferred) vs explicit. Production: explicit mappings.
  • Aggregations: terms, date_histogram, percentiles — analytics shape, not search.
  • ILM (index lifecycle management): hot/warm/cold tiers for log retention.
  • Not a system of record. Always derived from a primary store (Postgres / Dynamo) via CDC / dual-write / outbox.

S3

  • Strong read-after-write consistency since Dec 2020. Day 1 gotcha The "eventually consistent" answer is now stale and reads as a tell.
  • Listing (LIST API) was the last to go strongly consistent — it now is too.
  • Storage classes: Standard / Standard-IA / Glacier (Instant / Flexible / Deep Archive). Lifecycle rules auto-tier.
  • Pre-signed URLs: time-limited direct access without proxying through your service. Important for upload/download patterns.
  • Multipart upload: required for files >5GB; recommended >100MB.
  • Versioning + Object Lock: compliance/immutability.
  • "Directories" don't exist — keys are flat strings; "/" is just a delimiter convention.

ClickHouse / OLAP family

  • Column-oriented, MergeTree engine (LSM-style sorted runs), vectorized execution, aggressive compression.
  • Never serve user-facing reads from OLAP. Feed it async from Kafka / CDC; query for dashboards.
  • Sort key (in ORDER BY) determines on-disk layout. Materialized views pre-aggregate at write time.
  • No UPDATE/DELETE in OLTP sense — mutations are async background rewrites.
  • Alternates worth naming: BigQuery (managed, GCP), Snowflake (managed, multi-cloud), Druid / Pinot (real-time aggregations, sub-second), Redshift (AWS).

Communication Patterns

Soft-skill grading happens in parallel with technical grading. Day 1 surfaced patterns to drop and patterns to keep — drill these as discipline, not as performance.

Pacing — pause and let the interviewer probe

Senior+ candidates over-monologue. The most common bad pattern.

You speak for 200 words; you cover ground; but you also miss the hints the interviewer was trying to drop, and you signal that you can't read the room.

Rule: after every major point (closing a stage, finishing an NFR walk, answering a probe), pause 2-3 seconds. Let the interviewer pick up the conversation if they want to.

Specific stop points where you should always pause:

  • End of Stage 1 close — invite confirmation before moving to Entities.
  • End of each NFR walk in Stage 5 — let interviewer probe depth.
  • After articulating a non-obvious trade-off — the pause itself signals confidence.
  • After resolving a probe — don't immediately start the next thread.

  • Stage 2 entities: ~20 sec.
