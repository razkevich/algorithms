A field guide to six databases —
and the trade-offs they hide.

A senior-level interview turns on choices, not trivia. This atlas covers the architectures, consistency knobs, scaling models, and operational pitfalls of Postgres, MongoDB, Cassandra, Redis, Elasticsearch, and DynamoDB—then lets you pull the levers yourself.

Six engines covers ~90% of the systems you’ll be asked to defend in a system-design loop. Depth beats breadth: the goal is to make a defensible choice, justify it, and know exactly where it breaks.

§ 02  Engine Profiles

Six profiles. Each one defensible.

The fastest way to lose a system-design loop is to wave at “NoSQL” and hope. Each engine has a personality, a write path, and a place where it falls over.

Relational · Single-primary · MVCC

PostgreSQL

The default answer that’s correct more often than people admit.

ACID SERIALIZABLE JSONB Vertical-first

Architecture

Single primary, one or more streaming replicas (async by default, synchronous available per-transaction). Writes go to WAL, then heap; reads use MVCC (each row is multi-versioned by transaction ID; old versions reclaimed by VACUUM).

Logical replication enables per-table replication and zero-downtime upgrades. Citus (now Microsoft) bolts on sharding for OLAP/OLTP fan-out; for hyperscale, CockroachDB/Yugabyte/Aurora reimplement the wire protocol on a distributed engine.

Consistency & Transactions

Full ACID. Read Committed default; Repeatable Read is snapshot isolation; Serializable is true SSI (Serializable Snapshot Isolation) — rare among open-source engines. Cross-row, cross-table guarantees just work.

Indexing

B-tree, hash, GIN (inverted, great for JSONB / arrays / FTS), GiST (geometric, FTS, fuzzy), BRIN (block-range, cheap for time-series), expression, partial, covering (INCLUDE). pg_trgm for similarity search; pgvector for embeddings.

Scalability

  • Vertical first. A modern node can do 100k+ TPS comfortably.
  • Read replicas scale reads linearly — mind replication lag for read-after-write.
  • Connection bottleneck: use PgBouncer (transaction pooling) before you scale up.
  • Partitioning (declarative, by range/list/hash) for big tables; pair with BRIN.
  • Sharding requires app-level work or Citus; not native.

Operational reality

  • Vacuum debt: long transactions block cleanup; bloat eats disk and slows scans.
  • txid wraparound is the boogeyman; autovacuum mostly handles it.
  • Failover is not built-in; needs Patroni/Stolon/RDS multi-AZ.
  • HOT updates avoid index rewrite when no indexed column changes.

Best fits / Anti-patterns

Use it for
OLTP, integrity-critical writes, complex joins, geospatial (PostGIS), small-mid analytics, JSONB-tinged hybrid models.
Avoid for
Petabyte write fan-out, multi-region active-active, mutable schema-less workloads at extreme scale.
Interview gotcha: The default isolation level is Read Committed, not Serializable. Saying “Postgres is fully ACID” without picking the level is a yellow flag at staff. Also: you don’t “scale Postgres horizontally” — you scale reads, partition tables, and route by tenant.
Document · Replica sets + sharding · WiredTiger

MongoDB

Document-shaped data and a shard key you’d better get right.

ACID (multi-doc) Causal consistency Shard-key-sensitive 16 MB doc cap

Architecture

A replica set = 1 primary + N secondaries with an oplog. Writes go to primary, replicate to secondaries; secondary heartbeats elect a new primary on failure (Raft-like, since 3.4).

A sharded cluster adds config servers (themselves a replica set), one or more shards (each its own replica set), and mongos routers that pre-process queries and broadcast or target by shard key. Storage is WiredTiger — B-tree, MVCC, document-level locking.

Consistency & Transactions

Two knobs: write concern (w:1 — primary only, fast; w:majority — durable, slower) and read concern (local, majority, linearizable, snapshot). Causal sessions guarantee read-your-writes across primary+secondaries.

Multi-document ACID since 4.0 (replica sets) and 4.2 (sharded). Real, but: latency cost is real, and txns spanning shards are coordinator-heavy. Treat them as a tool, not a pattern.

Indexing

B-tree-style. Compound, multikey (auto on arrays), text (basic), 2dsphere (geo), partial, TTL, wildcard (catch-all on dynamic fields), Atlas Search bridges to Lucene.

Scalability

  • Shard key is the architecture. Bad shard key = hot shard, query broadcast, rebalance hell.
  • Hashed shard key spreads writes; ranged supports range queries but risks hot shards on monotonic keys.
  • Zone sharding pins ranges to nodes (e.g., region locality).
  • Reads from secondaries scale read throughput — at the cost of staleness.

Operational reality

  • Resharding is now online (4.4+) but expensive; pre-plan.
  • Document size cap (16 MB) drives schema choices — use GridFS for blobs.
  • Oplog window: too short = secondary rebuild on restart; too long = wasted disk.
  • Atlas hides much of this; self-managed is more work than people expect.

Best fits / Anti-patterns

Use it for
User profiles, content, catalogs, telemetry with rich nesting, fast iteration on schema.
Avoid for
Heavy joins, cross-shard transactions at scale, strict cost-of-consistency budgets.
Interview gotcha: When asked “why Mongo?”, never say “it’s schemaless.” It isn’t — the schema lives in the application. Better answer: document-shaped data, replica-set HA, predictable scaling once we’ve modeled the access pattern around the shard key.
Wide-column · Masterless · LSM

Apache Cassandra

Linear-scale writes, gossip-coordinated, opinionated to the bone.

Linear write scale Tunable per query Query-first modeling No joins

Architecture

Peer-to-peer ring. Every node is identical; coordination via gossip. Data placed on the ring by consistent hashing over the partition key, with vnodes (256/node by default) so additions and failures rebalance smoothly. Replication factor (RF) is per-keyspace; placement is rack/DC-aware via NetworkTopologyStrategy.

Storage is an LSM tree: writes hit the commit log + an in-memory memtable, flushed periodically to SSTables; reads merge candidates and use bloom filters. Compaction (size-tiered, leveled, or time-window) is the engine’s ongoing tax.

Consistency model

Per-query consistency level: ANY, ONE, LOCAL_ONE, QUORUM, LOCAL_QUORUM, EACH_QUORUM, ALL. Strong consistency holds when R + W > RF (most teams: RF=3, R=W=QUORUM=2). Multi-DC apps almost always use LOCAL_QUORUM.

Lightweight Transactions (LWT) use Paxos for compare-and-set on a single partition — useful but slow (multi-round trip). No general ACID; no joins; aggregation is best done in app or batch pipeline.

Indexing

Primary key = partition key + clustering columns. Within a partition, rows are sorted by clustering columns (so range scans inside a partition are cheap). Secondary indexes exist; they’re local per node and slow at scale — design tables per query instead. SAI (Storage-Attached Indexes, 5.0) improves this materially.

Scalability

  • Linear writes — doubling nodes ~doubles write throughput.
  • Reads scale similarly but read amp can hurt on wide partitions / many SSTables.
  • Multi-DC active-active is a first-class deployment, not an afterthought.

Operational reality

  • Tombstones from deletes/TTLs can slow reads dramatically (tombstone_warn_threshold exists for a reason).
  • Repair (anti-entropy via Merkle trees) is mandatory; mishandled, it overloads the cluster.
  • Hot partitions are the #1 design failure — partition keys must spread writes.
  • JVM tuning still matters; off-heap and chunk caches help.

Best fits / Anti-patterns

Use it for
Time-series, IoT, audit/event logs, write-heavy feeds, multi-region with regional locality.
Avoid for
Ad-hoc analytics, multi-row mutations, small datasets, transactional workflows.
Interview gotcha: Cassandra is query-first. You don’t model entities and relationships and then write queries; you write the queries first and design tables to serve them — possibly duplicating data across tables. Saying “we’ll join later” is the staff-level red flag.
In-memory · Single-thread per shard · Cluster slots

Redis

A toolbox of data structures that happens to be a server.

Sub-ms latency Atomic ops Async repl by default RAM-bounded

Architecture

A single-threaded event loop per shard (multi-thread I/O exists for parsing/output, not for command execution). Sentinel provides leader election + failover for non-clustered HA. Cluster partitions the key space across 16,384 hash slots; each slot lives on one master + N replicas. Clients are slot-aware (CRC16(key) mod 16384), with MOVED/ASK redirects on resharding.

Persistence: RDB snapshots (point-in-time, fork-and-dump), AOF append-only file with rewriting (always/everysec/no fsync). Most teams enable both: AOF for durability, RDB for fast restart.

Data structures (the actual reason)

Strings, Lists, Hashes, Sets, Sorted Sets (skiplist + hash — the leaderboard structure), Streams (since 5.0; consumer groups), Bitmaps, HyperLogLog (cardinality with ~0.8% error), Geospatial (geohash on a sorted set), Pub/Sub, Functions (server-side Lua/Wasm). Redis-Cell, Bloom filters via modules.

Consistency & durability

  • Async replication by default — primary acks before replicas confirm. WAIT n ms approximates synchronous writes.
  • MULTI/EXEC queues commands atomically (no rollback). Lua scripts run atomically end-to-end — the real transaction primitive.
  • Failover loses non-replicated writes; budget for it.
  • Cluster split-brain: cluster-require-full-coverage + quorum sizing.

Scalability

  • Single shard ≈ one CPU core. Throughput is bounded by request rate and RAM.
  • Cluster scales linearly across shards; pipeline + multi-key ops within a slot only.
  • Hot key kills you — shard, randomize, or precompute.

Best fits / Anti-patterns

Use it for
Cache (the canonical use), session store, rate limiting, leaderboards, queues (Streams), distributed locks (with Redlock caveats), real-time counters.
Avoid for
Source-of-truth without explicit durability + ops design, large objects (multi-MB strings), workloads bound by disk economics.
Interview gotcha: “Redis as the database” is fine if you can speak to AOF tuning, replication, RDB recovery, and the shape of the failure on power-loss. Redlock for distributed locks is contested (Kleppmann/Antirez debate); know it. Cluster transactions & multi-key ops require keys in the same slot — hash tags ({user:42}:cart) are the lever.
Search · Lucene · Inverted index

Elasticsearch

A search engine that some teams pretend is a database.

Full-text + vector Near-real-time Reindex to reshard Not a system of record

Architecture

A cluster has master-eligible, data (hot/warm/cold/frozen tiered since 7.x), ingest, coordinating, and ML nodes. An index is split into primary shards (fixed at creation) plus replicas; each shard is a Lucene index made of segments.

Writes go to a primary shard, then replicate to replicas in the replication group. Index changes become visible on refresh (default every 1s) — that’s the “near-real-time”. Translog provides durability between flushes.

Consistency model

Eventually consistent reads bounded by refresh interval. Document versioning + optimistic concurrency (if_seq_no / if_primary_term). Discovery + master election rewritten in 7.0 (no more split-brain footgun — quorum-based now, finally).

Indexing

Inverted index by default (analyzed text); doc_values (column-store) power aggregations and sorting; keyword for exact matches; dense_vector for kNN/ANN; scaled_float, geo_point/shape, nested, parent/child (join). Mapping is stricter than people remember; dynamic mapping at scale = pain.

Scalability

  • Shard count is a permanent commitment for an index; reshard = reindex.
  • Rule of thumb: shards 10–50 GB each; aim for <1000 shards/node.
  • Tiers move data by age: hot (SSD/replicas) → warm → cold → frozen (S3-backed).
  • Aggregations can be expensive; pre-aggregate (rollups, transforms) for dashboards.

Operational reality

  • Heavy updates are anti-pattern: each update writes a new document version; segments must merge. Append-only is the happy path.
  • Mapping explosions from dynamic JSON kill nodes (especially with deeply nested docs).
  • JVM heap should not exceed ~31 GB (compressed oops); rest goes to OS page cache for Lucene.
  • Search vs. analytics workloads benefit from cross-cluster search + dedicated tiers.

Best fits / Anti-patterns

Use it for
Full-text search, log/metric/trace observability (the ELK/Elastic stack), product search with relevance ranking, vector / hybrid retrieval.
Avoid for
Source of truth, transactional writes, frequently-mutated documents, “just throw it all in ES” observability without retention tiers.
Interview gotcha: “Why is search slow at p99?” almost always traces to one of: refresh interval too aggressive, segment merge contention, hot shard, or a query that fans out across thousands of shards. Know the difference between query phase (each shard returns top-K) and fetch phase (coordinator hydrates final docs); deep paging breaks both — use search_after or PIT.
Managed · Auto-partitioned · Serverless-friendly

DynamoDB

No knobs, no servers, no second chances on your key design.

Single-digit ms Multi-region active-active Hot partition risk No ad-hoc queries

Architecture

Fully managed by AWS. Items are placed on a partition by hash of the partition key; each partition is replicated 3× across AZs in a region with internal multi-Paxos for strong consistency. Storage is SSD; the engine, schedulers, and partition splitting are all opaque — you see only the API.

Global Tables add multi-region active-active with last-writer-wins reconciliation. DAX is an in-front, write-through cache for read-heavy paths. Streams push change records into Lambda / Kinesis.

Consistency & transactions

Default reads are eventually consistent (1/2 cost). Strongly consistent reads are an opt-in flag in single-region. TransactWriteItems/TransactGetItems give ACID across up to 100 items / 4 MB — idempotent via client tokens. ConditionExpression gives optimistic concurrency without a transaction.

Indexing

Primary key: HASH only or HASH + RANGE (sort key). LSI shares the partition key, alternate sort key, must be created at table create, max 5/table, eventually consistent only for non-key projections. GSI picks new partition+sort keys, eventually consistent, separate WCU/RCU, can be added/removed online — the workhorse for alternate access patterns.

Capacity model

  • RCU: 1 strongly-consistent read of an item up to 4 KB; 2 eventually-consistent reads at the same size; transactional reads cost 2×.
  • WCU: 1 write of an item up to 1 KB; transactional writes cost 2×.
  • On-demand auto-scales but costs ~7× provisioned for the same throughput — great for spiky/unknown, expensive for steady-state.
  • Adaptive capacity redistributes hot keys somewhat; a true hot key still throttles.

Operational reality

  • Partition limits: a single partition tops out at 3000 RCU / 1000 WCU / 10 GB. Above that, design or split keys.
  • Single-table design packs multiple entity types behind composite keys to minimize cross-entity calls; learn it before claiming Dynamo expertise.
  • Item size cap 400 KB; large blobs go to S3 with the key in Dynamo.
  • No GROUP BY, no SUM, no joins. Aggregations live in Streams + downstream pipelines.

Best fits / Anti-patterns

Use it for
Predictable key-based access at hyperscale, serverless AWS apps, multi-region active-active, session/token stores, IoT ingest with Streams.
Avoid for
Discovery queries, evolving access patterns, large items, anything where you want to write the schema later.
Interview gotcha: The fundamental trade is “model the access pattern up front, pay nothing later” vs. “model nothing up front, pay forever in Scans + GSIs.” If a candidate proposes Dynamo and then needs JOINs and aggregations, that’s the failure mode.

§ 05  Interview Q&A

The questions that actually come up.

A staff loop probes whether you understand why a system makes its trade-offs. These are the questions that separate “I’ve used it” from “I can defend it”.

Cross-cutting

Explain CAP. Then explain why CAP is wrong.

CAP: in the presence of a network partition, a system must trade consistency for availability. CAP is a useful triangle but it’s narrow — it only describes behavior under partition.

PACELC (Abadi) is the honest version: else (when no partition), a system trades latency for consistency. Cassandra is PA/EL, DynamoDB strong reads is PC/EC, Spanner is PC/EC, Postgres single-primary is PC/EC, Mongo replica sets default to PA/EC.

Saying the right thing in an interview: “CAP forces a partition-time choice; PACELC tells me how the system trades latency for consistency in normal operation. Both matter for the SLO.”

What’s the difference between linearizable, sequential, causal, and eventual consistency?

Linearizable: every operation appears to take effect at a single instant between its start and end — a single global timeline. Strongest single-object guarantee.

Sequential: all clients see operations in some single order, but that order may not match real-time.

Causal: if A happened-before B, every client sees A before B; concurrent ops can appear in any order. The intuitive “read-your-writes + monotonic reads” bundle.

Eventual: if writes stop, all replicas converge. Says nothing about when.

Picking the weakest model that meets the use case is a senior-level move. Most user-facing apps need causal, not linearizable.

Why are LSM trees better than B-trees for write-heavy workloads?

B-trees do in-place updates — each write may rewrite a page (and its WAL entry). LSMs append to an in-memory memtable, flush sequentially to immutable SSTables, and reconcile via compaction. Sequential writes pin the disk to its peak throughput.

The trade is read amplification (a read may consult multiple SSTables; bloom filters help) and write amplification (compaction rewrites data many times). Tunable via compaction strategy: size-tiered (Cassandra default, write-favored), leveled (read-favored), time-window (best for time-series).

How would you choose a shard key?

Three properties at once: cardinality (enough distinct values), uniformity (writes spread evenly — no hot shard), and locality (queries you actually run can be answered by hitting one or few shards).

Bad choices: monotonic (timestamp, autoincrement) — hot tail; very low cardinality (country, status) — few partitions to spread across; user-unaware (random hash) when most queries are per-tenant.

Good answer: in Mongo, compound shard key with a hashed prefix (e.g., {tenantId: hashed, createdAt: 1}). In Cassandra, compound partition key + clustering columns to keep tenant data co-located while spreading writes.

How does multi-region active-active actually work?

Three approaches:

Last-writer-wins (LWW): DynamoDB Global Tables, Cassandra, Mongo. Conflicts resolved by timestamp. Simple, lossy — never use for counters or money.

Per-region partitioning: shard so each region owns a key range. No conflicts, but cross-region access is expensive. Zone sharding in Mongo, NetworkTopologyStrategy in Cassandra.

Consensus across regions: Spanner, CockroachDB, Aurora Limitless. Real linearizability, latency cost = round-trip time.

The senior framing: “Most apps don’t need multi-region active-active — they need active-passive with fast failover. Active-active forces conflict resolution into the app.”

What are common consistency footguns?

Read-after-write across primary & secondary: Mongo w:1 + secondary read; Postgres replica without sync. Solution: read from primary or use causal sessions.

Stale write to GSI: Dynamo GSIs are eventually consistent — query it <1s after a write and you may not see the row.

Concurrent updates: “last write wins” is a bug for inventory, balances, counters. Use conditional writes (Dynamo ConditionExpression, Mongo findOneAndUpdate, SQL SELECT … FOR UPDATE).

Cassandra deletes returning data: tombstones + read-repair lag mean a deleted row may reappear if RF>repair window. Run repair on schedule.

Engine-specific

Postgres · What is MVCC and why does VACUUM matter?

MVCC = multi-version concurrency control. Every row has visibility info (xmin, xmax); writers create new versions instead of blocking readers. VACUUM reclaims dead tuples once no transaction can see them.

Failure mode: a long-running transaction (e.g., a forgotten BEGIN) holds open the visibility horizon, vacuum can’t clean, tables bloat, queries slow. Monitor pg_stat_activity for old transactions; consider idle_in_transaction_session_timeout.

Mongo · What changes when you go from a replica set to a sharded cluster?

Routing moves to mongos; you need config servers (themselves a replica set); every query needs a shard key strategy (or it broadcasts); multi-document transactions across shards work but are 5–10× slower; uniqueness across shards is only enforced on the shard key; aggregations gain a coordinate-and-merge phase.

A common mistake: starting unsharded, then sharding without revisiting indexes. Many indexes that worked on a replica set become non-targeted on shards (no shard-key prefix), forcing scatter-gather.

Cassandra · Why “query-first” modeling?

No joins, weak secondary indexes, expensive cross-partition reads. The model that works: one table per query, partition key chosen so the data needed is in a single partition, clustering columns to slice within it.

Cost: write fan-out (one logical entity may live in 3–5 tables). Done well, reads are sub-ms and predictable. Done poorly, you bolt SQL habits on top and hate Cassandra.

Redis · How would you implement a distributed lock? Where does Redlock fail?

Single-node: SET key value NX PX 30000 (atomic set-if-not-exists with TTL). Release with a Lua script that checks the value before deleting.

Redlock coordinates across N independent masters; you need a quorum of acquires within a clock-skew bound. Kleppmann’s critique: GC pauses or clock jumps can violate mutual exclusion. Antirez’s rebuttal: bound it with fencing tokens.

Senior answer: “For best-effort mutexes (cache stampede, rate limit), Redlock is fine. For correctness-critical locks (money, inventory), use a system-of-record fencing token from a strongly-consistent store — the lock is just for fairness.”

Elasticsearch · Why is reindexing a constant fact of life?

Shard count is fixed at index creation; many mapping fields can’t be changed in place; analyzers can’t be updated for existing docs without reanalysis. Anything that materially affects the inverted index requires a new index + reindex.

Operational pattern: aliases point apps at the current index; reindex into v2; flip the alias. The alias is the contract.

DynamoDB · Walk through single-table design.

One table holds multiple entity types. Partition key is a generic PK, sort key is SK; values are typed prefixes (USER#42, ORDER#42#001). Common access patterns are answered by collocating items under a shared PK.

GSIs are alternate access paths over the same items. GSI overloading (e.g., GSI1PK / GSI1SK) lets one GSI serve multiple lookups.

Trade: harder to onboard, painful to evolve once data is large, easy to scan accidentally if you forget the index. The win: every operation is constant-time and predictable.

Closing the loop

If I gave you 30 seconds to defend a database choice, what’s your structure?

Four sentences: (1) workload — access pattern, scale, consistency, geography; (2) candidate engines — the 2–3 with matching shape; (3) trade-off you’re accepting — e.g., “eventual reads on the cache, strong on the source of truth”; (4) failure mode — what breaks, what we monitor, what the runbook does.

Anything missing one of those four signals “hasn’t run this in production.”
