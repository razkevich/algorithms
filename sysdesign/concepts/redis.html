Redis — interview kit

Topologies, data types, persistence, eviction, the gotchas that trip senior candidates, and the system-design patterns Redis lets you transfer.

1. TL;DR

Redis is a single-threaded, in-memory K/V server with a rich type system (~9 data structures). One instance does ~100k ops/sec at sub-ms p99 with a typical workload. Persistence is optional (RDB snapshots, AOF log, or hybrid). Scale by adding read replicas (Sentinel) or by sharding across many primaries (Cluster). Default reach: cache + session store + leaderboard + rate limiter + distributed lock + pub-sub bus + lightweight stream/queue.

The 30-second framing. "Redis fits when the working set fits in RAM, the access pattern is K/V or one of the rich types (sorted set, stream), and the consistency model — async replication, lossy on failover — is acceptable. If I need durability of every write under failover I reach for Postgres or DynamoDB instead."

When NOT to use Redis

Knowing when to reach for Redis is only half the signal; knowing when to not reach for it is the other half. Do not propose Redis when:

  • Working set exceeds available RAM. Redis is memory-bound. If the dataset is 500 GB and growing, you need a disk-backed store (Postgres, DynamoDB, Cassandra) — not a bigger EC2 instance.
  • Durability on every write is a hard requirement. Async replication means a failover can lose the last second(s) of writes. For financial transactions, order placements, or anything where a single lost write is a business-critical incident, use a database with synchronous WAL (Postgres) or a managed durable store (DynamoDB).
  • Complex queries (joins, aggregations, full-text search). Redis is a key-access store. If the access pattern requires ad-hoc SQL, use Postgres. If it requires full-text search, use Elasticsearch.
  • Multi-key transactions across shards. Redis Cluster has no cross-shard atomicity. If the domain requires ACID across entities that can't be colocated by hash tag, Redis is the wrong primary store.

2. Topologies — pick by failure model and scale ceiling

Mode Read scale Write scale HA Consistency on failover Ops cost Pick when
Standalone 1 instance 1 instance none — single point of failure n/a (no failover) lowest dev, batch jobs, throwaway cache
Sentinel (master + replicas + sentinels) replicas serve reads 1 master auto failover ~10-30s async repl — may lose unacked writes medium HA needed, dataset still fits one node, single primary throughput is enough
Cluster (multi-shard, each shard has its own replica) per-shard horizontal per-shard horizontal (sharded by hash slot) replica per primary, gossip-detected failover async repl per shard, no cross-shard transactions highest dataset > one node's RAM, or write throughput > one primary
The slot count is fixed. Redis Cluster always has 16384 hash slots. CRC16(key) % 16384 maps to slot maps to primary. This is not consistent hashing — adding/removing a primary triggers explicit slot migration with MIGRATE. The trade-off is simpler tooling at the cost of manual rebalancing.

Sentinel vs Cluster — the fork in the decision tree

The most common topology mistake in interviews is jumping straight to Cluster when Sentinel suffices. The decision tree is simple: can the entire dataset fit in one node's RAM (typically 25-100 GB usable)? If yes, Sentinel gives you HA with much lower operational complexity — no hash slots, no MOVED/ASK redirects, no cross-slot restrictions on MULTI or Lua. The write ceiling of a single primary (~100k ops/sec) is enough for the vast majority of workloads.

Cluster is the answer when you need to shard writes across primaries (write throughput > one node) or the dataset genuinely exceeds one node's RAM. State that trade-off explicitly in the interview: "I'd start with Sentinel because our dataset is ~20 GB and a single primary handles our write QPS; if we outgrow that, we migrate to Cluster and accept the cross-slot constraints."

Transfers to:

  • Standalone generalizes to any single-writer, single-reader embedded store (SQLite, BoltDB).
  • Sentinel generalizes to leader-follower with external election (Postgres + Patroni, MySQL + Orchestrator).
  • Cluster generalizes to static-shard architectures (Vitess, MongoDB sharded cluster, DynamoDB partitions).

Eviction policies

Policy What it evicts Pick when
noeviction nothing — writes fail when maxmemory hit persistent store, can't lose data (default if you're using Redis as primary store)
allkeys-lru least-recently-used from any key general-purpose cache, mixed access patterns
allkeys-lfu least-frequently-used from any key cache where access is heavily skewed (a few hot keys, long tail)
volatile-lru LRU among keys with a TTL mixed: some keys are cache (TTL set), some are durable (no TTL) — only the cache portion evicts
volatile-lfu LFU among TTL'd keys same as above with skewed access
volatile-ttl shortest-remaining-TTL first TTL is your priority signal (shorter = less important)
allkeys-random random rarely useful — only when access is uniform
volatile-random random among TTL'd same — rare
The default is wrong for caches. Out-of-the-box Redis uses noeviction, which is correct for "primary store" mode and dangerous for "cache" mode (writes start failing when memory fills). Always set maxmemory-policy explicitly. For most caches: allkeys-lru.

Caching patterns — which to name in the interview

Pattern Flow Consistency Pick when
Cache-aside (lazy load) App checks cache; on miss, reads DB, writes cache stale until TTL expires or explicit invalidation default for most read-heavy workloads; simplest to implement
Write-through App writes cache and DB together (or cache writes through to DB) cache always fresh after write reads must be fresh immediately after writes; willing to accept write latency increase
Write-behind (write-back) App writes cache; cache async-flushes to DB risk of data loss if cache node dies before flush write-heavy; DB can't keep up with write rate; acceptable risk of loss
Refresh-ahead Cache proactively refreshes keys before TTL expires near-zero stale reads for hot keys hot keys with predictable access; eliminates cache-miss latency spikes
The safe default. In an interview, start with cache-aside. It is the simplest, has no data-loss risk, and works for 90% of read-heavy patterns. Mention write-through or refresh-ahead only when the interviewer's scenario specifically demands fresher data or lower tail latency on cache misses.

5. Gotchas — what trips senior candidates

Single-threaded means one slow command blocks everything

KEYS *, SUNIONSTORE on huge sets, FLUSHALL, large LRANGE 0 -1 all block the event loop. Use SCAN, UNLINK (async delete), and bound result sizes. In interviews, always mention this when proposing Redis for anything — it shows you understand the execution model, not just the API.

Hot keys

One key getting 90% of traffic concentrates load on one shard. Mitigations: client-side caching of hot reads, key splitting (like:post:123:{0..9} and pick a random suffix), hash tags to colocate related keys, or read replicas for read-heavy hot keys. In Cluster mode, a hot key on shard 5 doesn't help if shard 5's primary is pegged — the hot key is the bottleneck, not "Redis."

Big keys

A 100 MB value blocks the event loop during serialization, slows replication, and stalls expiration. Cap value sizes; for blobs, store in object storage (S3) and put the URL in Redis. Use redis-cli --bigkeys to audit. The rule of thumb: keep values under 10 KB for normal keys; if you need larger, use Hashes with partial reads (HGET) instead of one giant String.

Expiration jitter / cache stampede

Many keys expiring at the same instant triggers a thundering herd of cache misses, which hammers the database behind the cache. Add +/-10% random jitter to TTLs. For very hot keys, refresh proactively (refresh-ahead) or use a "request coalescer" lock — one request rebuilds the cache, others wait on a short-lived lock key rather than all hitting the DB.

MULTI vs pipeline

They look similar; they are not. Pipelining is just network batching — the commands are not atomic and other clients interleave. MULTI/EXEC is atomic but blocks the server for the duration. For multi-key atomicity in Cluster mode, use Lua scripts on a hash-tagged key group. Do not confuse "pipeline = transaction" — it is one of the most common Redis misconceptions in interviews.

Replication is async

A write acked by master can be lost on failover if the replica hadn't caught up. WAIT N timeout lets you require N replicas to ack — but it is optimistic, not synchronous, and adds latency. Treat replicas as eventually consistent for reads. If you need every write durable under failover, Redis is the wrong primary store — use Postgres or DynamoDB with synchronous replication / WAL.

Cluster: multi-key ops must hit one slot

MGET k1 k2, MSET, transactions, Lua — all require keys to be on the same slot. Use hash tags: {user:42}:profile, {user:42}:sessions colocate via the {...} portion only. The CRC16 hash is computed only on the substring inside the first {...}, so all keys sharing that tag land on the same shard.

Resharding redirects

During slot migration, in-flight requests get ASK (one-shot redirect for this request) and after migration completes, MOVED (permanent — update your client routing table). Smart clients (redis-cli with -c, Lettuce, Jedis) handle automatically. In interviews, mention this when discussing Cluster topology changes to show you understand the operational mechanics.

SAVE vs BGSAVE

SAVE is synchronous and freezes the server. BGSAVE forks. Never run SAVE in production. Even BGSAVE has a cost: the fork doubles memory briefly (copy-on-write pages) and can pause the event loop for hundreds of milliseconds on large datasets. Size your instances so that RSS + fork overhead stays well under available RAM.

Distributed locks (Redlock)

Redis is commonly proposed for distributed locks (SET key val NX EX 30). A single-instance lock works for leader election or distributed rate limiting where occasional double-acquisition is tolerable. The Redlock algorithm (acquire on N/2+1 independent Redis instances) attempts stronger guarantees but is controversial — Martin Kleppmann's critique shows it can fail under clock skew and process pauses. In interviews, the safe framing: "I'll use a Redis lock for distributed coordination where brief double-holding is acceptable; if I need a strict mutual-exclusion lease, I'll use etcd or ZooKeeper which have consensus-backed sessions."

Memory sizing

Redis overhead per key is non-trivial: a simple String key-value pair with a short key costs ~90 bytes of overhead (dict entry, SDS header, robj). A million keys at 100 bytes each does not use 100 MB — it uses ~190 MB. Hashes with ziplist encoding (small hashes, hash-max-ziplist-entries 128) are significantly more memory-efficient than individual String keys. In interviews, mention this when the interviewer probes memory — "I'd use Hashes to batch small objects and cut per-key overhead."

The transfer test. When you mention a Redis feature in an interview, immediately follow with "this is the same shape as X in system Y" — that is the senior signal. "Use sorted sets for the leaderboard" is a junior answer. "Sorted sets give us a B-tree-ish ordered index in memory; the same shape as a Postgres BTREE on score, but with O(log N) updates and no disk write" is the senior answer.
