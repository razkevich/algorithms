Trie (Prefix Tree)

Edges carry characters, nodes carry no character — the path from root to a node is the string. A boolean isWord flag on a node marks "a complete inserted word ends here." The same node can be both a word-end AND a passthrough prefix for longer words.

Inserted words: cat, car, care, cars, do, dog

Prefix-only node    isWord = true (a real word ends here)

Notice three interesting things: (1) car's node is BOTH a word-end (green) AND a passthrough for care/cars. (2) do is a complete word AND a prefix of dog — same pattern. (3) ca is reachable (you can walk there) but its node has isWord = false, so search("ca") returns false while startsWith("ca") returns true. That flag is the entire difference between the two APIs.

search vs startsWith — the distinction

Both walk the same path. The only difference is what they check at the end node.

Why this shape unlocks hard problems

The trie turns a set of strings into a shared-prefix state machine. That matters whenever you'd otherwise repeat prefix work across many strings:

  • Word Search II (grid + dictionary) — one trie of all words; DFS the grid while walking the trie in lockstep. The moment the current path has no matching child in the trie, prune the entire subtree of DFS calls. Without the trie you'd re-solve Word Search I per word and TLE.
  • Auto-complete — walk(prefix) lands you at a subtree whose every descendant with isWord = true is a suggestion. Emit via DFS.
  • Replace Words — walk the input word char-by-char and stop at the first isWord node encountered. That's the shortest root that forms a prefix.
  • Binary trie for Max XOR of Two Numbers — the alphabet is {0, 1} and keys are 32-bit numbers. To maximize XOR you greedily take the opposite-bit branch at each level. O(n·32) instead of O(n²) pairwise.

The mental shift: "trie" isn't really about strings — it's the right structure for any fixed-alphabet sequential-key data set where prefixes are meaningful. Strings and bit-strings are just the two common cases.
