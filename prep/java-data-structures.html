Java Data Structures — Interview Reference

Trimmed to the two with genuinely non-obvious Java idioms — the ones people routinely miss or reach for the wrong class. Everything else (ArrayList, HashMap, PriorityQueue, HashSet, StringBuilder) is already in your muscle memory; the traps for those live in the file headers of the specific solutions that use them.

API traps for the ones not listed here (keep mental):
  • PriorityQueue / Deque / Queue use peek / poll / offer. Not peek / pop / push.
  • Deque is an interface. Instantiate with new ArrayDeque<>().
  • Reverse-sorted collection: Comparator.reverseOrder(). .reversed() only exists on an existing comparator.
  • Top-K largest → min-heap of size K. Top-K smallest → max-heap.

ArrayDeque — the stack / queue / deque answer

Every "I need a stack" and "I need a queue" in Java should reach for this. Stack is legacy and synchronized; LinkedList-as-queue is cache-unfriendly. ArrayDeque is a circular buffer: O(1) on both ends, no allocations per op.

AspectDetail
Class java.util.ArrayDeque<T> implements Deque<T>, Queue<T>
Big-O push/pop/peek: O(1)
offer/poll/peek: O(1)
contains / remove(Object): O(n)
Stack API push(t), pop(), peek()
Queue API offer(t), poll(), peek()
Deque API offerFirst / offerLast,
pollFirst / pollLast,
peekFirst / peekLast
Why not Stack? Legacy (pre-collections-framework), synchronized (slow), extends Vector. Never use in new code.
Why not LinkedList as queue? Node-per-element allocations; bad cache locality; ArrayDeque is faster on every benchmark.
Gotchas Throws NullPointerException on null — don't store nulls. poll() returns null if empty; remove() throws. Pick the version that matches your control flow.
Canonical uses
  • Stack: iterative DFS, monotonic stack (Daily Temperatures, histogram), balanced parens, expression eval.
  • Queue: BFS, level-order tree traversal.
  • Deque: sliding window maximum (monotonic deque), 0-1 BFS.

TreeMap — the secret weapon

Red-black tree, O(log n) everything, keys kept sorted. The killer methods are floorKey / ceilingKey / floorEntry / subMap — "nearest key ≤ X" and range queries that are awkward to write by hand. When a problem says "most recent", "nearest timestamp", "intervals by endpoint", "calendar booking" — TreeMap is usually the answer.

AspectDetail
Class java.util.TreeMap<K,V> implements NavigableMap<K,V>
Big-O get/put/remove: O(log n)
floor/ceiling/higher/lower: O(log n)
firstKey/lastKey: O(log n)
subMap view: O(log n) setup, range iter O(k + log n)
Ordering Natural order (Comparable) or custom Comparator in the constructor. For descending iteration: descendingMap() / descendingKeySet() — views, not copies.
Point queries firstKey(), lastKey(),
firstEntry(), lastEntry()
Nearest-neighbor queries floorKey(k)   // largest key ≤ k
ceilingKey(k)   // smallest key ≥ k
lowerKey(k)   // largest key < k (strict)
higherKey(k)   // smallest key > k (strict)
floorEntry(k)   // entry variant, returns Map.Entry
Range views subMap(lo, hi)   // [lo, hi)
subMap(lo, true, hi, true)   // inclusive bounds
headMap(k) / tailMap(k)   // (-∞, k) / [k, +∞)
Poll the endpoints pollFirstEntry() / pollLastEntry()
Gotchas
  • Don't forget the "strict" variants: floor/ceiling are inclusive (≤, ≥); lower/higher are strict (<, >). Off-by-one is a classic bug.
  • Keys must be comparable; null keys throw NullPointerException.
  • Views (subMap, descendingMap) are backed by the map — mutations flow both ways.
Canonical uses
  • Time-based Key-Value Store (LC 981) — floorEntry(timestamp) gives the most recent value at or before t.
  • My Calendar I/II/III (LC 729/731/732) — interval overlap via floorEntry + ceilingEntry on interval endpoints.
  • Range Sum in a BST-shaped problem — subMap(lo, hi).values() + sum.
  • Find max window / sliding-window-like problems where monotonic deque doesn't fit because values aren't strictly monotonic — TreeMap<value, count> with increment/decrement, lastKey() = running max.
  • Event-driven scheduling — pollFirstEntry() on a TreeMap<timestamp, List<Event>>.
vs. TreeSet Same API family (floor, ceiling, etc.) on a NavigableSet. Use when you only care about keys.
vs. PriorityQueue PriorityQueue: O(log n) insert, O(1) peek-min, O(log n) poll-min, but no random access / no nearest-neighbor. Use when you only ever touch the extreme. TreeMap when you also need "nearest key to X."
vs. ConcurrentSkipListMap Thread-safe navigable map — same API, O(log n) expected, lock-free. Drop-in replacement when concurrency matters.
