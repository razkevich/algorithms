§ 01  JVM internals

The runtime under your code.

Java’s portability story is “write once, run anywhere”. Its performance story is “run cold, get fast.” The JIT, the class-loading pipeline, escape analysis, and the off-heap escape hatches are how Java delivers C-adjacent performance from a managed runtime — and where most production weirdness lives.

Concept · Runtime anatomy A running JVM holds: heap (objects, split into young gen [Eden + 2 Survivors] and old gen), metaspace (class metadata, native, replaced PermGen in 8), code cache (JIT-compiled native code, default ~240 MB), thread stacks (each frame holds locals + operand stack), and direct memory (off-heap buffers, native libs).

A class entering the JVM goes through load → verify → prepare → resolve → initialize. Bytecode runs in the interpreter first, gets profiled, and the hot methods are JIT-compiled by C1 (fast, light optimization) then C2 (slow, aggressive). Recompiles, deopts, and on-stack replacement happen in real time. Knowing this lets you read a JFR profile without flinching.
Walk through what happens when a .class file is loaded.

Five phases: Load (find bytes, build a Class object, internal representation), Verify (bytecode is type-safe, stack consistency, no jumps out of bounds), Prepare (allocate static fields, default values), Resolve (symbolic references → direct references, may be lazy), Initialize (run <clinit>, static initializers, in source order).

Initialization is lazy — triggered by first active use (instantiation, static method call, static field read of a non-constant). The JLS guarantees thread-safe init of a class via an internal lock on the Class object — this is the foundation of the holder idiom for thread-safe lazy singletons.

What the interviewer is probing: do you know that initialization order is a runtime guarantee, not a compile-time one? It’s the basis of correct lazy-init patterns and a common source of static-init-order bugs.
Explain the classloader hierarchy and parent-delegation.

Bootstrap (loads java.* from the JDK image; written in C) → Platform (was ExtClassLoader pre-9; loads platform modules) → Application/System (loads classpath/modulepath). Each loader, when asked for a class, asks its parent first; only loads itself if the parent fails. That’s why you can’t override java.lang.String.

Frameworks invert this: web containers, OSGi, JPMS layers each load classes per-app/per-module to isolate versions. Two classes loaded by different loaders with the same FQN are not equal — they live in separate runtime types. ClassCastException: Foo cannot be cast to Foo is the classic symptom.

// Loader identity matters for equality of Class objects
Class<?> a = loaderA.loadClass("com.x.Foo");
Class<?> b = loaderB.loadClass("com.x.Foo");
// a != b. a.isAssignableFrom(b) == false.
What the interviewer is probing: have you ever debugged a real classloader leak (stuck war redeploys, Tomcat PermGen/Metaspace OOM)? “Yes I have, here’s how I traced it” is the senior signal.
What is the constant pool? When is a String interned?

Each .class file has a constant pool: indexed entries for class refs, method refs, field refs, and constants (strings, ints, etc.). At class load, these get resolved into runtime constant pools. String literals in source are added to a JVM-wide string table (the “intern pool”) at class load. String.intern() manually adds a runtime-built string.

Pre-JDK 7: intern pool lived in PermGen (small, fixed). JDK 7+: moved to the heap (size-tunable, GC’d). Tune via -XX:StringTableSize=N (default 65536 buckets in modern JDKs).

String a = "hi";
String b = "hi";
String c = new String("hi");
a == b;            // true  — same intern entry
a == c;            // false — new heap allocation
a == c.intern();   // true
Gotcha: Don’t use intern() as a poor-man’s cache. The string table is a global hash table; aggressive interning of high-cardinality data leaks until GC catches up.
How does tiered compilation work? What is C1 vs C2?

HotSpot has multiple tiers: 0 = interpreter, 1–3 = C1 (client compiler — fast compile, light opts), 4 = C2 (server compiler — slow compile, aggressive opts: inlining, escape analysis, scalar replacement, vectorization). Methods start at tier 0, get profiled, escalate to C1 then C2 once hotness thresholds (loop back-edges, invocation counts) trip.

Deoptimization happens when an assumption breaks (a class hierarchy gets a new subclass, an inlining decision becomes unsafe, a guard fails). The method falls back to a lower tier and may recompile later. OSR (on-stack replacement) recompiles a long-running loop mid-execution — you don’t restart the method.

Tunables: -XX:CompileThreshold, -XX:+TieredCompilation (default on), -XX:TieredStopAtLevel=N. For short-lived workloads people sometimes pin to C1 to skip C2’s warmup cost.

Probing: “why is the first request slow but the 1000th fast?” is the warmup question. Knowing it’s C2 + profiled inlining — not classloading — is the staff-level answer.
Explain escape analysis, scalar replacement, and lock elision.

Escape analysis (EA): at JIT time, C2 proves whether an allocated object “escapes” the current method (returned, stored in a field, passed to an unknown call). If not, three optimizations apply:

  • Scalar replacement: the object is decomposed into its fields, kept in registers/stack. No heap allocation, no GC pressure. This is why a tight loop allocating short-lived helper objects can run with zero allocations in steady state.
  • Lock elision: if a synchronized block’s monitor object never escapes, the JIT removes the locking entirely. StringBuffer in a method body becomes lock-free.
  • Stack allocation: rarer than scalar replacement; some HotSpot variants do it.

EA is fragile: any debug instrumentation that captures the object, any reflective access, or any megamorphic dispatch can defeat it.

public int sum(int[] xs){
    Stats s = new Stats();   // EA: doesn't escape → scalar-replaced
    for(int x : xs) s.add(x);
    return s.total();
}
What is the code cache? When does it become a problem?

JIT-compiled native code lives in the code cache, a fixed-size native segment (default ~240 MB in modern HotSpot, split into non-method, profiled, and non-profiled segments since 9). When it fills, compilation stops; everything stays interpreted — performance falls off a cliff.

Symptom: a long-running app that’s fine for hours, then spikes p99 with no GC change. Check jcmd Compiler.codecache or JFR. Bump -XX:ReservedCodeCacheSize; verify with -XX:+PrintCodeCache.

Modern JVMs do code-cache sweeping (eviction of cold methods); it’s usually enough. Apps with huge classpaths (Spring + dozens of dynamic proxies + lambdas) are the typical victims.

What does AOT compilation buy you? Where does GraalVM Native Image fit?

AOT trades JIT’s peak throughput for fast startup and low memory. GraalVM Native Image compiles your closed-world Java app to a native binary using static analysis — no JVM at runtime, no JIT, instant startup, ~10–20× smaller RSS. Cost: no dynamic classloading, reflection requires config, peak throughput is typically lower than C2-warmed HotSpot.

Project Leyden (incubating, JDK 24+) brings AOT to mainline HotSpot via “condensers” — pre-resolved classes, pre-linked methods, AOT-cached profiles. Less radical than Native Image, more compatible with reflection & dynamic loading.

Sweet spot for Native Image: serverless lambdas (cold-start sensitive), CLIs, sidecars. Anti-pattern: long-running services with heavy reflection / dynamic codegen (Hibernate, JSPs).

Probing: “why isn’t Native Image just better?” The closed-world assumption is the answer. Reflection, dynamic classloading, and ServiceLoader-discovered impls all need explicit hints.
Direct ByteBuffers, Unsafe, and the Foreign-Function & Memory API — when which?

Direct ByteBuffer: off-heap memory backed by malloc; freed by the buffer’s Cleaner when it’s GC’d. Used by NIO; safe but reclamation is non-deterministic. -XX:MaxDirectMemorySize caps it.

sun.misc.Unsafe: the original native escape hatch. Pointer arithmetic, raw memory ops, unsafe field access, CAS primitives. Used by every concurrency lib pre-9. Officially internal, on the deprecation path.

FFM API (JEP 442/454, finalized JDK 22): MemorySegment + Arena + Linker. Replacement for both Unsafe’s memory ops and JNI. Bounded segments, scoped lifetimes (deterministic close), structured access via VarHandle / MemoryLayout. The forward path.

try (Arena arena = Arena.ofConfined()) {
    MemorySegment seg = arena.allocate(1024);
    seg.set(ValueLayout.JAVA_INT, 0, 42);
    int v = seg.get(ValueLayout.JAVA_INT, 0);
} // arena closes → segment becomes inaccessible, memory freed
Why was PermGen replaced with Metaspace?

PermGen was a fixed-size heap region holding class metadata, interned strings, and (pre-7) static fields. The fixed cap caused the legendary OutOfMemoryError: PermGen space on Tomcat redeploy storms. Metaspace (JDK 8+) lives in native memory, defaults unbounded (capped by -XX:MaxMetaspaceSize), and is freed when its classloader becomes unreachable.

The leak shape didn’t go away — if a classloader pins (a static field references something from the parent loader, or a thread holds a context-classloader reference), Metaspace still grows. The error message just changed.

Heap layout: explain young / old / TLABs.

Young gen = Eden + two Survivor regions (S0, S1). New objects allocate in Eden. A minor GC (young collection) copies survivors out of Eden and the live survivor region into the empty one; objects that survive enough collections (the “tenuring threshold”, typically 15) get promoted to old gen.

TLABs (thread-local allocation buffers) are per-thread Eden chunks. Allocation is a pointer bump — ~10 ns — with no synchronization. When a TLAB fills, the thread grabs a new one. This is why Java allocation is “fast” despite being managed.

Large objects (> some threshold per GC, e.g. G1’s humongous limit at 50% of region size) bypass Eden and go straight to old. Excessive humongous allocations fragment G1 badly.

Why is reflection slow? Has anything changed recently?

Classic reflection went through native bridge code (NativeMethodAccessorImpl) until ~15 invocations, then JIT-generated bytecode (GeneratedMethodAccessor). Still expensive: argument boxing (varargs Object[]), security checks, and inability to inline through reflective dispatch.

JDK 18 (JEP 416): reimplemented Method.invoke on top of MethodHandles. Same surface, much better steady-state. VarHandle + MethodHandle are the modern primitives — bind-once, invoke-many, JIT inlines them as if they were direct calls.

For hot paths: cache MethodHandle at init time, use invokeExact. Don’t do field-by-name lookup in a loop.

What does final on a local variable buy the JIT?

For locals: nothing measurable. The JIT does its own SSA / def-use analysis; final is documentation. It does enable lambdas/inner classes to capture the variable (the “effectively final” rule).

For fields: very different. final instance fields get JMM publication guarantees (see §02). static final primitive/String fields with constant initializers become compile-time constants — the JIT folds them in and the field reference disappears.

Gotcha: “final for performance” on locals/methods is cargo cult. final on methods is a hint for inlining decisions, but C2’s class-hierarchy analysis already handles this for most cases.
§ 02  Java Memory Model

Happens-before is the only contract.

The JMM is a contract between the programmer, the compiler, and the hardware. Without it, the compiler will reorder your writes, the CPU will reorder your reads, and threads will see a kaleidoscope of states. With it, you have a small set of happens-before guarantees that make multi-threaded reasoning tractable.

Concept · Happens-before An action A happens-before action B (written A → B) if A’s effects are guaranteed to be visible to B and A appears to occur before B in any consistent execution. HB is the only thing the JMM actually guarantees about cross-thread visibility — everything else is fair game for the compiler & CPU to reorder.

HB edges are created by: program order within a thread; volatile write → subsequent volatile read of same field; synchronized exit → subsequent synchronized entry on same monitor; Thread.start() → first action in started thread; thread’s last action → thread.join() return; final field write in constructor → any read after the constructor returns (publication safety). Without an HB edge, no ordering or visibility is guaranteed.
What does volatile guarantee, and what does it NOT?

Guarantees: (1) reads/writes are atomic for the field (true even for long/double, which without volatile may tear on 32-bit JVMs); (2) every read sees the latest write — no caching in registers; (3) creates HB edges — every action before the volatile write happens-before every action after a subsequent volatile read of that field. This is the “memory fence” effect.

Does NOT guarantee: atomicity for compound operations. counter++ is read-modify-write — volatile gives you visibility but two threads will still race.

// WRONG — volatile does NOT make ++ atomic
volatile int count;
public void inc(){ count++; }     // race
// Right — AtomicInteger or LongAdder
private final AtomicInteger count = new AtomicInteger();
public void inc(){ count.incrementAndGet(); }
Probing: “volatile makes it thread-safe” is the junior answer. The staff answer separates visibility from atomicity from ordering — volatile gives you two of three.
Why is double-checked locking broken without volatile?

The classic broken DCL:

private Singleton instance;
public Singleton get(){
    if(instance == null){
        synchronized(this){
            if(instance == null) instance = new Singleton();
        }
    }
    return instance;
}

Why it’s broken: new Singleton() is three ops — allocate, run constructor, assign reference. The compiler can reorder the publish-reference and the constructor-body. A thread reading instance outside the lock can see a non-null reference to a partially-constructed object.

Fix: declare instance volatile. The volatile write inserts a release fence, ensuring constructor effects are visible before the reference is.

Better: use the holder idiom — a static nested class that’s loaded lazily by the JVM’s thread-safe class init machinery. No volatile, no locks, faster.

public final class Singleton {
    private static class Holder { static final Singleton I = new Singleton(); }
    public static Singleton get(){ return Holder.I; }
}
What guarantees does final on instance fields give you?

Final field semantics (JSR-133): any thread that obtains a reference to an object after its constructor finishes is guaranteed to see the correctly-initialized values of its final fields — without synchronization.

This is what makes String, Integer, and most immutable types safe to share. The constructor effectively has a release fence at the end before the reference can escape.

Where it breaks: if this escapes from the constructor (registering a listener, starting a thread that captures this, calling an overridable method), other threads can see the object pre-construction. final only protects you if the publication itself is safe.

public class Bad {
    private final int x;
    public Bad(EventBus bus){
        bus.register(this);   // THIS escapes — final guarantee voided
        this.x = 42;
    }
}
Explain VarHandle. Why does it exist?

VarHandle (JDK 9, JEP 193) is a typed reference to a variable (instance field, static field, array element) with a full menu of memory-ordering modes: get/set (plain), getOpaque/setOpaque (atomic but no ordering), getAcquire/setRelease (acquire-release semantics), getVolatile/setVolatile (sequentially consistent), plus compareAndSet, getAndAdd, etc.

It’s the public, supported replacement for sun.misc.Unsafe’s atomic ops — same performance (the JIT inlines them), no internal API. The java.util.concurrent.atomic package internally moved to VarHandles.

private static final VarHandle COUNT;
static {
    try { COUNT = MethodHandles.lookup()
        .findVarHandle(Foo.class, "count", int.class); }
    catch(Exception e){ throw new Error(e); }
}
private int count;
public int inc(){ return (int) COUNT.getAndAdd(this, 1); }
Probing: “why don’t we just use volatile always?” Volatile is one mode; sometimes you want acquire-release (cheaper) or opaque (atomicity without ordering). Library authors care about this; app code rarely does.
What is “safe publication”? Why does it matter?

To safely share a mutable object reference across threads without locks, the publication itself must establish an HB edge. Safe ways:

  • Initialize the reference in a static initializer (class-init lock).
  • Store into a volatile field.
  • Store into an AtomicReference.
  • Store into a field protected by a lock used by all readers.
  • Store into a final field of a properly-constructed object (final-field semantics).

Unsafe publication: a plain non-volatile reference write read by another thread may yield the reference but not the object’s fields. Common bug shape: a config object built and stashed in a non-volatile static field; reader threads see the reference but null fields. Goetz’s JCIP chapter 3 is required reading.

What was biased locking and why was it removed?

Biased locking was an optimization that “biased” an object’s monitor toward the first thread that locked it — subsequent synchronized entries by that thread were near-free (a CAS-less mark-word check). Helped uncontended single-threaded code that used legacy synchronized collections (StringBuffer, Hashtable).

Disabled by default in JDK 15 (JEP 374), removed in 18. Reasons: the bookkeeping cost grew with multi-core; the workloads it helped have moved to ConcurrentHashMap, StringBuilder, lock-free atomics; revoking a bias under contention triggers a safepoint, which became expensive.

Stop bringing this up in interviews unless asked. If you do, the right framing is: “biased locking optimized a workload that doesn’t exist anymore.”

What memory fences does synchronized insert?

Lock acquire = acquire fence (subsequent reads cannot move before it). Lock release = release fence (prior writes cannot move after it). Combined, this gives you the full HB edge: everything done in one synchronized block, on the same monitor, is visible to the next acquirer.

It does not give you a global StoreLoad barrier — reads after acquire could in principle be reordered with reads outside the block. In practice on x86, lock acquire/release maps to weakly-ordered ops the hardware already orders for you; on ARM/AArch64 the JIT inserts dmb instructions.

Two takeaways: (1) you must hold the same monitor for HB to apply — locking different objects in two threads doesn’t synchronize them; (2) the body of the synchronized block can be reordered internally as long as it’s consistent with single-threaded execution.

How do CAS, Atomic*, and the “ABA” problem relate?

CAS = compare-and-swap. Atomically: “if the variable holds X, set it to Y; otherwise fail.” Hardware-supported (cmpxchg on x86, LL/SC on ARM). The foundation of every lock-free algorithm.

ABA: thread T1 reads X, gets paused. Another thread changes X → Y → X. T1 wakes up, CAS(X, Z) succeeds — but the world isn’t the same; if X is a pointer to a recycled node, T1 just clobbered something. Lock-free linked-list pop-and-push is the canonical case.

Defenses: (1) version stamps — AtomicStampedReference wraps a (ref, int) pair; (2) AtomicMarkableReference for boolean-tag variants; (3) hazard pointers / epoch-based reclamation in lock-free data structures; (4) GC saves you from ABA on object identity in many cases — Java’s GC means a recycled pointer can’t be live yet.

What’s the deal with long tearing?

JLS allows non-volatile long and double writes/reads to be split into two 32-bit ops. On a 64-bit JVM you almost never see this in practice; on 32-bit JVMs (mostly historical now) you absolutely could observe a value that was “half of write A, half of write B.”

Mark such fields volatile and the JLS guarantees atomicity. Or use AtomicLong. In modern code this is mostly a trivia question, but the answer demonstrates you read the spec.

What is “sequential consistency” and does Java provide it?

Sequentially consistent = there exists a single global interleaving of all ops that respects program order in each thread. The strongest typical model.

The JMM provides SC only for sequentially-consistent operations: volatile reads/writes, lock acquire/release, atomic operations. Plain reads and writes are not SC; the compiler may reorder them within program-order constraints.

This is why the answer to “why don’t I see this write?” is almost always “because there’s no HB edge and you’re assuming SC.”

When would you reach for VarHandle over AtomicInteger?

AtomicInteger wraps a value in an object — one extra pointer hop, one extra heap object per atomic. Fine for hundreds of counters, painful for millions.

VarHandle on a plain int field gives you the same atomic ops with no wrapper. Used heavily in JDK collections: ConcurrentHashMap’s buckets, StampedLock’s state, etc.

Trade: ergonomics — VarHandle setup is verbose. For app code, AtomicInteger is fine. For library / framework code with allocation budgets, VarHandle wins.

Explain the “piggybacking” pattern with volatile.

Because a volatile write/read pair establishes a full HB edge between the two threads, all writes done by the writer before the volatile write become visible to the reader after the volatile read. You can “piggyback” multiple non-volatile writes on a single volatile flag.

private int a, b, c;        // not volatile
private volatile boolean ready;

void writer(){
    a = 1; b = 2; c = 3;
    ready = true;             // release fence
}
void reader(){
    if(ready){              // acquire fence
        // a, b, c are guaranteed to be 1, 2, 3
    }
}

This pattern underpins many fast-path designs (initialization-once, immutable-after-publish state machines).

§ 03  Garbage collection

Six collectors. One workload. Pick wrong, suffer.

Modern GC is no longer a single dial between “throughput” and “pause”. It’s a menu: low-latency concurrent collectors that target sub-millisecond pauses (ZGC, Shenandoah), region-based generational collectors with predictable pauses (G1), and old-school throughput collectors for batch work (Parallel). Choose wrong and you’ll spend a quarter chasing a tail latency that the collector was never built to deliver.

Concept · The collector lineup Serial (single-threaded, embedded/tiny heaps), Parallel (throughput-first; default in 8, gone as default since 9), G1 (default since 9; region-based, mostly concurrent, ~10–100 ms pauses), ZGC (concurrent, sub-millisecond pauses, generational since JDK 21, scales to multi-TB heaps), Shenandoah (Red Hat’s concurrent collector, similar pause goals to ZGC, generational since 24), Epsilon (no-op — allocates, never collects; for short-lived perf work).

CMS is gone (deprecated 9, removed 14). If your runbook references CMS flags, your runbook is out of date. The strict throughput-vs-pause trade has softened: ZGC’s overhead is now within ~10% of throughput collectors for many workloads.

Walk through a G1 collection cycle.

G1 divides the heap into regions (1–32 MB each). At any time, regions are tagged Eden / Survivor / Old / Humongous. Two phases:

  • Young GC (STW): evacuates live objects from Eden + Survivor into a new Survivor region (or Old, if tenured enough). Short pause, scales with live young set.
  • Mixed GC (STW): after a concurrent marking phase identifies regions with the most garbage, G1 evacuates a mix of young + chosen old regions. The “collection set” (CSet) targets the goal of -XX:MaxGCPauseMillis (default 200 ms).

The concurrent marking is SATB (snapshot-at-the-beginning) — uses a write barrier on reference updates to track changes. Humongous objects (> 50% of region size) bypass young, go straight to old, and fragment the heap if frequent.

Failure modes: “to-space exhausted” (not enough free regions to evacuate into — full GC), allocation rate > concurrent marking rate (mixed GCs can’t keep up — full GC).

How does ZGC achieve sub-millisecond pauses?

Three ideas:

  • Colored pointers: pointer metadata bits encode mark state (Marked0, Marked1, Remapped, Finalizable). Reading any pointer goes through a load barrier that masks/checks these bits.
  • Concurrent everything: mark, relocate (move objects), and remap (update pointers) all run while the application is running. STW pauses happen only at root scanning & phase transitions — bounded, independent of heap size.
  • Region-based heap (“ZPages”) in small/medium/large flavors; relocate copies live objects to fresh pages and patches pointers via the load barrier on first dereference (lazy remap).

Generational ZGC (JDK 21+, JEP 439): adds young/old separation, addressing ZGC’s historical weakness on allocation-heavy workloads (it had to scan the whole heap each cycle). With generational, allocation-driven workloads see ~2–3× throughput improvement vs the original single-gen ZGC.

Flag: -XX:+UseZGC -XX:+ZGenerational in 21; just -XX:+UseZGC in 23+ (generational is default).

Probing: “sub-ms pauses sound magical, what’s the catch?” CPU overhead (~5–15% throughput tax for the load barrier), more memory (colored pointers + page metadata), and historically less mature than G1.
How is Shenandoah different from ZGC?

Both target sub-10ms pauses with concurrent everything, but the implementations differ:

  • Brooks pointers: Shenandoah originally used a forwarding pointer in each object header. Reads dereferenced through it. Simpler than ZGC’s colored-pointer scheme but added a per-object overhead. JDK 13+ moved to load reference barriers — closer to ZGC’s model.
  • Read & write barriers: Shenandoah uses both; ZGC uses load-only.
  • Backports: Shenandoah is available in JDK 11 LTS via the OpenJDK backport (Red Hat-maintained); ZGC is too but considered experimental there.

Picking: ZGC for the largest heaps + lowest pauses, Shenandoah if you’re on Red Hat’s OpenJDK and want concurrent GC on JDK 17. The performance gap has narrowed; either works for most low-latency services.

Explain reference types: strong, soft, weak, phantom.
  • Strong: the default. As long as a strong reference exists, the object is reachable, never collected.
  • Soft (SoftReference): collected when the JVM “needs memory.” In practice, the policy is fuzzy and tied to -XX:SoftRefLRUPolicyMSPerMB. Don’t use for caches — Caffeine with explicit size limits is what you actually want.
  • Weak (WeakReference): collected on the next GC cycle if no strong refs remain. Foundation of WeakHashMap. Useful for canonicalizing maps, ThreadLocal value cleanup.
  • Phantom (PhantomReference): never returns the referent; only enqueued in a ReferenceQueue after the object is finalized. Used to schedule cleanup actions deterministically — the modern replacement for finalize().

finalize() is deprecated (since 9, marked for removal). Use java.lang.ref.Cleaner: a phantom-reference-backed mechanism that runs cleanup in a separate thread without resurrection risk.

What are common GC anti-patterns?
  • Massive allocation in a hot loop creating short-lived garbage that overwhelms the young gen — promotes objects prematurely. Fix: reuse buffers, use StringBuilder, pool primitives.
  • Soft refs for caches. See above. Use a real cache lib.
  • Long-lived ThreadLocals in a thread pool — the value pins on the thread for the pool’s lifetime. Memory leak by design. ScopedValue is the JDK 21 replacement for the request-scoped use case.
  • Huge static caches with no eviction. Filling old gen forces frequent old-gen collections / mixed GCs.
  • Calling System.gc() in production. It’s a hint that can trigger a Full GC. Fight whoever added it.
  • Heap sizing wrong: -Xmx too small → thrashing; -Xmx too large → long old-gen scans. Right answer: size to expected working set + headroom (~30%); profile with JFR.
Why set -Xms == -Xmx in production?

Heap-resize events trigger Full GCs, return memory to the OS (then re-mmap on grow), and confuse pause-time tuning. In a steady-state long-running service, you want predictable behavior. Set -Xms == -Xmx; let the GC pace itself within a fixed envelope.

Also: container-aware JVMs (8u191+) honor cgroup memory limits; -Xmx sized as a fraction of container memory (-XX:MaxRAMPercentage=75) is the modern idiom.

What does MaxGCPauseMillis actually do?

For G1 it’s a soft target. G1 sizes the young gen and CSet so that the pause comes in under the target on average; it’s not a guarantee. Set it too low (e.g., 5 ms) and G1 will starve the young gen, causing heavy mixed GC pressure and worse overall pauses.

For ZGC/Shenandoah the flag is largely irrelevant — pauses are already sub-millisecond by design.

Sane defaults: 200 ms (G1 default) for general apps; lower (50–100 ms) only if you measure it’s achievable. If you need < 10 ms p99 GC pause, switch collectors, don’t tune G1 to death.

How do you actually diagnose GC pressure?

Modern toolchain:

  • JFR (Java Flight Recorder): always on, near-zero overhead. jcmd PID JFR.start duration=60s filename=app.jfr. Open in JDK Mission Control.
  • GC log: -Xlog:gc*:file=gc.log:time,level,tags. Read with GCViewer or GCEasy.
  • Native: async-profiler for allocation profiling (-e alloc). Identifies allocation hot spots that GC won’t tell you about.
  • Heap dump: jcmd PID GC.heap_dump out.hprof; analyze with Eclipse MAT for retention paths and dominator trees.

The questions: What’s the allocation rate? What’s the promotion rate? Is old gen growing? Are pauses dominated by mark, evacuation, or root-scanning? “GC is slow” without these numbers is a guess.

What is a “safepoint”?

A point in execution where the JVM can pause all threads consistently — required for STW phases of GC, deoptimization, biased-lock revocation (historically), and various jcmd ops. The compiler inserts safepoint polls at loop back-edges, method entries, etc.

Safepoint “time-to-safepoint” is sometimes the actual pause culprit, not the GC itself. A long counted loop without safepoint polls can hold up the whole JVM. Symptom: GC pause shows ~50 ms “sync” phase before any actual GC work.

Diagnose with -XX:+PrintSafepointStatistics (older), -Xlog:safepoint* in modern JDK. Fix: ensure JIT-compiled hot loops have safepoint polls (uncounted loops do automatically; counted int loops in some JIT modes don’t until JDK 10+’s loop-strip-mining helps).

When should you use Epsilon GC?

Three cases: (1) perf testing — eliminate GC noise from benchmarks; (2) extremely short-lived JVMs where you’ll exit before exhausting the heap (CLI tools, lambdas); (3) memory-pressure regression detection — OOM is a clear signal that allocation budget changed.

Not for production services. Allocate > -Xmx and the JVM dies.

What does “humongous allocation” mean in G1?

An object > 50% of G1 region size is a humongous object. It’s allocated in contiguous old-gen regions (it can occupy multiple). G1 has special handling: humongous regions are reclaimed in concurrent cycles, can fragment the heap if frequent, and bypass the young gen entirely.

Region size is tuned via -XX:G1HeapRegionSize (defaults to a power of 2 between 1 and 32 MB based on heap size). If your app frequently allocates 1–4 MB byte arrays / images, bump the region size to keep them out of humongous handling.

Why is finalize() dead?

Finalizers are slow (resurrection-checking adds GC overhead), unreliable (no guaranteed run, weird ordering), and dangerous (can resurrect objects, causing double-finalize). Officially deprecated since JDK 9; marked for removal.

The replacement is java.lang.ref.Cleaner (JDK 9+). You register a cleanup action with a Cleaner instance; it’s tracked via a phantom reference and run on a dedicated thread when the object becomes phantom-reachable. No resurrection, no GC overhead beyond the phantom ref.

private static final Cleaner CLEANER = Cleaner.create();
public class NativeBuf implements AutoCloseable {
    private final Cleaner.Cleanable cleanable;
    public NativeBuf(long ptr){
        cleanable = CLEANER.register(this, () -> freeNative(ptr));
    }
    public void close(){ cleanable.clean(); }
}
§ 04  Concurrency

Threads, locks, and the post-Loom landscape.

Java’s concurrency story has three eras: the synchronized/wait/notify era (1.0–1.4), the java.util.concurrent era (5.0+), and the Loom era (21+). Knowing which patterns are still alive in each era is the staff-level test. A reactive solution is the right answer to a 2018 question; in 2026, it’s probably over-engineered.

Concept · The post-Loom shift Project Loom (JEP 444, GA in JDK 21) introduces virtual threads: lightweight threads scheduled by the JVM, not the OS. A million virtual threads cost what a few thousand platform threads used to. The classic trade — “blocking I/O is wasteful, write reactive” — largely evaporates: blocking a virtual thread is cheap because the carrier (platform thread) is freed during the block.

Implication: for most server apps, the “thread per request” model is back, simpler, and competitive with reactive. Reactive (Reactor, RxJava) still has uses — backpressure, complex stream composition, pre-21 codebases — but the default has shifted.
synchronized, ReentrantLock, StampedLock — when each?
  • synchronized: the default. Simple, JIT-optimized to death, biased toward correctness. JDK 21 fixed virtual-thread pinning (JEP 491 finalized in 24 removed the last cases). Pre-21, holding a synchronized monitor pinned the virtual thread to its carrier — a major Loom footgun.
  • ReentrantLock: when you need tryLock, fairness, multiple condition variables (newCondition), or interruptible acquisition. Lock fairness costs throughput — only enable if starvation is a real problem.
  • StampedLock: when reads dominate writes by a wide margin and you can tolerate optimistic-read complexity. Not reentrant; not interruptible by default; tricky API. Reach for it only when profiling proves ReentrantReadWriteLock is the bottleneck.
// StampedLock optimistic read pattern
long stamp = lock.tryOptimisticRead();
int snap = value;
if(!lock.validate(stamp)){    // concurrent write happened
    stamp = lock.readLock();
    try{ snap = value; } finally{ lock.unlockRead(stamp); }
}
Probing: “why prefer synchronized when you have ReentrantLock?” Modern HotSpot’s synchronized has had decades of optimization; ReentrantLock’s only wins are the API features, not raw speed.
What is AQS and what does it power?

AbstractQueuedSynchronizer is the framework underneath most java.util.concurrent primitives: ReentrantLock, Semaphore, CountDownLatch, ReentrantReadWriteLock, FutureTask, SynchronousQueue internals.

Core idea: a single volatile int state + a CLH-style FIFO wait queue. Subclasses override tryAcquire / tryRelease defining what the state means (lock held count, permits, etc.); AQS handles queueing, blocking via LockSupport.park, and signaling.

You almost never subclass AQS directly — but knowing it exists lets you read the JDK source and answer “how does Semaphore actually work?” with confidence.

How would you size a ThreadPoolExecutor?

Rule of thumb (Brian Goetz): N_threads = N_cpu * U * (1 + W/C) where U is target CPU utilization, W is wait time, C is compute time per task.

Practical:

  • CPU-bound: N_cpu or N_cpu + 1. More threads = context-switch overhead, no throughput gain.
  • I/O-bound: sized by concurrency limit, not CPU. A pool of 200–500 for a service hitting Postgres is normal — bounded by DB connection pool size, not CPU. Or: use virtual threads & let Loom schedule.
  • Mixed: separate pools by workload class. Don’t use the common pool for blocking I/O.

Queue + rejection: bounded queue + sensible RejectedExecutionHandler (CallerRunsPolicy applies backpressure). Unbounded queues are a footgun: a slow consumer means the queue grows, OOM, and meanwhile the pool size never reaches maximumPoolSize because the queue isn’t full.

What changes with virtual threads?

Virtual threads are scheduled by a small pool of carrier threads (platform threads, default = ForkJoinPool with parallelism = CPU count). When a virtual thread blocks (I/O, lock wait, sleep), it’s unmounted from its carrier; the carrier picks up another. When the block resolves, the virtual thread is rescheduled.

Cost per virtual thread: a few hundred bytes of stack metadata that lives on the heap. You can have millions. Thread.ofVirtual().start(task) or Executors.newVirtualThreadPerTaskExecutor().

Pinning (the carrier can’t be released): historically caused by holding a synchronized monitor across a blocking op, or by native (JNI) frames. JEP 491 in JDK 24 fixed synchronized pinning. Native pinning still applies — rare in app code.

var exec = Executors.newVirtualThreadPerTaskExecutor();
List<Future<String>> results = ids.stream()
    .map(id -> exec.submit(() -> fetchFromDb(id)))
    .toList();
Gotcha: don’t pool virtual threads — they’re cheap, the point is unbounded creation. Pooling them just adds a synchronization layer for no gain. Use a virtual-thread-per-task executor.
What is structured concurrency?

StructuredTaskScope (JEP 480, preview through 23, finalizing): a way to start a group of subtasks whose lifetimes are bounded by a lexical scope. If the scope exits (normally, with exception, or via cancellation), all subtasks are cancelled. Treats threads like resources — AutoCloseable.

try(var scope = new StructuredTaskScope.ShutdownOnFailure()){
    Subtask<User> user = scope.fork(() -> fetchUser(id));
    Subtask<List<Order>> orders = scope.fork(() -> fetchOrders(id));
    scope.join().throwIfFailed();
    return new Profile(user.get(), orders.get());
}

Replaces the “launch a bunch of CompletableFuture.supplyAsync + remember to cancel on failure” pattern that nobody got right. Pairs naturally with virtual threads.

What is ScopedValue and how does it differ from ThreadLocal?

ScopedValue (JEP 487, finalizing): an immutable, scope-bounded value accessible to a callable and its callees, without leaking outside the scope. Replaces ThreadLocal for the request-scoped use case.

static final ScopedValue<User> CURRENT = ScopedValue.newInstance();

ScopedValue.where(CURRENT, user).run(() -> {
    handleRequest();    // CURRENT.get() returns user inside this scope
});                     // outside: not bound

Why it matters: ThreadLocal is mutable, leaks easily across thread-pool reuse, and balloons memory in the virtual-thread-per-task era (a million ThreadLocals is a million entries). ScopedValue is immutable, scope-bounded, and the JVM can share storage efficiently across virtual threads.

How does CompletableFuture compose? When does it bite?

CF gives you a future plus a fluent combinator API: thenApply, thenCompose (flatMap), thenCombine, allOf, anyOf, exceptionally, handle. Composition is async by default; without Async suffix, callbacks may run on the completing thread (caller may bear the work).

Bites:

  • Default executor is the common ForkJoinPool. A blocking call inside supplyAsync stalls the pool, hurts parallel streams, hurts everyone.
  • Exception swallowing: if you don’t terminate the chain with exceptionally / handle / whenComplete, errors silently disappear unless someone calls get/join.
  • get wraps in ExecutionException, join wraps in CompletionException (unchecked) — mind which you call.

Post-Loom: the “CF for async I/O” story is mostly redundant. scope.fork(() -> blockingCall()) on virtual threads is simpler, has structured cleanup, and benchmarks roughly as fast.

How would you cancel a long-running task?

Java has cooperative cancellation only. You signal; the task checks the signal. The signal is Thread.interrupt(), which sets the interrupt flag and causes blocking ops (sleep, wait, BlockingQueue.take) to throw InterruptedException.

while(!Thread.currentThread().isInterrupted()){
    try{ doStep(); }
    catch(InterruptedException e){
        Thread.currentThread().interrupt();   // re-set flag
        break;
    }
}

Common bug: catching InterruptedException and swallowing it — the flag is cleared, the task can’t notice cancellation later. Either re-throw or Thread.currentThread().interrupt() to re-set the flag.

Hard cases: blocking on InputStream.read on a socket — doesn’t respond to interrupt. Close the socket from another thread; the read throws SocketException.

What’s the deal with ForkJoinPool and parallel streams?

FJP is a work-stealing pool: each thread has a deque, pushes/pops from one end, steals from others’ opposite end. Optimized for divide-and-conquer recursive tasks (RecursiveTask). The common pool is shared across the JVM — default parallelism = availableProcessors() - 1.

Parallel streams use the common pool. One blocking I/O call inside a parallel stream stalls the pool for everyone. Fix: don’t mix I/O with parallel streams. For CPU-bound work over collections (image processing, math), parallel streams are great.

To use a separate pool: submit the parallel stream as a task to your own FJP — the work executes on that pool because FJ tasks see currentThread().getPool().

ForkJoinPool myPool = new ForkJoinPool(8);
long sum = myPool.submit(() ->
    nums.parallelStream().mapToLong(Long::longValue).sum()
).join();
When is reactive (Reactor, RxJava) still the right answer?

Three reasons reactive still earns its keep:

  • Backpressure as a first-class signal — producers can be slowed by slow consumers. Loom’s answer is “the producer blocks”, which works for many cases but not for streaming pipelines that need explicit demand control.
  • Composition operators — flatMap, window, buffer, retryWhen, publishOn. The Reactor algebra is dense; rebuilding it on top of virtual threads + manual coordination is doable but verbose.
  • Existing investment — if your stack is Spring WebFlux + R2DBC + Reactor, switching to MVC + JDBC + virtual threads is a major migration with marginal gains.

For new business apps, Loom-flavored MVC is simpler. The reactive default of the late 2010s was an over-correction.

Probing: “reactive vs Loom” is a litmus test for whether you’ve actually used Loom in anger. Knowing the line — backpressure / streaming yes, request-response no — is the senior signal.
How do you handle ThreadLocal cleanup correctly?

In a thread-pool world, ThreadLocal values persist across task boundaries on the same thread. Three failure modes:

  • Memory leak: the value retains a reference to a request-scoped object, holding it until the next task overwrites or the thread dies.
  • State bleed: task A sets the TL, task B (later, same thread) reads stale value from A.
  • Classloader leak: a TL set by an undeployed webapp pins its classloader (very common Tomcat issue).

Discipline: try/finally with ThreadLocal.remove() at the end of each task. Or use InheritableThreadLocal only when you need it (it copies on thread creation, not on task scheduling).

Modern fix: for request context, use ScopedValue; it’s scope-bounded by design.

What does LongAdder do that AtomicLong doesn’t?

AtomicLong is a single CAS-protected long. Under high contention, every increment fights for the same cache line — throughput collapses.

LongAdder stripes the counter across multiple cells (one per thread when contended). Each thread updates its own cell with no contention. sum() walks the cells. Trade: reads are slower (linear in cells), writes are much faster under contention.

Use: high-frequency counters (request count, allocation count). Don’t use: when you frequently need the exact current value for logic, since sum() is not atomic w.r.t. concurrent updates.

Why is wait/notify a code smell now?

Three reasons:

  • Spurious wakeups are real — wait must always be in a while loop checking the condition.
  • Lost wakeups: notifying before the waiter has gotten in is a race; you have to hold the same monitor.
  • Better tools exist: BlockingQueue for producer-consumer, CountDownLatch/CyclicBarrier/Phaser for coordination, Condition on a ReentrantLock for explicit guarded wait.

If you’re writing wait/notify in 2026, you’re probably reinventing one of the above. The classic JCIP rule still holds: use the highest-level coordination primitive that solves your problem.

§ 05  Concurrent collections

Pick the data structure, not the lock.

Wrapping a HashMap in Collections.synchronizedMap is a junior reflex. The java.util.concurrent collections are differentiated by access pattern (read-heavy, write-heavy, append-only, blocking), and choosing right is what separates “it works” from “it scales.”

Concept · Collections taxonomy Three families: thread-safe maps (ConcurrentHashMap, ConcurrentSkipListMap), copy-on-write lists/sets (CopyOnWriteArrayList, CopyOnWriteArraySet), blocking queues (ArrayBlockingQueue, LinkedBlockingQueue, SynchronousQueue, LinkedTransferQueue, PriorityBlockingQueue, DelayQueue).

Modern HashMap (since 8) treeifies a bucket to a red-black tree at >8 entries (and >64 total table size) — so worst-case lookup is O(log n) under hash collisions, not O(n). It’s still not thread-safe; concurrent put can corrupt the structure (infinite loops on resize were the JDK 7 bug).
Walk through HashMap’s internals.

An array of buckets (default capacity 16, load factor 0.75 → resize at 12 entries). Hash is computed from key.hashCode() then mixed (h ^ (h >>> 16)) to spread bits to the low end (since the bucket index is hash & (n-1)).

Each bucket is a linked list of entries. Since JDK 8, when a bucket reaches 8 entries AND the table is ≥ 64 buckets, the bucket converts to a red-black tree. Below 64 entries total, it resizes the table instead. Untreeify happens at 6.

Resize doubles the table; entries split between “low” (same index) and “high” (index + oldCap) buckets based on one hash bit. Smart move — no full rehash.

Why not thread-safe: concurrent put during resize can put a node into a bucket on the new table while another thread is still walking the old; in JDK 7 this caused infinite loops on next get. JDK 8 doesn’t infinite-loop but still corrupts state.

How does ConcurrentHashMap achieve thread safety?

Pre-JDK 8: segment-based locking — the map was split into N segments, each its own lock. Concurrency level = number of segments.

JDK 8+: rewritten. Buckets are still arrays + linked lists / trees. Updates use CAS on the bucket head for empty buckets, fall back to synchronized on the bucket head for collision chains. Reads are completely lock-free (volatile reads on the table reference + bucket head).

Bonus methods: computeIfAbsent / compute / merge are atomic w.r.t. the bucket; safe for things like “get-or-create” counters. size() uses a LongAdder-style striped counter — reads are approximate, writes are fast.

Iterators are weakly consistent: never throw ConcurrentModificationException, may or may not see concurrent updates.

// Atomic get-or-compute — no race with another thread doing the same
counts.computeIfAbsent(key, k -> new AtomicLong()).incrementAndGet();
Probing: “why not just synchronizedMap?” That single-lock wrapper serializes all ops; CHM lets unrelated buckets be touched concurrently. The throughput delta under contention is order-of-magnitude.
When is CopyOnWriteArrayList right?

When reads vastly outnumber writes (think 1000:1) and the list is small enough that copying it is cheap. Each write copies the entire backing array; reads are a volatile-read of the array reference and have no synchronization at all.

Sweet spot: listener / observer registries, immutable-after-startup config lists, small whitelists.

Wrong tool: high-write workloads (each write is O(n)), large lists (the copy itself becomes the cost), iteration-during-mutation when you need to see the latest state (you see the snapshot taken when the iterator was created).

Compare the blocking queues.
  • ArrayBlockingQueue: bounded, fixed-size circular buffer. One lock for both ends. Simple; predictable memory.
  • LinkedBlockingQueue: optionally bounded, linked nodes. Two locks (head & tail) — producers and consumers don’t contend with each other. Higher throughput at the cost of per-node allocation.
  • SynchronousQueue: capacity zero. A put blocks until a take; a take blocks until a put. Hand-off, not a buffer. Used in Executors.newCachedThreadPool — if no thread is free, queue rejects, pool grows.
  • LinkedTransferQueue: linked queue with a transfer() method — producer can wait for a consumer to take. Higher throughput than SynchronousQueue + LinkedBlockingQueue combined for hand-off workloads.
  • PriorityBlockingQueue: unbounded, priority-ordered (heap). Watch out: unbounded means OOM if you keep producing.
  • DelayQueue: elements are Delayed; take blocks until the head element’s delay expires. Used for scheduled tasks (ScheduledThreadPoolExecutor internally).
Why is Vector a code smell?

Vector synchronizes every method on this. The compound-op problem strikes hard:

if(!v.isEmpty()) v.remove(0);   // race: two threads pass isEmpty, one fails on remove

It’s also slower than ArrayList in single-threaded use due to the synchronization overhead. Modern alternatives:

  • Single-threaded: ArrayList.
  • Read-heavy concurrent: CopyOnWriteArrayList.
  • Concurrent with full ops: ConcurrentLinkedDeque or wrap with explicit lock.

If you see Vector or Hashtable in modern code, it’s almost always a port from 1.x days that nobody updated.

How do you implement an LRU cache with stdlib?

Trick using LinkedHashMap: pass accessOrder=true to the constructor, override removeEldestEntry to return true past your size limit. Not thread-safe — wrap with Collections.synchronizedMap for low-volume use, or use Caffeine (the de-facto Java cache library) for production.

public class Lru<K,V> extends LinkedHashMap<K,V> {
    private final int max;
    public Lru(int max){
        super(16, 0.75f, true);   // access-order
        this.max = max;
    }
    protected boolean removeEldestEntry(Map.Entry<K,V> e){
        return size() > max;
    }
}

For real production: Caffeine offers W-TinyLFU eviction, async loading, refresh-after-write, async cache, all the things you actually want.

What is ConcurrentSkipListMap for?

A concurrent sorted map — the lock-free analog of TreeMap. Skip lists are probabilistically balanced (no rebalance needed), making them friendlier than red-black trees for concurrent updates.

Use: when you need a sorted view (range queries, headmap/tailmap/subMap) under concurrent access. Don’t use for plain key lookups — CHM is materially faster (O(1) vs O(log n) and better cache behavior).

How does ConcurrentHashMap handle null?

It doesn’t. Both null keys and null values throw NullPointerException. The reason: in a concurrent map, get(k) returning null is ambiguous — absent or present-with-null? Forbidding nulls makes the contract clean.

HashMap allows both (one null key, many null values). Cross-context bug magnet: code that worked on HashMap NPEs when refactored to CHM.

Why does HashSet care about equals and hashCode consistency?

A HashSet is backed by a HashMap. contains: hash the element, find bucket, walk for equals. If two equal objects have different hashCodes, they land in different buckets and the set holds both as “different” — violating set semantics.

The contract: if a.equals(b) then a.hashCode() == b.hashCode(). The reverse is not required (collisions are fine). Records (JDK 14+) generate equals + hashCode from components — one of the strongest reasons to prefer them for value objects.

Bug shape: mutate a field that participates in equals/hashCode after adding to a set. The element “disappears” (lookup hashes to a different bucket than where it was stored). Cure: don’t put mutable objects in hash collections; use immutable identity.

What’s special about ConcurrentLinkedQueue?

Unbounded, lock-free queue (Michael & Scott’s algorithm). All operations are CAS-based; no blocking, no waiting. poll returns null on empty rather than blocking.

Use when: producers can’t block, you don’t need backpressure, and unboundedness is fine. Don’t use: for producer-consumer where consumers should block on empty — use a BlockingQueue instead. Also no size() in O(1) — it walks the list.

What does Collections.synchronizedMap still buy you?

Wrap-and-forget thread safety for small maps with low contention — e.g. a config map populated at boot, read occasionally. Single coarse lock; iteration must be manually wrapped (synchronized(map) { for (... : map.entrySet()) }) or you get CME.

For anything performance-sensitive: use ConcurrentHashMap. The wrapper exists mostly for legacy compatibility.

§ 06  Modern features

Post-8 Java is a different language.

If you write Java like it’s 2014, your code is twice as long and half as expressive as it should be. Records, sealed types, pattern matching, switch expressions, and text blocks together form a coherent “data-oriented Java” that the language committee has been driving toward for years.

Concept · Data-oriented Java Records = transparent carriers of immutable data. Sealed types = closed sum types — the JVM’s answer to algebraic data types. Pattern matching = destructure those types in switch with exhaustiveness checking. Together you can express “a Shape is a Circle, Square, or Triangle” in 6 lines and dispatch on it with compile-time exhaustiveness, no Visitor pattern in sight.

Brian Goetz has called this data-oriented programming: model your data as transparent immutable records of an exhaustive set of cases; let pattern matching dispatch the behavior. It’s the most significant shift in idiomatic Java since lambdas.
What does record actually generate?

For record Point(int x, int y) {}:

  • private final int x; private final int y;
  • Canonical constructor (you can override; supports compact constructor for validation).
  • Accessors named x() and y() (not getX).
  • equals, hashCode, toString derived from components.

Records are final, extend java.lang.Record, and components are shallowly immutable (you can still hold a mutable list inside). Compact constructor is the idiomatic place for validation:

public record Range(int lo, int hi) {
    public Range {
        if(lo > hi) throw new IllegalArgumentException();
    }
}

Use: DTOs, value objects, message types. Don’t force it: if you want to vary toString or hide fields, a regular class is fine.

How do sealed types and pattern matching work together?

A sealed interface/class declares a closed set of permitted subtypes. Switch over a sealed type with patterns gets exhaustiveness checking — the compiler errors if you miss a case.

sealed interface Shape permits Circle, Square, Triangle {}
record Circle(double r) implements Shape {}
record Square(double side) implements Shape {}
record Triangle(double b, double h) implements Shape {}

double area(Shape s) {
    return switch(s) {
        case Circle c -> Math.PI * c.r() * c.r();
        case Square sq -> sq.side() * sq.side();
        case Triangle t -> 0.5 * t.b() * t.h();
    };  // no default needed — exhaustive over sealed
}

Add a Pentagon to permits and the switch fails to compile until you handle it. This is the killer feature: refactor-safe sum types in Java.

Record patterns (JEP 440, JDK 21) extend this with deconstruction: case Circle(double r) -> ... binds r directly.

When should you NOT use var?

var is local-variable type inference (since 10). Rules of thumb for when not to use it:

  • When the RHS doesn’t express the type clearly: var x = compute(); — what is x? Bad.
  • When you want a different type than the RHS: assigning a HashMap to a Map reference is impossible with var.
  • For numeric literals: var x = 0; infers int — if you wanted long, you got a bug.
  • For diamond on the LHS: var list = new ArrayList<>(); infers ArrayList<Object>.

Sweet spot: builder chains, long generic types, Map.Entry<String, List<Foo>> in for-each. Anywhere the type adds visual noise without information.

What are common Optional abuses?
  • Field of type Optional: wrong tool. Optional is a return type. As a field it’s an extra heap object per instance, not Serializable, and signals you should restructure.
  • Method parameter of type Optional: just overload, or accept null with documentation. Forces every caller to wrap.
  • Optional.get() without isPresent: the equivalent of != null-then-deref. Use orElse, orElseGet, orElseThrow, map, ifPresent.
  • Wrapping a non-null collection: empty list/map already represents “no values.” Don’t double-wrap.

Right use: a method return type indicating “may not produce a value, please handle the absence.” In streams, the terminal ops (findFirst, reduce) naturally return Optional.

What are the Stream API gotchas?
  • Streams are lazy and one-shot. A stream can be consumed once. Re-streaming requires re-creating from the source.
  • Side effects in operations are forbidden (forEach excepted) — map writing to an external list is the classic broken-parallel-stream bug.
  • Parallel streams use the common ForkJoinPool. Blocking I/O inside one starves the pool. CPU-bound work over collections is the right use.
  • Order: parallel() may break encounter order; findFirst respects it (and is therefore slower in parallel than findAny).
  • collect(toList()) (since 16) returns an unmodifiable list. Pre-16 Collectors.toList() returned a mutable ArrayList. Migration trap.
Why didn’t the module system (JPMS) take over?

Modules (JDK 9, JEP 261) brought strong encapsulation and explicit dependency declarations. Adoption was muted because:

  • Build tools already solved most of the dependency problem via Maven/Gradle.
  • Migration cost for non-trivial codebases (split packages, reflective access to internal APIs) was real.
  • Most apps live behind a build tool boundary — the encapsulation gain over package-private didn’t justify the friction.

Where it shipped value: jlink (custom runtime images), strong encapsulation of JDK internals (no more sun.misc.Unsafe imports without warnings), Native Image closed-world analysis. JPMS quietly works in the background; few application devs author module-info.java.

What do text blocks change?

Triple-quoted multiline strings (since 15). Compile-time concatenation, indent normalization (the leading whitespace common to all lines is stripped). Backslash at end suppresses the newline; \s escapes a trailing space.

String json = """
    {
      "id": %d,
      "name": "%s"
    }
    """.formatted(id, name);

Gotcha: indent normalization is based on the least-indented non-blank line including the closing """. Move the closing quotes to control normalization.

Switch expressions vs switch statements?

Switch expressions (returns a value, exhaustive, no fallthrough by default) replaced almost every use of switch statements. Arrow form (case X -> expr) blocks fallthrough; yield returns from a block.

int daysIn = switch(month) {
    case JAN, MAR, MAY, JUL, AUG, OCT, DEC -> 31;
    case APR, JUN, SEP, NOV -> 30;
    case FEB -> isLeap ? 29 : 28;
};

Combined with patterns, this becomes the primary dispatch mechanism in modern Java.

What did instanceof patterns change?

Pattern instanceof binds the typed reference inline:

if(obj instanceof String s && !s.isEmpty()){
    // s is in scope here, typed as String
}

Eliminates the (String) obj cast that everyone used to write right after the check. Combined with record deconstruction:

if(shape instanceof Circle(double r)){
    area = Math.PI * r * r;
}
What is the “effectively final” rule?

A local variable can be captured by a lambda or anonymous inner class only if it’s final or effectively final — assigned exactly once, never reassigned. The compiler enforces this.

Why: the lambda’s “captured” variables are copied at capture time. Allowing reassignment would create a hidden mutable shared state with surprising semantics.

Workaround when you need mutability: capture an array of one (int[] count = {0}; count[0]++) or an AtomicInteger. Both signal “I knew what I was doing.”

How do you migrate code to use records safely?
  • Pure DTOs with no behavior — trivially convert.
  • Hibernate / JPA entities: don’t use records directly — they need mutable proxies, lazy fetching, no-arg constructors. Hibernate 6 has limited record support; treat with care.
  • JSON binding: Jackson 2.12+, Gson, and java.beans.JavaBean-style frameworks support records via the canonical constructor.
  • Builders: for many fields, records are awkward. Either generate a builder (@Builder-style with Lombok or Avaje), or stick with a class.

Rule: if the class is a transparent carrier of values with derived equals/hashCode/toString, it’s a record candidate. If it has identity, lifecycle, or mutability, it isn’t.

What changed about String internals?

JDK 9 introduced compact strings (JEP 254): String’s backing array became byte[] + a coder byte. Latin-1-only strings use 1 byte per char; UTF-16 strings use 2. Most Western text halves its memory footprint.

Implication: charAt reads through the coder; tight loops doing per-character access took a small hit but most string ops got faster from cache friendliness. Most apps saw 5–15% heap reduction on upgrade.

String concatenation via + uses invokedynamic + StringConcatFactory (JDK 9+) — the bytecode no longer hardcodes StringBuilder. The runtime picks an optimal strategy.

§ 07  Performance & profiling

Measure, then measure better.

Java performance is measurable with surprisingly cheap tooling — if you know what to measure. The question is rarely “is the code fast?” but “where is it spending time?” and “what is the JIT actually doing?” Get this wrong and you’ll spend a week optimizing a method that runs 0.1% of the workload.

Concept · The profiling toolbox JFR (always-on, cheap, JVM-aware): allocation profiling, lock contention, GC events, JIT events. async-profiler (kernel-aware sampling, flame graphs, allocation profiling, no safepoint bias): the gold standard for CPU + alloc profiling. JMH: the only sane way to write a Java micro-benchmark. JIT logs (-XX:+PrintCompilation, -XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining): understand what got inlined, what didn’t. Mission Control: the GUI on top of JFR.
Why does JMH exist? What goes wrong without it?

Naive Java micro-benchmarks are wrong by default:

  • JIT warmup: the first iterations run interpreted/C1, the steady state runs C2. Mix them, your number is meaningless.
  • Dead code elimination: if your computed value isn’t used, the JIT removes the call entirely. Your “1 ns method” was a no-op.
  • Constant folding: if inputs are final, the JIT precomputes the answer at compile time.
  • Loop unrolling, vectorization, scalar replacement — all distort what you think you’re measuring.

JMH handles all of this: warmup iterations, Blackhole.consume, @State for per-thread state, fork isolation. @BenchmarkMode, @OutputTimeUnit, sane defaults.

@BenchmarkMode(Mode.AverageTime)
@OutputTimeUnit(TimeUnit.NANOSECONDS)
public class HashBench {
    @Param({"100","10000"}) int n;
    @Benchmark
    public int sum(Blackhole bh){ /* ... */ }
}
What is “false sharing”? How do you fix it?

Two threads hot-write to two distinct fields that happen to live in the same cache line (typically 64 bytes). Each write invalidates the line in the other CPU’s cache. Throughput drops 10–100× despite there being no logical contention.

Diagnosis: perf c2c on Linux, async-profiler with cache-miss events. Heuristic: tight per-thread counters with abnormally bad multi-thread scaling.

Fix: pad fields to occupy whole cache lines. @Contended (since 8) annotation does it for you, but is hidden behind -XX:-RestrictContended in newer JDKs. Or pad manually with dummy longs:

public class PaddedAtomicLong {
    public volatile long v;
    public long p1, p2, p3, p4, p5, p6;   // pad to a cache line
}

JDK’s LongAdder’s cells use @Contended internally for exactly this reason.

How do you read a JIT inlining log?

-XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining dumps decisions: inline (hot), too big, callee is too large, not inlineable, direct call, virtual call (megamorphic).

The two failures that hurt:

  • Megamorphic dispatch: a call site sees > 2 implementations — C2 falls back to a virtual call, no inlining. Common in heavily abstracted code with many small impls.
  • Too big to inline: hot method body exceeds -XX:MaxInlineSize (default 35 bytes); deeper hot paths exceed FreqInlineSize (default 325 bytes). Methods that should be hot get truncated.

Fix: split large hot methods so the hot path is small. For megamorphic, consider @Stable on framework hot fields, or refactor to monomorphic dispatch where you can.

What is a deopt loop and how do you spot it?

The JIT inlines based on profiled type info; if a fresh class arrives that breaks the assumption, the method deoptimizes back to the interpreter, gets reprofiled, recompiles. Usually fine. Pathological: if the workload alternates between two type assumptions, the JIT may oscillate — deopt loop — spending more time recompiling than running.

Diagnose with -XX:+PrintCompilation looking for repeated made not entrant + made zombie + recompile cycles for the same method. JFR’s Compilation events also surface this.

Mitigations: pre-load all subtype implementations at warmup, exclude the offending method from compilation (-XX:CompileCommand=exclude), or refactor to remove the bimodal dispatch.

What does async-profiler give you that JFR doesn’t?
  • No safepoint bias: JFR’s sampler waits for safepoints; long-running native sections / counted loops without safepoint polls are invisible. async-profiler uses perf_events + AsyncGetCallTrace — samples wherever execution is.
  • Native + JVM unified stacks: see C library calls, kernel time, alongside Java frames. Indispensable for I/O analysis.
  • Flame graphs out of the box: asprof -f profile.html — the most readable perf visualization there is.
  • Allocation profiling via TLAB events: where are bytes coming from? Often more useful than CPU profiling for GC-heavy workloads.

JFR is still better for JVM-internal events (locks, monitors, GC details, JIT events). They’re complementary — use both.

How much overhead does JFR have?

Default profile: ~1% in steady state. The default config is what production should run continuously — you get a recording when something breaks instead of trying to reproduce it under a profiler.

Tunable: -XX:StartFlightRecording=settings=profile,duration=60s,filename=app.jfr. Profile-level settings (more events) ≤ 2–3% overhead. The JFR ring buffer is bounded; old events drop, new ones write.

Operational pattern: always-on JFR with the default profile. jcmd PID JFR.dump filename=... when an alert fires. Open in Mission Control or Honest Profiler.

What allocation hotspots are easiest to miss?
  • Autoboxing in collections: Map<Integer, ...> boxes every key. Use Eclipse Collections / fastutil for primitive maps.
  • Stream allocations: stream pipelines allocate intermediate operations, lambdas, and (for collectors) result containers. Per-call cheap; in tight loops, expensive.
  • String concatenation in logging: log.debug("x=" + x) always concatenates, even at INFO level. Use parameterized SLF4J: log.debug("x={}", x).
  • Iterator allocation: for (X x : list) on an ArrayList allocates an Iterator. Indexed loops avoid it (rarely matters but visible in profiles).
  • Implicit lambdas with captured state allocate — non-capturing lambdas are cached; capturing ones are not.
How do you measure tail latency correctly?

Use HdrHistogram — a high-dynamic-range histogram that records sub-microsecond resolution over a wide range without losing precision at the tail. Most monitoring stacks (Micrometer, Dropwizard) have HdrHistogram backends.

Avoid mean and stddev for latency. The distribution is multimodal and heavy-tailed; the mean lies. p99, p99.9, p99.99, plus max, are what matter.

Coordinated omission is the killer bug: if your benchmark stops sending requests when the system stalls, you don’t record the stall in the latency histogram. wrk2, jitter, JMH’s SampleTime mode handle this; naive scripts don’t.

What does branch prediction have to do with Java?

The CPU speculates which side of a branch will be taken. Predictable branches: ~0 cycles. Unpredictable (50/50 random): a mispredict every other time, ~15–20 cycles to flush + refetch.

The famous Stack Overflow question (“why is processing a sorted array faster than an unsorted one?”) is exactly this. Sort the data → branch becomes predictable → 6× speedup, no algorithm change.

Practical: branches in tight inner loops should be predictable. If they’re not, branch-free alternatives (bitwise tricks, conditional moves) help. C2 occasionally generates cmov automatically.

What’s the deal with -XX:+UseStringDeduplication?

G1 + ZGC have a string dedup feature: during GC, identify String objects with identical character data and merge them to share a single backing array. Helps memory-bound apps with lots of duplicate strings (Hibernate, JSON parsing).

Cost: extra GC work; only kicks in for old-gen tenured strings. Off by default; turn on with the flag. Win is highly workload-dependent — measure heap before/after.

What’s the cheapest way to confirm an optimization helped?

The right answer is JMH with proper baseline + variant + statistical analysis (JMH reports confidence intervals).

The shortcut for “yes/no”: deploy to a canary, run real traffic, compare percentile latencies on a histogram. Real workloads exercise paths micro-benchmarks miss.

Anti-pattern: System.nanoTime() around a single method call. Useless — warmup, JIT, GC, scheduling jitter all dwarf the signal.

§ 08  Design questions

Build it on a whiteboard.

The interview classics — LRU, rate limiter, producer-consumer — are not about whether you can write the code. They’re about whether you can pick the right primitives, articulate the tradeoffs, and identify the failure modes. The wrong solution often also works; the senior signal is knowing why it’s wrong anyway.

Concept · Common patterns Most of these problems share a small set of tools: concurrent maps for shared state, BlockingQueue for hand-off, AtomicReference + CAS for lock-free updates, ReentrantLock + Condition when you need explicit guarded waits, Semaphore for permit-based concurrency limits. The art is matching the problem to the smallest set of these that solves it correctly.
Implement a thread-safe LRU cache.

Naive: wrap a LinkedHashMap (access-order) in Collections.synchronizedMap. Correct but every op contends on a single lock.

Better: use Caffeine in production. For an interview, sketch a segmented design:

public class LruCache<K,V> {
    private final int capacity;
    private final LinkedHashMap<K,V> map;
    private final ReentrantLock lock = new ReentrantLock();

    public LruCache(int capacity){
        this.capacity = capacity;
        this.map = new LinkedHashMap<>(16, 0.75f, true);
    }
    public V get(K k){
        lock.lock(); try{ return map.get(k); } finally{ lock.unlock(); }
    }
    public void put(K k, V v){
        lock.lock();
        try{
            map.put(k, v);
            if(map.size() > capacity){
                Iterator<K> it = map.keySet().iterator();
                it.next(); it.remove();   // evict eldest
            }
        } finally{ lock.unlock(); }
    }
}

Talk through: why not ConcurrentHashMap? Because LRU requires ordered access tracking that’s not part of CHM. Caffeine solves this with sampled probabilistic eviction (W-TinyLFU) over CHM — that’s the “production” level answer.

Probing: the interviewer wants to hear “single-lock LRU is the canonical answer; production uses Caffeine; truly contended designs need ConcurrentLinkedHashMap or W-TinyLFU.”
Implement a token-bucket rate limiter.

State: tokens, capacity, refillPerSec, lastRefillNanos. On each request: refill based on elapsed time, then attempt to consume.

public class TokenBucket {
    private final double capacity, refillPerSec;
    private double tokens;
    private long last = System.nanoTime();

    public synchronized boolean tryAcquire(int n){
        long now = System.nanoTime();
        double elapsed = (now - last) / 1e9;
        tokens = Math.min(capacity, tokens + elapsed * refillPerSec);
        last = now;
        if(tokens >= n){ tokens -= n; return true; }
        return false;
    }
}

Distributed version: Redis Lua script that does the read-update-write atomically on a key per bucket. Watch for clock-skew issues across nodes.

Talk through: token bucket vs leaky bucket (smoothness vs burst tolerance), why System.nanoTime() not currentTimeMillis() (monotonic, not subject to NTP jumps).

Implement bounded producer-consumer.

Trivial with ArrayBlockingQueue:

BlockingQueue<Task> q = new ArrayBlockingQueue<>(1024);
// producer
q.put(task);     // blocks if full — backpressure
// consumer
Task t = q.take();   // blocks if empty

Hand-rolled with ReentrantLock + 2 Conditions shows you understand the underlying mechanics. Two conditions because a producer waiting for “not full” should not be woken when the queue becomes “not empty”:

private final ReentrantLock lock = new ReentrantLock();
private final Condition notFull = lock.newCondition();
private final Condition notEmpty = lock.newCondition();

public void put(T x) throws InterruptedException {
    lock.lock();
    try{
        while(buf.size() == cap) notFull.await();
        buf.add(x);
        notEmpty.signal();
    } finally{ lock.unlock(); }
}
Probing: if you say signalAll instead of signal, the interviewer expects you to know why it’s wasteful (thundering herd) and when it’s required (multiple condition predicates on the same Condition).
Implement a TTL cache with capacity bound.

Two ideas combined:

  • TTL: store (value, expiresAtNanos). On get, check expiry; if past, treat as miss + remove.
  • Capacity: LRU as above. Or sampled eviction (Caffeine’s approach).

For high concurrency: ConcurrentHashMap<K, Holder> where Holder has the value + expiry. Lazy expiry on get; periodic sweep thread for the long tail. Eviction policy is the hard part — for production, Caffeine.

Pitfall: if reader threads do the eviction work synchronously, GC can stall reads. Caffeine offloads eviction to a small drainer thread — reads pay only an O(1) record-access bookkeeping cost.

Implement a copy-on-write state container.

Single source of truth + atomic reference swap:

public class Cow<T> {
    private final AtomicReference<T> ref;
    public Cow(T initial){ ref = new AtomicReference<>(initial); }
    public T get(){ return ref.get(); }
    public void update(UnaryOperator<T> f){
        T curr, next;
        do { curr = ref.get(); next = f.apply(curr); }
        while(!ref.compareAndSet(curr, next));
    }
}

Reads are lock-free, updates are CAS-loop. Critical: T must be immutable — readers may hold a reference to an old version while a new one is being computed.

Use: small frequently-read state (config, routing table, listener registry). Don’t use: large state where copy is expensive, or write-heavy workloads where CAS-loop spins forever.

Implement a counting semaphore from scratch.

If you understand AQS, the answer is “subclass AbstractQueuedSynchronizer with state = permits.” If you don’t, build it on a ReentrantLock + Condition:

public class Sem {
    private int permits;
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition avail = lock.newCondition();

    public void acquire() throws InterruptedException {
        lock.lock();
        try{
            while(permits == 0) avail.await();
            permits--;
        } finally{ lock.unlock(); }
    }
    public void release(){
        lock.lock();
        try{ permits++; avail.signal(); } finally{ lock.unlock(); }
    }
}

Talk through fairness (FIFO vs barging), why signal not signalAll, why while not if (spurious wakeup, also the ABA problem on the predicate).

Why is String immutable?

Several reasons, layered:

  • Security: file paths, class names, network addresses passed across trust boundaries can’t be modified after validation.
  • Hashcode caching: String.hashCode() is computed once, cached in a final field — only safe if the value can’t change.
  • Interning: a string pool only works if entries can’t mutate.
  • Concurrency: share freely between threads, no synchronization.
  • Substring sharing (pre-JDK 7): substring shared the backing array; mutability would have leaked into the parent.

Cost: every transformation allocates. StringBuilder is the mutable companion for hot string-construction paths.

Why does equals require hashCode consistency?

Hash-based collections (HashMap, HashSet) bucket entries by hash. When you contains(x), the collection hashes x, finds the bucket, and walks looking for an equals match. If two equal objects have different hashes, they live in different buckets — the contains lookup misses and the set silently holds duplicates.

The contract: if a.equals(b), then a.hashCode() == b.hashCode(). The reverse isn’t required (collisions are allowed). Records auto-derive both correctly; for hand-written classes, always override both together.

Mutability gotcha: if equals/hashCode depend on a mutable field and you mutate after adding to a set, the element is “lost” (different hash, walks the wrong bucket). Don’t store mutable objects in hash collections by mutable identity.

How would you detect a deadlock at runtime?

jstack PID dumps thread states; the JVM detects deadlocks and prints “Found one Java-level deadlock” with the cycle. Programmatic: ManagementFactory.getThreadMXBean().findDeadlockedThreads().

JFR records lock contention events; long blocking on a monitor with a circular wait shows up as a deadlock cluster. In production, set up an alert on jstack-detectable deadlocks — one is enough to take action.

Prevention: consistent lock ordering (always acquire A before B), avoid nested locks, prefer tryLock with timeout for fallible paths, replace pairs of locks with concurrent collections where possible.

Implement a CountDownLatch from scratch.

Conceptually: a counter that threads wait on; reaching zero releases everyone.

public class Latch {
    private int count;
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition zero = lock.newCondition();
    public Latch(int n){ this.count = n; }

    public void await() throws InterruptedException {
        lock.lock();
        try{ while(count > 0) zero.await(); }
        finally{ lock.unlock(); }
    }
    public void countDown(){
        lock.lock();
        try{ if(--count == 0) zero.signalAll(); }
        finally{ lock.unlock(); }
    }
}

Note signalAll — everyone waiting needs to wake. Compare to CyclicBarrier (resets, used for repeated phases) and Phaser (dynamic-party variant).

Why is Iterator.remove() the only safe way to remove during iteration?

Most collections track a modCount; the iterator captures the current value when created and checks it on next. If the underlying collection mutated through any path other than the iterator, modCount diverges and you get ConcurrentModificationException. CME is fail-fast detection of incorrect iteration; it’s your friend.

Iterator.remove() updates both the collection and the iterator’s internal state. Use that, or Collection.removeIf(Predicate) (since 8) which is cleaner.

Concurrent collections (CHM, COW lists) have weakly consistent iterators — never throw CME, may or may not see concurrent updates. Different contract; know which you’re using.
