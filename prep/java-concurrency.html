Java Concurrency — Interview Reference

Every primitive, pattern, and pitfall that shows up in senior/staff JVM loops (Databricks, Netflix, Anthropic, Shopify). Grouped by purpose, with the why next to the what.

The mental model: every concurrency problem is one of four shapes — mutual exclusion (one at a time), coordination (wait for something), communication (hand off data), or composition (assemble many async tasks). Pick the primitive that matches the shape, don't reach for the heaviest hammer.

1. Threads — lifecycle & interruption

2. Mutual exclusion — one at a time

PrimitiveJavaKey methodsWhen to use
Intrinsic lock synchronized (block / method) — (language-level) Simple mutual exclusion. Every object has a monitor. Concise but inflexible — no timeout, no interruptible acquire, no multiple conditions.
Explicit reentrant lock ReentrantLock lock(), unlock(),
tryLock(), tryLock(timeout),
lockInterruptibly(),
newCondition()		 When you need timeout, interruptible acquire, multiple Conditions, or fairness (constructor arg). Always unlock() in finally.
Reader-writer lock ReentrantReadWriteLock readLock().lock(),
writeLock().lock()		 Many readers, occasional writers. Wins only when reads heavily dominate — overhead is higher than plain ReentrantLock, so balanced workloads lose.
Optimistic read StampedLock tryOptimisticRead(),
validate(stamp),
readLock(), writeLock()		 Read-heavy hot paths. Not reentrant. Optimistic reads don't block writers; you re-read if the stamp is invalidated.
Volatile volatile T field; — (field modifier) Visibility without mutual exclusion. Every read/write is a memory barrier — other threads see the latest value. Doesn't make compound ops atomic (count++ is still a race even on a volatile int).
synchronized vs ReentrantLock — the interview answer:
  • synchronized — simpler, auto-release on exception, JIT-friendly. Default choice.
  • ReentrantLock — use when you need tryLock with timeout, multiple Conditions on one lock (Bounded Blocking Queue template), interruptible acquisition, or fairness.

The canonical wait pattern

lock.lock();
try {
    while (!predicate) {          // while, not if — spurious wakeups
        condition.await();
    }
    // predicate now true; do the work
    ...
    otherCondition.signalAll();    // wake waiters whose predicate may now hold
} finally {
    lock.unlock();
}

4. Communication — thread-safe handoff

StructureJavaKey methodsWhen to use
Bounded blocking queue ArrayBlockingQueue put (blocks if full),
take (blocks if empty),
offer(timeout),
poll(timeout)		 Producer-consumer with back-pressure. Fixed capacity means producers block when consumers can't keep up — a feature, not a bug.
Unbounded blocking queue LinkedBlockingQueue (same interface) Producer-consumer when you trust producers not to overwhelm. Risk: memory explosion if consumers lag.
Synchronous handoff SynchronousQueue put, take Capacity zero — every put must meet a take. The engine of Executors.newCachedThreadPool.
Priority blocking queue PriorityBlockingQueue (blocking + PQ order) Priority scheduling with consumer threads. Unbounded.
Delay queue DelayQueue<T extends Delayed> put, take (blocks until head expires) Timeouts, scheduled cleanup, retry-after. Element emerges only after its delay.
Lock-free queue ConcurrentLinkedQueue offer, poll, peek Non-blocking, high-throughput. No blocking semantics — poll returns null if empty. Use when you don't need to wait for data.
Thread-safe map ConcurrentHashMap get, put (atomic),

Copy-on-write list CopyOnWriteArrayList,
CopyOnWriteArraySet		 (List/Set interface) Read-heavy, write-rare (e.g., listener lists). Every mutation copies the whole array. Don't use for frequent writes.

5. Executors — thread pool machinery

Shutdown discipline: ExecutorServices have non-daemon threads by default — if you don't call shutdown(), the JVM won't exit. Pattern: 
try {
    pool.shutdown();
    if (!pool.awaitTermination(30, TimeUnit.SECONDS)) {
        pool.shutdownNow();   // interrupt remaining
    }
} catch (InterruptedException e) {
    pool.shutdownNow();
    Thread.currentThread().interrupt();
}

6. Async composition — CompletableFuture

MethodTakesReturnsMeaning
supplyAsync(Supplier) Supplier<T> CF<T> Run a computation async (default: ForkJoinPool.commonPool; pass an Executor to override).
runAsync(Runnable) Runnable CF<Void> Same, for side-effecting work.
thenApply(Function) T → U CF<U> Map. Sync transformation when upstream completes.
thenAccept(Consumer) T → void CF<Void> Consume, no return.
thenCompose(Function) T → CF<U> CF<U> FlatMap. When your continuation itself returns a CF, thenCompose unwraps (vs thenApply which gives CF<CF<U>>).
thenCombine(other, BiFn) (T, U) → V CF<V> Zip two CFs. Runs the BiFunction when both complete.
allOf(cf...) CF<?>... CF<Void> "Wait for all." Result is Void — collect values separately by joining each input.
anyOf(cf...) CF<?>... CF<Object> "First to complete wins." Winning value (as Object).
exceptionally(fn) Throwable → T CF<T> Recover from failure. Only runs if upstream failed.
handle(BiFn) (T, Throwable) → U CF<U> Runs on success OR failure — general "finally-like" transform.
whenComplete(BiConsumer) (T, Throwable) → void CF<T> Side-effect on completion without transforming the value.
get() / get(timeout) — T Block + unwrap. Throws ExecutionException (wraps cause) + InterruptedException.
join() — T Same as get but throws unchecked. Preferred in stream/pipeline code.
Staff-loop pattern — fan-out + combine: 
List<CompletableFuture<Result>> futures = ids.stream()
    .map(id -> CompletableFuture.supplyAsync(() -> fetch(id), pool))
    .toList();

List<Result> results = CompletableFuture
    .allOf(futures.toArray(new CompletableFuture[0]))
    .thenApply(v -> futures.stream().map(CompletableFuture::join).toList())
    .join();
The allOf(...).thenApply(...join) dance is idiomatic — commit it to muscle memory.

8. Thread-local state

ClassKey methodsWhen to use
ThreadLocal<T> get, set, remove,
ThreadLocal.withInitial		 Per-thread state (e.g., SimpleDateFormat, request context, DB connection). In thread pools, ALWAYS remove() when done — leaked ThreadLocals are a classic memory-leak source.
InheritableThreadLocal<T> (same as ThreadLocal) Child thread inherits parent's value at creation. Doesn't work cleanly with thread pools (threads are reused, not created per task).
ScopedValue (Java 21+) ScopedValue.where(v).run(...) Structured replacement for ThreadLocal — automatic cleanup, immutable, plays well with virtual threads. Know it exists for modern JDKs.

9. Virtual threads (Java 21+)

Thread.ofVirtual().start(r) or Executors.newVirtualThreadPerTaskExecutor().
  • Millions of lightweight threads; the JVM multiplexes them onto a small pool of OS carriers.
  • Blocking I/O no longer requires async code — write synchronous, get async throughput.
  • Still pins on synchronized (the carrier can't park) — prefer ReentrantLock in code paths meant for virtual threads.
  • Don't pool virtual threads; create one per task.

10. Memory model essentials

ConceptWhat it meansInterview-critical takeaway
happens-before Ordering guarantee: actions before a release are visible after the matching acquire. Established by: synchronized unlock→lock, volatile write→read, Thread.start, Thread.join, thread-safe collection put/get, CountDownLatch countDown/await.
Data race Two threads access the same non-final, non-volatile field; at least one writes; no happens-before between them. Undefined behavior — may see torn values (long/double on 32-bit) or stale reads. "Works on my machine" is not a proof.
volatile semantics Write = release barrier; read = acquire barrier. Guarantees visibility, not atomicity. volatile int i; i++; is still racy.
final field safety Correctly constructed final fields are visible to other threads without synchronization. Immutability is the fastest concurrency strategy. Prefer records and final fields.
Safe publication How a newly-created object becomes visible to other threads. Safe idioms: static initializer, volatile/final/AtomicReference, concurrent collection. Unsafe: plain field assignment from constructor + unsynchronized reads.
Double-checked locking Singleton pattern for lazy init. Broken without volatile on the instance field (pre-Java 5 bug that the memory model explicitly fixes). Modern canonical form: 
private static volatile X inst;
public static X get() {
  X i = inst;
  if (i == null) synchronized(X.class) {
    i = inst;
    if (i == null) inst = i = new X();
  }
  return i;
}

11. Canonical patterns

Producer-Consumer (the foundation)

BlockingQueue<Task> q = new ArrayBlockingQueue<>(100);
// producer
q.put(task);                    // blocks if full → back-pressure
// consumer
Task t = q.take();              // blocks if empty

Roll-your-own: ReentrantLock + notFull Condition + notEmpty Condition. That's Bounded Blocking Queue (LC 1188).

Fan-out / fan-in with CompletableFuture

See section 6 for the allOf(...).thenApply(...join) idiom.

Thread-safe lazy cache (Java Concurrency in Practice §5.6)

ConcurrentHashMap<K, CompletableFuture<V>> cache = new ConcurrentHashMap<>();

public V get(K key) {
    return cache.computeIfAbsent(key, k ->
        CompletableFuture.supplyAsync(() -> expensiveCompute(k))
    ).join();
}

Caches the future, not the value — multiple concurrent misses for the same key share one computation. The Brian Goetz classic.

Rate limiter — Token Bucket

Semaphore tokens = new Semaphore(burst);
ScheduledExecutorService refiller = Executors.newScheduledThreadPool(1);
refiller.scheduleAtFixedRate(() -> {
    if (tokens.availablePermits() < burst) tokens.release();
}, 0, refillMs, TimeUnit.MILLISECONDS);

// caller:
if (!tokens.tryAcquire(timeout, TimeUnit.MILLISECONDS)) throw ...;

Parallel task runner with deps (topo sort + ExecutorService)

Kahn's topo sort gives you the ready set; submit ready tasks, each completion decrements deps and enqueues newly-ready tasks. Synchronize via CountDownLatch (wait for all) or CompletableFuture.allOf.

12. Classic pitfalls

PitfallWhat happensFix
Deadlock Two threads each hold a lock the other wants. Consistent lock ordering (always acquire A before B). For multi-object locks, sort by identity hash. Or use tryLock(timeout).
Livelock Threads keep yielding/retrying and making no progress. Add randomized backoff (jitter). Common in optimistic CAS retry loops.
Starvation A thread never gets the lock because others keep taking it. Use a fair ReentrantLock or fair Semaphore. Accepts throughput hit for fairness.
Priority inversion Low-priority thread holding a lock blocks a high-priority thread waiting on it. Mostly an RTOS concern; in JVM, don't rely on thread priorities.
Swallowed InterruptedException Catch-and-ignore kills cancellation semantics. Rethrow, or Thread.currentThread().interrupt(); to restore the flag.
Unbounded task queue Executors.newFixedThreadPool backlog OOMs under load. Use ThreadPoolExecutor directly with a bounded queue and CallerRunsPolicy for back-pressure.
ThreadLocal leak in pool Pooled thread retains state across unrelated tasks, blocks GC. try/finally { tl.remove(); }. Or use ScopedValue (Java 21).
Forgotten shutdown() JVM never exits; tests hang. Always pair construction with shutdown. Daemon threads OK for fire-and-forget.
Racy "check-then-act" on ConcurrentHashMap if (!map.containsKey(k)) map.put(k, v); is racy across threads. Use putIfAbsent, compute, or merge.
Pinning on virtual threads Virtual thread enters synchronized and pins its carrier. Prefer ReentrantLock in code paths running on virtual threads (Java 21+ migration tip).

Quick-pick cheat sheet

  • Mutual exclusion → synchronized (simple) / ReentrantLock (need timeout / multi-condition / fairness).
  • Read-heavy → ReentrantReadWriteLock or StampedLock (optimistic).
  • Wait for N tasks → CountDownLatch.
  • Phase sync (all arrive, then proceed, repeat) → CyclicBarrier.
  • Throttle to N-at-a-time → Semaphore.
  • Producer/consumer → ArrayBlockingQueue (bounded) / build with Lock + 2 Conditions.
  • Safe shared map → ConcurrentHashMap + compute/merge for compound ops.
  • Lock-free counter → AtomicLong (low contention), LongAdder (high).
  • Async composition → CompletableFuture: supplyAsync → thenCompose / thenCombine / allOf.
  • Scheduled / periodic → ScheduledExecutorService.scheduleAtFixedRate.
  • CPU-bound divide-and-conquer → ForkJoinPool.
  • I/O-bound at massive concurrency → virtual threads (Java 21+).
